# 改动记录

这里存放影响本仓库的决策记录：需求、缺陷修复和中间结论。重点记录代码本身无法说明的选择原因、曾考虑的方案和验证边界。

## 布局与命名

每条记录的路径编码两个维度：`{生命周期}/{类别}/yyyy-mm-dd-主题.md`。

生命周期是记录的状态，记录随状态在目录之间移动：

- `proposed/`：实施前的提案，尚未完成或只完成一部分。正文注明是否已获用户同意、实施进度和剩余验收项。
- `implemented/`：决策已交付。记录与实际交付保持同步：代码移动文件、改名、改默认值时，在同一个变更里更新记录中的事实。只更新事实，不改决策本身。阶段记录明确交付范围，后续待做项继续注明。
- `rejected/`：提案讨论后被否决。只有决策依据仍有后续参考价值时保留，否则删除。

类别沿用 etf-watch：

| 类别 | 覆盖范围 |
| --- | --- |
| `feature` | 面向用户的新能力 |
| `bug-fix` | 缺陷修复 |
| `simplification` | 不增加能力的删减 |
| `architecture` | 交付源码的结构性决策 |
| `process` | 代码周边的工具与流程：构建、交付、脚本约定 |
| `testing` | 测试基础设施与策略 |

文件名中的日期是主题首次提出的日期，以 Git 历史为准；会话提供更早且可核对的提出时间时，记录该时间及来源。历史补录另写补录日期。记录之间用相对路径链接。不设集中索引，目录树本身就是工作清单。

## 何时必须写

每个非平凡变更必须在同一次提交中新增或更新至少一条记录。变更涉及行为、架构、跨文件约定、流程工具、测试策略、存储格式或接口格式，或者维护者可能重新审视的决策，都算非平凡。纯机械的局部修改豁免。

提案在实施前记录问题、选择和验收条件；已获授权的开发继续进行。发现缺陷先记录触发条件、实际行为和调查结果，修复后追加原因、处理和验证。未经确认的原因注明推断。

更新已经持有该决策的记录即可，避免重复建记录。决策反转要写新记录并互相链接；旧记录可以更新事实，不能改写成相反的决策。所有状态改变同步更新文件位置、文件头和引用。

## 文件格式

前三行固定为：

```markdown
# 决策记录: <标题>

状态: <状态>
```

状态取 `proposed`、`implemented` 或 `rejected — 一句话原因`，必须与所在生命周期目录一致。

正文骨架按生命周期区分：

- `proposed/`：`## 问题`、`## 提案`、`## 曾考虑的替代方案`、`## 验收标准`、`## 风险`。
- `implemented/`：`## 问题`、`## 决策`、`## 曾考虑的替代方案`、`## 影响`。
- `rejected/`：沿用原记录骨架，在文件头和正文中说明原因、适用范围与后续决定。

每条记录必须有「曾考虑的替代方案」：列出真实备选及各自未采用的原因。历史规格无法还原备选时使用固定说明：「本文档由早期规格文档改写，备选方案未记录。」不要补写没有发生的比较。

验证内容放在「决策」或「验收标准」下：列出实际命令或结果文件、环境、预期、实际结果和未覆盖的条件。复杂度审查与实现偏离放在相关小节。故障记录保留最初失败、本机复现、修复后检查和设备结果之间的对应关系。

性能结果注明设备、系统、构建、负载、配置、单位和统计方式。原生计算、Java JIT/解释器、旧 QEMU 与完整 Android 分别比较；条件不一致时写清限制。

## 与其他文档的关系

- `implemented/` 同时容纳描述现行行为的规格记录和解释某次选择的决策记录，两者使用相同格式。
- [轮次工作记录](implemented/process/2026-10-07-轮次工作记录.md)保留状态摘要，指向详细记录。历史实验单独保存，正文中的日期和验证边界继续有效。
- 根目录 [AGENTS.md](../../AGENTS.md) 是开发约定入口；根目录 README 和组件 README 保留使用入口。
- `experiments/` 内结构化测试结果与 `work/` 内可再生成产物保持现有位置，通过记录引用。
- 已否决与已结束阶段的历史计划不作为当前实施依据。当前范围以最近明确的用户决定及对应记录为准。
