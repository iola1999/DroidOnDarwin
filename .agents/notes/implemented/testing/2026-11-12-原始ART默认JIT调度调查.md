# 决策记录: 原始 ART 默认 JIT 调度调查

状态: implemented

2026-11-12 HyperOS 4 KiB 接续阶段完成默认与后台 JIT 的 CLI/GCD 观察。默认单轮 JNI 成功，稳定 RX 内未命中；后台诊断负载两入口各确认 324 条完成样本。源码、fixture 和观察窗口沿用 `4e1b510`，结果见下文。

## 问题

2026-11-12 的 HyperOS 接续阶段已在 `4e1b510f43a39730d0c400ccc01a3f9accaae963` 完成 first-use 观察。既有 HyperOS default 的 CLI/GCD 已通过 16 项 JNI 检查，观察关闭；接续开始时尚无默认阈值下的完成 PC 确认。本阶段复用原 default 单轮和 background 十轮、九次 200 ms 等待的 fixture 契约，分别启用观察运行两个入口。验收按原完整窗口、稳定 RX、同 PID/TID/mm 和 VM 失效检查判断，未命中或失败保留实际结果。完整系统和性能目标保持原条件。

[已完成指令观测](2026-11-12-原始ART的JIT执行观测.md)确认首次调用同步编译下的 JIT cache 指令执行。默认阈值与降低阈值的短热循环均未得到命中；每次 Direct run 只保存最后一个整数 PC，已有结果无法区分采样遗漏、编译任务等待、编译失败或尚未执行编译代码。主会话授权继续调查默认配置，要求保留普通 Java/JNI 语义。

## 决策

将执行观测与编译选项分别设置。`--stock-art-observe-jit 1` 只启用宿主完成记录，`--stock-art-jit-mode` 指定组件负载，默认 `default`。三个模式均加载原始 SDK36 ART、Bionic、类库和同一份 DEX。

| 模式 | ART 编译选项 | Java 负载与等待 |
| --- | --- | --- |
| `default` | `-Xusejit:true`，原始阈值 | 单次 `warmup(200000)`，无额外等待 |
| `first-use` | 加入 `-Xjitthreshold:0` | 单次 `warmup(200000)`，无额外等待 |
| `background` | `-Xusejit:true`，原始阈值 | 调用 `warmup(200000)` 十次；第二至第十次调用前各申请 200 ms `nanosleep` |

`background` 总计执行 2000000 次 Java `hot` 调用，申请等待总计 1.8 秒。每轮核对返回值 `340011506336`；等待被信号中断后继续等待剩余时间。选择该时长用于给后台编译保留一个有界观察区间，实际唤醒时间受调度影响。产品启动和应用运行不使用这个等待，也未确定产品预热时长。

fixture 在 VM 创建后重新设置 liblog 的 stderr logger；后台诊断模式设置 VERBOSE 最低级别，启用原 ART 的 `-verbose:gc,jit` 和 `-XX:DumpJITInfoOnShutdown`。其他模式使用 INFO 级别和原有 GC 日志。原始库和 Java 方法未修改，没有调用 ART 私有编译接口。

supervisor 从现有组件装载目录读取枚举模式并通过 argv 传入 fixture。`stock_art_config.jit_mode` 记录实际模式，每轮 `stock_art_warmup` 记录序号、调用次数、申请等待毫秒数和 Java 返回值；`stock_art_jit.warmup_calls` 记录本次总调用次数。严格解析同时检查配置、完整轮次、等待值和结果。现行运行不接受旧配置字段；历史报告保留当时内容。

执行观测仍以同一 PID/TID/mm 的已完成整数指令和稳定 JIT RX 映射为条件。`--stock-art-observe-jit 1` 的整轮成功仍要求至少一次实际命中。普通单轮启用观测后没有命中，结果保留失败，不会因 JNI 成功而获得执行确认。

### 实际运行

[结构化结果](../../../../experiments/native-linux/results-stock-art-background-jit-20261112.json)保存报告身份、命令、输入摘要、JNI/轮次结果、完成指令关联和相关编译日志。原始报告、stdout/stderr 和全部样本位于独立工作树 `work/offline-stock-art/work/native-linux-nce/` 的各输出目录。设备为 Apple M5 Ultra，macOS 27.0，构建 26A428；客体单 CPU、16 KiB 页、sparse 64 GiB、1 GiB RAM、PTE/Direct flat、dual、数据 TBI 开启，每次 Direct run 预算 50000 条指令。功能运行允许与其他构建并行，以下数据不作性能比较。

| 输出目录末级名称 | 配置 | 结果 |
| --- | --- | --- |
| `stock-art-default-diag-v1` | 原阈值、单轮、恢复日志 | CLI 的 13 项 JNI 成功，1013 个完成样本，JIT 命中 0；观测验收失败 |
| `stock-art-default-diag-v2` | 原阈值、十轮，每轮调用后等待 200 ms | CLI 十次 Java 返回值正确，288 条 JIT 完成样本；调查用额外 JSON 尚未进入严格契约，整轮 `validated=false` |
| `stock-art-background-verified-v3` | 原阈值、正式后台诊断模式 | CLI/GCD 整轮成功，各 2220 个完成样本，其中 288 个位于稳定 JIT RX 映射 |

| `stock-art-default-verified-v3` | 原阈值、单轮、观测关闭 | CLI/GCD 整轮成功，宿主观察事件 0 |

第一轮重新设置 logger 和最低日志级别后，原 ART 日志开始输出。热循环结束、VM 开始 shutdown 后，TID 3 才完成 `String.equals`；退出统计为一个 optimized、零 baseline、零 OSR。日志报告该次编译用时 480.423 ms。该诊断运行的短观察区间没有覆盖 `warmup` 编译后的执行。

正式后台轮中，TID 3 记录了 `StockArtProbe.warmup` 和 `StockArtProbe.hot` 的编译；两入口退出统计均为 2 次 baseline、24 次 optimized、0 次 OSR、0 次代码缓存回收。CLI 首个命中 PC 为 `0x196cce24`，同一进程日志记录的 `warmup` 代码范围为 `[0x196cce10,0x196cce50)`；GCD 为 `0x14000e24` 与 `[0x14000e10,0x14000e50)`。这些地址关系支持本轮完成样本来自编译后的 `warmup`，代码缓存内部复用仍未独立跟踪。监督进程转发 stdout 存在延迟，因此不使用输出行相对次序断言首个样本发生在哪轮 Java 调用。

上述结果确认后台编译任务可以执行，原阈值下生成的代码随后可以执行。第一轮无命中与后台编译完成时间相关；每次 run 只保留最后样本的覆盖限制继续有效。尚未测出编译排队延迟分布，也未验证任意短负载都能在结束前完成编译。

最终三种模式的 CLI/GCD 共六轮均通过 13 项 JNI、原始输入前后核对、五份 maps 导出和退出检查，每轮翻译上下文释放均为 11/11。原始输入继续为 290 份唯一文件、147750805 字节；DEX 摘要保持 `264469d1bc89a2df416042faec29cfc2f6726a5b36a666afd7bf24057d456470`。

### 复杂度复查与偏离

按 reclaim-code-entropy 检查调用方。模式由探针传入 supervisor，再传入 fixture，解析器使用同一枚举验证报告；编译模式和执行观测控制不同的实际行为，保留两个选项。删除模式区分会再次让打开观测隐式改变编译阈值，或迫使普通 JNI 检查执行额外等待。

后台观察复用同一 DEX、标准 JNI 入口、maps 快照和已有完成指令关联，没有新增编译器接口、线程控制器或全量 trace。十轮和 200 ms 固定在诊断模式内，未增加任意轮数和任意延迟选项。删除轮次结果会失去中间 Java 结果、少跑一轮和等待配置错误的检查。日志与地址比较直接来自原始输出，没有维护另一份 JIT 方法表。

调查中增加重复调用与等待，因单轮在后台编译完成前结束。第二轮调查输出暂不满足旧严格契约，已保留其失败状态；正式模式新增明确契约并重新实际运行。默认单轮负载和产品编译策略保持原配置。

## 曾考虑的替代方案

直接将同步编译设为产品默认值。已有检查只验证指令执行，缺少应用启动、总编译成本和持续负载结果。增加全量逐指令回调。当前日志与有界后台运行已经取得默认阈值下的实际完成样本，无需新增这一接口。仅增加连续热循环。此前九轮连续调用没有确认执行，本轮在调用间明确允许后台线程继续运行，申请等待成本单独记录。

## 影响

原始 ART 的默认阈值已在本机后台诊断负载中确认生成并执行 JIT 代码，首次调用编译继续作为独立对照。日志、指令观测与等待改变运行时序，此前 SDK36 阶段没有原生性能、完整 framework、HyperOS JIT 或 iPhone 运行结论。后续整机集成需保留默认编译策略，按实际应用的编译活动、页面操作和持续负载测量成本。
