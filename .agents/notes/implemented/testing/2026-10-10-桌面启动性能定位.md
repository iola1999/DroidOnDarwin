# 决策记录: 桌面启动性能定位

状态: implemented

## 问题

N4-D1 提前包在 iPhone 17 / iOS 27.2 的滑动体验得到用户确认，但启动和首次操作仍慢。用户要求定位瓶颈，并判断是否需要补性能统计或运行 profile。当前组件计时包含嵌套初始化与等待，无法据此直接确定 CPU 热点。

## 决策

保持 N4-D1 的内核、系统内容、1 GiB RAM、demand 映射和 360×640 显示配置，在可见 Mac 窗口采集启动与空闲阶段。先复用 `NCE_MAP_PROFILE` 和 Android 原有日志，再用 macOS `sample` 读取调用栈。采样文件与原始日志放在 `work/native-linux-nce/`，结构化摘要进入 `experiments/native-linux/`。

分析脚本计算调用树节点自身的样本数，单独列出明确的等待栈。`vm_remap` 内的 Mach 调用继续计入映射操作，普通线程事件循环的 Mach 等待单独记录。剩余样本用于查找热点，样本份额只描述这次采样；宿主调度、信号采样和异步运行会影响它，不能据此承诺优化倍数。

对 Android 计时保留各组件原始名称、时间和日志位置；父子计时分别保存。映射统计保留累计值，并计算相邻报告的差值。当前采样不足以区分某个 Java 构造函数的实际计算时间、Binder 等待和被其他任务抢占的时间，后续按已定位的热点决定补充范围。

## 曾考虑的替代方案

- 根据 SystemUI 单个服务名称直接删减服务：该计时可能包含依赖构造与等待，先查具体执行内容。
- 对所有线程、系统调用和缺页逐条打印：启动已有上千万次相关事件，新增日志会干扰测量；先使用现有汇总和短时调用栈采样。
- 立即增加 CPU 数量：不同进程当前复用宿主地址窗口，并行执行需要先解决隔离和映射语义；该改动需有针对性方案。

## 验证要求

1. 记录实际构建、设备、配置和工作负载；正常进入 Launcher 并退出，数据盘保持 clean。
2. 区分启动、空闲、Android 组件计时与宿主样本，保留原始文件哈希。
3. 分析器覆盖嵌套栈、等待识别与 Mach 映射调用的统计边界。
4. 按当前测量排序后续优化，明确可确认的开销和仍需新增采样的部分。

## 影响

Mac 与 iPhone 的调度、内存和 CPU 条件不同。短时采样会干扰被测进程，现有映射计时也有开销。当前数据可用于选择方向，整机收益需用完成优化后的相同配置对照确认。


### 本轮测量结果

运行源码基准为 `f3f3796`，二进制、内核及系统镜像哈希见 [results-macos-n4-d1-profile.json](../../../../experiments/native-linux/results-macos-n4-d1-profile.json)。设备为 Apple M5 Ultra / macOS 27.0 (26A428)，1 GiB RAM、demand、360×640、JIT 阈值 1024，沿用已安装桌面应用的数据盘。每轮重启宿主与 Linux，未清除 Mac 文件缓存。映射采样轮启用 `NCE_MAP_PROFILE=1`，关闭逐项故障日志；ART 线程栈使用另一次启动，开启 `NCE_TRACE_SYSTEMUI=1`，其耗时单独保留。

映射采样轮的 SystemServer StartServices 为 36,391 ms，SystemUI StartServices 为 90,643 ms，Launcher 首帧为 71,564 ms。SystemUI 内的 SystemActions 为 46,659 ms，AssistantAttentionMonitor 为 15,061 ms。各项计时包含嵌套与并行等待，不能相加。先前手机日志的对应 SystemUI 两项为 22,360 ms 和 13,789 ms，说明同类初始化在两种设备上均较慢；手机数据来源仍为提前包，不能用两轮之比估算性能。

Launcher 首帧日志前后的映射报告覆盖 165.142–175.196 秒累计窗口。数据恢复、代码恢复和撤销访问分别累计 16.653–17.720 秒、3.264–3.456 秒及 13.297–14.113 秒，总计 33.214–35.289 秒，约占对应窗口的 20%。首次报告开始前的少量初始化不在这一窗口内；函数内计时包含被宿主调度挂起的时间。整个含空闲等待的会话共记录 15,020,251 次延迟缺页、14,009,937 次数据映射和 9,970,495 次访问撤销，这些次数覆盖整个会话。

macOS `sample` 每次采集 5 秒，间隔参数为 5 ms。在宿主启动后约 11、35、115 和 279 秒分别开始采样，最后一次已进入桌面并保持空闲。SystemUI 初始化期间的第 3 组共有 612 个排除明确等待后的自身样本：

| 调用分类 | 样本数 | 该组非等待样本份额 |
| --- | ---: | ---: |
| 缺页信号处理与入口 | 177 | 28.9% |
| 数据/代码映射与权限处理 | 136 | 22.2% |
| 返回入口查找、改写和缓存同步 | 85 | 13.9% |
| 未解析的原生地址 | 193 | 31.5% |
| 宿主图形调用 | 5 | 0.8% |
| 其他宿主代码 | 16 | 2.6% |

这些份额描述短时调用栈采样，尚未完成全部原生地址符号解析，也未采集 GPU 硬件时间。第 3 组中的前三类合计约 65%，支持优先检查地址窗口恢复、缺页往返和返回入口；它们的整体优化上限与实际收益尚未测量。不能将 65% 直接用于推算加速倍数。

进入空闲桌面后，后五个统计窗口每约 10 秒仍花费 0.50–0.58 秒处理映射、代码恢复与访问撤销。后台运行仍有这类成本，后续应同时检查启动和稳定空闲状态。

### ART 线程栈

独立的 SIGQUIT 诊断轮捕获了 SystemUI 和 system_server 的主线程与 ART 统计。SystemUI 正处于 `SystemActions.start` 发起的依赖构造：`registerActions` → `registerOrUnregisterDismissNotificationShadeAction` → Dagger provider → `NotificationMessagingUtil` 构造 → `ContentResolver.registerContentObserver` → Binder transact。Dagger 方法已有 JIT 代码，Framework 部分仍经过 `ExecuteSwitchImplCpp`。采样时的主线程正在一次 Binder 调用内；单次快照不能说明整段 46 秒都用于 Binder 等待。

SystemUI 快照报告 490 个 JIT 代码缓存条目、约 1,973 KB 已用代码缓存、0 次代码缓存回收，GC 累计 1.086 秒，其中阻塞 GC 697.848 ms。system_server 报告 2,371 个条目、3,481 KB 已用代码缓存，GC 累计 677.554 ms。JIT 已实际工作，解释执行与依赖初始化仍需分析；该轮数据尚未显示 GC 或 JIT 缓存回收占据主要启动时间。

构建脚本 `scripts/build_android_art.py` 显式传入 `ART_USE_RESTRICTED_MODE=1`，ART 的 `IsNterpSupported()` 在此条件下直接返回 false，当前未启用 ARM64 汇编解释器 nterp。未编译方法使用 C++ switch 解释器；受限编译器也会拒绝尚未适配的 IR 图。这与本次栈中的 `ExecuteSwitchImplCpp` 一致，具体耗时份额仍缺少按方法采样。此前的[验证缓存记录](../../proposed/architecture/2026-10-10-复用SDK字节码验证缓存.md#0838-初始化等待与后续方向)已记录 nterp 的适配范围：对象引用、字段和数组访问、调用参数与返回值、异常及 GC 栈扫描。当前 MS 收集器的寄存器配置也需要核对；解除 restricted 条件本身不足以完成适配。

[AOSP 的 SystemUIApplication](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/packages/SystemUI/src/com/android/systemui/SystemUIApplication.java) 将 provider 获取与组件 start 放在同一项初始化计时内。SDK Google SystemUI 的实际线程栈也包含上述依赖构造。因此，优化应深入这些调用和跨进程等待，不能按服务标签直接认定某项系统功能耗尽了全部时间。

线程栈采集会暂停或协调其他线程，原始记录中的单线程 DumpLatencyMs 最高约 11.7 秒。因此该轮只用于诊断调用关系。两轮均进入真实 Launcher、正常退出；数据盘 superblock 为 clean，只读 e2fsck 成功。映射采样轮无 Java 主线程异常或 ANR。

### 下一步统计与优化顺序

1. **进程地址空间与缺页。** 补充实际 mm 切换次数、每次切换恢复/撤销的页数，以及延迟缺页中 Linux PTE 已有效与实际 Linux 缺页的分类；再按进程对拆分 Binder 往返、可运行等待与宿主恢复时间。当前累计次数足以确定投入方向，尚不足以选择保留哪些页或更换地址空间设计。已有 512 页热页表和批量数据视图尝试未取得收益，后续设计必须利用新统计，不能仅扩大旧缓存。
2. **ART 启动执行。** 按方法采样解释执行与 JIT，并汇总编译拒绝原因；优先评估 nterp 适配，减少尚未编译方法的解释开销。另一路是 boot image / AOT：当前显式使用 `/data/no-boot-image.art`、`-Xnoimage-dex2oat`，安装编译过滤器为 `verify`。验证能否用修改版 ART 生成并加载匹配的 boot image 与预编译 Framework/SystemUI，减少每次冷启动的解释执行、类构造准备与重复编译。[AOSP ART 配置说明](https://source.android.com/docs/core/runtime/configure)区分 VDEX 验证元数据、ODEX 方法代码与 ART 类/字符串镜像；现有 VDEX 复用尚未覆盖后两项。新产物需要处理 NCE 引用表示、重定位、代码登记及执行权限，并保留异常、GC、JNI 和跨进程回归。两条路径分别对照，当前没有整机收益数字。
3. **返回入口。** `prepare_resume`、代码同步和返回分支区已有可见开销。先按程序统计缓存命中/冲突与实际刷新量，核对固定返回入口、缓存布局及现有 RW/RX 访问方式。此项可独立对照，但不能替代对缺页次数与进程切换的处理。
4. **连续交互与图形。** 后续对固定滑动和切换负载采集完整帧间隔、提交与等待时间、传输字节数。当前启动样本中的宿主图形调用较少，图形优化优先级低于前述问题；持续动画与更高分辨率需另测。

新增统计应采用可关闭的累计值或采样直方图，按阶段输出，避免每次事件格式化日志。普通统计与 ART 全线程转储分开运行；比较优化前后时，还需要一轮关闭详细统计的相同负载。Android 的 `schedstat` 在当前线程栈中为零，不能据此计算就绪等待；该项需要在实际 Linux 调度位置补充测量。

### 工具与复杂度复核

新增 `scripts/analyze_nce_profile.py` 只分析离线文件，复用现有宿主计数、Android 日志、`sample` 和 ART SIGQUIT 入口。它计算调用树自身样本，防止父子调用重复计数；明确区分普通 Mach 等待与 `vm_remap` 内的 Mach 调用。组件计时按两种标签各保留最慢 40 项，原始数量与日志行号同时记录。原始文件哈希用于重新核对输入。

生成离线统计的命令如下。已提交的结果另含设备配置、实际二进制哈希和退出检查；这些信息来自运行记录，分析器不会推断。

```sh
python3 scripts/analyze_nce_profile.py \
  --log work/native-linux-nce/processes/profile-desktop-baseline.log \
  --results work/native-linux-nce/processes/profile-desktop-baseline.jsonl \
  --sample work/native-linux-nce/profile-desktop-baseline-t011.sample.txt \
  --sample work/native-linux-nce/profile-desktop-baseline-t035.sample.txt \
  --sample work/native-linux-nce/profile-desktop-baseline-t115.sample.txt \
  --sample work/native-linux-nce/profile-desktop-baseline-t279.sample.txt \
  --art-log work/native-linux-nce/processes/profile-desktop-art-trace.log \
  --output work/native-linux-nce/profile-desktop-summary.json
```

`python3 scripts/test_nce_profile.py` 的 4 项检查成功，覆盖嵌套调用、映射中的 Mach 调用、普通等待、不一致调用树、嵌套组件计时及 ART 进程/线程边界。该轮未增加运行时状态或新的后台线程。删除离线分析器会使后续每次对照都需重新处理等待样本和父子计时；保留这两个职责明确的脚本。

本轮交付为瓶颈定位与可复用分析工具，执行引擎优化和整机提速仍待后续实现与对照。源码目录中另一会话的 iOS 界面修改保持原状；本次测量使用启动前的 N4-D1 二进制。
