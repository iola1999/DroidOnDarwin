# 决策记录: 翻译执行的 Android 桌面验证

状态: implemented

## 问题

Bionic/ART 的局部负载已经成功，仍需验证运行时 ELF 装载能否覆盖 Android 服务与桌面，以及取消用户窗口映射后增加的翻译、内存和图形成本。此阶段继续使用已适配的系统镜像，产品仍使用原生 NCE。

## 决策

扩展现有 `probe_lkl_translation.py`，复用 `/system/bin/android-services-test`、gfxstream 和桌面检查。`--workload services|desktop` 分别选择服务或完整桌面，`--entry both|cli|gcd|window` 选择宿主入口，可见窗口沿用现有 AppKit 测试程序。每轮使用新建的 512 MiB 稀疏 ext4 数据盘，系统镜像只读；启动前记录输入摘要，结束后核对源文件、二进制及磁盘状态。

运行时布局表从固定 64 项改为按需增长的数组；首次失败的第 65 项是 `/system/lib64/liberrno.dylib.so`。地址分配仍受既有 512 MiB 库范围约束，最小 256 KiB 对齐决定最多 2,048 项。宿主继续不引用构建期程序登记表。

服务和桌面日志由宿主线程读取，完整 JSON 行写出后才允许内存样本穿插；结束时通知线程停止并等待退出。内存采样保持默认 100 ms，可关闭；记录内核准备、文件准备、执行和清理阶段的 footprint/RSS 样本均值、采样峰值、最新值及独立的进程生命周期 RSS 峰值。阶段结束后先将数据盘重新挂载为只读，再卸载和停止 Linux；主机检查 ext4 为 clean 且没有待恢复日志或 orphan 标记。

只读提取并检查 `desktop-launcher.png`、`desktop-clock.png`、`desktop-files.png`，三张均为 360×640。Clock 显示闹钟列表，Files 显示 Downloads 页面，Launcher 截图只出现搜索栏、壁纸和导航栏；这轮没有人工持续操作验证。整段耗时包含前置服务测试、Android 启动、应用检查及服务退出，不能与产品单独的启动秒数直接比较。

复现命令：

```sh
python3 scripts/probe_lkl_translation.py --mapping pte --preemption timer --workload services --linux-fastpath 1 --cache-mib 128 --output work/native-linux-nce/lkl-translation-services-128
python3 scripts/probe_lkl_translation.py --mapping pte --preemption timer --workload desktop --entry cli --linux-fastpath 1 --cache-mib 128 --output work/native-linux-nce/lkl-translation-desktop-128
```

### 失败轮次与后续比较

首次可见窗口桌面检查未在 240 秒的客体启动轮询期限内完成，整段执行 312.525 秒后正常回收上下文与图形通道；当时数据盘尚未增加只读卸载。该轮请求 16 MiB，后来确认实际分配约 1 GiB，详见[缓存容量修复](../bug-fix/2026-10-11-翻译缓存容量设置未生效.md)。启动期间另做了 3 秒、5 ms 间隔的 `sample` 诊断，因此该轮耗时用于故障记录。Mac 屏幕当时锁定，未完成宿主窗口像素观察。与后来的 CLI 存在入口、缓存容量及采样差异，不能将成功或耗时变化归因于单一参数。

`--exec-cache pages` 实验保留 exec 后未修改的物理代码。核心 CLI/GCD 成功，早期服务 CLI 成功，GCD 一轮在 property 协议负例的 `sendmsg` 返回 EPIPE，尚未确认原因。两轮数据盘都完成干净卸载。后续实际 128 MiB 的桌面 GCD 完整检查成功，宿主全量清空为 0，引擎总清空为 83，翻译块失效为 7,264,395；1,087 个用户上下文全部释放。该轮仍有 262,604,617 次软件 TLB 填充及 810,768 次 TLB 刷新。

两轮桌面分别使用 CLI/GCD，且各执行一次，尚不足以归因于 exec 参数。当前未观察到明确耗时或内存收益，默认继续使用 `full`。下一阶段先区分地址空间切换与单页变化引起的 TLB 刷新，评估按页失效及保留同 mm 转换结果。容量和 exec 开关仍可用于后续同入口成组比较，当前优先调查约 2.6 亿次 TLB 填充的来源。

### 复杂度审查

按 reclaim-code-entropy 检查新增状态和调用方：布局数组由实际 ELF 装载使用，删除增长逻辑会恢复第 65 项加载失败，另设固定大表会长期保留未使用项；当前保留连续数组和既有线性查询。日志线程只属于一次 `run_program`，条件变量用于退出时立即唤醒，客体退出后 join，再销毁同步对象；不新增任务队列或日志协议。桌面直接复用现有图形与 guest 检查，数据盘准备留在实验脚本，宿主只负责挂载和卸载。引擎统计读取已有字段，删除它会失去实际缓存容量检查；没有新增逐指令计时。

## 曾考虑的替代方案

- 根据 ART 微基准直接接入手机：尚未覆盖服务、桌面和完整内存成本，先完成本机桌面。
- 把全部库加入产品构建期登记：无法验证运行时接收新 ELF 的要求，继续使用动态解析。
- 复用产品数据盘：会改变已有会话数据并增加冷热状态差异，实验使用自己的空白数据盘。
- 保留固定 64 项表并删减测试服务：会缩小原有桌面检查范围，改为受地址范围限制的动态数组。

## 影响

本阶段确认完整服务和桌面负载能使用运行时 ELF 解析和软件 TLB 执行。iPhone 执行缓存授权、原始签名 JNI APK 安装、应用更新及通用 4 KiB 库仍待验证；本轮不生成新的手机包。性能比较继续记录实际生效容量及阶段内存，产品默认执行路径保持现有已验证配置。
