# 决策记录: 两端性能实验自动化

状态: implemented

## 问题

用户要求后续功能便于在 Mac 和 iPhone 上比较参数组合，减少修改设置、启动、操作和收集日志时的手动参与。这项要求加入当前持续优化任务，与 ART、映射和多核的实施一起推进。

现有 Mac 应用可以启动独立运行进程，iPhone 使用同进程核心和内置 JIT。两端已有共享设置、会话状态和日志读取，但参数通过多个布尔值传递，缺少一次实验的固定配置、操作序列和结果文件。iPhone 完成一次核心运行后需要重新启动 App；自动化必须遵守此生命周期。

## 决策

### 用户入口与参数

将已实现的性能选项归入共享、可编码的启动配置；界面、Mac CLI 和 iPhone Deep Link 使用相同默认值、取值及生效规则。初期包含 nterp、扩展 JIT 编译、已有数据页快速恢复、稀疏页表扫描、性能统计及诊断模式。尚未实现的 CPU 数量、RAM 和 AOT 选项不接受请求。

每次实验携带唯一运行编号、明确的设备编号、完整参数和有界操作序列。配置仅作用于本次启动，普通启动继续读取用户设置。重复编号、运行中启动、未知字段和越界输入返回明确错误。启动后的实际配置写入会话日志和结果。

iPhone 采用 `droidondarwin://benchmark` 入口，在设置中启用自动化后接收请求。通过已配对设备的 `devicectl` 启动参数也可以开启当前进程的自动化入口，便于安装后直接测试。请求只允许操作已有设备和指定实验行为，不接受任意文件路径、shell 或下载地址。Mac CLI 直接向运行进程传入相同请求文件，保留可见窗口。

### 执行和结果

操作序列在 App 内执行，先等待桌面就绪，再按顺序等待、点击、滑动或发送导航键，完成后正常停止 Android。外部控制程序负责组合参数、交替顺序、重启 App 和收集结果，Android 的实际运行仍全部位于手机内。

每次实验在固定结果目录保存请求、状态、构建标识、资源清单中的内核/ART/系统哈希、运行设备与系统、实际配置、阶段时间、操作完成情况、热状态和日志位置。状态文件仅在阶段变化或操作边界更新，不在帧回调或解释器循环写入。高频统计仍默认关闭；测量时明确日志观察延迟，区分准备/JIT、Android 启动、操作序列和停止。

Mac 直接读取结果文件。iPhone 使用 `devicectl device copy from --domain-type appDataContainer` 收集指定运行的结果与日志；按低频状态轮询判断结束，不反复复制整个日志或数据盘。连接不可用、App 闪退、自动锁屏或 JIT 失败均保留为失败或未完成结果，不能计入成功样本。

编排脚本保存所有样本，按配置分组输出中位数和范围。失败时先收集日志并尝试正常停止，不能在未确认上一轮结束时启动下一轮。数据盘沿用还是首次创建、宿主缓存是否清除、设备温度及前后台状态须记录；首轮和重复运行分别保留。

### 实施进展

共享 `RunConfiguration` 已替换多组布尔参数；日常设置、Mac 子进程和 iOS 本地运行使用同一快照。`BenchmarkRequest` 校验完整参数、设备/运行 UUID、输入范围和时限，`BenchmarkSession` 执行操作并记录低频状态。脚本、接口和组合示例见[性能实验说明](../../../../experiments/native-linux/app/BENCHMARK.md)。

Swift 检查覆盖配置往返、URL 与字段校验、空坐标、重复运行、输入顺序、输入失败后的停止和结果保存顺序。Mac 宿主检查与 iOS 构建已成功，iPhone 的接口组合尚未做真机验证。

真实 Mac 预热首次出现 Android 正常停止而结果仍为 running：宿主原有结束回调直接退出，异步状态观察来不及写入。现改为先保存实验结果，再调用原回调退出；同步停止导致的结果覆盖也一起修复。回归要求宿主回调执行时完成结果已经存在。修复后六轮正式 App 组合实验均成功，全部结果保存为 completed，配置和日志检查成功，最后检查 ext4 已正常卸载。测量见[普通 App 对照](../../../../experiments/native-linux/results-macos-desktop-nterp.json)。

后续交互指标将优先使用 gfxstream 的帧事件通知，记录提交间隔与操作时间窗口；采集需单独开启，关闭时不注册监听器。该通知不能确认屏幕实际显示时间，也不能区分重复内容，分析须保留这些限制。当前版本先记录启动与输入提交，帧指标尚未实施。

### 复杂度检查

请求、运行协调和外部编排分别负责输入校验、宿主生命周期及 USB/进程控制；使用当前会话、日志、输入通道与停止入口。未增加调试网络服务、通用策略注册表或第二套 Android 生命周期。必要的状态包括当前请求、操作任务、超时任务和首个失败原因；关闭自动化后普通启动不创建这些任务。

## 曾考虑的替代方案

- 长驻 HTTP 控制服务：当前 USB、CLI 和 URL 入口足以完成组合测试。先实现这些入口，减少端口、鉴权和网络生命周期的维护工作；后续有具体远程测试需求时再评估。
- 每个操作都由 Mac 发送一条通知：操作时间会受连接和 App 激活延迟影响。预先提交序列并在设备内执行，外部仅观察状态与收集结果。
- 直接修改偏好文件：无法确认运行进程已读取配置，也容易影响用户之后的普通启动。采用本次实验的配置快照。
- 启动后实时切换执行策略：当前 NCE、ART 和内存策略有启动期约束，实验之间通过正常停止和重新启动切换。

### 验证要求

- 共享配置覆盖默认值、完整读取、非法组合和当前会话不受后续设置修改影响。
- 请求覆盖重复编号、错误设备、无效参数、启动未完成时停止、异常退出和结果写入失败。
- Mac 可自动完成至少两组交替参数的可见桌面启动、操作、停止和日志收集；iPhone 包含相同入口，本机编译与接口检查完成后，集中到阶段真机测试验证 USB/JIT/日志导出。
- 普通启动不启用实验任务或额外轮询；统计开启和关闭的测量分开，结果说明时钟与计时边界。
- 文档给出一条命令运行组合实验与收集结果，后续优化接入现有配置和结果格式。

## 影响

已配对的 Mac 能否启动或读取侧载 App，仍取决于当时连接、解锁、开发者模式和签名条件。iOS 的 Deep Link 激活与内置 JIT 切换需要真机验证。宿主观察到桌面就绪的时间包含现有一秒日志轮询延迟，操作提交完成也不足以说明目标应用已经完成绘制；结果必须分别标注这些范围。
