# 决策记录: N4-D1 提前包真机体验

状态: implemented

## 问题

用户在 iPhone 17 上运行 `N4-D1-preview-iOS-20261010-090514`，提供 `native-linux-n2-ios 6.log`，反馈滑动还算流畅。需要将这次设备运行与正在进行的 Mac 桌面验收分别记录，并处理应用崩溃。

## 决策

日志显示 iOS 27.2、1 GiB Linux RAM、demand 映射、360 × 640 Android 显示。678 个固定代码区域的写入与执行检查、脱离调试器后的数据重映射、原生 Linux 启动、Binder、图形与系统服务检查通过。系统完成 boot_completed，Launcher3 获得焦点并进入 `android_desktop_running`，之后继续收到触摸事件。

Android 记录的 SystemServer StartServices 为 22,033 ms，SystemUI StartServices 为 62,230 ms，Launcher 首帧为 67,259 ms。这些计时覆盖各自组件，不能相加作为宿主完整启动耗时。设置首页首帧为 5,270 ms，随后一个 SubSettings 页面为 3,320 ms。用户反馈记录为主观体验；日志仅输出部分慢帧，无法据此计算平均 FPS 或完整帧时间分位数。

发生两次 Java 主线程异常：09:14:47 的 Wi-Fi 设置页面因 WifiManager 为空，在 WifiTrackerInjector.isVerboseLoggingEnabled 崩溃；09:14:58 的 Google 时钟因找不到 `com.google.android.gsf.gservices` ContentProvider，注册观察者时抛出 SecurityException。设置首页随后正常启动，Wi-Fi 页面故障范围应单独记录。日志未出现 `ANR in`、`Fatal signal` 或宿主停止完成记录；不能确认本次退出后的数据盘状态。

结构化结果、输入日志哈希与验证边界保存在 [results-ios-n4-d1-preview.json](../../../../experiments/native-linux/results-ios-n4-d1-preview.json)。原始日志沿用用户提供的 Downloads 文件，不复制大日志。

后续先补齐当前 Google 时钟实际依赖的同版 SDK 提供者，检查 Wi-Fi 页面与当前硬件功能声明的关系，再从全新测试数据盘检查首次应用启动。新建测试盘仅用于回归，原有开发数据盘和手机数据继续保留。正式交付仍按方案 A 的桌面、两个应用、导航、持久化和正常退出条件验收。

## 曾考虑的替代方案

- 仅引用用户的滑动反馈作为完整验收：日志已显示两个具体应用故障，继续实现和回归。
- 从慢帧日志推算平均 FPS：这类日志只包含被框架选中的慢帧，样本缺少正常帧。
- 立即要求重新侧载：目前故障可以先在本机复现，继续按集中交付方式推进。

## 影响

真机已验证真实桌面的持续触摸运行。首次应用启动、冷启动时间与硬件相关页面仍需处理。日志没有完整运行期内存采样，也没有热状态数据；此前 JIT 分配阶段的内存值只用于该阶段。

Wi-Fi 子页面的服务缺失与当前配置一致：`nce-features.xml` 只声明触摸、竖屏、桌面和 widgets；AOSP SystemServer 在声明 `FEATURE_WIFI` 后才启动 WifiService。当前方案 A 的网络与无线硬件页面尚未验收，设置首页与已打开的 SubSettings 页面分别保留其成功结果。Wi-Fi 服务与硬件接口仍待实现。

### 本机后续复现

09:23 的 Mac 持续运行模式从 Launcher 打开时钟首页成功，点击 Alarm 后出现相同的 GSF 提供者 SecurityException。既有开发数据盘同样可以触发故障。现增加同版 SDK 原始 GoogleServicesFramework APK，并在桌面回归中通过 SHOW_ALARMS Intent 实际进入闹钟页面，再检查控件与合成像素。全新数据盘仍用于检查最初的应用初始化，第二、三轮继续使用该盘检查数据保留。原测试盘保留供交互回归使用。

09:44 的全新数据盘 CLI 回归已完成时钟首页、SHOW_ALARMS、应用保存闹钟与 Files 检查。人工查看导出的截图，确认 Alarm 页显示原有两个闹钟及 `NCE storage check`，Files 显示 Downloads 页面；此次未出现 GSF 提供者崩溃。正常退出与 ext4 clean 检查成功，继续用同一盘进行 GCD 和可见窗口重启检查。

### 重启回归失败与组件调整

随后 GCD 重启在 09:48 再次触发时钟的相同异常，窗口检查按预期失败。第一轮成功不能覆盖应用恢复上次页面后的启动，相关失败记录保存在 `experiments/native-linux/results-macos-clock-provider-restart-failure.json`。检查原始 APK 资源确认 `bool/gsfOwnsProviders=false`，`string/checkin_gservices_authority=com.google.android.gms.gservices.provider.do.not.use`；当前 SDK 的 GoogleServicesFramework 默认不提供时钟要求的 authority。补入该 APK 的改动不足，继续评估同版 AOSP 时钟，保留已有 Google 时钟数据。

已经比较的处理包括携带完整 Google Play 服务、改写或覆盖 GSF 资源以启用旧提供者，以及采用同版 AOSP 时钟。前两项会增加后台组件或需要维护 Google 应用内部配置；本阶段仅要求两个真实 Android 应用和持久化，优先核对 AOSP 时钟的原始 APK。

10:00 的 AOSP 时钟首轮检查通过：实际 Alarm 页面显示 `NCE storage check`，应用保存闹钟 row_id=3，`android_preview_clock_data_preserved` 返回 `present=true`，确认旧 Google 时钟记录继续保留；Files 页面与系统停止检查也通过。此次使用前轮测试盘覆盖升级，AOSP 应用数据首次创建，随后继续检查宿主重启。所用 APK 与两个包的数据处理方式见[桌面实施记录](../../proposed/feature/2026-10-09-Android可交互桌面.md)。

随后 GCD 宿主重启通过：AOSP 闹钟 row_id=3 且 `restored=true`，旧 Google 时钟记录 `present=true`，Keystore 原有密钥读取成功；闹钟页、Files 与数据盘只读停机检查通过，日志未出现 Java 主线程崩溃或 ANR。继续完成可见窗口回归与人工操作。
