# 决策记录: 原始 ART 的 JIT 执行观测

状态: implemented

2026-11-12 接续阶段在独立 `work/continue-hyperos-jit`、`codex/continue-hyperos-jit` 完成 4 KiB 观察适配；基线为 `544e15d6195b3e70a10bbf5d2c928f23b3ff4d71`。原始 HyperOS first-use 的 CLI/GCD、SDK36 16 KiB 回归与两种页大小的 iOS 静态运行库编译成功，结果见下文。

## 问题

4 KiB 接续阶段的问题是 CLI 观察限制为 16 KiB，解析器也按 16 KiB 扩大 VM 长度。候选 RX 位于 `[0x11000,0x12000)`、修改请求为地址 `0x10000`、长度 1 时，4 KiB Linux 只涉及前一页，现有解析器仍将候选失效。方案沿既有 `guest_page_bytes` 传给 `observe`、`may_replace` 和 `overlaps`，保留 16384 默认与单 CPU Direct 顺序契约；不修改宿主页粒度。验收要求相邻页请求保留候选、跨页或重叠请求使候选失效，HyperOS 实际完成 PC 位于稳定 RX 映射，SDK36 原契约继续成功。原库、签名和 policy 字节保持原值；iPhone 执行与持续性能仍待真机验证。

[标准 JNI 实验](../../proposed/testing/2026-11-12-原始SDK36ART标准JNI实验.md)已在单 CPU、Direct flat、sparse、数据 TBI 的 CLI/GCD 入口成功。原始 SDK36 ART 创建了 `/memfd:jit-cache (deleted)` 的 RX/RW 映射，Java 热循环返回确定结果。已有结果没有记录实际执行的 JIT PC，因此保留 `jit_execution_confirmed=false`。

Direct 的 resolve、块入口和退出 PC 都不能单独确认某条客体指令已经完成。分支可以返回尚未执行的目标 PC，首次访存也可能产生 fault；内部块链接还会绕过 C++ 的 resolve/enter 调用。

## 决策

主会话授权在独立 `work/offline-stock-art` 工作树准备并实际运行诊断。原始 SDK36 库与 JAR 字节保持原样，fixture 使用标准 JNI 和 ART 命令行参数。主工作区由主会话管理，本工作树没有修改其源码或轮次记录。实施依赖采用原始 ART `f71b038`、sparse/TBI 及 tagged IC `fd063ca`；后者在本树的依赖副本为 `17396e0`。

### 指令完成记录

[direct.h](../../../../experiments/native-linux/direct/direct.h) 的 `NceDirectMemory.completed_integer_pc` 是可选输出。指针非空才启用诊断，启用状态进入代码缓存的编译标志。每次 `nce_direct_run` 先写 `UINT64_MAX`，返回前输出最后一条受支持整数指令完成后的 PC。保存发生在该整数指令及结果写回之后；PC 指向该指令自身。访存、分支、trap 和 fallback 入口均不产生记录。默认关闭后，生成代码不包含这些记录操作。

[compile.cpp](../../../../experiments/native-linux/direct/compile.cpp) 使用当前 `Frame.code_page` 加页内偏移计算实际客体 PC，内部块链接和代码别名执行相同的记录。使用的临时寄存器为 Direct 已保留的 X16/X17，生成的 LDR/ADD/STR 保持 NZCV。记录保存在本次 run 的 Frame 中；引擎的跨调用缓存不保留调用者输出指针。

每次 run 只保留最后一条样本，可能漏掉已经执行的 JIT 代码。没有命中只得到「本轮未确认」。观察会增加生成代码和运行开销，本轮全部结果用于功能检查。

### 进程、观测区间和映射

[execution-observation.h](../../../../experiments/native-linux/translation/execution-observation.h) 独立保存单 CPU 组件诊断。fixture 用标准 `prctl(PR_SET_NAME)` 设置 `art-jit-begin` 和 `art-jit-end`，区间包住 `maps-before-warmup.txt`、单轮热循环与 `maps-after-warmup.txt`。宿主根据 prctl 实际成功时点输出标记，顺序不依赖 supervisor 对 stdout 的转发。线程身份由 Linux getpid/gettid 得到；clone 后重新获取，子任务不继承观察窗口。

已完成指令记录包含 PID、TID、当前页表地址、顺序号、指令 PC 与退出 PC。同一页表的 VM 系统调用在进入 Linux 前记录，因此共享 mm、PID 不同的任务也被覆盖。记录包括 mmap、mprotect/pkey_mprotect、mremap/remap_file_pages、munmap、brk、madvise/process_madvise、execve/execveat、shmat/shmdt、userfaultfd；可能失败的重叠请求同样使候选失效。process_madvise 可以修改其他进程，因此记录所有调用方并保守使候选失效。另一个线程的 VM 调用可能在 begin 前进入并阻塞；全局在途计数覆盖这一情况，开始和结束标记均须观察到 0。该计数覆盖本诊断记录的 VM 调用，进入和返回各更新一次。需要扩展内核接口或多 CPU 观测时，必须重新检查这些事件和顺序。

[stock_art_jit.py](../../../../scripts/stock_art_jit.py) 只接受同一 PID/TID/mm、完整开始结束窗口内的已完成样本。前后快照中的候选 RX 映射须具有相同范围、权限、文件偏移、设备、inode 和 `/memfd:jit-cache (deleted)` 路径。解析拒绝窗口内可能覆盖候选的 VM 调用；普通非 fixed mmap、范围无关的修改和 brk 可以保留候选。无法从当前参数准确判定范围的 shmat/shmdt、exec、userfaultfd 和 process_madvise 会使全部候选失效。页长按客体页大小对齐检查，默认 16 KiB；4 KiB 适配与结果见下文接续阶段。

该检查处理显式 VM 调用造成的同 VA 复用。JIT cache 的映射保持不变时，ART 仍可在缓存内复用代码位置。本次只确认缓存内代码执行，具体 Java 方法及编译版本未确认。

### 运行入口和结果契约

新增 `--stock-art-observe-jit 0/1`，默认 0，仅供单 CPU Direct 的 stock-art 负载使用。该开关启用宿主完成记录。编译选项与负载由后续[默认 JIT 调查](2026-11-12-原始ART默认JIT调度调查.md)拆为独立 `--stock-art-jit-mode`；复现本节同步编译结果需显式选择 `first-use`，supervisor 通过现有组件装载目录传入该模式。fixture 加入原始 ART 支持的 `-Xjitthreshold:0`。本机对应 ART `runtime/jit/jit.cc` 的 `JitAtFirstUse()` 以 optimize threshold 为 0 判定首次调用同步编译。普通组件检查继续使用原来的 `-Xusejit:true`、默认阈值和 200000 次单轮热循环。

本阶段标准 JNI 结果增加 `stock_art_config.jit_first_use` 和第五份 maps 导出；后续默认 JIT 调查将配置字段改为 `stock_art_config.jit_mode`，以区分普通、同步编译和后台编译观察负载。fixture 仍输出自身未确认 JIT 的原有字段；宿主的 `stock_art_jit_observation` 单独保存关联结果。观察模式同时要求 13 项 JNI 成功、原始输入一致、五份 maps 完整和已完成 PC 命中。默认模式要求原标准 JNI 行为成功，并且本次实测没有输出宿主观察事件。

旧四份 maps 的历史报告保持原始格式和当时解析结果。新 runner 使用新 fixture 源码摘要与五份 maps 契约，不为历史报告增加运行时兼容分支。

## 曾考虑的替代方案

- 仅输出 resolve/enter 前 PC：无法排除首次指令 fault，也无法覆盖全部内部块链接。
- 只统计编译次数或缓存分配：可以检查编译或内存状态，缺少指令执行信息。
- 给每条指令增加通用回调和完整 trace：本阶段只需确认一次实际执行，通用回调会增加接口、状态与大量日志。
- 使用 JVMTI 编译事件：仍需另行关联实际执行，当前组件也尚未配置该接口。
- 重复九轮热循环：默认阈值和较低阈值的九轮检查仍无 JIT 命中；首次调用编译模式的单轮已能确认执行，最终删除重复循环与轮数字段。

### 复杂度复查与偏离

按 reclaim-code-entropy 检查实际调用方后，保留一个 Direct 可选输出和一份 Frame 状态，Linux 组件与独立指令测试是两类实际调用方。缺少后置记录会重新产生「尚未执行的 PC 被确认」问题；删除 PID/TID/mm、窗口或 VM 事件会失去对应的身份与生命周期检查。生成代码没有通用 trace 回调，宿主没有逐指令队列；只有单次最后样本。脚本从原始 maps 派生候选，不维护另一份 JIT 地址表。

supervisor 复用现有文件装载和 argv，只新增一个 first-use 设置。多个阶段用同一个 fixture，通过真实参数切换标准 ART 选项；没有新增运行时 provider、产品设置或私有 ART API。实施中删除了九轮循环与额外轮数字段，缩小了观测日志范围。为了检查同 mm 不同 PID，过滤条件从 PID 改为页表身份，没有增加另一份映射状态。额外的在途 VM 计数记录跨窗口的未完成调用；删除这一计数会漏掉 begin 前进入、begin 后恢复执行的调用。

与最初的默认参数实验相比，最终增加首次调用同步编译诊断，因为前三轮没有得到 JIT 完成样本。该选项仅用于本次可观测性检查，普通组件模式保持默认阈值。共享 `stock_art.validate` 预留的 `guest_page_bytes` 参数与并行 HyperOS 输入工作采用同一契约；此前的 JIT 关联验证 SDK36 的 16 KiB 页，4 KiB 接续结果见下文。

## 影响

本阶段确认原始 ART 的 JIT cache 中存在已执行的整数指令，以及同轮标准 JNI 行为成功。具体 Java 方法归属、默认阈值下的编译时机和覆盖率、完整 Android framework、产品 namespace、HyperOS 与 iPhone 仍需各自验证。每次 run 只保留最后样本；观察缺失不支持反向推断。诊断的代码体积与执行开销不能用于接近原生性能的结论。缓存内部代码地址复用及后续新增 VM 入口需要保留上述限制并重新设计检查。

### 页边界回归与复杂度复查
