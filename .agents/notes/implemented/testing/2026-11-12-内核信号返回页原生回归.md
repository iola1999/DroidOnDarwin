# 决策记录: 内核信号返回页原生回归

状态: implemented

## 问题

[内核信号返回特殊映射](../bug-fix/2026-11-12-内核信号返回特殊映射.md)已在 Direct 和原 init 观察中通过，但 `lkl-nce-elf.c`、`lkl-nce-signal.c` 也供原生 NCE 使用。原生执行会从 Linux RAM 复制原页字节到宿主登记的代码段并修改 SVC 指令，需要独立检查真实信号返回、fork、重复 exec 和退出回收。

## 决策

在独立树 `work/continue-native-signal`、分支 `codex/continue-native-signal` 上合入 `9e93f1216f334012d355c91399dedeec373e6f58` 与 `646ac08385d2f8eeb2f991fe28dab703b3b6aca3`，构建来源为 `103490a0e9ccc901077adfd3e662756adb7e3abb`。使用原 native 配置重新构建单 CPU、16 KiB 内核，保留标准 special mapping、Linux PTE、NCE 宿主窗口与代码处理。依赖从主线读取后创建独立 APFS 副本；内核 source/build、诊断、磁盘与日志均位于本树 `work/native-signal-check-v1`。本阶段提交记录和结构化结果，正式源码没有新增修改。

### 源码审查

- LKL UAPI 定义 `SA_RESTORER`，64 位原始 `rt_sigaction` 的字段顺序为 handler、flags、restorer、mask，总长 32 字节；系统调用的 mask 参数为 8 字节。检查先保存原 action，再安装 flags/restorer 均为 0 的 action，读回确认并实际执行信号，最后恢复原 action。
- `dup_mm` 复制原 mm；`nce_init_mm` 只为 accessed 分配新存储，`context.sigreturn` 随 fork 保留。标准 VMA/PTE 复制继续提供子进程映射。每次 exec 重新安装返回页并调用 `nce_populate_code`，成功后设置该 mm 的入口。
- 标准 `special_mapping_fault` 为页面调用 `get_page`，各 mm 的 PTE 引用由 Linux 回收。缓存页初始引用、页数组和描述符保留到本次内核 RAM 释放。初始化失败关闭文件并释放未发布页面；单个 mm 安装失败保留已发布缓存。
- 映射没有 `VM_MAYWRITE`，测试实际检查增加写权限返回 EACCES。mremap 回调约束原 base 和单页长度；本机测试确认改址失败，允许原 native 执行映射检查返回 EACCES 或特殊映射回调返回 EINVAL。测试通过后清理目标映射并恢复原 action。
- native 仍从真实 Linux RAM 向登记的宿主执行段复制代码，并处理原 SVC 指令。缓存页保留原 ELF 字节。原 NZCV、x9、x18、v0、v31、FPCR、FPSR 恢复检查和异常返回测试继续运行。

### 本机验证与 iOS 编译

环境为 Apple M5 Ultra、macOS 27.0（26A428），原生 NCE、单 CPU、16 KiB、`NCE_MM_MODE=demand`、sparse scan 开启、fault prefetch 关闭。诊断宿主副本只替换 `nce_process_run` 的程序选择与本专项准备，保留正式运行、代码复制、信号、定时器和最终清理路径。helper 调用原 `signal_tests` 与原寄存器汇编，分别构建为 musl 和项目构建 Bionic 程序；fork 子进程检查 raw restorer，exec 自身后再次检查，父进程随后再检查。Bionic/linker 为项目构建产物，与原始 SDK36 Bionic 的验证分别记录。

`summary-v3.json` 的 CLI/GCD 均为 returncode 0、validated true，最终 `result=passed`。每个入口均实际运行两个 helper，包含 8 条 `linux_signal_kernel_restorer`、2 条 `linux_signal_suite`、2 条 `linux_signal_context_redirect`、2 条 `native_signal_fork_exec` 和 2 条 `native_signal_reexec`。两入口各释放 21/21 上下文，内核告警检查和 `/data` 只读退出检查通过。专项生成的 64 MiB ext4 数据盘在退出后经 `e2fsck -fn` 检查，返回 0。

正式 `lkl-host.c`、正式 `lkl-process-host.c` 与实际诊断副本均成功编译为 `arm64-apple-ios17.0`，使用 iPhoneOS27.1 SDK。这个结果覆盖相应源文件的编译，iOS 应用链接和真机运行继续由对应阶段检查。

### 首次失败与实现偏离

现有 `probe_lkl.py --processes` 同时构建全部 Android 库并执行 framework。本专项先使用工作目录内的诊断副本，完整 Android 集成由主线处理。首次独立构建依次发现 lld 路径不正确、HOSTCC 缺少 Linux UAPI include、三个内核导出符号缺失，以及 Bionic ELF 需要原检查器的 `function_symbols` 模式。调整诊断构建脚本后成功；`build.log` 至 `build-v5.log` 和相应内核日志全部保留。

首次运行的 musl 检查成功，Bionic 因诊断没有准备随机设备而在 `getentropy` 失败，CLI/GCD 均退出 -6，报告为 `summary.json`。复用正式随机设备准备后的 `summary-v2.json` 已通过两套信号检查，退出仍因诊断没有挂载 `/data` 失败，且 linker config 缺失产生警告。v3 复用正式 sysfs、`mount_android_data`、随机设备和原 `art/ld.config.txt`，两入口全部成功。旧报告保留当次输入摘要，当前文件匹配结论仅适用于最终报告。

### 复杂度审阅

实际使用方为原生 NCE 的用户态信号处理、fork 和 exec。缓存页面与标准 PTE 引用承担不同生命周期；删除初始页面引用会破坏后续 mm 的映射，删除固定地址约束会破坏宿主登记的执行地址。原 signal suite 与寄存器汇编已检查实际恢复行为，本次只用工作目录 helper 增加 fork、exec 和父进程后续信号的组合。移除 helper 后会失去这一组合检查；新增产品运行模式会增加仅用于专项诊断的接口，因此保留工作目录诊断。没有增加 host API、mm 字段或正式构建选项。

## 曾考虑的替代方案

- 运行完整 Android 桌面回归：主线负责组合验证，本专项先覆盖共享信号路径，避免重复构建全部 Android 组件。
- 复用旧 signal ELF：旧二进制没有本次 raw restorer 检查，因此重新编译原测试源码和 helper。
- 增加产品运行模式：本次用途仅为阶段验证，诊断保留在工作目录，产品接口保持原值。
