# 决策记录: 快速非阻塞系统调用的调度进展

状态: implemented

## 问题

原 SDK v12 的 read 负结果汇总为 CLI 348407287、GCD 375322599，独立样本包含请求 `524288 bytes`、返回 `-11/EAGAIN` 的请求。汇总包含全部负值，实际任务和 FD 仍待[读取身份诊断](../../proposed/bug-fix/2026-11-14-原SDK图形读取忙循环.md)确认，当前无法据此判断调度原因。

固定 v12 内核的 `arch/lkl/kernel/syscalls.c` 中，`nce_run_syscall()` 调用 handler 与 `task_work_run()` 后返回。`nce_user_return()` 处理信号和用户地址准备；`nce_user_preempt()` 另行处理宿主等待者与 `cond_resched()`。宿主 `linux-execution.c` 的 timer 只给 `timer_active` 的执行器请求停止，用户执行结束后清除该标志。本轮用受控 guest 检查连续短系统调用中的客体任务、延迟数据、timer 与信号进展。

## 决策

保留 v12 原内核与 loader，在 Mac 上分别运行纯用户循环、快速 `getpid`、非阻塞 pipe 的 read/EAGAIN 与 poll 等待。CLI/GCD 的八次运行均取得另一客体任务、延迟数据、timer 与 SIGUSR1 的进展，退出和回收成功。后续继续确认实际 Android 的读取身份与等待契约。

### 负载与测量范围

四份 ELF 使用同一 [guest.c](../../../../work/syscall-progress-audit-v1/guest.c)，通过 `PROGRESS_CASE=0/1/2/3` 编译选择负载。已有 loader 的 `bionic` 分支执行 `/probe-guest`，本轮实际 guest 为静态 musl 程序。循环中的原 read 请求为 524288 bytes，pipe 设置 `O_NONBLOCK`。实际 ELF 反汇编确认 `user_loop` 主体没有 svc 或函数调用，`getpid` 使用 syscall 172，`read_eagain` 使用 syscall 63，musl poll 传递 `ppoll` syscall 73；POLLIN 后执行 read，poll 等待期限为 50 ms。

guest 通过 fork 创建 worker，父任务在 ready 后等待 150 ms，写入一字节 `0x5a` 并发送 SIGUSR1，再等待 100 ms 设置共享 stop。worker 的首个 SIGALRM 为 50 ms，第二个位于 2000 ms，第二次处理函数设置 stop 与 expired。父任务创建 worker 后设置 3000 ms 截止；宿主复用 `process_observer.observe()`，期限为 20 秒。四种模式各自依次运行 CLI/GCD，原 Android init 与其他 LKL host 保持停止。

原始时间取 guest `CLOCK_MONOTONIC`，单位为 ns；下表差值换算为 ms。入口日志的 `entry_marker_ns` 在 printf 前采集，`loop_started_ns` 在 printf 后采集。setitimer、write 与 kill 调用前后分别记录时间；表中的范围以完成时间为下界、开始时间为上界。timer/SIGUSR1 handler 与成功 read 后的计时包含 clock_gettime，普通 EAGAIN 分支保持原 read 调用，`user_loop` 与 `getpid` 主体没有计时或日志调用。handler 保存并恢复 errno。

`user_loop` 与 `getpid` 在循环结束后读取延迟数据；另两种模式要求在循环内取得数据。poll 只在当前等待返回后检查 stop，`stop_requested_ns` 至 `loop_ended_ns` 的实际间隔单独保留。

### 首轮失败与实现偏离

[build-01](../../../../work/syscall-progress-audit-v1/build-01/report.json) 的 guest 编译和链接成功，随后在辅助运行时路径检查处失败，尚未启动 guest。原路径位于 plain-repo 的 `android/android36`，实际 SDK 文件位于主仓库 `work/native-linux-nce/android/android36/com.android.runtime`；build-02 使用实际目录的 APFS 克隆，失败日志、原输入摘要与错误路径保持。

时间记录补充了日志 marker、实际 loop 开始、setitimer/write/kill 前后以及首个和最后 timer 时间，以区分接收早于调用返回的情况。四种循环的主体和原内核保持；本轮成功后继续实际 Android 的读取诊断。

### 复杂度审查

guest 的实际使用方只有本轮四种模式。共享 stop 与信号记录使用 lock-free 原子；其他普通字段由 worker 写入，父任务在 waitpid 后读取。ready 确定 worker 完成 timer 设置的顺序，loop_active 与信号时间用于确认循环期间的到达，FD 与子进程状态用于回收检查。移除这些状态会分别失去启动顺序、信号进展或生命周期记录。

四份 ELF 使用编译宏，保留已有 `/probe-guest` 入口；prepare 复用内核偏移、依赖解析和摘要函数，run 复用环境还原与 `process_observer.observe()`。已有宿主 timer 与 LKL 调度入口承担执行，guest timer 和父任务期限只服务本轮检查。原实现的四类负载均成功，当前继续验证 Android 请求的使用方与等待契约。

## 曾考虑的替代方案

- 依据 read 负值计数直接增加调度调用：未确认实际任务、FD 与其他任务的进展，无法区分用户重试、驱动等待与调度问题。
- 先改原图形库的 EAGAIN 分支：图形读取身份与等待契约仍在核对，受控 guest 可以独立验证系统调用返回的进展。
- 为该问题增加新的 timer 或长期采样状态：当前已存在宿主 timer 与 LKL 调度状态，先验证现有入口，额外状态的必要性尚未确定。

## 影响

四种受控循环的任务、延迟数据、timer 与 SIGUSR1 进展已在原 v12 内核和 CLI/GCD loader 上验证。实际 Android read 的任务、FD 与等待契约继续由 v13 诊断，完整 boot、应用操作和持续性能按原目标分别验收。

受控循环与 Android 图形请求的使用方和负载不同，宿主后台进程与调度会影响时序，本轮结果只覆盖上述八次运行。iOS 实际执行、JIT 授权、设备资源与热状态待真机验证。
