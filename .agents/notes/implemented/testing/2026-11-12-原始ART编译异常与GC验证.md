# 决策记录: 原始 ART 编译异常与 GC 验证

状态: implemented

## 问题

[framework 依赖审查](../../proposed/testing/2026-11-12-原始运行库framework依赖审查.md)确认项目 ART 曾关闭隐式空指针检查并限制部分编译路径。原始 ART 标准 JNI 已覆盖显式异常，已确认编译的热方法主要执行整数计算。本记录最初要求实际验证编译后空指针访问、递归栈溢出、捕获后继续执行和对象跨 GC 存活。

## 决策

新增独立 `StockArtExceptions.java`，通过现有组件的标准 JNI 调用。空指针用例先完成具有可观察写入的循环，再读取传入对象字段，捕获 `NullPointerException` 后核对执行状态。栈用例以非尾递归触发 `StackOverflowError`，检查异常栈并继续普通计算。GC 用例保留对象引用，执行 `System.gc()` 后检查字段及引用关系。

原始库、JAR 和运行行为保持原样。默认组件检查 Java/JNI 语义；显式 first-use 模式用于已编译对照，保存原 ART 编译代码范围和宿主已完成 PC。宿主在已有观察区间内记录 page fault 未能由 Linux 建立映射的 PC、地址、访问类型与进程身份，再按既有方式交给 Linux 信号路径。该记录仅观察实际失败，不拦截或代替原 ART 异常处理。

先完成空指针、栈溢出及继续执行，保留真实失败。异常路径确认后再决定 OSR 实验的具体负载，当前不启用或关闭额外 ART 优化。

## 曾考虑的替代方案

仅显式 `throw` 异常。它无法检查原编译代码通过访存故障进入 ART 信号处理的路径。调用项目私有编译入口或关闭隐式检查。会改变原库行为，现有原 ART 的 first-use 参数可以提供独立编译对照。增加泛化 fixture 调度器。当前只有三个具体用例，复用标准 JNI 组件与已有观察窗口即可。

## 影响

CLI/GCD 均执行原库和标准 JNI；各用例返回规定结果，异常类型、栈来源和捕获后状态正确，GC 后对象字段与关系保留。已编译结论同时记录方法编译日志、完成 PC 与稳定 RX 映射；隐式异常结论还需实际访存 fault PC 落入对应方法代码范围。缺少某类观察即保留未确认。完整报告继续检查输入未变化、映射快照、VM 退出与上下文释放。

### 验证边界

日志与完成指令采样影响时序，结果仅用于功能验证。编译器可能为某个用例生成显式检查，必须按实际 fault 和代码路径判断。异常处理中的栈展开、信号恢复或原始 JNI 编译可能暴露新的执行器问题，失败后保留原日志并定位原因。

## 实施与验证记录

2026-11-12 已新增 `StockArtExceptions.java`，通过标准 JNI 顺序调用空指针、栈溢出和对象跨 GC 用例。空指针用例先对有效对象执行 200000 次循环，再对 null 执行相同循环并访问字段；捕获后检查异常栈、循环状态和继续计算的结果。栈用例包含浅层递归校验、深层递归以及捕获后的普通计算。GC 用例保留 4096 个对象组成的环，调用 `System.gc()` 后核对每个对象字段、首尾引用和遍历结果。

宿主新增 `guest_fault` 观察记录，只在已有目标线程窗口内记录 Linux page fault 返回失败的 PC、地址、访问类型、返回值和进程身份。失败仍进入原有 `user_fault`。解析器检查记录身份、窗口和格式，故障 PC 单独保存；完成指令采样仍只统计 `integer_completed`。first-use 增加原 ART 的 JIT 日志，原库及其异常处理保持原样。

### 首轮本机结果

Mac 为 Apple M5 Ultra、macOS 27.0 build 26A428。首轮仅运行 CLI，原始 SDK36 ART、16 KiB 客体页、Direct、单 CPU、flat/sparse、data TBI、dual code memory、每批 50000 条指令，模式为 `first-use`。完整命令、输入摘要、所选原始日志与失败记录保存在[暂停结果](../../../../experiments/native-linux/results-stock-art-exceptions-paused-20261112.json)。原始输入 290 个不同文件共 145501325 字节；加上 `/system/bin/linker64` 同字节别名后，安装的原始文件为 291 个、147750805 字节。本次运行报告确认输入未改变。

`readAfterLoop` 编译日志记录代码范围 `[0x1400fa40, 0x1400fac0)`。该范围内记录了 65 个已完成整数指令样本，首条 PC 为 `0x1400fa60`，PID/TID 均为 2。随后记录实际读故障 `pc=0x1400fa80 address=0xc access=0 result=-14`，PC 位于该方法范围内。guest libc 随后输出 `Fatal signal 11 (SIGSEGV), code 128 (SI_KERNEL), fault addr 0x0`，组件以 signal 11 退出。

`implicit_null` 检查尚未返回，空指针捕获及后续计算尚未通过。栈溢出和新增的对象跨 GC 用例未执行；GCD、默认阈值、background 与 OSR 尚未执行本次新增用例。进程在结束标记和 `after-warmup` maps 之前退出，整轮报告 `validated=false`，JIT 观察器报告「观测窗口缺失或重复」。当前可记录方法编译日志与局部完成 PC、故障 PC 的对应关系；完整窗口的稳定映射条件尚未通过。

暂停前已完成报告解析器 364 个拒绝案例、JIT 关联解析器 54 个拒绝案例和输入校验 9 个拒绝案例，均成功。C 格式化和 `git diff --check` 已成功。这些解析检查未覆盖实际异常恢复成功。

### 复杂度审查

三个用例复用已有 Java 编译、标准 JNI 调用和报告检查。新状态只有用例内的循环进度与递归深度，分别检查异常前写入和递归范围。宿主故障记录复用现有线程身份及窗口，不引入第二套生命周期。删除故障记录会失去隐式访问的 PC 与线程来源；删除 Java 用例会失去本次实际失败的复现入口。尚未增加泛化 fixture 调度器或私有 ART 调用。

### 用户要求暂停

用户要求推送仓库并暂缓任务后，停止了新增开发、修复和实验。首轮 CLI 与准备命令均已结束，本工作树没有运行中的实验。暂停时修改保存为未完成实验检查点，提案保持 `proposed`，此分支单独推送。恢复后的结果见下文。

恢复后先调查编译方法隐式 null 访问之后的 `SIGSEGV/SI_KERNEL`。源码中 `lkl-nce-signal.c:109` 的 `force_sig(SIGSEGV)` 是待核查位置，当前尚未确认实际经过该错误路径。完成原因定位与异常恢复后，再执行栈溢出、对象跨 GC、GCD 和默认阈值检查。本次没有进行 iPhone 验证。

### 恢复后的首次运行与线程栈条件

2026-11-12 主线信号恢复修复 `bd8f129` 合入本工作树为 `41e58f0`。16 KiB 构建脚本沿用本树接口，并补充复制源码摘要，原始库和 fixture 继续使用暂停时字节。第一轮 `stock-art-exceptions-sigreturn-v2` 的 `implicit_null` 返回 47，原 SIGSEGV/SI_KERNEL 消失。递归调用触发栈边界访问，ART 日志记录主线程栈大小 8176 KiB；随后 `Throwable.getOurStackTrace` 将深递归栈轨迹转换为 Java 对象，耗尽 fixture 的 64 MiB Java 堆。`stack_overflow` 因 OutOfMemoryError 失败，组件退出码为 1、signal=0、timed_out=false，11/11 上下文释放，GC 存活引用用例与 GCD 未执行。失败的报告和日志继续保留。

栈溢出用例改用标准 Java Thread 构造器请求 256 KiB 栈，保留 StackOverflowError 类型、实际递归深度、`recurse` 栈轨迹、浅递归和恢复后的正常计算。线程通过 `join()` 完成后读取返回值与异常，检查线程中的任何 Throwable 均继续使组件失败。实际分配大小由 ART 决定，本轮没有测量新线程栈大小，系统默认线程栈与 Java 堆配置保持原值。

曾考虑增大 Java 堆，它会改变原 JNI/GC 负载及资源条件；也曾考虑去掉栈轨迹检查，它会减少异常返回位置的验证。本轮选择独立线程请求较小栈。返回值数组与异常数组分别承载用例结果和实际失败，`join()` 建立读取条件，复用现有 Thread 生命周期，没有增加线程控制接口或产品配置。原 null 用例和 4096 对象环的 GC 检查继续使用原条件。

首次准备较小栈 fixture 的 `bounded-v3` 使用 lambda，本机 SDK35 Java stubs 缺少所需 `LambdaMetafactory.metafactory`，javac 失败，尚未运行 Linux。改为与既有 Java 线程用例一致的匿名 Runnable 后，重新准备到 `work/stock-art-exceptions-bounded-v4` 成功；原始输入仍为 290 个不同文件，安装原始字节 147750805，只有 fixture Java/DEX 和来源摘要改变。

### 主线组合与 iOS 构建

主线合入 `1a93f8c` 和 `6ff4b3f` 的 fixture、标准 JNI 与故障观察改动，保留当前 `runtime_source`、`guest_page_bytes` 和 `attach` 接口。来源摘要按所选 SDK36 或 HyperOS 的 `lock_path` 记录；重复移植信号修复的 `41e58f0` 未合入。Java 注释说明 256 KiB 为请求值，新线程实际栈分配大小继续保留未测量。SDK36 与 HyperOS 均用主线生成脚本重新准备，分别得到 294、303 个 staging 文件，原始字节及 linker 别名分别为 147750805、166946345 字节。

主线的 `stock-art-main-exceptions-v2` 使用 SDK36、16 KiB、first-use、单 CPU、sparse/TBI、Direct flat 和 dual。CLI/GCD 各 16 项标准 JNI 检查成功，两个入口均 `implicit_null=47`、`stack_overflow=47`、`gc_live_references=8386560`，12/12 上下文释放，输入保持一致。稳定 JIT RX 区间各有 103 条已完成指令样本，实际地址 12 的读故障 PC 位于原日志中 `StockArtExceptions.readAfterLoop` 的编译范围内，原 ART 处理后继续执行成功。

`hyperos-art-main-exceptions-v2` 使用同源 HyperOS ART、4 KiB、默认 JIT 参数、单 CPU、sparse/TBI、Direct flat 和 dual，开启 code-watch、cross-page 与 native-exclusive。CLI/GCD 的同一 16 项检查成功，结果与 SDK36 一致，12/12 上下文释放，原始输入不变。该轮关闭完成 PC 观察，HyperOS JIT 实际执行继续待确认。宿主环境与前述独立回归相同，日志与并行功能任务影响时序，本轮没有性能比较。

原 iOS 运行库构建在 `mach/mach_vm.h` 处失败，同时发现客体页大小未传给宿主与引擎编译。处理和验证见[iOS 稀疏映射编译与客体页大小](../bug-fix/2026-11-12-iOS稀疏映射编译与客体页大小.md)。修复后的 sparse core CLI/GCD 为 71/72 条检查成功，各 70/70 上下文释放；iOS 16 KiB 与 4 KiB 各生成完整 Direct 静态运行库。设备执行、完整系统、HyperOS 桌面与持续性能继续待验证。
