# 决策记录: 交互采样窗口长帧统计

状态: implemented

## 问题

[交互分析器](../../../../scripts/analyze_interaction_profile.py)原先要求一帧的 `IntendedVsync` 与 `FrameCompleted` 都落在采样窗口内，跨边界帧仅计入排除数量。窗口 `[1s,3s]` 中，`[1.2s,1.21s]` 与 `[1.3s,3.3s]` 两帧会得到 `failures=[]`、一个接受帧和 10 ms 最大耗时；实际导出的 2000 ms 帧没有进入耗时统计。窗口内已有完整帧还会掩盖完成时间缺失的其他帧。

本轮已获离线实现授权。修改前执行 `python3 -B -m unittest discover -s scripts -p 'test_interaction*.py'`，原有 14 项测试成功，当时没有覆盖此行为的分析器端到端回归。

## 决策

按 `IntendedVsync` 选择 `[start,end)` 内起始的帧。完成时间有效且起始时刻归属明确的帧保留完整耗时，跨结束边界也进入耗时与阶段分布。逐帧记录边界关系与完成状态；完成时间缺失或无效的帧保留原始字段和采样结束距起始的时间，不生成完整耗时。

跨越窗口起止、窗口内缺失或无效的完成时间、时钟不确定范围覆盖边界均使帧采集检查失败。起始在窗口之前且完成时间缺失或无效的记录标为 `overlap_unknown`，采集检查失败。报告保留诊断数值并通过既有 `failures` 与 CLI 非零退出码限制性能结论。时钟归属明确的帧，起始时刻等于窗口开始则纳入，等于窗口结束则排除；完成时刻等于结束边界视为完整。

耗时样本选择改变，报告 `version` 从 1 升为 2，`duration_scope` 说明样本范围，`exported_frame_window_complete` 表示已导出帧、帧总数与采样窗口检查是否通过。帧记录增加 `completion_status`、`window_boundary` 和 `clock_boundary_uncertain`；缺失或无效的完成时间额外保留 `elapsed_to_window_end_ms`，值为对齐后的窗口结束减去起始时刻。该值描述窗口区间，不能作为真实耗时或其下界。

`duration`、`phase_duration` 和 `frame_counts` 等原有字段保留；窗口外排除原因从 `outside_or_crossing_window` 改为 `outside_start_window`，跨结束边界的有效帧计入 `accepted`。`duration_ms` 也保存在完成时间有效的排除行中，汇总仍以 `excluded` 为空的帧为准。历史结果归档保持原样。仓库搜索确认实际入口为分析器 CLI；结果文件、测试和文档是当前可见消费者，没有发现依赖旧 `duration` 选择条件的运行脚本。

### 本机验证

环境为 macOS 27.0 arm64、Python 3.14.6，使用合成的 `request.json`、`result.json`、时钟校准与 `frames.txt`；这些结果验证分析行为，不包含 Android 运行性能测量。

`python3 -B -m unittest discover -s scripts -p 'test_interaction*.py'` 的 23 项回归成功。其中新增 9 项直接分析临时运行目录，覆盖跨结束边界完整耗时、缺失与倒序完成时间、半开起始区间与精确完成边界、开始前已知或未知重叠、时钟不确定范围内的起止时刻、窗口外帧的可能重叠、重复与非零 Flags、客体时钟偏移。长帧用例另通过真实 CLI 检查报告落盘和退出码。`git diff --check` 成功。

同一两帧输入分别调用提交 `96c23aa96a13df233ec2fc591290553e9ec43727` 的代码与修改后分析器，得到：

| 指标 | 修改前 | 修改后 |
| --- | --- | --- |
| `frame_counts.accepted` | 1 | 2 |
| 最大耗时，ms | 10 | 2000 |
| P99，ms | 10 | 1980.1 |
| 超过 1000 ms 的帧数 | 0 | 1 |
| `failures` | `[]` | `["frame crosses capture window boundary"]` |

P99 沿用线性插值，两个样本继续带有小样本标记。新 CLI 返回 1，并保存完整报告。完成时间分别为 `0`、`2**63-1`、`1299999999` 的三个子用例均以 `1300000000` 为起始时刻，记录 1700 ms 窗口区间、保留完成状态、排除完整耗时统计，并使帧窗口检查失败。

### 复杂度与文字审查

按 reclaim-code-entropy 检查实际调用方、JSON 使用点和分支用途。新增状态由原始帧与时钟推导，直接写入现有报告；失败原因使用集合去重，继续交给已有 CLI 退出逻辑处理，没有增加协议、依赖或独立统计器。删除完整耗时保留会重新得到 10 ms 最大值；删除跨界或完成时间缺失检查会允许不完整采集通过。逐帧状态用于解释排除原因和汇总样本，保留这些字段。文档按 humanizer-zh 复核，仅陈述实际行为、复现数值和未覆盖条件。

## 曾考虑的替代方案

- 继续排除跨边界帧，仅增加失败标记：保留了失败状态，但摘要仍缺少已知长帧耗时，难以直接检查尾部统计。
- 将跨边界帧截断到采样结束：会把不完整耗时加入分位数，2000 ms 示例仍被低估。
- 自动延长采集或新增连续追踪：需要改动采集协议和运行时，本轮先修复现有原始记录的解释；完全未导出的帧仍需后续连续事件采集。

## 影响

新旧报告的耗时统计口径有差异，重算必须保留对应分析器版本和哈希。帧窗口完整性仅描述已导出记录及已有总数检查；`dumpsys gfxinfo` 完全未导出的应用工作仍无法由这些字段确认。未完成记录中的结束距起始时间只描述窗口长度，不能据此宣称真实帧完成耗时。此次检查使用合成文件，不含真机运行或交互性能测量。
