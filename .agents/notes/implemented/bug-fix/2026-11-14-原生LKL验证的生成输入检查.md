# 决策记录: 原生 LKL 验证的生成输入检查

状态: implemented

## 问题

`probe_lkl.py --processes` 在开始运行时记录 `started_ns`，结束时拒绝修改时间晚于该值的输入。ashmem 的实际编译输入加入清单后，适配源码、生成头文件、配置、对象和依赖清单都会触发这一检查。

候选 `b1fdf1becbbba5f62e6fb8184d105a176e26814b` 在独立工作树首次运行标准原生 16 KiB 验证。CLI 和 GCD 均完整结束，各有 204 项 `passed=true` 检查；GCD 的 `inherited_blocked_threads` 为 67，独立数据盘代次为 1、2，ext4 关闭状态正常。外层脚本随后列出 79 条晚于启动时间的输入并退出 1，没有生成 `lkl-summary.json`。原失败、来宾结果与输入摘要保存在[首次结果](../../../../work/native-processes-merge-validation-v1/result.json)和[完成检查失败](../../../../work/native-processes-merge-validation-v1/initial-completion-failure.json)。

## 决策

本阶段已获主会话授权，在独立工作树修改完成检查。仓库源码继续使用启动时间作为检查边界；LKL 源码使用适配完成且编译尚未开始的时间；构建目录中的配置、对象、依赖清单和生成头文件使用实际依赖清单产出完成的时间。实际编译源码在编译或验证期间修改，仍须拒绝整轮结果。输入清单和最终内容摘要沿用既有格式。

`changed_inputs()` 根据实际路径选择对应时间，目录外的输入使用 `started_ns`。LKL 源码与构建目录在原生入口中分别位于 `lkl-source` 和 `lkl-process-build`，两者为并列目录。源码准备时间在 `apply()`、`file2alias.c` 适配完成后记录，先于 `headers_install` 和内核编译；构建完成时间在 `all` 和 `compiled_inputs()` 完成后记录。

### 复杂度审阅与偏离

按 reclaim-code-entropy 核对实际使用方。输入判断由 `probe_lkl.main()` 调用，新的宿主回归直接覆盖这项判断。新增状态限于本轮的源码准备和构建完成时间；原输入清单、命令行和产物格式继续使用。handoff_audit 独立只读检查了两个时间值的位置、目录关系与回归范围，结果成功。

将所有边界改为启动时间会复现首次运行的 79 条生成输入拒绝；将源码边界移到编译完成后，会接受编译期间修改的源码，源码变化回归随之失败。按准备阶段分别记录时间保留了这两项行为要求。

原计划只补原生验收。首次运行复现完成检查缺陷后，主会话授权在隔离树修复并增加必要回归。主仓库、候选源码和共享 CORE 保持原有内容；补丁与记录由主会话接收，本侧未提交或推送。技术文字按仓库约定与 humanizer-zh 审阅。

## 曾考虑的替代方案

- 所有输入继续使用启动时间：首次实际运行已经复现生成输入导致的失败。
- 所有 LKL 输入使用编译完成时间：编译期间修改实际源码会通过检查。
- 清除生成文件的修改时间或从输入清单删除它们：会改变产物元数据或减少实际输入记录。

## 影响

完成检查沿用修改时间检测，最终输入摘要继续记录内容。保持原修改时间的内容改动不在这项完成检查的检测范围内。新原生结果覆盖既有 Bionic、Binder、ART 与平台固定件，原 SDK 默认显示和 HyperOS 阶段另行验收。设备资源、JIT 授权、持续性能和热状态待真机验证。
