# 决策记录: 启动日志乱序导致就绪状态丢失

状态: implemented

## 问题

`0.20.0` Mac 构建 9 的公共镜像对照在第五轮关闭镜像时持续显示启动中。该轮日志先记录 `android_desktop_running`，随后才记录 `android_desktop_first_frame` 和 `android_desktop_ready`。Android 已完成就绪检查，宿主 benchmark 没有进入操作阶段。原始日志为 `work/native-linux-nce/benchmarks/20261010-224050-2c6c7c/6F4C3BC1-82CE-49F1-A435-DF75EBF0FDB1/session.log`；相邻记录出现在 2026-10-10 14:49:38 UTC 附近。

`desktop-session.cpp` 在就绪检查完成后向 stderr 记录 running，辅助 Java 进程向 stdout 记录 first_frame。宿主分别读取两个流，文件中的顺序可能变化。`ProbeLogReader` 按最后一个已知 phase 更新快照，`SessionModel` 只检查该 phase 是否为 running；同一批次中较晚出现的 first_frame 会覆盖已就绪的阶段。读取器已有单调递增的 step，running 对应 4，first_frame 对应 3，可以复用它。

## 决策

SessionModel 根据快照中已经达到的启动步骤识别就绪，继续由运行时完成事件控制停止和失败。保留最近 phase 供日志展示，不新增一份就绪标志。回归覆盖同一读取批次里 running 后出现 first_frame、正常顺序、仅有 first_frame，以及停止期间收到就绪日志。已结束实验保留，使用修复后的同包构建重跑性能对照。

2026-10-11 的 `python3 scripts/test_native_linux_macos.py` 再次通过状态顺序、日志替换和停止边界检查。`0.22.0` 正式 App 对照的前两轮均从就绪进入操作并正常停止；第三轮 Android 没有发出就绪事件，宿主保持启动状态，到期后请求停止。第三轮随后发生的客体初始化与退出问题单独保留，详见[公共镜像结果](../../../../experiments/native-linux/results-macos-desktop-boot-image.json)。原失败轮次及磁盘检查仍保存在该结果中。

## 曾考虑的替代方案

- 只调整 stdout/stderr 刷新顺序：多个进程和两个读取流仍可能产生不同观察顺序，宿主必须正确处理已经收到的就绪事件。
- 使用首帧事件直接完成启动：会跳过现有父进程确认及后续步骤，改变就绪的验收条件。
- 延长 benchmark 时限：无法恢复已经被覆盖的就绪阶段。

### 验证条件

1. 状态回归通过上述顺序和停止边界；日志替换后开始的新会话清除旧步骤。
2. 同一构建下重新运行公共镜像启停对照，保存启动、操作、退出和阶段内存。
3. 原失败单独记录，不能用修复后的结果改写旧轮次的就绪耗时。此前的其他慢启动仍需各自检查日志，不能一并归因。

## 影响

本次已确认日志读取与会话状态之间的问题；此前的 ART 辅助进程 SIGSEGV，以及其他未绘制或慢启动样本仍未定位。
