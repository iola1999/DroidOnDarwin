# 决策记录: 内核信号返回特殊映射

状态: implemented

## 问题

[原 SDK36 init 实验](../../proposed/architecture/2026-11-12-原始SDK36-init与rc启动实验.md)恢复原 `/etc` 后，vendor_init、ueventd 和 apexd 的 exec 继续返回 EACCES，并收到 SIGSEGV。原 `arch_setup_additional_pages` 在 exec 提交新凭据之后打开 `/lib/nce-sigreturn.so`，再以 RX 权限进行文件 mmap。原策略将这个文件标为 `u:object_r:rootfs:s0`；各任务域的文件访问权限不同。

独立诊断 v23 的 CLI/GCD 都实际记录 vendor_init 的 `filp_open=-13`、任务域 `u:r:vendor_init:s0`；apexd 同为 `filp_open=-13`、任务域 `u:r:apexd:s0`。ueventd 打开成功，`vm_mmap(PROT_READ|PROT_EXEC)=-13`、任务域 `u:r:ueventd:s0`。目标 inode 的有效标签均为 rootfs。原 init 在 `u:r:init:s0` 下填页成功。任务域和文件标签由内核 LSM 查询取得，原 policy、enforcing、服务二进制和 rc 保持原状。Linux 在 exec 的 point_of_no_return 之后失败会强制 SIGSEGV，对应原服务的 signal 11。

诊断只修改独立生成内核 `work/native-linux-nce/stock-init-sigreturn-diagnostic-kernel`，结果位于 `stock-init-sigreturn-open-v23/summary.json`。v20 复用旧 runner，v21 只更新 `lkl-image.h`，都使用了旧内核符号偏移；重新生成 `translation-symbols.h` 的 copy/lookup 地址后，v22 四入口观察与回收成功。v22 的 printk 在原 init 设置日志状态后没有输出后续记录；v23 使用宿主日志回调，取得上述返回值。失败日志保留，临时诊断函数未进入正式源码。

## 决策

`lkl-nce-elf.c` 使用标准 Linux `_install_special_mapping` 为每个 mm 提供内核信号返回页。第一次 exec 在 mutex 内从原 stub 读取完整文件，校验 ELF64/AArch64、唯一 RX `PT_LOAD`、单页布局、入口范围与对齐，并用已有 `nce_elf_file_layout` 核对宿主登记的路径、header、phdr 和 base。当前原文件为 1,296 字节、load filesz/memsz 为 360、entry 为 120。页面由 `alloc_page(GFP_KERNEL | __GFP_ZERO)` 分配，保留文件末尾后的零字节，关闭文件后发布 base、绝对 entry 和 `page[0]`。现有 helper 在原 policy 加载前首次执行；v23 记录其任务域为 kernel、文件标签为 unlabeled，打开与填页成功。

缓存只保存 base、entry、空终止的 `page[2]` 和初始化 mutex。descriptor、页数组和内核持有的初始页面引用保留至本次内核 RAM 释放。初始化失败关闭文件并释放未发布页面；单个 mm 安装失败保留完整缓存。后续 exec 在 mmap 写锁内检查固定地址冲突，再安装 `VM_READ | VM_EXEC | VM_MAYREAD | VM_MAYEXEC` 映射，解锁后调用现有 `nce_populate_code`，成功后设置 `context.sigreturn`。页面不能增加写权限；mremap 回调拒绝改变 base 或单页长度。

fork 沿用已有 mm/VMA 复制和 `context.sigreturn`，退出释放 PTE 引用。native 继续在宿主 alias 中复制原 RAM 字节并应用现有 SVC 补丁，缓存页保持原 ELF 字节。translation 复用相同 additional-pages 实现。普通 ELF 打开、域转换、文件映射和执行权限检查继续走原 LSM；后续服务使用内核提供的返回页。本次修复沿用已有 guest 文件的所有者、mode 和标签；原 `/system` 内容与元数据由只读 ext4 提供。原 policy、enforcing 与 rc 保持原输入。此前恢复的 `/etc` 原链接 mode 为 0644，Linux 新链接 mode 为 0777，差异见[原 `/etc` 阶段记录](../../proposed/architecture/2026-11-12-原始SDK36-init与rc启动实验.md#原-etc-链接的独立复验)。

### 实际信号返回检查

原 musl `sigaction` 会设置 `SA_RESTORER` 并使用 libc 的 `__restore_rt`。已有 signal suite 可以检查信号恢复，尚未检查本次内核返回页。新增检查以原始 `rt_sigaction` 安装 32 字节 kernel action，mask 参数为 8 字节，读回确认 flags/restorer 为 0，再复用 `signal_register_test(getpid())` 检查 NZCV、x9、x18、v0、v31、FPCR 和 FPSR。

handler 记录实际 LR，检查其地址位于 `/proc/self/maps` 的 `[nce-sigreturn]` 单页 `r-xp` 映射；增加写权限必须返回 EACCES，改址的 mremap 必须失败。translation 通过特殊映射回调返回 EINVAL；native 允许由现有执行映射检查先返回 EACCES。测试恢复原 action，并清理用于 mremap 的目标映射。core 的 exec 入口和 stock-init helper 的 exec 后 main 均执行这项检查；lifecycle 的现有 fork 子进程再次执行，报告要求 PID 1、2 的成功记录。

### 复杂度审阅

实际使用方为 AArch64 无 `sa_restorer` 的信号返回路径、原 init 派生的服务 exec，以及 native/translation 的用户态执行。缓存页、固定地址、入口、描述符和初始化 mutex 各自承担页面引用、宿主登记和发布同步。删除缓存会恢复 v23 的文件权限失败；删除初始页面引用会让后续 mm 使用已释放页面；允许 mremap 移动会破坏宿主已登记的执行地址。用内核静态字节数组替代 alloc_page 会违反宿主要求的 Linux RAM 页面范围。

复用标准 fault、VMA 和 fork 处理，未新增 host API、auxv、mm 字段、每 mm 页副本、自定义 close/fault 或已修改标志。测试复用现有寄存器汇编和 signal-tests，stock-init 只增加两个调用位置及原有构建脚本的链接输入。独立审阅确认缓存发布、失败清理、页引用、地址约束和 raw action 布局；代码注释改为当前映射的实际权限，标准 arm64 vDSO 另带 `VM_MAYWRITE`。

## 曾考虑的替代方案

- 给各服务域增加 rootfs 文件权限：需要改变原策略，本阶段保留原策略与 enforcing。
- 将这个宿主文件改标为系统库：文件归属没有对应的原系统库类型，采用内核特殊映射保留 guest 标签。
- 长期保存 file 句柄：后续文件 mmap 仍会执行新域的权限检查，ueventd 已在这一阶段失败。
- 新增 host 接口提供返回代码：已有 ELF 登记提供地址和入口，首次读取原 stub 即可完成本阶段用途。

## 影响

本阶段解除服务 exec 的信号返回文件依赖，保留原 init 的服务启动、失败处理和重启行为。首次缓存仍依赖 helper 在 policy 加载之前读取已登记的原 stub；单页 ELF 契约由检查与宿主匹配约束。独立树使用旧检查点执行器与页表实现，主线已重建并验证上述组合及 iOS 编译。设备资源、JIT 授权、持续性能和热状态继续由对应阶段验证；本阶段没有真机结果。
