# 决策记录: 原始 init 观察日志与并发回归

状态: implemented

## 问题

主线 `c15cda8` 的 DM 两种页大小 lifecycle 已通过，CLI original 首轮解析出现 JSONDecodeError。4 KiB 的 `sdk-dm-main-4k-v1/cli-original.jsonl` 有两条坏行，首条为 51758；16 KiB 的 `sdk-dm-main-16k-v1/cli-original.jsonl` 有三条，首条为 49455。原始输出在主线 work 中保留，GCD original 尚未由这两份首轮结果验证。

旧 `stock-init-trace.h` 的 write/security/block 通过多个 stdio 调用输出一条 JSON，其他线程的单次 `printf` 可以插入记录中间。首轮坏行的 write hex 中插入了完整 memory_sample JSON。task context 同样使用多次输出，需要保持整条记录完整。

旧脚本解析失败后只保存此前完成的 lifecycle summary，没有保存 original 的宿主返回码。原始尾部的停止与回收记录仅供诊断，首轮 original 保持观察失败。

## 决策

每条多段记录使用 stdout 的 `flockfile`/`funlockfile`，客体复制与 block getpid 在加锁前完成。单次 printf 继续使用 stdio 自身的流锁。字段、捕获字节、采样范围与原 init 行为保持。

`probe_stock_init.py` 使用严格的逐行 JSON 解析。解析失败保存文件、行号、列号、宿主返回码和原始输出 SHA-256，并在 failure.json 与 summary.json 中把入口标记为 `observation_validated=false`。原始输出保留，不跳过坏行。

在 `work/stock-init-keymint` 新增 `experiments/native-linux/translation/stock-init-trace-test.c` 和 `scripts/test_stock_init_trace.py`，直接 include `--trace-header` 指定的实际头文件。四个 pthread 分别记录 write/writev、setxattr/fsetxattr、mount/syscall 和单次 printf 的 memory_sample。客体读取用 memcpy，getpid 用宿主进程 ID；测试保存全部 stdout/stderr、输入摘要和编译命令。

Python 检查所有物理行的 JSON、完整记录数量、字段和 hex 内容。Counter 核对无序的完整记录，包含 writev 的两个 vector、2304-byte write 的 2048-byte 捕获和 300-byte 标签的 256-byte 捕获。解析失败仍输出 failure.json 和非零退出码，原始输出保持。

### 原 init 与 iOS 组合复验

`sdk-dm-main-4k-v2` 与 `sdk-dm-main-16k-v2` 的 CLI/GCD lifecycle、original 共八个入口均 returncode=0、`observation_validated=true`，全部 JSON 可解析。lifecycle 各回收 2/2 上下文；4 KiB original CLI/GCD 分别回收 190/190、191/191，16 KiB original 两入口各回收 190/190，页表告警为零。五个 DM 分区的严格移除、原策略后的卸载拒绝及标准 halt 分别保持。

两页各 31 项 SDK contract 与 27 项共享 HyperOS contract 检查成功。两页 iOS runtime 各 15 条编译命令、115 项输入，实际 init runner/execution 各两条命令、172/171 项输入全部匹配。首次 iOS 实验副本编译因旧 runtime 的头文件摘要不匹配而停止，随后重新构建 runtime 和实际副本，原失败继续保存。

[主线组合归档](../../../../experiments/native-linux/results-sdk-dm-main-20261113.json)保存八入口的关键记录及原索引、输入身份、并发回归、首轮交错失败和 iOS 身份失败。原 KeyMint exec/VINTF 成功，原 SQLite 的 EROFS 和 NetBpfLoad 的首次失败继续记录；完整原系统与 iPhone 执行尚未通过。

### 复验

在主线执行，使用新输出目录。旧头来自固定提交，预期退出 1 并生成 failure.json；修复头预期退出 0：

```sh
git show ddc064b6:experiments/native-linux/translation/stock-init-trace.h \
  > work/native-linux-nce/old-stock-init-trace.h

python3 -u scripts/test_stock_init_trace.py \
  --trace-header work/native-linux-nce/old-stock-init-trace.h \
  --output work/native-linux-nce/stock-init-trace-concurrent-old-v2

python3 -u scripts/test_stock_init_trace.py \
  --trace-header experiments/native-linux/translation/stock-init-trace.h \
  --output work/native-linux-nce/stock-init-trace-main-v2
```

### 复杂度审阅

按 reclaim-code-entropy 核对使用方和必要状态。Python 脚本是 C fixture 的构建与执行入口；fixture 的一个 atomic 起始标记让四个独立 pthread 同时开始。输入与 raw 输出的摘要用于检查本轮测试身份，Counter 用于核对并发产生的无序记录。没有新增生产日志队列、线程或锁接口。

移除影响已按实际失败核对。删除 memory_sample 线程将停止覆盖原坏行中的采样输出；只检查 JSON 语法会漏掉旧头的 110 条合法但内容不符记录；替换被测头中的 stdio 调用会改变本次实际使用方。两份测试保持同一 C/Python 源码和参数，按实际头文件区分结果。

## 曾考虑的替代方案

- 使用测试自带的 printf 包装或重新实现头文件：会改变被测 stdio 的锁范围。
- 加入日志队列或额外写线程：生产代码已有 stdout 的标准流锁，本回归只需独立竞争线程。
- 停用内存采样：会改变现有观察范围，多段记录仍可能与其他线程输出交错。
- 为每条记录增加序列化缓冲区：需要维护容量和截断检查，现有字段可继续使用标准流锁。
- 只核对行数和 JSON 语法：旧结果已经包含内容不符的合法 JSON，需要继续检查完整字段和客体字节。

## 影响

此回归验证宿主 stdio 并发记录，原 init 两页组合分别覆盖实际并发输出和资源结束。fixture 的 memory_sample 数值由测试生成，本阶段没有内存或性能结论。流锁会影响不同线程记录的先后次序，持锁期间仅执行 stdio 输出。

[结构化结果](../../../../experiments/native-linux/results-stock-init-trace-concurrent-20261113.json)为 19,976 bytes，SHA-256 为 `4c896450c97e0dd03d51cf214d7a8e68b25cdeb64ec34f1df28fecca3b08549a`，保存两份完整报告、头文件身份、所有原始产物摘要和复杂度检查。技术文字按仓库约定与 humanizer-zh 审阅。
