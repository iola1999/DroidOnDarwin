# 决策记录: 带标签缓存操作数的代码失效

状态: implemented

## 问题

标准 VM/IC 修复和用户数据 TBI 合并后，`cache_instruction()` 仍将 `IC_IVAU` 的完整操作数传给 `translate_user()`。数据 TBI 已在普通读写与缺页路径清除顶字节，缓存操作尚未采用同一规则。合并后的真实 Direct sparse 检查复现了该问题：内核 `pwrite` 已更新目标函数，使用标签 `0x02` 的缓存操作后，函数仍返回 202，预期为 205。CLI 返回 1，完整验证失败。

## 决策

在标准 JIT fixture 中加入带标签 `IC_IVAU` 的 memfd 更新场景，复用已有 `fallback_call()` 和 `clear_code()`，对同一可执行页先取得旧返回值，再由内核 `pwrite` 更新，最后使用标签 `0x02`、`0xb4`、`0xff` 的缓存操作数逐次要求新值。函数调用本身保持无标签，符合当前 fetch 配置。回归仅在 `NCE_DATA_TBI=1` 启用，报告验证器根据实际 TBI 配置要求完整结果。

修复后的 hook 在 `data_tbi` 开启时清除操作数位 63:56，再查询 Linux PTE 并沿用现有物理页失效流程。顶字节之外的地址位、执行地址规则和内核 tagged syscall ABI 保持原有检查。

## 曾考虑的替代方案

每次缓存操作全量清空 Unicorn 代码。该方式增加无关失效，现有物理页失效接口已经能处理所需更新，先修正地址转换。直接跳过 tagged cache 操作。它保留了当前可能遗漏代码失效的行为，无法满足标准动态代码更新。

### 验证结果

本机为 Apple M5 Ultra、macOS 27.0（26A428），单 CPU、PTE、16 KiB 客体页、dual 128 MiB、timer、pages。Direct 使用 flat、code-watch、跨页与原生独占；Unicorn 使用 host 布局。功能实验与其他任务并行，耗时未用于性能比较。

`work/native-linux-nce/tagged-ic-before/` 保留未修复的实际失败，包含 stdout/stderr 和源码摘要。修复后的 `tagged-ic-sparse`、`tagged-ic-unicorn`、`tagged-ic-off` 均运行 CLI/GCD，returncode=0、validated=true。前两组各入口通过 28 个标准 JIT 场景，最后一组关闭 TBI，各入口仍通过原有 27 个场景。新场景依次使用标签 `0x02`、`0xb4`、`0xff`，每次均通过内核 `pwrite` 改写代码并返回预期新值 205、206、207；调用 PC 保持无标签。

[结构化结果](../../../../experiments/native-linux/results-tagged-ic-20261112.json)记录四组源码、配置、报告摘要、命令和实际输出。标准 JIT 解析器对修复后三组实际报告分别拒绝 706、706、684 份错误输入，包括切换 TBI 预期；TBI 验证另拒绝 134 份错误输入。两个修改的 C 文件格式检查和差异检查成功。

复杂度审查保留已有 `data_tbi` 状态与物理页失效接口，只在现有 SYS hook 中转换操作数。hook、普通数据访存与 Linux syscall 分属不同入口，处理范围各有契约；未增加配置、地址表或缓存失效状态。测试复用现有 memfd、fallback 与报告检查，删除该回归会失去带标签 cache 操作与内核代码更新的联合覆盖。实际 ART JIT 执行继续由原始 ART 实验单独验证。

## 影响

当前 hook 根据可读 PTE 查询物理页；无效缓存操作数的硬件异常行为仍未完整模拟。本次只解决已开启数据 TBI 的有效映射更新。单核限定继续沿用 TBI 提案；iPhone 执行未验证。
