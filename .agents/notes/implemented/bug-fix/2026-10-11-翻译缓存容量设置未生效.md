# 决策记录: 翻译缓存容量设置未生效

状态: implemented

## 问题

Android 服务与桌面接入后，阶段内存占用持续增加。新增引擎统计读到的代码区容量为 1073725364 字节，与请求的 16 MiB 不符。核对固定版本 Unicorn 2.1.4：`UC_CTL_TLB_TYPE` 先执行 `UC_INIT`，以默认 1 GiB 建立代码缓存；之后的 `UC_CTL_TCG_BUFFER_SIZE` 写操作只更新字段，保留已分配的代码区。原型此前先设置 TLB 模式，再设置容量。

这个顺序出现在 `d497c64`、`90c86ee`、`389ffe7` 的 Linux 翻译执行入口。独立指令微基准 `translation/benchmark.c` 先设置容量再设置 TLB 模式，不受此处顺序问题影响。

## 决策

在任何触发引擎初始化的调用前设置容量。引擎完成初始化后，通过私有 ARM64 入口读取已分配代码区容量；扣除保护页与入口代码后，实际可用字节必须不大于请求值，差值小于 64 KiB，否则立即失败。日志分别保存请求字节和实际字节，报告校验器核对配置、结束统计和使用量。

同一入口读取已有的缓存清空次数、翻译块失效次数、当前块数及当前代码字节。读取发生在初始化完成和执行结束后，不增加逐指令、逐访存计数。原型仍由单个 Linux CPU 使用引擎。

### 验证

`probe_lkl_translation.py --mapping pte --preemption timer --linux-fastpath 1 --exec-cache pages --cache-mib 16 --output work/native-linux-nce/lkl-translation-cache-capacity` 已通过 CLI/GCD 的内存边界、代码替换、fork/exec、信号和阶段内存统计检查。实际可用容量为 16760756 字节。

`--workload services --cache-mib 128 --exec-cache full` 的 CLI/GCD 均成功，实际可用容量为 134201268 字节；两轮服务数据盘均完成只读卸载，ext4 元数据检查成功。同容量完整桌面 CLI 也成功，详情见[桌面验证](../testing/2026-10-11-翻译执行的Android桌面验证.md)。分别修改报告中的实际容量、移除引擎统计或损坏内存均值，校验器均拒绝通过。手机执行尚未接入。

## 曾考虑的替代方案

- 只使用 `uc_ctl_get_tcg_buffer_size()` 回读：该接口返回已被后续 setter 改写的字段，无法确认已分配缓存。
- 依据 RSS 或 footprint 推断容量：指标还包含 Linux RAM、页表、线程及图形资源，不能判断代码缓存的实际配置。
- 在运行中重新设置容量：固定版本 setter 没有重新分配行为，当前参数只在启动前设置。

## 影响

历史 Linux 翻译、PTE 对照及 Bionic/ART 报告已增加 `configuration_correction`，保留原始请求值、耗时与源码摘要。此前 16/64 MiB 的差异不能作为容量收益。全量失效、按页失效和 Linux 执行调整的比较使用相同实际容量，局部耗时观察继续保留，解释范围修正为约 1 GiB 缓存下的对应负载。

修正后较小缓存可能增加重新翻译次数，容量选择需要重新测量；当前独立原型默认请求仍为 16 MiB，产品继续使用原生 NCE。相关整机接入与失败见[地址与翻译原型记录](../../proposed/architecture/2026-10-10-独立地址范围与应用进程重启.md)。
