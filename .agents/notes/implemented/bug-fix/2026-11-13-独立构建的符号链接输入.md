# 决策记录: 独立构建的符号链接输入

状态: implemented

## 问题

SDK first-stage 独立树用符号链接读取主树已有的 Linux、Unicorn 和 Android 输入。首次 16 KiB core 构建在保存输入摘要前失败，原 `/init` 与四个候选盘均未运行。命令、日志和来源摘要保存在 `work/sdk-first-stage-validation-v1/core-16k-v1-stage.json` 与同名 `.log`；这一轮产物未通过功能验收。

`build_lkl_translation_kernel.py` 对 `work/native-linux-nce/lkl-source` 执行 `cp -cR`。该入口在本树中是符号链接，macOS 复制后生成的 `lkl-translation-kernel/source` 仍为链接，两者实际指向主树 `lkl-source`，inode 同为 `62931756`。随后补丁修改了共享源码。此前清单只登记源码 revision marker，没有逐文件运行前摘要；受影响路径和可恢复来源需要分别核对。

构建还使用共享 Unicorn `build.json` 中的主树绝对 `path`。保存 `libunicorn.a` 的输入身份调用 `relative_to(ROOT)`，该路径超出 SDK 独立树，Python 抛出 ValueError。内核和宿主已生成，客体执行尚未开始。

## 决策

复制 Linux 源码前先解析顶层符号链接，将实际目录交给 `cp -cR`。创建目录、删除旧源码和复制前，检查输出、source、build 三个目录各自为本树 WORK 内的独立目录；末级链接与改变实际写入位置的祖先链接被拒绝。复制后再检查生成目录与原输入分离。已有链接立即报错，原产物保持。

core 与 iOS runtime 从各自依赖记录所在目录的 `prefix` 访问 Unicorn，并核对它与记录中的 `path` 指向同一实际目录。摘要中的路径继续位于当前树，实际文件与已核对的共享输入一致，依赖记录原字节保持。

独立审阅发现，iOS runtime 在依赖记录缺失或摘要失配后执行 `build_translation_engine.build()`；core 的 `--reuse-engine-build` 分支失配直接失败，未指定复用则直接构建。该函数会重写补丁源码、CMake 输出、安装目录和记录；路径核对放在调用后无法阻止写入。现已在 `build_translation_engine.build()` 入口增加检查，source、output 与需要下载的 archive 必须位于本树 WORK，检查先于 mkdir、下载和补丁。有效共享记录仍可只读复用，外部共享目标的重建在写入前失败。

builder 的源码摘要因此改变，旧共享依赖记录与当前源码不再匹配。本轮移除 SDK 树中的 `unicorn-dual-source`、`unicorn-tb-stop-dual` 和 `unicorn-tb-stop-dual-ios` 三个链接，原主树来源、库和记录继续保留。实际 Unicorn 源码用 APFS 克隆到本树，两个目标的依赖在独立输出目录重新构建。清单 `work/cleanup-2026-11-13/sdk-first-stage-owned-unicorn-input-v1.json` 的 SHA-256 为 `2a5ea2c1c79216722e2c6ced51b96041bf6ecd412f6d443c8463e3b5d8b4efc9`；1032 个普通文件的内容匹配、inode 独立，21,472,307 bytes 原来源在准备前后保持。

核对共享 Linux 输入的受影响文件，按固定 revision 与主线补丁恢复可再生成源码。保存恢复前后的路径、摘要、来源和操作清单，删除本轮生成的源码链接与无效构建目录后重新构建。第一次失败的日志、构建记录和源码摘要继续保留。

### 本机恢复与第二轮结果

共享 Linux 恢复使用固定 archive，SHA-256 为 `894c691d3443055ebc11d1f60fbc176be87d474402e19c11607a3b490c2eaf8b`，大小 250,308,000 bytes。运行前快照记录 86,826 个普通文件、1,490,797,027 bytes。恢复清单 `work/sdk-first-stage-validation-v1/linux-source-rebuild-v1/restore.json` 的 SHA-256 为 `5f06a12b0910810eb3284eb2b07cd961c9db18e809771e31c2abd2471d4dc72f`；17 项已有摘要和 file2alias 匹配，与事故快照有 12 条差异，最终 base 与该轮 prepared 一致，21 项主线准备输入保持。完整历史字节对应仍未验证。

独立 archive 审阅随后发现 13 对大小写文件在当前 APFS 合并，并确认 TCPMSS 源码与对象有实际消费者。上述恢复清单继续保留其实际结果；完整上游路径保真失败与下一轮处理见[Linux 大小写记录](2026-11-13-Linux源码与构建的大小写文件.md)。

两份独立 Unicorn 依赖构建成功，汇总 `work/sdk-first-stage-validation-v1/owned-unicorn-builds-v1.json` 的 SHA-256 为 `c30697643b2b3899521accf2cfde2f9ba3f4b5e47da65f8d20c7e6fd4fff19ac`。16 KiB v2 core 随后成功，`core-16k-v2-stage.json` 保存原命令、来源、返回码 0 与源码保持结果。该轮尚未运行原 `/init`，后续大小写文件修正会产生新的构建身份。

独立小目录复现发现，旧 builder 对 out 指向共享目录而 source 为普通目录的输入执行了 rmtree 与真实 cp，直到 apply sentinel 才停止；原共享小文件被替换。首次失败保存在 `work/translation-shared-inputs-review-v1/ancestor-output-initial-result.json`，真实源码与候选盘未参与。新增 out/source/build 检查覆盖该失败及外部 WORK 链接，`final-result.json` 的 48 项回归成功，SHA-256 为 `a6d128b063a6f3dff22afc3359895c7b20816d2946b2cc7433a80fcf6e3a5ba2`；原 38 项与两页首次失败保持。该结果归属 builder `2cda707`，Linux 文件系统检查的新增来源继续单独验收。

`work/raw-first-stage-c-review-v1/build-out-ancestor-review-v5.json` 的 SHA-256 为 `80d6e9688d1e64ef08fe78a82c9fd9221c8fee5feab91940332add7dfa9b01cf`；10 项静态检查核对所有目录检查先于 mkdir/rmtree/cp/apply，core 的 PTE、CLI、SMP、highres 和 4 KiB 名称分支均消费同一入口。该审阅没有执行真实构建，后续 Linux 文件系统检查按新 SHA 复核。

### 验收标准

1. 符号链接输入经实际 APFS 克隆后得到独立目录和文件 inode，修改候选源码不会改变来源；已有源码链接在补丁执行前被拒绝。
2. 当前树的 Unicorn `prefix` 与记录路径指向同一目录才能使用，错误目录与缺失目录被拒绝；共享依赖记录摘要保持。
3. builder 的共享 source/output 与缺失外部 archive 在任何写入前被拒绝，目标目录、文件和记录保持。独立 source/output 可进入正常构建。
4. 受影响的共享 Linux 输入按可核对来源恢复，明确区分运行前状态已知的文件与缺少运行前摘要的文件。原始系统镜像和候选盘保持本轮运行前状态。
5. 修正后重新完成两页 core，再继续原 first-stage、同盘恢复与 iOS 编译。所有失败保存，源码与记录在同一检查点提交。
6. 增量变更按 reclaim-code-entropy 和 humanizer-zh 复核，检查目录、库路径和来源身份各自的实际使用方。

### 本轮阶段结果

恢复后的完整 pristine/prepared 来源已按 86,901 项清单核对，21 项 MAIN 原准备输入保持原路径。两页 v9 使用独立的大小写敏感内核目录，core、raw/recovery 与 iOS 编译成功；独立构建来源核对和最终保留清单完成，历史共享输入的原始缺失范围仍按原记录说明。

## 曾考虑的替代方案

- 使用 `cp -RL`：会同时展开源码内部的符号链接，本次只需要解析顶层输入。
- 为各独立树改写共享依赖记录中的绝对路径：会增加派生记录，现有目录引用和实际路径核对足以满足当前使用方。
- 继续复用首次内核和宿主：此次写入违反输入隔离要求，且没有客体功能结果，重新生成并验收。

## 影响

原共享 Linux 目录缺少完整的运行前文件摘要，无法仅靠 revision marker 确认每个文件的原字节。恢复使用固定上游和主线补丁来源，现有已验收内核仍归属其历史构建，恢复后的源码已重新生成两页 v9 构建身份。符号链接保留目标写权限，来源共享前必须核对后续调用方的复制与写入行为。
