# 决策记录: VS Code 索引范围与缓存清理

状态: implemented

## 问题

2026-10-12 在 Mac17,15、macOS 27.0（26A428）、C/C++ 扩展 1.34.4 上检查本项目的 `.browse.VC.db`，文件大小为 84,204,920,832 字节，`files` 表有 1,852,961 条记录。按文件 ID 倒序抽查的 1,000 条记录全部位于 `work/` 下的 Linux 源码及构建目录。cpptools 高占用时的采样包含 `collect_store_garbage_work_item_t` 和 SQLite 查询；原始采样为 `work/cpptools-sample-20261012.txt`。这些结果说明构建目录进入了符号索引，数据库清理也在消耗 CPU。

## 决策

使用项目级 `C_Cpp.files.exclude` 排除 `work/`、`build/`、`.build/` 和 `third_party/gpu/`。这些目录存放下载、构建源码副本及生成物；项目源码继续参与索引。配置只作用于 C/C++ 扩展，文件浏览与文件内容保持原状。清理前核对 VS Code 工作区标识 `075d5b70049131aa7de77e207f95acea` 指向本项目，`lsof` 未发现数据库及辅助文件的打开使用方，随后删除对应的 `.browse.VC.db`、`.browse.VC.db-wal` 和 `.browse.VC.db-shm`，由实际 VS Code 会话重新生成。

配置通过 JSON 解析和当前安装扩展的设置定义检查。此次只调整编辑器索引，使用真实重建验证，未运行 Android 构建和设备测试。

### 复杂度审查与偏离

使用扩展原有的一个配置项表达排除范围，未增加维护脚本或新的目录白名单。若移除排除配置，数据库重建仍可重新扫描下载与构建目录，因此配置与本次清理均有必要。实际实施与提案一致。

## 曾考虑的替代方案

- 只删除数据库：下一次打开项目仍会扫描相同目录。
- 只降低解析优先级或 IntelliSense 缓存上限：无法限定符号数据库收录的文件范围。
- 使用 `files.exclude`：会同时改变文件浏览器可见内容，超出本次索引修复的需要。
- 另设 `browse.path` 白名单：需要在新增源码目录时同步维护；现有构建目录排除规则足以表达此次边界，先用实际重建验证。

## 影响

排除目录内的文件将退出项目范围的符号索引。需要研究某份上游源码时，可单独打开对应源码目录并为它设置适合该目录的索引范围。
