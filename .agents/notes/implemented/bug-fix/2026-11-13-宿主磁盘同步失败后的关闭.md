# 决策记录: 宿主磁盘同步失败后的关闭

状态: implemented

## 问题

`nce_disk_close()` 对 slot 0 的 fsync 和所有槽的 close 使用 REQUIRE。同步失败会 abort，后续只读槽、执行上下文和内核映射的清理没有完成。原 init 的可写数据阶段需要保留同步失败，同时完成其余关闭步骤。

## 决策

接口改为 `int nce_disk_close(void)`，返回首个负 errno。每个已打开槽分别记录 sync_result 和 close_result，slot 0 执行一次 fsync，随后所有槽各执行一次 close。同步失败继续处理全部槽。宿主槽在关闭尝试后停止接受 I/O。原生 lkl-main 完成内核和映射释放后传播失败；translation runner 由主会话同步修改。

Darwin SDK 的 close.2 列出 EINTR/EIO，没有约定错误返回后的描述符状态。关闭失败按实际错误报告，最终释放状态保留未确认，不重试可能已经重新分配的编号。fsync.2 说明 fsync 与 F_FULLFSYNC 的持久性范围不同，本阶段覆盖宿主关闭失败和锁释放，断电持久性继续单独验收。

### 验证与交付

在主线 `0dffcbb` 派生的 `codex/init-data-host` 实施。`test_host_disk_close.py` 是独立检查入口，也由 `probe_lkl.py` 的原 host-context 检查位置调用。输出目录沿用主 probe 的 started_ns 区分轮次，重复运行保留各次结果。

```sh
python3 -u scripts/test_host_disk_close.py \
  --host-ops work/native-linux-nce/lkl-translation-kernel/lkl-host-ops.h \
  --output work/native-linux-nce/host-disk-close-v3
```

`host-disk-close-old-v1/result.json` 使用原 `0dffcbb` 的 lkl-host.c、编译注入 fsync=EIO，实际进程返回 -6，stderr 在 `fsync(disks[index].fd) == 0` 的 REQUIRE 处停止。该失败保持原源码摘要和 fixture 内容。

`host-disk-close-v2/result.json` 的五项 host-context 检查成功：原磁盘边界/只读/锁检查、线程信号 mask 保持，以及 sync_error、sync_and_close_error、close_error 三个关闭失败用例。每个失败用例执行一次同步与四槽关闭尝试，所有测试文件的锁可重新取得，四槽停止 I/O，第二次 nce_disk_close 返回 0 且未再次执行同步/关闭。测试还逐项核对 16 条 host_disk_close 的槽、sync_attempted、同步返回和关闭返回。

故障注入只存在于测试编译：host 对象将 fsync/close 绑定到 fixture wrapper，fixture 的 close wrapper 先执行真实 close，再返回指定错误。sync_error 返回 -EIO；同步和关闭同时失败仍保留首个 -EIO；关闭单独失败返回 -EINTR。该注入检查错误传播与清理继续执行，Darwin 实际 EINTR 后的描述符状态仍未验证。

实际 lkl-host.c 以 NCE_PROCESS、arm64-apple-ios26.0 编译成功。lkl-main.c 的 NCE_PROCESS Mac 与 iOS 对象均编译成功，报告为 `host-disk-close-caller-v2/result.json`。首次调用方编译使用主 work 的 NOMMU lkl-image.h，缺少 NCE_SET_LAYOUT 等进程导出定义，两端均失败；后续改用本侧树已有进程内核的实际生成头文件，原失败报告继续保留。此阶段没有执行完整原生 Android 或原 init 数据组合。

C 格式、Python 语法与 git diff 检查成功。[结构化归档](../../../../experiments/native-linux/results-host-disk-close-20261113.json)保存旧失败、首轮与固定回归、调用方首次失败和成功编译、命令、15 项当前输入摘要及原始产物身份。归档后删除十个可再生成二进制/对象，清单为 `work/cleanup-2026-11-13/host-disk-close-v1.json`；源码、原报告和日志保留。

### 复杂度审阅与偏离

按 reclaim-code-entropy 核对实际使用方。nce_disk_close 的返回值由原生 lkl-main 和主线 translation runner 消费；每槽实际返回由数据验收报告读取。宿主槽的 fd/bytes 继续承担资源所有权和 I/O 边界，局部 first_error 只保存本次关闭的首个失败，没有增加资源管理器或另一组关闭状态。关闭尝试后清除槽，后续 disk_io 无法使用可能已经重新分配的编号。

移除影响按失败回归核对。继续使用 void 会丢失同步失败的返回值；保留旧 REQUIRE 会在 slot 0 失败后中断其他槽处理；只检查测试退出码会漏掉实际关闭记录中的错误字段。测试 wrapper 和注入宏均限 fixture 编译，生产构建继续调用系统 fsync/close。新脚本承接原 host-context 检查入口，未增加生产环境变量或独立线程。

执行中增加关闭错误的注入和调用方编译；首次调用方头文件选择错误已保存并纠正。主线 translation runner 的声明、返回值传播和 SDK shutdown 报告由主会话同步实施，本侧树保持其授权边界。技术文字按仓库约定与 humanizer-zh 审阅。

## 曾考虑的替代方案

- 同步失败立即 abort：后续槽和内核映射无法按标准流程释放。
- 忽略同步错误：无法验证本轮持久化结果。
- 对 close 错误直接重试：错误后的编号可能已被其他线程重新分配，当前公开说明不足以确认可安全重试。

## 影响

close 返回错误后描述符的实际释放状态尚未验证。调用方须以每槽 close_result 为准，错误入口继续作为失败结果。设备运行、资源和持续热状态按离线目标保留待验证。
