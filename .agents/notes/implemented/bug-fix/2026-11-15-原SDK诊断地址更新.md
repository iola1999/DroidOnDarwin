# 决策记录: 原 SDK 诊断地址更新

状态: implemented

## 问题

原 SDK v14 使用新 ARM64 只读 regset 内核，lifecycle CLI/GCD 成功，CLI original 在 PID1 早期启动收到宿主 SIGSEGV，退出 -11；后续三个入口尚未运行，`full_boot_validation` 为 null。原输入、源测试盘和失败日志保持。独立测试盘上的 LLDB 复现取得访问地址 `0x18`、宿主 `x8=0`，实际指令为 `ldr x11, [x8, #0x18]`，PC 位于新内核 ELF 的 `0x19845c`。来源见[原失败](../../../../../../../native-linux-nce/sdk-plain-init-regset-16k-v14-180s/failure.json)和[独立诊断](../../../../../../../sdk-plain-validation-v1/sdk-regset-sigsegv-diagnostic-v1/run-01/report.json)。

SDK 的 logd、PID1 ashmem 和 read 身份诊断共用 `STOCK_LOGD_GET_SECCOMP`，从内核基址加该偏移调用 `prctl_get_seccomp()`。v14 沿用旧值 `0x198448`，新内核的同名函数已移到 `0x1987f0`，两个版本的函数大小均为 24 bytes。旧值在新内核中位于 `__seccomp_filter+0x21c`，该跳转跳过函数入口和局部变量初始化。LLDB 中的 `x21=221`、`x9=0x125`、`x20=0x135` 与该指令序列一致。新内核、生成头和翻译地址头之间的既有检查未覆盖这项诊断私有地址。

## 决策

在独立 v15 中沿用 v14 的内核、宿主生产实现、SDK 图形内容、Direct 参数、180 秒观察、450 秒 Binder/SIGQUIT 条件和原六入口验收。从实际新内核 ELF 的 `prctl_get_seccomp` 符号生成诊断头，检查该函数完整位于可执行段，函数字节与实际 `lkl-image.bin` 相同，再核对生成头的地址。准备和运行前均执行该检查，原 v14 结果与输入保持。

先验证旧诊断头在新 ELF 上被拒绝，正确头通过检查；随后使用独立测试盘定向复验原 PID1 启动，成功后继续完整 CLI/GCD 六入口、停止回收、同盘恢复和 iOS 编译。图形 Common 的后续对照另用独立候选盘。

### 复杂度审查

实际使用方共用同一份诊断头和现有的 seccomp 查询函数。更新该生成值即可恢复原调用关系，无需新增生产内核接口或宿主状态。移除查询会使诊断缺少原 seccomp 条件检查；改用其他查询接口会改变诊断调用方式。本轮保留原调用契约，仅增加实际 ELF、镜像和生成地址之间的检查。

### 本机准备检查

[私有地址回归](../../../../../../../sdk-plain-validation-v1/sdk-regset-original-init-v15-180s/kernel-private-regression-v1/report.json)的 17 项检查成功。实际符号为 `prctl_get_seccomp@0x1987f0`，大小为 24 bytes，完整函数字节与 raw image 相同；旧头、缺失输入、镜像损坏或截断、不可执行段、函数末字节越界、错误架构和重复定义均被拒绝。复核发现前导零整数与 C 八进制含义不同，以及条件编译、后续 `#undef` 和块注释中的定义被接受；校验现限定整个头文件为单条整数定义与空白，四项拒绝回归成功。生成头仍为原宏的十六进制整数定义。

[最终独立复核](../../../../../../../cleanup-2026-11-15/v15-kernel-private-symbols-independent-review.json)成功，模块、实际 nm 命令与工具、ELF、raw image、原 v14 头和输入身份已核对。诊断副本按[清单](../../../../../../../cleanup-2026-11-15/kernel-private-symbols-regression.json)删除，原输入保持。[v15 build-01](../../../../../../../sdk-plain-validation-v1/sdk-regset-original-init-v15-180s/build-01/report.json)完成 CLI 的 14 个 C 单元、GCD 的 15 个 C 单元和两个链接，八项 macOS/iOS 检查成功。九项 Direct 对象按原对象、源码和头文件摘要复用，原依赖保留，`recompiled:false`。4320 项准备输入保持，[独立构建审阅](../../../../../../../sdk-v15-build-result-review-v1/report.json)核对 4434 个路径、46 份依赖及实际链接输入。v13 清理后的[运行预检](../../../../../../../sdk-plain-validation-v1/sdk-regset-original-init-v15-180s/run-preflight-after-v13-cleanup.json)返回 ready，4322 项输入保持。

[v15 实际运行](../../../../../../../sdk-plain-validation-v1/sdk-regset-original-init-v15-180s/run/report.json)随后完成六入口，每项观察、退出 0 与进程组回收成功；两个 original 均越过 v14 的故障位置，读取身份诊断和完整寄存器恢复成功。同盘 recovery、metadata 原 rc 属性和 SQLite 检查成功，data/metadata 最终均为 clean，4322 项输入保持。完整 boot 仍为 failed，两个 original 均保留 180 秒观察与 450 秒诊断条件。外层 capture 的 ashmem 校验缺少冻结 `pid1_validation.py`，原分析错误保持；[独立重分析](../../../../../../../cleanup-2026-11-15/v15-offline-capture-reanalysis.json)恢复原解析依赖后完成六份结构检查，450 秒诊断契约继续为 incomplete。[转储审阅](../../../../../../../cleanup-2026-11-15/v15-tombstone-independent-review.json)取得实际寄存器与连续回溯，[结束审阅](../../../../../../../cleanup-2026-11-15/v15-completed-result-independent-review.json)核对全部输入、观察、回收及恢复。该结果确认本轮诊断调用的地址修正，implemented 指诊断地址生成和本机复验已交付；完整系统继续按原验收推进。

### 验收标准

1. 原 v14 的完整输入、失败报告、日志和源测试盘摘要保持；独立诊断进程回收完成。
2. 新诊断头由实际内核 ELF 生成；同名符号唯一、大小非零、完整位于可执行段，实际镜像中的函数字节与 ELF 相同。旧偏移在新内核检查中失败。
3. 修正地址后的原 PID1 启动越过原故障位置，宿主正常退出；完成原 CLI/GCD 六入口观察、停止回收和同盘恢复，保留完整 boot 的实际结果。
4. 实际宿主 C 编译依赖包含新诊断头，macOS/iOS 检查通过；内核、SDK 图形组件和 Direct 参数保持。

## 曾考虑的替代方案

- 直接修改 v14 的冻结头并重跑：会改变本次失败的实际输入，采用独立 v15。
- 手工填写新偏移：当前可修复，但后续内核构建仍需人工重新确认，采用实际 ELF 生成和检查。
- 修改 seccomp 或 Direct 实现：当前复现由错误的诊断跳转地址解释，先修正诊断地址并定向复验。

## 影响

该修复覆盖诊断跳转地址。SDK 转储的实际范围见[寄存器读取](2026-11-15-LKL读取ARM64寄存器.md#原-sdk-v15-转储与离线分析)。完整 boot、SurfaceFlinger 退出、system_server ANR、桌面、APK、HyperOS 和持续性能继续按各自实际结果验收；iOS 执行和设备资源待真机验证。
