# 决策记录: 导入镜像启动前运行组件检查

状态: implemented

## 问题

[项目审查](../architecture/2026-11-12-项目路线与性能审查.md#p2镜像运行组件身份仅在导入时检查升级后没有继续核对)复现了导入镜像的版本检查缺口：`DeviceStore` 导入期间比较镜像与应用的 `runtime`，设备记录没有保存该值。应用升级后，设备继续引用旧镜像，`LocalRuntime` 只检查当前包的配置选项。执行实现与准备数据可能来自不同构建。

## 决策

导入 `.droidimage` 与原始 `system.img` 均把导入期间的 `Runtime.json.runtime` 保存到 `device.json.runtime`。每次启动读取该记录，并与当前包的运行组件标识比较；检查在准备数据盘、打开日志和启动核心之前完成。设备列表继续允许读取、重命名和删除旧设备。

导入设备缺少标识、标识类型错误或与当前包不同，启动返回明确错误，保留原目录和数据盘。当前没有可信的旧记录迁移信息，因此不根据现有应用自动补写旧导入设备的标识。内置设备继续使用包内完整运行资源，其数据盘跨版本兼容约定单独处理。

校验由 `NceDeviceStore` 的无状态类方法提供，直接读取磁盘记录。`LocalRuntime` 的普通启动和 benchmark 共用这一入口。

`validateDeviceAtDirectory:resources:runtimeResources:error:` 同时核对目标资源来源：内置设备使用当前应用资源，导入设备使用对应目录的 `Images`。已有独立 CLI 与 benchmark 可以直接指定新数据目录，尚无 `device.json`；这种入口仅在使用当前包资源时通过，不生成设备记录。已有导入记录仍需通过版本检查，改为指定包内资源也会被拒绝。

Mac 的 `ProcessRuntime` 在创建子进程前执行相同检查，使设备列表直接显示具体错误。`LocalRuntime` 继续在 worker 内检查；失败原因同时输出 stderr，直接 CLI 可以读取。首次实现的审查发现了父进程丢失具体错误、独立 CLI 没有设备记录的两项问题，均在本次提交中处理。

### 本机验证

2026-11-12 使用 Apple M5 Ultra、macOS 27.0（26A428）、Xcode 27.1（27A9275）。`DeviceStoreTests.mm` 使用 `xcrun clang++ -std=c++17 -O2 -fobjc-arc -Wall -Wextra -Werror -framework Foundation` 编译，检查成功。覆盖 `.droidimage` 与原始镜像记录版本、导入后运行组件变化、恢复原组件、缺失/空白/错误类型标识、错误资源目录、旧设备加载与重命名，以及数据保持原样。既有导入、ext4 和目录锁检查继续成功。

使用现有 `AppSmokeTests.mm` 核心替身和全部真实宿主 Swift 源码构建 `work/project-audit-2026-11-12/runtime-startup-check/Host Checks.app`。无设备记录的包内资源启动成功；匹配版本的导入设备启动成功。随后改为不同版本和缺失版本，两个实际 worker 均退出 1，stderr 含具体原因，核心未运行，数据盘摘要保持一致，设备日志目录没有新增文件。相应回归加入 `scripts/test_native_linux_macos.py`，完整 Android 核心由独立集成检查验证。

Mac 全部宿主 Swift 类型检查成功。iOS 使用 SDK 27.1、`arm64-apple-ios17.0` 完成宿主 Swift 类型检查与 `DeviceStore.mm` 编译语法检查；首条手工检查命令遗漏三份 JIT Swift 源文件而失败，补齐打包脚本已有的 `JITBuiltIn.swift`、`JITPairingFileStore.swift` 与 `JITMessages.swift` 后成功。以上 iOS 检查不含链接、IPA 生成和设备运行。

### 复杂度审查

实际调用方为 Mac 父进程和两端 `LocalRuntime`。两个边界复用同一磁盘记录检查，父进程负责显示错误，worker 在准备数据前再次核对；删除其中一处会分别失去明确反馈或独立启动检查。持久标识只在 `device.json` 保存一份，没有新增迁移框架、兼容列表或界面状态。按 humanizer-zh 审阅文案，原始镜像兼容与内置数据盘升级边界继续保留。

## 曾考虑的替代方案

- 设备列表加载期间拒绝不兼容设备：会同时影响其他设备的显示和旧设备的数据管理，因此校验放在启动入口。
- 为旧记录写入当前运行组件标识：无法确认旧镜像来源，可能接受不兼容组合。
- 在 `RunTarget` 增加标识与兼容状态：需要继续传递并同步持久记录，启动时直接读取记录即可完成检查。

## 影响

旧导入记录无法自动确认来源，修复后会在启动时提示重新导入匹配镜像，旧数据保持原样。原始 `system.img` 的 Android/HAL 兼容性仍由原导入约束与运行检查决定，本项只绑定导入期间使用的运行组件。
