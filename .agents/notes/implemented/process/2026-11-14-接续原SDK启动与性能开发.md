## 决策

已阅读原聊天的早期接续说明、最后两个轮次与本机保存的原始消息。聊天工具无法返回中间的单个过大轮次，改用本机该聊天的 JSONL 读取早期和用户消息。原会话早期接续 ART 信号返回与原生恢复栈对齐，目标沿用[离线开发目标](2026-11-12-离线开发目标与持续推送.md)。最新阶段已选择无加密 SDK 启动；原 ART 的 boot classpath 与 system server 编译成功，原 NetBpfLoad 要求真实 BPF JIT，完整系统启动尚未验收。

本聊天已通过目标工具创建 active goal，保留完整 Linux/Android、HyperOS 3、通用原始签名 APK、手机独立运行和持续性能目标。用户随后明确「如果必须加密就加，必须 jit 就按 jit 做」。当前先完成无加密候选的实际系统启动；原加载器所需 BPF JIT 继续实施。加密依据实际系统或应用依赖接入，并检查实际 I/O、重启后的内容和资源成本。

接续开始的主工作区干净，主分支为 `3a4d470157f224b4e3e1d720cc6eb1ce39d92f95`。实际候选位于 `work/sdk-vold-linux-v1/mount/plain-repo` 和 `bpf-jit-repo`，均有原会话未提交修改；加密树 `codex/sdk-vold-default-key` 的检查点为 `677c9f8`，另有未提交测试。全部候选继续保留，按各阶段验证结果提交，持续推送授权沿用原目标。

下一阶段先检查 BPF 终止后的执行池释放与真实宿主线程 join，重建来源已变化的 plain core，验证首次和子程序 JIT 发布失败与 pin 生命周期，再运行原 init、NetBpfLoad 和系统服务观察。验收逐项采用实际 `sys.boot_completed`、Zygote、system_server、系统服务、桌面及应用操作；随后测量同条件启动、应用操作、帧时间、输入到实际显示与内存。已有组件检查和 wrapper 耗时各自保留其范围。

本阶段继续离线开发与 CLI/GCD、本机窗口和 iOS 编译。iPhone 安装、设备 JIT 授权、资源预算、实际持续性能与热状态待真机验证。必要接口与状态按 reclaim-code-entropy 核对使用方、停止顺序和替代实现，新增文字按 humanizer-zh 审阅。

### BPF 与原启动检查点

`codex/sdk-plain-bpf-takeover` 已提交并推送 `fedc97e6967fdcf261de0a82c5f544c758ccd310`。该检查点保存原 SDK 所需的真实 BPF JIT、发布失败后的解释器入口与 charge/执行池回收、pin 终止释放、原系统观察器、无加密候选和日志采样。CLI/GCD 九程序与 ringbuf、十入口发布失败回归、四入口 pin 生命周期、真实宿主 join 与 trace 检查成功。pre-commit 格式化后的 51 项提交输入保持，独立审阅未发现必要源码或记录遗漏。

v13 的 lifecycle、original、同盘 recovery CLI/GCD 六入口通过各自观察、停止与回收检查，原 first-stage 完成，两盘最后 clean；CLI 原 NetBpfLoad 报告 success，35 个网络程序加载返回有效 fd，bpfloader 退出 0。完整 boot 验收为 failed，SurfaceFlinger 的 SIGABRT 继续调查。原报告已压缩并核对解压摘要；数据盘只读导出的 50 份文本 tombstone 均为 media.swcodec 的 Goldfish allocator 打开失败，SurfaceFlinger 自身文本缺失。

iOS runtime 与实际 v13 runner/execution 的 arm64 Mach-O 编译成功，分别核对 129 和 159 项输入。结构化结果见[候选阶段报告](../../../../work/sdk-vold-linux-v1/mount/plain-repo/experiments/native-linux/results-sdk-plain-bpf-takeover-20261114.json)，故障来源与后续诊断见[SurfaceFlinger 记录](../../../../work/sdk-vold-linux-v1/mount/plain-repo/.agents/notes/proposed/bug-fix/2026-11-14-原SDK的SurfaceFlinger启动退出.md)。当前代码仍由独立分支继续开发，主工作区保存接续状态；完整系统、APK 操作和性能目标仍待完成。

## 曾考虑的替代方案

只按主分支摘要继续加密移植：原会话随后已调整优先级，实际无加密候选与 BPF 集成需要先接续。直接复用 plain 的原 core：其 144 项输入中六项已经改变，不能支持最终候选的来源核对，先重新构建。重新创建所有候选：会重复准备磁盘并丢失同盘恢复的连续状态，继续采用原工作树与实际磁盘。
