# 决策记录: 提交前自动格式化

状态: implemented

## 问题

手工运行格式命令容易遗漏。用户于 2026-10-10 询问是否可以在 pre-commit 自动格式化，以及这种方式是否合理。已有[格式化工具](2026-10-10-C代码格式化与文档段落约定.md)可以复用；本地同时有其他会话开发，自动格式化需要保留提交者选择的文件范围。

## 决策

增加 [.githooks/pre-commit](../../../../.githooks/pre-commit)，由 Git 的本地 `core.hooksPath` 启用。克隆后执行 `git config --local core.hooksPath .githooks`；该设置仅作用于当前仓库，本机已启用。Hook 使用现有 [scripts/format.sh](../../../../scripts/format.sh)，按文件类型调用 clang-format 或 SwiftFormat。

Hook 选取暂存区中新增、复制、修改或重命名的 C、C++、Objective-C、Swift 文件及对应头文件。格式化成功后重新暂存这些文件，再继续提交。删除项、符号链接以及其他语言文件保持原有处理；第三方与生成文件的排除规则由现有格式工具执行。

如果选中的文件还有未暂存修改，Hook 在写入前中止，提示提交者处理该文件。这样可以保留部分暂存的内容和工作区修改。文件名按 NUL 分隔，Git 选择文件时使用字面路径，名称中的空格或通配字符按文件名处理。工具缺失或格式化失败会阻止本次提交；只有文档等范围外文件变更时可以直接继续。混合提交在任何格式写入前检查两种所需工具；只提交一种语言时只要求该语言的工具。

本 Hook 在本地提交前执行。远端格式约束需要单独配置 CI；当前实现覆盖本地自动格式化。源码排版变化会影响构建输入哈希，后续打包继续按实际源码执行现有检查。

### 验证

2026-10-10 首次接入 C 系列时运行 `python3 scripts/test_precommit.py -v`，8 项测试全部通过。测试在独立临时 Git 仓库中执行真实提交，覆盖自动格式化与暂存更新、部分暂存在任何写入前中止、含空格/通配字符/换行或以连字符开头的文件名、仅文档提交、工具缺失、第三方排除、重命名与删除，以及符号链接。测试结束自动清理临时仓库，主项目历史保持原样。

随后按用户要求增加 Swift。12 项测试通过，新增覆盖 C/Swift 混合提交、Swift 部分暂存、SwiftFormat 缺失、Swift 路径与第三方排除及长行保持。存量格式化范围与检查见 [Swift 记录](2026-10-10-Swift存量与提交格式化.md)。

`bash -n .githooks/pre-commit scripts/format.sh` 和 `git diff --check` 通过。本地 `core.hooksPath` 已核对为 `.githooks`。测试同时确认格式脚本传给 clang-format 的路径使用 `./` 前缀，使以连字符开头的文件名按路径处理。

### 复杂度审查

复用现有 Shell 格式入口，Hook 只选择暂存文件、检查未暂存改动并更新对应暂存项。clang-format 和 SwiftFormat 在同一入口内按文件类型调用，无需增加 Node 依赖、Python 工具环境或额外调度框架。部分暂存的处理保持明确中止，未引入自动 stash、合并或自定义索引重写。

## 曾考虑的替代方案

- 每次提交格式化全仓库：会产生与本次提交无关的改动，采用暂存文件范围。
- 格式化后执行 `git add -A`：可能扩大提交范围，采用明确文件列表。
- 自动暂存和恢复未暂存修改：可以支持更复杂的部分提交，但需要处理恢复冲突；当前使用提交前中止提示。
- 只检查并要求手工格式化：需要额外运行命令，本次选择完整暂存文件自动格式化。
- 引入 pre-commit 或 lint-staged 工具链：现有工具数量和依赖范围较小，先使用 Git 原生 Hook。

## 影响

启用后，本地普通 `git commit` 自动处理本次暂存的 C 系列及 Swift 文件；部分暂存情况需要提交者明确处理。Hook 跟随仓库版本管理，新的克隆仍需执行一次启用命令。
