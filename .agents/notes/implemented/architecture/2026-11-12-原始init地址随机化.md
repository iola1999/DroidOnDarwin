# 决策记录: 原始 init 地址随机化

状态: implemented

## 问题

原 SDK36 init 在四个 bootstrap APEX 激活和 `perform_apex_config --bootstrap` 成功后，打开 `/proc/sys/vm/mmap_rnd_bits` 返回 `-ENOENT`，随后记录 `Unable to set adequate mmap entropy value!` 和 `InitFatalReboot: signal 6`。APEX 固定阶段为 `0005831684dfe065d4454cd6b39d6db8867f8233`，原 CLI/GCD 报告在 `work/offline-stock-bionic/work/native-linux-nce/stock-init-apex-formal-original-v2/summary.json`。原 policy、enforcing、rc 和二进制均保持原输入。

固定 Android 16 源码使用 system/core 的 `android-16.0.0_r2`、`68be0c2c0006a0740d0b1809abe4717308f90d15`；`init/security.cpp:119` 的 AArch64 路径从 33 位尝试到 24 位。SDK36 init 的 SHA-256 为 `c27d13897025ad72d68f5d9a57e3c76cd250f53e82817cf2b5eb04d3e01ec12a`，BuildId 为 `649038d41dde87a6f7a29d2c84a63468`。实际二进制在 `0x16b8c8` 设置最小参数 24、`0x16b8cc` 设置最大参数 33；源码与二进制的精确提交对应尚未确认。

APEX 固定阶段的 LKL 缺少 `HAVE_ARCH_MMAP_RND_BITS`，generic `arch_pick_mmap_layout()` 使用固定 `TASK_UNMAPPED_BASE`。主线 `runtime-main-address-overlap-v2/summary.json` 已验证 512 GiB 数值范围的生成副本与完整释放，来源为旧 `fb224a4` 阶段；`d17162f` 的正式 sparse 布局为 64 GiB。16 KiB 页的 24 位偏移覆盖 256 GiB，需要扩大正式数值范围。Linux 标准 `MAX_GAP=STACK_TOP/6*5` 在 512 GiB 与极大有限栈组合下，再减去完整 256 GiB 随机范围可能下溢。

## 决策

在 `work/stock-init-aslr`、`codex/stock-init-aslr` 接续已合入 APEX 的主线 `d17162f`，仅 translation 生成层启用 Linux 标准 topdown mmap 与 `HAVE_ARCH_MMAP_RND_BITS`。正式 sparse guest 上界设为 512 GiB，保留 64 KiB 下界和 4 GiB Direct flat 覆盖；宿主预留大小继续由 RAM 与 VMALLOC 决定。原生内核配置保持原值。实施前的提案提交为 `cbda52e`。

`nce_set_layout()` 在 `lkl_init`、`lkl_start_kernel` 之前执行。首次发布布局前检查既有 `nce_task_size` 为空；按当前任务窗口可容纳的完整范围计算并发布 `mmap_rnd_bits_max`，保留 `__ro_after_init`，后续调用拒绝重复发布。标准 `mmap_rnd_bits` sysctl 使用原 minmax 处理器，运行期改变只影响后续 exec 的布局抽样。min 使用 16/18 位，512 GiB 的 max 使用 24/26 位，分别对应 16 KiB/4 KiB 页；小 host/low translated 窗口在启动之前收紧 max，不接受无法容纳的位数。

初始化先拒绝 `nce_task_size <= 16 * PAGE_SIZE`，再推导 `STACK_TOP`，防止非法小窗口使无符号减法回绕。令 `S=STACK_TOP`、`L=TASK_UNMAPPED_BASE`，先检查 `S>=L`、`S-L>=MIN_GAP`、原 `MAX_GAP>=MIN_GAP`，再计算 `Q=(S-L-MIN_GAP)>>PAGE_SHIFT`。完整范围须满足 `2^bits-1<=Q`；最大位数取配置上限与 `floor(log2(Q+1))` 的较小值，低于 min 的窗口直接失败。初始 `mmap_rnd_bits` 随后限制到已发布的 min..max。4 GiB 的 translated 窗口实际 max 为 17/19 位。

实际采样沿用 `get_random_long() & ((1UL << mmap_rnd_bits)-1)`，再左移 `PAGE_SHIFT`。不对采样值截断、缩放或取模。令完整最大偏移为 `Rmax=((1UL<<mmap_rnd_bits_max)-1)<<PAGE_SHIFT`，地址随机化关闭后为零；stack gap 上限取标准 `MAX_GAP` 和 `STACK_TOP-TASK_UNMAPPED_BASE-Rmax` 的较小值。初始化须先确认最小空隙和完整范围可容纳。这个约束也适用于高 host 基址与 `ADDR_NO_RANDOMIZE`，保证计算结果位于当前任务窗口。

极大有限栈的预留空隙上限会缩小到完整随机范围可容纳的值。`RLIMIT_STACK` 本身、栈增长、相邻 VMA 碰撞、guard gap 和失败行为保持 Linux 检查。保留 `ADDR_NO_RANDOMIZE`、`ADDR_COMPAT_LAYOUT`、`RLIM_INFINITY`、`sysctl_legacy_va_layout` 与 topdown 耗尽后的 bottom-up 回退。generic topdown 搜索下限改为至少 `nce_user_base`，固定映射、hint、内部栈扩展与页表释放沿用既有独立边界。

ELF 与 interpreter 继续由 NCE 登记固定基址，brk 保留 `NCE_ELF_BRK`；本阶段检查 mmap 基址与已有 stack 随机化，完整 ELF/brk ASLR 仍待实施。原 `seed_entropy` 在 guest setup 使用宿主 `arc4random_buf`，向 Linux `RNDADDENTROPY` 写入 256 bits；core 在首个 guest exec 前复用该初始化，并以 `getrandom(GRND_NONBLOCK)` 检查 CRNG 就绪，保留 Linux 随机源。

## 曾考虑的替代方案

- 仅增加 sysctl 文件：当前布局仍固定，不能提供要求的实际随机范围。
- 将原 init 的最小位数降低：会改变原启动检查，保留实际 33..24 要求。
- 使用 standard arm64 的最大位数公式：512 GiB、16 KiB 页按 `VA_BITS-PAGE_SHIFT-3` 只能提供 22 位，无法满足原 init；本阶段按 LKL 实际窗口限制最大 stack gap。
- 将 16 KiB sparse 扩到至少 2 TiB 后完全使用原 MAX_GAP：扩大数值范围、宿主映射与两种页大小的边界，本阶段先使用已验证的 512 GiB 范围。
- 对过大随机样本截断：会使接受的位数和实际范围不同，保留每个已接受位数的完整采样范围。

## 验收标准

1. 两种页大小的正式内核、头文件、布局与报告保持同一构建输入。最大位数在首次用户映射与 sysctl 访问前发布，之后不再变化。
2. 标准 sysctl 对下界、上界和越界输入执行真实检查；接受值写入后重新 exec，观察 mmap 地址，验证范围和地址变化。fork 与同一 mm 内的普通 mmap 不重新生成 mm 基址。
3. 实跑 `ADDR_NO_RANDOMIZE`、`ADDR_COMPAT_LAYOUT`、`RLIM_INFINITY`、极大有限栈、topdown 耗尽后的 bottom-up 回退，以及 64 KiB 下界。以源码完整随机区间和端点算术检查配合多次实际 exec，不使用样本数量估计精确熵位数。
4. CLI/GCD core 保留信号、fork/COW、exec、标准 JIT、内存容量、栈限额和完整释放检查；地址重叠与准备失败驱动继续验证原行为。移除已被正式 512 GiB 默认值替代的范围改写。
5. 原 init/APEX 的 CLI/GCD 保留原策略、enforcing、节点标签、原 rc 与重启行为；mmap entropy 检查通过后记录实际下一处失败。两种页大小 iOS 编译及实际原 init 副本编译成功。

### 最初失败与修正

`aslr-core-16k-v1` 的首个失败发生在 fallback fixture：读取 `/proc/self/maps` 后关闭 FILE，musl 释放了快照中记录的 FILE 缓冲区 VMA，后续填充跳过该已空闲区，最低地址检查失败。修正只把 `fclose()` 移到分配检查之后；musl 1.2.5 的 `__fdopen.c`、`fclose.c` 和 `mallocng/free.c` 的实际分配与释放路径已核对。随后 16 KiB/4 KiB sparse core 成功。

`aslr-core-16k-host-v1` 的 8 组 ASLR 检查成功，fallback 的 `lower==base` 失败。实际主 ELF 从 `guest_base=481036337152` 开始，占用 196608 bytes；host 预留的对齐使首个 guest 页已有 VMA。fixture 现从已排序的 maps 跳过占用区，保留最低空闲页并填满其上到 topdown 起点的空洞，要求分配返回该最低空闲页。既有 VMA 保持原值，`base-PAGE` 的 `EACCES` 检查继续执行；low/sparse 仍要求返回 65536。

最终复验的 v2 调度曾让同页大小的多个 core 同时调用 builder。builder 每次都重写 `.config` 并执行构建，产生配置和对象构建竞态。该组构建失败日志保留，阶段结果使用逐页大小顺序执行的 v3。16 KiB 和 4 KiB 使用各自的 builder，主线构建目录未被修改。

### 复杂度审阅与偏离

按 reclaim-code-entropy 核对实际使用方、状态与移除后的行为。`nce_mmap_layout_init()` 只由现有 `nce_set_layout()` 调用，使用已有 `nce_task_size` 拒绝重复发布；运行期值继续由 Linux 的 minmax sysctl 管理，未增加发布标志或另一组随机状态。移除容量检查或 gap 限制会恢复完整随机区间与极大有限栈的下溢问题，端点算术和实际大栈/no-randomize 回归检查该行为。

新增 `aslr-guest.c` 由现有 PTE core 编译和 `/probe-guest` exec 入口使用，保留 sysctl、fork、personality、栈、下界与 fallback 的实际检查。探针的 maps/FILE 生命周期和最低空闲页分别对应已发生的两个失败；删除这些检查会失去实际地址分配回归。低地址 PTE/COW/uaccess 对照使用明确的低页地址，普通客体 mmap 继续使用 Linux 布局。

正式 512 GiB 默认值替代地址重叠与准备失败驱动的范围改写，删除了重新生成 guest 与额外编译的分支；这些驱动仍检查实际数值重叠、执行准备失败与完整释放。PC 取自严格验证的 advertised guest 范围，4 KiB 参数沿现有报告传递。两种页大小的真实回归保留了这些边界。

本轮增加了启动前小窗口拒绝和 host fixture 的已有 VMA 处理，来源为算术审阅和实际失败。构建调度改为每页大小顺序执行。原 init 检查、policy、rc、库、安全级别与完整启动验收条件保持原值。文档、注释与提交描述按技术事实及 humanizer-zh 审阅。

## 影响

极大有限栈的预留空隙改变可能使栈较早遇到已映射的 VMA，实际增长仍受原限额与碰撞条件限制。普通匿名映射将使用随机 topdown 地址，原探针中依赖固定低地址的检查须按其实际目的显式选择地址；系统程序继续使用 Linux 的普通分配规则。512 GiB 为客体数值范围，设备上的宿主地址空间、资源与持续性能仍待真机验证。所有构建、镜像和日志仅写独立树，当前阶段只做离线检查。

普通 sparse topdown 匿名页位于高地址范围，进入既有 PTE 访存路径；4 GiB Direct flat 覆盖保持原值。本阶段覆盖 JIT、COW/uaccess、信号和原 init/APEX 功能，持续性能未测量。SMP 在本阶段未重新运行。完整 Android 启动继续处理原 KeyMint 失败；本分支只做本地提交，主会话合入后按其当前构建重新验证。
