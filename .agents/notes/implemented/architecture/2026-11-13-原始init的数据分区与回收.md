# 决策记录: 原始 init 的数据分区与回收

状态: implemented

## 问题

SDK36 原 DM 分区观察已越过 property_contexts 读取，执行原 KeyMint 并通过 VINTF 实例检查。侧树 `work/stock-init-keymint/work/native-linux-nce/keymint-sdk36-dm16-original-v1/summary.json` 的 CLI/GCD 随后记录 `/data/misc/keystore/persistent.sqlite` 的创建返回 `-30`，SQLite 错误码 14，原 keystore2 panic/signal 6。该报告 SHA-256 为 `d1e1f44e65d911e5c43318be40e026a29b2e9aee8790f638bda2eb1859e90be6`，固定阶段与主线接受结果继续由 [SDK36 原始分区与 KeyMint](../../proposed/architecture/2026-11-12-SDK36原始分区与KeyMint启动.md)记录。

现有原 init setup 只创建 `/data` 与 `/metadata` 目录。正式 translation runner 的 slot 0 打开和 ext4 挂载在 services/desktop 分支，原 init 的 bionic 观察分支未使用它。原 `/system/etc/init/hw/init.rc` 的 post-fs 执行 `mount rootfs rootfs / remount bind ro nodev`；两入口实际 mount syscall 的 flags 为 4133，返回 0。目录继续属于只读根文件系统，后续 chown、chmod、mkdir 与 SQLite 创建返回 EROFS。

固定 SDK 的发布目录包含 system.img、vendor.img、ramdisk.img 和 encryptionkey.img，没有独立 userdata 初始镜像。原 `/vendor/etc/fstab.ranchu` 规定 `/dev/block/vdc` 挂载 `/data`，使用 ext4、quota、fileencryption、fsverity 和 metadata keydirectory。当前生成内核关闭 FS_ENCRYPTION、FS_VERITY、QUOTA 与 DM_CRYPT；完整 first-stage 和启动硬件/fstab 输入尚未验证。可写数据盘、原加密/配额要求与完整 first-stage 需要分别记录实际范围。

## 决策

沿用离线开发授权，在现有 SDK36 mounted-partition 观察入口通过可选 `--data-image` 接收显式数据盘路径。复用 slot 0 的可写 ext4、排他锁、关闭前 fsync 和标准 host disk close；原五个 LP 分区继续由只读 slot 1 和 DM linear 使用。两种页大小各使用一份独立的 512 MiB 数据盘，容量沿用 `probe_lkl.py` 的现有 data seed。实验在新的 `work/` 目录创建镜像，记录大小、格式、初始摘要及每次运行后的摘要，现有应用数据盘与 Android 参照数据继续保留。

Linux 启动前打开数据盘，在原 init setup 中将 slot 0 对应的 `/dev/block/vdc` 挂载到 `/data`，使用原 fstab 的 noatime、nosuid、nodev 挂载标志；原加密、配额和 metadata 要求继续单独验收。随后由原 rc 完成所有者、mode、标签与 Keystore 目录准备。使用 guest 实际创建、读取、文件及目录 fsync 和跨入口 generation 检查持久写入；每次 Linux 停止后保存超级块状态与整盘摘要，完成同盘恢复后导出 Keystore SQLite。

`stock_init_run()` 完成 0..2 标准流准备后，在 launch 前打开 `/data` 的 O_RDONLY|O_DIRECTORY|O_CLOEXEC fd，要求编号至少为 3，核对 ext4 类型。该 fd 属于父任务，子任务独立复制文件表，exec 关闭其 CLOEXEC 副本；父任务保留实际文件系统引用到 namespace wait 完成。Linux worker 仍运行期间执行 syncfs(267)，随后关闭目录 fd，再尝试卸载 `/data`。lifecycle 严格卸载；original 保留原策略的卸载拒绝，分别记录 syncfs、fd 关闭、内核 halt、host fsync 和映射释放。同步错误使该入口验收失败，同时继续标准关闭和停止。

现有 DM 分区 fd 可占用 1/2，后续标准流 dup3 会提前关闭这些 fd 并使用相同编号。数据阶段用 F_DUPFD_CLOEXEC 将保存的分区 fd 放到编号至少为 3 的位置，保留它们到明确 cleanup，避免保存的编号对应到标准流。继续通过容量、边界读取和最终设备移除验证原持有关系。

每次运行后读取 ext4 state、needs_recovery 与 orphan_present。syncfs 会等待 ext4 日志提交，正常 put_super 才清除 needs_recovery；original 保留未回放 journal 的实际状态。完成两入口 original 后，再从同盘运行 lifecycle，通过标准 Linux 挂载回放并读取 generation，随后严格卸载。`export_clean()` 在回放后的干净文件系统上导出 SQLite，再通过独立 APFS 副本查询；核对 header、quick_check，记录 schema 和实际存在的 -wal/-journal/-shm 文件摘要。

DM 固定阶段已通过主线接受检查，本轮数据分区变更在该基准上实施。两种页大小的 CLI/GCD 已覆盖生命周期、原 init、写入和重启恢复，实际生成的 runner/execution 与 iOS runtime 编译成功。原 policy、rc、APEX 和服务行为继续使用固定字节，报告原 KeyMint、Keystore 的实际进入程度及首个失败；完整 boot 成功继续按系统和桌面结果验收。

## 曾考虑的替代方案

- 把 `/data` 改为 tmpfs：能够检查当前写入，但无法验证停机后的数据恢复。
- 修改原 rc 的根只读挂载：会改变原启动行为，独立数据文件系统可以继续按原 rc 工作。
- 使用已有 Android 参照 AVD 或应用数据盘：这些文件承担已有实验和用户数据，采用新实验目录的数据盘。
- 同时扩展加密、quota、metadata 设备与 first-stage：这些要求涉及额外内核配置、启动输入和原 vold 路径。先检查当前明确的可写数据盘缺失，后续按原 fstab 验证这些实际依赖。

## 影响

### 实现与故障记录

主线 DM 与日志阶段已固定为 `0dffcbb`，两页 original 的 EROFS 同样复现。数据盘复用实际 `NCE_TRANSLATION_DATA` 环境变量与 slot 0；原 fstab 的 `errors=panic` 随 mounted-partition 挂载保留。`reservedsize=128M` 由原 fs_mgr 限制到文件系统的 2%，当前实验镜像创建使用 2% 预留块，并记录实际 reserved UID/GID；原 fs_mgr 的 AID_RESERVED_DISK 及 late mount 行为继续按原执行结果验收。

launch 前父任务持有普通目录 fd，父任务检查 CLOEXEC 与块设备身份。`user_run()` 先执行 `/probe-guest` 的 exec，该 exec 关闭子任务中的 CLOEXEC 副本；guest 检查该编号返回 EBADF，再打开自己的目录 fd，从实际 st_dev 读取设备号，校验父任务提供的值并记录实际值，随后创建和同步 generation 文件。原 init 之后再从同盘运行 CLI/GCD lifecycle，检查 journal 恢复、generation 和干净卸载后导出 SQLite。SQLite 验证标记只覆盖原文件 header 与 quick_check，schema 按实际记录，原 Keystore 初始化进度分别报告。运行前后读取数据盘失败须保存该入口及错误，跨运行的输入摘要须等于上次输出摘要。原 fstab 的加密、quota、fsverity、metadata keydirectory 和原属性/命令结果仍需记录，mounted-partition 阶段继续保留完整 first-stage 的待验收范围。

宿主 `nce_disk_close()` 的独立修复已进入主线 `435863c`，返回实际错误并继续关闭各槽；运行器在内核和映射释放后传播失败。本轮主线独立回归的五项关闭检查和 iOS host 编译成功，结果为 `work/native-linux-nce/host-disk-close-main-v1/result.json`。根目录准备使用 APFS 克隆，克隆清单按 work 约定保存。数据头负责挂载、持有和同步，guest fixture 负责实际文件写入，Python 检查原盘状态与 SQLite；复用现有磁盘槽和 Linux 文件系统接口。

两页首次数据 lifecycle 均挂载成功，随后在父任务打开目录处 abort，客体尚未执行。原使用的 `0x90000` 包含 arm64 Linux 的 O_DIRECT；本机构建的 musl `bits/fcntl.h` 规定 O_DIRECTORY=`040000`、O_CLOEXEC=`02000000`，目录打开改用 `0x84000`，并在断言前记录 fd 与实际 flags。失败后两份原盘均有 needs_recovery/orphan_present，后续继续使用原盘验证标准挂载恢复，原失败报告与摘要保留。此前从清单文件名推算运行库目录导致的准备失败也保留；后续运行使用原记录的实际来源目录。

修正目录 flags 后，两页 lifecycle CLI/GCD 已完成写入、fsync、syncfs、卸载和关闭；original 进入 post-fs-data，并记录原 Keystore 密钥初始化。用户 kill 随后返回 EACCES，旧断言使本轮回收未完成，修复和对应失败见[namespace 停止](../bug-fix/2026-11-13-原始init的namespace停止.md)。后续使用最初的两份数据盘完成六入口和恢复，保留所有失败结果。

SQLite 3.53.2 的实际实验发现 mode=ro 可修改已有 SHM，或为 WAL 数据库创建 SHM；immutable=1 在两次查询中均遗漏已提交的 WAL 数据，quick_check 仍为 ok。查询改为使用原导出的独立 APFS 副本，DB/WAL/journal/SHM 一同复制，显式关闭连接并清理副本；保存原导出与查询前后摘要和克隆/清理清单。结果为 `work/native-linux-nce/sqlite-export-semantics-v1/summary.json`。完整 export_clean 的两个 toy ext4/WAL 复验均成功，原盘与导出字节保持，WAL 中创建的表与两条数据读取正确；结果为 `sqlite-export-regression-v2/summary.json`，首次 fixture 摘要检查失败另行保留。原 init 的 SQLite 完整性要求 header 和 quick_check 成功；schema 和服务初始化进度单独报告，完整 Keystore 行为与其他 SQLite 版本继续待验证。

### 关键选择与实施偏离

数据盘复用已有 slot 0 与 Linux ext4，同一份原只读 SDK 镜像继续由 slot 1/DM linear 使用。目录引用由父任务持有到 namespace 回收，guest 通过 exec 关闭其副本后检查实际文件系统与持久写入；移除这份引用会使原策略后的 syncfs 缺少可用 fd。停止修复见[namespace 停止](../bug-fix/2026-11-13-原始init的namespace停止.md)，宿主关闭错误传播复用已有关闭入口。

实施中修正了目录 flags、分区 fd 与标准流编号冲突、停止权限错误和报告顺序校验。SQLite 查询从 mode=ro 的原导出改为独立 APFS 副本；immutable 查询遗漏 WAL 的实际结果保留。reclaim-code-entropy 审阅未发现可安全删除的新增抽象，技术文字按 humanizer-zh 复核。交付范围增加了原策略后的受限停止和 WAL 查询边界检查；原 fstab 加密、配额、metadata 与完整启动继续分别验收。

### 待验证范围

原 PID 1 在已有系统服务失败后请求 namespace reboot，数据盘可能需要下次挂载回放 journal；宿主 fsync 只能提交已经传到 host block 接口的写入。持久化结论必须同时覆盖 Linux 同步、实际原盘内容与下次挂载。原 `/metadata` 分区、加密、quota、fsverity 和 fstab 启动条件继续作为完整系统的验收项。设备执行、资源和持续热状态按[离线开发目标](../process/2026-11-12-离线开发目标与持续推送.md)保留待验证。
