# 决策记录: SDK36 原 ramdisk 输入读取

状态: implemented

## 问题

[原 SDK36 init 实验](../../proposed/architecture/2026-11-12-原始SDK36-init与rc启动实验.md)的旧 ramdisk 清单只读取第一个 newc trailer 前的 12 条记录。主线只读调查 `work/native-linux-nce/sdk-first-stage-source-review-v2/ramdisk.json` 确认固定 SDK ramdisk 包含两个串联 archive，共 29 条非 trailer 记录；第二段有原 `first_stage_ramdisk/fstab.ranchu`、四份 modules 配置和九个模块。完整 first-stage 输入需要保留第二段内容和原元数据。

## 决策

新增 `scripts/stock_init_sdk_ramdisk.py`，只读取 SHA-256 为 `5eff5ed46490588b7576716741e19709b8a99dccd5a7f1e7ee1256c027dacf1d` 的 SDK36 ramdisk。`read(path)` 返回输入与解码摘要、archive 边界以及按 stream 顺序排列的 entries。每条 entry 保留原 path、inode、mode/type、uid/gid、nlink、mtime、dev/rdev、header/data/end offset、文件摘要及 `data: bytes`。调用方按原顺序向 guest ramfs 写入文件、目录和节点；结构化报告省略 data，保留元数据与摘要。

解码和 CPIO 读取都在内存完成，不增加压缩格式选择或持久副本。固定输入的两个 `dev` 目录记录按原顺序返回。全部 29 条记录的 nlink 均为 1，普通文件没有硬链接组；本模块只返回实际字段。原 `/init`、fstab、modules 配置和模块字节保持。

解码调用本机已有 `lz4 -d -c -`，输入通过 stdin 提供。输入摘要、newc 结构或目标路径不符要求会抛出 ValueError；lz4 启动、超时或非零退出的异常继续向调用方抛出。本模块用于 Mac 上的输入准备，运行所需内容由后续 staging 随包交付。

路径检查用于约束后续 staging 的目标路径；绝对路径、父目录跳转、NUL 和不支持的记录类型在返回前拒绝。stream 必须包含完整 header、文件名、文件数据、对齐字节及每段 trailer，段间只接受零 padding。原第一段有效而第二段截断的输入必须失败。

### 验收标准

1. 读取固定 SDK 输入，两个 archive 分别返回 12、17 条记录，原 `/init` 和 early fstab 的摘要与只读调查一致；逐条元数据和摘要对应原 29 条记录。
2. 从完整实际解码 stream 截去第二段、trailer、header、文件名、文件数据或对齐字节后拒绝；完整两个 archive 的零 padding 保持。
3. 读取前后固定 ramdisk、只读调查和新源码摘要保持，结果不包含解码大文件或展开目录。
4. 原 guest first-stage、节点创建、模块加载、挂载和 SwitchRoot 由主会话继续验收，本模块结果只覆盖输入读取。

### 本机输入结果

候选源码在 `codex/sdk-first-stage`、基准 `b8d746a` 上完成，随后包含主线 `6f041e4`；本轮代码检查点为 `8d43081`。执行 `python3 -B work/sdk-ramdisk-input-v1/verify.py` 后，[18 项回归](../../../../work/sdk-ramdisk-input-v1/result.json)全部成功。结果保存实际清单、原输入与源码 SHA-256、每项结果和截断错误；[回归脚本](../../../../work/sdk-ramdisk-input-v1/verify.py)保留具体变体与只读命令。

解码 stream 为 4,211,712 bytes，SHA-256 为 `f91f0c6a193106dc58e1d7472c8bde201225ab40ca07caa7f0ee461a787355ea`。两段分别返回 12、17 条记录，archive 起始、trailer、records end 与 padding end 均与原只读清单一致。原 `/init` 的 SHA-256 为 `791508ed71b84ee8869417ee751966d3bf337ec6a2b99cd34f1d34cc3ec6119b`，early fstab 为 `b4572d0245a6bd33fec9b3fcee224a314e4ad62d44dd4f88d636983e6d47b144`。29 条记录的元数据和数据摘要、原 inode/mtime 字段、两条 `dev` 目录的顺序以及全部 nlink=1 均核对成功。

原第一段完整而第二段缺失，以及两段的 header、第二段文件名、fstab 内容和四字节记录对齐、第二段 trailer 缺失或截断均拒绝。段间非零字节、绝对目标路径、父目录跳转和固定输入之外的 symlink 类型也被拒绝。输入摘要变更先于解码失败。原 ramdisk、独立清单、模块与回归脚本在执行结束后摘要保持；本轮没有创建解码文件或展开目录，未执行客体、构建或候选盘操作。末段 trailer 后的零 padding 长度不参与 newc 结构判断，原输入总字节及摘要由 `read(path)` 在解码前检查。

后续部署的宿主 C 检查已核对生成表的 29 项属性与全部普通文件载荷，输入摘要保持；部署与 caller、实际 Linux 属性和原 first-stage 的后续结果见[启动记录](2026-11-13-SDK36原始first-stage启动.md#构建前结果与输入准备)。输入读取模块继续保持原字段与接口。

### 复杂度与文字审阅

当前使用方是 `stock_init_first_stage.prepare()`，按 entries 原顺序消费元数据和 bytes 并生成 runner 表；`stock-init-ramdisk.h` 按表部署客体 ramfs，结构化报告只省略 data 字段。模块只提供 `read(path)`，一个私有解析函数负责完整串联 stream，未增加 CLI、压缩格式配置、目录展开或另一份持久输入表示。文件内容和原字段共同保存在每条记录中，避免并行列表或文件名映射的同步要求。移除后段读取会再次遗漏原 fstab 和模块；移除固定段数检查会使首段完整的截断输入被接受；移除原顺序会改变重复目录的恢复顺序。

源码注释仅记录固定第二段与 first-stage fstab 的关系，其他字段和控制流直接由代码表达。文档与注释已按 humanizer-zh 复核，保留原路径、摘要、类型和未验证范围。生成表与部署消费者已实现并经宿主检查；本轮两页原 first-stage 的实际 Linux 属性与部署验收成功。

两页 v9 原始入口已完成部署、设备发现、五个 LP 挂载、SwitchRoot 与后续 init exec，原 29 项 ramdisk 元数据和文件载荷验收成功。输入读取模块与原固定 ramdisk 保持，完整启动及原模块 ABI 继续按各自实际返回验证。

## 曾考虑的替代方案

- 只读取第一个 archive：会再次遗漏原 early fstab 与模块输入。
- 从 vendor 复制 fstab：原 ramdisk 已有对应文件，会增加另一个来源和 staging 选择。
- 将解码 stream 或目录写入 work 后再读取：当前输入可以在内存处理，持久副本没有独立使用方。
- 预先支持多种压缩格式和通用硬链接恢复：固定输入为 LZ4 legacy frame，全部 nlink 为 1，当前调用方没有这些需求。

## 影响

源码与 SDK 原二进制的精确构建对应尚未确认。该模块返回原记录及数据，guest staging 对 mode、uid/gid、节点和重复目录的实际恢复已由两页 raw 入口检查。原模块的 ABI 与 LKL 构建兼容性继续按实际加载返回验收。
