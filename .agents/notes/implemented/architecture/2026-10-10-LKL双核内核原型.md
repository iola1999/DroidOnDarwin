# 决策记录: LKL 双核内核原型

状态: implemented

## 问题

Android 多核开发首先需要验证 Linux 内核的每 CPU 状态和宿主线程交接。原有 LKL 构建仅支持单 CPU，NCE 还使用共享执行入口和用户地址窗口；同时修改两者会使初始化、调度与映射故障难以区分。原型范围与后续 M2/M3 见[多核规划](../../proposed/architecture/2026-10-10-后续提速与多核可行性评估.md)。

## 决策

使用独立源码和构建目录，固定 Linux 6.12 提交 `d0f76a77e8c2ca68bd7d96190b8da09040eab072`，配置为双 CPU、NOMMU、开启内核调试。`scripts/probe_lkl_smp.py` 先应用当前宿主 ABI 补丁，再应用 `scripts/lkl_smp_patch.py`；源文件位于 `experiments/native-linux/smp/`。桌面包仍使用原有 UP/MMU 构建。

CPU 身份存入现有宿主 TLS 接口，任务恢复后根据 Linux 的 CPU 归属更新。owner、current、切换前任务、IRQ 屏蔽与待处理位图分别属于各 CPU。IPI 由两个宿主通知线程向指定 CPU 发出，时钟分别登记；CPU 1 空闲时释放 owner 并等待事件，宿主系统调用固定在 CPU 0。普通原子操作使用内联 AArch64 指令，futex 原型只接受受控 NOMMU 宿主内存；MMU 配置通过编译错误拒绝使用这份 futex 实现。

初始化需在 `setup_per_cpu_areas()` 前登记可能的 CPU，并启用 `GENERIC_SMP_IDLE_THREAD` 创建第二个空闲任务。LKL 的可重定位中间文件在最终链接时会重新排列数据段，因此打包时显式保留 `.data..percpu` 的 4096 字节对齐。早期 panic 在控制台尚未注册时直接输出消息，保留 BUG 的源文件和行号。停止时关闭时钟、等待两 CPU 退出并结束通知线程，最后释放 TLS。

### 验证

在 Apple M5 Ultra / macOS 27.0 (26A428) 上运行 `python3 scripts/probe_lkl_smp.py`，CLI 与 GCD 各三轮成功。每轮覆盖两个绑定 CPU 的计算任务，32 位共享计数为 200,000，64 位共享计数从 `1 << 40` 增加 200,000，futex 原子加法也得到 200,000；另检查交换、比较失败、位操作、无效操作和 NULL 地址。两任务计算区间重叠为 4.616–14.583 ms。该区间用于确认执行重叠，当前没有 UP/SMP 耗时对照或 Android 提速结论。

定向回调分别观察到 CPU 0/1，绑定任务完成定时睡眠，迁移任务从 CPU 0 转到 CPU 1。原有文件、计时器、宿主管道、futex 等待/唤醒和正常关机检查继续成功。原始日志未记录 WARNING、BUG 或 panic。[结构化结果](../../../../experiments/native-linux/results-macos-smp-kernel.json)保留配置、每轮输出、输入和产物摘要。脚本检查验证期间输入未发生变化。

### 复杂度审查

原型复用 Linux 的调度器、锁、每 CPU 分配器和现有宿主线程/TLS 接口。通知线程承担异步 IPI，避免持有一个 CPU owner 时进入另一个 CPU；直接嵌套调用会改变锁与调度条件，因此保留通知队列。队列只保存待处理位和一个信号量，没有引入通用消息系统。CPU 数量固定为两个，未增加 App 配置或 CPU 热插拔；后续是否扩展由 M2/M3 的实际需求决定。

## 曾考虑的替代方案

- 直接合入旧 LKL SMP 分支：其 Linux 版本、宿主 ABI 和 ELF TLS 使用方式与当前构建不同，仅参考每 CPU owner、IRQ 和线程恢复设计。
- 同时启用 SMP 和现有 NCE 用户态：共享 active、抢占目标、代码发布和用户窗口仍缺少并发同步，当前不足以安全执行。
- 将内核每 CPU 数据的全部内部间距扩大为页：最终中间文件的节对齐仍需单独保留，内部额外填充没有必要；检查通过后保留原有内部布局。

## 影响

本阶段交付独立内核原型。Android、ART、Binder 用户进程、COW/unmap 并发、映射公平切换和 iPhone 执行继续由 M2/M3 验证。NOMMU futex 的受控指针条件、两 CPU 空闲与停止流程均需要在接入 MMU 时重新检查。
