# 决策记录: 稀疏客体地址与原始 Bionic

状态: implemented

## 问题

[原始组件检查](../testing/2026-11-12-原始linker与Bionic组件验证.md)已确认 SDK36 r07 的原始 libc 在 `main` 前请求 8.25 GiB 的 `PROT_NONE` 连续虚拟地址范围，低 4 GiB 客体布局返回 `ENOMEM`。本阶段建立 Mac 受限原型，扩大客体虚拟范围，检查同一原始 runtime 的实际执行阶段。

客体上界暂定 64 GiB，用于地址容量对照。产品默认范围尚未决定。宿主 RAM 别名、backing 与客体范围的数值分离约束继续保留；Mac 仍只为 RAM/VMALLOC 预留 1.0625 GiB，独立 backing 为 1 GiB。iOS 若无法在客体数值范围外获得这些宿主映射，准备阶段会失败。允许地址数值重叠前，需改造来源判定和初始化/撤销路径，并增加对应回归。本阶段未做 iPhone 验证。

## 决策

### 地址与调用来源

增加 `--guest-layout sparse`，限 16 KiB、单 CPU、PTE、Direct flat。`guest_base` 为 `0x10000`，`guest_end` 为 `1UL << 36`。内核 `TASK_SIZE` 使用该上界；`physical_base` 保持真实宿主 RAM 别名，PTE 中的物理地址通过它转换为独立 backing 偏移。内核与宿主均检查溢出、对齐、页表上界和宿主映射分离。原 host/low 布局保留。

现有三级页表为 14 位页内偏移加三级 11 位索引，可表达 47 位地址；本阶段不修改页表级数。每个用户 mm 的 PGD 独立分配，内核 VMALLOC 使用 `init_mm`。原生 NCE 的 `NCE_USER_SIZE` 继续为 4 GiB；扩大客体范围的内核改动只进入 translated overlay。原有全局 ELF 地址分配、动态执行窗口与 VM 限制继续生效。

宿主 kernel text、静态缓冲或 stack 数值可以位于 64 GiB 范围内。`nce_access_ok`、`nce_copy_user` 与字符串复制继续通过 `current->thread.nce_state` 区分显式宿主 syscall 与客体调用；字符串长度上界由 `nce_user_string_limit` 提供。客体复制经过本 mm 的 PTE，宿主调用使用原宿主指针。`revoke_pages` 仍依赖客体与宿主 RAM 数值分离，本阶段保留该前置条件。

[核心测试](../../../../experiments/native-linux/translation/sparse-guest.c)先用未映射的同值客体指针执行读、写、`openat`、`write`、`pread`，要求访问失败；随后在宿主低地址缓冲的相同数值处建立客体页，验证客体文件路径与数据复制，并由宿主检查原缓冲内容保持。测试记录实际宿主低/高缓冲、stack 和 text 地址。`FIRST_USER_ADDRESS`、低地址空洞、栈增长、`mmap` hint、固定映射和用户复制上界使用实际 guest 范围。

### Direct 与宿主内存

每个 mm 的 flat 表继续覆盖从 `guest_base` 开始的 4 GiB，表容量保持 4 MiB。低范围访存保持当前查表；高范围访存调用已有 PTE 汇编查询，校验完整 64 位地址、用户范围、PTE 权限、代码页写入条件和物理 RAM 偏移。PTE 缺失交回 Linux 处理。`flat_update` 与 `flat_refresh` 截止于 flat 覆盖上界；完整客体范围继续用于映射和代码失效通知。

`NceDirectPageTable.user_size` 在 sparse 布局传递实际 guest span。host/low 保留原配置。read-view 仍要求 4 GiB 用户范围。本阶段未增加稀疏 read alias 或扩大 flat 表。

sparse 的宿主预留和 backing 使用 `mach_vm_map`，以 `guest_end` 为最低地址，使用 `VM_FLAGS_ANYWHERE` 选择空闲范围，保留地址分离和既有宿主上界检查。host/low 继续使用原 mmap 分配路径。核心测试的低地址缓冲使用宿主静态页，高地址缓冲使用相同 Mach 分配方式。

初轮测试发现了三项地址准备差异，产物保存在独立工作树的 `sparse-core-v1` 至 `v6`。Darwin mmap 未采用低地址 hint；无 hint 的产品预留曾返回 `0x105df8000`，位于 64 GiB 客体数值范围内，准备检查拒绝继续。固定 256 GiB 的 Mach 预留返回 `KERN_NO_SPACE`。独立小程序检查固定 8、16、32、64、128、256、384 GiB 均失败，448 GiB 成功；`mach_vm_map` 使用 64 GiB 最低地址和 `VM_FLAGS_ANYWHERE` 返回 448 GiB。测试中的 `mach_vm_allocate` ANYWHERE 也曾返回低于 64 GiB 的地址，因此最终使用 `mach_vm_map`。这些失败均发生于客体测试之前；本记录保留实际 API 与地址条件，未把固定地址作为产品配置。

### 本机验证

环境为 Apple M5 Ultra，macOS 27.0，构建 `26A428`。源码基于组件提交 `271300af0f7ca11583a61189ca5292b83079aeee`，位于 `work/offline-stock-bionic` 的 `codex/offline-sparse-guest` 分支。所有输出留在该工作树；依赖沿用组件阶段的最小 APFS clone，本轮未复制 ART 或 Android 整盘。标准 VM 候选尚未合入该分支。

所有 Linux 检查使用 1 GiB RAM、16 KiB 页、单 CPU、PTE、Direct flat、128 MiB 代码缓存、dual 代码内存、timer 抢占、按页执行缓存与 TLB 失效。`code_watch`、`cross_page`、`native_exclusive` 开启；`memory_groups`、`route_epochs`、`retain_routes`、`vector_table`、`simd_math` 关闭。功能检查允许与其他离线工作并行，无性能结论。

### 原始 SDK 组件结果

原始四文件与[低地址基线](../../../../experiments/native-linux/results-stock-bionic-sdk36-20261112.json)完全相同。两个入口的 linker 帮助阶段 exit 0 并输出 Usage，随后动态阶段 exec errno 0。8.25 GiB 的 `mmap(0, 8858370048, 0, 16418, -1, 0)` 在 CLI 返回 `758759424`，GCD 返回 `763363328`，地址容量失败已消除。

动态程序随后在 `main` 前收到 SIGSEGV（11）。CLI 记录 `guest fault pc=2d28b0a8 address=2000001ad3ac6c0 access=1 result=-14`，GCD 记录 `guest fault pc=2d3070a8 address=20000021d818700 access=1 result=-14`。两次都是顶字节 `0x02` 的写访问，原始异常指针值保留在报告中。`validated` 为 true，`component_compatible` 为 false；BSS、分配内容、TLS 和 libm 的五项 `main` 内检查仍未执行。下一项 TBI 调查需分别核对普通用户数据访问、内核 tagged-address ABI 和系统调用参数规则，先定位 fault PC 与原 Bionic tag/prctl 路径。

### 复杂度审查

按 reclaim-code-entropy 检查新增路径。`sparse` 由明确 CLI 配置调用，继续使用现有 PTE 汇编、Linux 页表、异常处理和进程生命周期。flat 以外只增加地址范围分支，没有第二套高地址缓存或逐页映射表。固定 64 GiB 实验范围由配置验证保持，尚未增加任意地址范围接口。核心边界测试独立于已有 guest 主程序；准备失败沿用原注入、整区间检查和负对照。主会话已只读复核 flat/PTE 分支和 overlay 范围修改，未发现确定错误。

## 曾考虑的替代方案

- 把全 flat 表扩大到 64 GiB。会让每 mm 表的容量随地址范围增长，本阶段保留已有 PTE 查询，先验证原始 runtime 的功能条件。
- 立即允许客体与宿主 RAM 数值重叠。当前 `revoke_pages`、准备检查及回归尚依赖分离，需要单独核对全部宿主回调与客体复制来源；本阶段保留并明确平台限制。
- 同时修改 4 KiB 客体页、标准执行映射和上游 ART。会使 SDK 地址容量对照同时改变多项条件，先完成 sparse 候选，再按各阶段结果组合。

## 影响

原始 SDK Scudo 的 8.25 GiB 预留已在 sparse 布局成功，后续执行受带顶字节标记的写访问阻塞。当前结果支持继续调查 TBI 与原始 Bionic ABI，尚未完成原始 runtime 五项基本行为验收。高地址 PTE 访问的功能检查成功，本轮没有测量该路径的持续性能。

64 GiB 仍是 Mac 实验上界。iOS 宿主地址摆放、客体与宿主 RAM 数值重叠、完整 ART 的低地址对象分配和原始 HyperOS linker 仍待独立验证。HyperOS 16 KiB 权限共页的早期故障未在本轮改变；其原始 libc 的地址请求仍未执行到。后续 TBI、4 KiB 客体页和原始 ART 按独立条件验证。
