### N0 的架构选择

先验证单执行线程、固定客体地址窗口。普通 ARM64 指令和访存保持原样；进入
系统调用时保存寄存器、回到宿主栈，再切换客体内存映射。共享映射保持不变，
连续私有区间按区间 remap。分别测单页、连续大区间与分散页，检查区间合并的
收益能否保留到频繁进程切换场景。

测试代码由独立的 AArch64 ELF 工具链生成，仅改写 SVC 与 TPIDR_EL0 读写。
N0 的回调只提供探针需要的返回值，Linux 尚未接入。客体代码限定为仓库中的
受控汇编，x18 保留给 Darwin；任意 Android ELF 的指令检查、地址布局、安全
隔离、异步抢占和 JIT 页面发现放在后续实现中。

当前 SVC/TLS 跳板临时使用客体 SP 下方 16 字节保存寄存器，要求该范围可写、
SP 按 16 字节对齐。任意客体代码的栈边界与跳板内异常恢复仍需处理。

使用独立的 RX/RW 代码地址，iOS 构建接收 Husk 已获得的 JIT 映射。Mac 负责
开发和对照测试，手机运行时所需部分均编译为本机代码。

### Linux 基础的选择条件

[ARM64 UML](https://github.com/zalexdev/linux-um-arm64/tree/8897487c52233cd00cf2850008ca068892f1ae91)
保留 Linux 用户进程和 MMU 语义，但宿主部分依赖 clone、ptrace、seccomp。
后续评估用 Darwin 内存映射与 NCE 替换该宿主执行部分。

[LKL](https://github.com/lkl/linux/blob/d0f76a77e8c2ca68bd7d96190b8da09040eab072/Documentation/lkl/lkl.txt)
提供可嵌入的 Linux 内核及宿主操作接口，可用于早期验证真实 Linux 子系统。
其用户进程、信号和地址空间仍需扩展；选择它作为最终基础前，必须列出这些
扩展对 Linux 调度与 MMU 的影响。N1 已使用 LKL 验证原生内核与 NCE 的接口。

### 判断与停止条件

N0 的测试通过只支持继续移植 Linux。若固定地址窗口需要重映射大量分散页，
且成本已超过合理的调度时间片，应先验证其他地址空间实现。若 iOS 拒绝必需的
内存操作，应记录具体调用和返回值，调整架构后再继续。

原生计算对照用于判断 NCE 是否仍有逐指令开销。系统调用与地址切换测试用于
发现计算循环隐藏的成本。两者均不能推导 HyperOS 的加速倍数。

### 性能记录与解释

以下来自完成检查后的最后一轮运行。N0 计算对照取五轮中位数；N1 与 remap
为该轮单次样本。数据保存于 `experiments/native-linux/results-macos.json`。

| 测量对象 | 结果 | 覆盖范围 |
| --- | ---: | --- |
| 400 万次计算与访存，直接调用 / NCE | 3.633 / 3.677 ms | 同一受控汇编循环；NCE 耗时为原生的 1.012 倍 |
| NCE 每次循环经过探针回调 | 约 22 ns 增量/次 | 完整寄存器保存恢复；回调只返回固定值 |
| 原生 Linux 内核启动 | 34.947 ms | 64 MiB RAM、最小 LKL 配置 |
| 直接调用 Linux `getpid` | 14.95 ns/次 | 10 万次；宿主侧 LKL 系统调用入口 |
| NCE + Linux `getpid` + 少量计算访存 | 46.46 ns/次 | 10 万次；真实 Linux 系统调用 |
| 两地址空间切换并执行探针 | 1.974 μs/次 | 每个私有窗口 64 KiB；只访问部分页面 |
| 连续 2 MiB 重映射，仅访问首页 / 访问每页 | 2.057 / 48.350 μs | 两组已经驻留的后备内存 |
| 分散 128 页重映射，仅访问首页 / 访问每页 | 103.203 / 193.982 μs | 每页 16 KiB，共 2 MiB |

直接执行和系统调用入口已经表现出较低开销。访问完整工作集后，映射切换仍有
明显成本；只测 remap 返回时间会漏掉后续页面访问的开销。后续需要结合实际
Linux VMA 布局、共享页比例、调度频率和工作集验证。

这些 Mac 数据支持继续实现用户进程环境。iPhone 的 R3 结果见后文；当前尚无
HyperOS 或旧 QEMU 后端与本原型的同负载对照，整机加速倍数未知。

### N2a：Linux 用户进程原型

2026-10-08：已将 NCE 上下文与 Linux task/mm 绑定。`--processes` 构建启用
`CONFIG_MMU=y`，使用 16 KiB 页、独立进程页表和宿主映射切换。Linux 内核、
客体普通 ARM64 指令及访存均原生执行。每个 Linux 任务对应一个宿主线程，
由 LKL 的单 CPU 调度器决定运行顺序。

本阶段选择继续扩展 LKL。父子关系、PID、页表复制、COW、文件描述符、futex、
ELF 装载和退出状态沿用 Linux 实现。新增部分处理 Darwin 内存映射、异常与
NCE 寄存器上下文；`execve` 经 Linux 的 `binfmt_elf` 装载第二个受控 ARM64 ELF。

N2a 初版的连续 32 轮检查覆盖以下行为：

- `clone(SIGCHLD | CLONE_SETTLS)` 创建独立地址空间；按照 AArch64 的参数顺序
  设置子进程 TLS。父进程保留 TLS 值 123，子进程收到 456，随后修改为 789。
- 父进程私有数据保持为 7，子进程修改自己的副本为 11；客体栈同样经过 COW。
- 匿名共享页在子进程写入 88 后，父进程读取到 88。
- Linux futex 实际唤醒一个等待者。检查允许子进程先运行，通过 `sched_yield`
  等待父进程进入 futex，随后验证共享页和 pipe 中的数据。
- 子进程通过继承的 pipe 写入 90，父进程读取同一数值。
- 子进程调用 `execve`，新 ELF 检查 Linux 参数栈中的 `argc`、`argv[0]` 和
  清零的 TLS，随后以状态 42 退出。父进程通过 `wait4` 收到对应状态。
- 改写可执行指令前，Linux 为代码页建立私有副本；32 次 exec 后，文件内容
  与原始 ELF 完全一致。
- 每轮的父子执行上下文都被回收；合计分配和释放各 64 个。负数及越界
  系统调用号返回 `-ENOSYS`。

N2a 初版记录的原生内核启动为 34.485 ms；32 组流程共 12.344 ms，平均每组
0.386 ms，期间处理 288 次缺页。N0/N1 回归检查均通过。结果与源码哈希保存在
`experiments/native-linux/results-processes-macos.json`。
这组测量包含小内存进程的创建、通信、exec 和回收，未包含 Android 启动、ART、
图形或大工作集。不能据此计算 HyperOS 加速倍数。

#### 地址空间与执行入口

宿主启动时申请连续虚拟地址范围，并将实际地址传给 Linux。N2a 初版的客体
窗口为 256 MiB，物理内存为 64 MiB，后面保留 64 MiB 的内核虚拟地址范围。
R2 将客体窗口缩为 64 MiB，并纳入调试器准备的映射。运行时分配可避开宿主
已有映射；固定数值地址在本机返回过 `KERN_NO_SPACE`。

切换 `mm` 时，数据页先取消旧窗口的访问权限，再按新进程的页表映射。
当前逐页映射，尚未合并连续区间。R2 的代码区保持原始 RX 映射，通过复制
恢复新进程的代码。COW 写异常交给 Linux `handle_mm_fault`。
NCE 跳板读取当前进程的上下文指针，共享代码可服务多个依次运行的进程。

调试时发现，继承内核页表目录会让父子进程共用部分页表，子进程退出后父进程
读到 0。改为独立分配页表后，私有数据和栈的检查通过。这个改动是多地址空间
实现的必要条件。

Darwin 拒绝本轮尝试的 RWX 映射。客体可执行页保持 RX，改写使用独立 RW
别名；可写的 Linux 页面保持不可执行。当前受控 ELF 为跳板预留了 64 KiB
代码区，任意 ELF 的代码布局与动态生成代码仍需扩展。

### N2a 阶段边界

N2a 已有 Linux 管理的用户进程及 ELF exec。第一个探针进程仍通过宿主调用
启动；PID 1 保留 LKL 的内部初始化逻辑。下一阶段需要接通独立用户态 init、
Linux 信号帧与 `rt_sigreturn`，并扩大 ELF、线程和内存故障覆盖。

N2a 仅执行仓库中的受控程序。宿主系统调用接口接受宿主地址，尚未隔离任意
客体指针；非法访问仍可能终止整个宿主程序。Darwin 信号回调目前直接调用
Linux 缺页处理，尚未解决所有重入和持锁条件。后续需要建立可恢复的异常入口，
分别处理客体访问失败与宿主故障。

2026-10-09 已将内核装载和 N2a 进程检查接入 iOS 应用，生成
`work/native-linux-nce/ios/Husk-NativeLinux-N2-R3.ipa`。安装包的构建、签名完整性
和 ZIP 检查通过。R1 在执行重映射代码时失败；R2 通过执行预检，在 Linux
初始化的数据映射中失败。R3 已在 iOS 27.2 完成全部受控进程检查，结果见后文。
运行方式见[手机测试说明](../testing/2026-10-09-N2手机测试与故障记录.md)。

其他待做项包括任意 ELF 的指令检查、x18 使用、4 KiB/16 KiB 混合保护、
异步抢占、多核、ART 动态代码和 Android 图形。

### N2 iOS 测试包

R1 手机日志确认 80 MiB JIT 分配、原始 RX 地址执行和调试器断开成功；断开
等待 13 ms。系统报告显示新重映射地址取指触发 `KERN_CODESIGN_ERROR`，
页面权限为 `r-x`。具体报告与版本对应关系见[手机测试说明](../testing/2026-10-09-N2手机测试与故障记录.md)。

R2 将客体执行地址放在最初准备的 RX 映射中，执行代码期间保持该 VM 映射。
以下记录 R2 的布局；R3 在后文调整了 JIT 准备范围。
R2 的 Mac 和 iPhone 检查共用 208 MiB RX/RW 内存池，包含预检、计算探针、
Linux 内核映像、192 MiB 的地址范围和进程启动代码。192 MiB 分为 64 MiB
客体窗口、64 MiB Linux 物理内存和 64 MiB 内核虚拟地址区。`layout.h`
同时提供宿主与内核需要的布局常量。

受控 ELF 由 Linux 装载到客体窗口起点，代码区位于偏移 `0x10000`，长度
64 KiB。代码映射回调将 Linux 私有页复制到固定 RW 别名，并刷新指令缓存；
切换进程时恢复相应页面。SVC/TLS 改写也写回 Linux 私有页，因此后续切换
能够恢复改写后的代码。数据仍用 `vm_remap`；Linux 数据和栈默认保持读写。
撤销代码映射时清零固定区，保留 RX 地址。这只适用于受控程序，尚未提供
任意客体的完整权限隔离或动态代码语义。

这个选择增加了进程切换时的代码复制成本，并要求为执行地址预留内存。
当前只验证一个 64 KiB 代码区。扩大工作集和执行区数量后，需要重新测量
内存占用与调度开销。

手机检查顺序：

1. 申请 JIT 页面，写入并执行两条 ARM64 指令，确认基本执行条件。
2. 等待 `P_TRACED` 清除。在原始 RX 地址交替更新两段代码，执行八次；再做
   八次数据页重映射和读取。
3. 对同一段 400 万次计算/访存循环做五轮直接执行与 NCE 对照，并核对结果。
4. 装载 Linux 6.12 内核，检查启动和 `uname`。
5. 执行 32 轮进程检查。exec 后继续 clone、栈 COW、TLS 与 wait，以确认固定
   代码在实际任务切换后仍能执行；检查 ELF 文件原文和系统调用边界。
6. 关闭内核，确认 96 个 NCE 上下文全部释放。

R2 的 Mac 检查通过。该版内核启动 28.086 ms，32 轮进程
检查共 15.237 ms，缺页 352 次，复制代码页 512 次。
最新 Mac 结果与源码哈希保存在 `experiments/native-linux/results-prepared-memory-macos.json`。
Mac 使用本地 RX/RW 分配，未运行 iOS 的调试器准备流程。这些结果只覆盖短时
受控程序；R2 手机已完成预检与计算对照，在 Linux 初始化的物理内存映射中触发断言。

早期代码执行探针增加限定地址范围的信号恢复，失败时记录信号、PC 和访问
地址。Mac 回归通过正常与错误返回值、非法指令、访问异常、后续正常执行和
原信号处理器恢复。它仅用于这个短探针；Linux 执行中的异常恢复仍需扩展。

应用复用 Husk 的内置 JIT 助手、StikDebug 脚本和配对文件存储。运行时禁用
自动锁屏，日志写到手机的 `Documents/native-linux-n2-ios.log`。重新打开应用
可导出上次内容。每次进程启动只允许执行一轮，下一轮需要关闭并重新打开；
再次开始会覆盖日志。

### 重建

需要 Apple Silicon Mac、Xcode SDK、Python 3.12+、Homebrew LLVM、LLD、
GNU Make 和 GNU sed。首次 LKL 构建下载约 239 MiB 压缩源码；展开源码约
1.6 GiB，内核构建目录约 65 MiB。构建脚本固定 LKL 提交及 musl ELF 头文件版本。

```sh
python3 scripts/probe_native_linux.py
python3 scripts/probe_lkl.py
python3 scripts/probe_lkl.py --processes
python3 scripts/package_native_linux_ios.py
```

第一条输出 N0 测试、五轮计算对照与 iOS 静态库。第二条执行 N1 内核子系统
检查。第三条应用 N2a 的 LKL 架构修改，构建并执行用户进程检查，同时编译
对应 iOS 宿主代码；输出位于 `work/native-linux-nce/processes/`。第四条需要
XcodeGen，生成独立 iOS 工程并构建 IPA，输出位于 `work/native-linux-nce/ios/`。
打包前检查参与 Mac 验证的源码及内核哈希；源码变化时使用
`python3 scripts/package_native_linux_ios.py --rebuild-kernel` 重新验证。

N2a 初版修改脚本曾在固定提交的原始文件上检查，生成的 21 个文件与构建源码
一致。R2 在当前源码上连续应用两次，文件内容保持一致。失败返回非零状态，
原始输出保留在工作目录。

### 实现取舍与审查

保留一个 NCE 入口和一个 Darwin 宿主实现，三个阶段共用寄存器切换代码。测试
ELF 由构建脚本解析，运行程序只装载自己构建的映像，尚未加入通用动态链接器。
iOS 目标增加测试界面并复用原有 JIT 助手；运行核心仍使用同一个实现。

对额外后端、通用 ELF 动态链接器和设备层做了必要性检查：当前受控测试没有
使用这些功能，暂不增加。保留独立原生汇编对照，因为它用于测量执行入口和
回调成本。Linux futex 检查要求实际唤醒一个等待者，覆盖了宿主线程、Linux
任务和阻塞系统调用之间的关系。

与初始顺序的调整是：先借助 LKL 验证真实内核子系统与调用接口，将独立 init

R2 复杂度审查：原有每进程 `exec_rw` 映射已由固定代码区替代，分配与释放也

### R3：限定 JIT 准备范围

R2 的数据映射错误没有记录具体 Mach 返回码。Apple 的
[XNU 实现](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/vm/vm_map.c)
包含将已关联代码映射标记为 `vme_permanent` 的处理；永久映射的替换受到
限制。这与 R2 把数据目标也纳入 JIT 准备范围的布局吻合，实际拒绝分支仍待
带返回码的日志确认。

R3 使用普通内存保留 208 MiB 地址，前 16 MiB 用于内核和 NCE 主代码池，
后 192 MiB 仍按客体窗口、Linux 物理内存映射、内核虚拟地址区各 64 MiB
布局。仅主代码池和客体窗口偏移 `0x10000` 处的 64 KiB 代码区接受调试器
准备。两个可执行区域各有 RW 别名；数据保持普通映射。Linux RAM 的后备
存储单独申请 64 MiB 匿名内存，由进程运行模块释放。

`husk_ios_jit_prepare_range` 复用现有脚本的指定地址分支、连接检查、别名
创建和执行自检。原有申请新区域的调用仍传空地址。预检和 Linux 的数据
映射共用 `nce_memory_remap`，失败时记录 `kr` 或 `errno`、源地址、目标
地址和字节数。Linux 初始化之前，预检覆盖实际代码区两侧的数据地址以及
64 MiB RAM 目标；映射失败直接返回测试界面。

Mac 已通过两个代码区各八次更新、两个数据目标各八次切换、64 MiB RAM
映射、五轮计算对照和 32 轮 Linux 进程检查，96 个上下文全部释放。失败
回归使用无效源地址得到 `KERN_INVALID_ADDRESS`，正常代码随后仍能执行。
iOS Release 构建通过；R3 的手机执行结果见下一节。

内存释放按代码区域和普通区域分别处理。iOS 若拒绝释放已准备的代码映射，
日志记录该状态，代码区域保留到应用进程退出。本原型每次进程启动只运行
一轮。当前仍只支持固定布局的受控 ELF。

R3 复杂度审查：共用一个 Mach 映射函数；64 MiB RAM 由运行模块持有，代码
和虚拟地址范围由内存模块持有。指定地址准备复用原有 JIT 实现。此次调整
保留了代码复制策略，改变了代码与数据的分配方式。

#### R3 验收时的 N2b 计划

以下保留 R3 验收时的计划。已完成内容和更新后的顺序以
[N2b 实现记录](2026-10-09-Linux用户态与抢占.md)为准。

下一阶段以手机内运行独立 init、shell 和普通 C 程序为交付目标。先完成下列
基础，再开展 Android 的 Binder、Bionic、Zygote、ART 和图形集成。

| 优先级 | 当前代码中的限制 | 实现与验收要求 |
| --- | --- | --- |
| 1：ELF 与执行地址 | `user_exec` 要求入口等于固定 RX 起点，长度来自 `EXEC_TEXT_SIZE`；执行区只有 64 KiB | 沿用 Linux `binfmt_elf`，根据 ELF 段处理代码、只读数据和可写数据；先运行编译器生成的静态程序，再覆盖 PIE、解释器和共享库。验证多个执行区、函数指针、PC 相对寻址及 exec 后 fork |
| 1：指令改写 | `nce_prepare_shared` 逐个扫描 32 位字，跳板附在文本后；x18 保留给 Darwin | 处理代码中的常量、跳板空间与分支距离；明确 x18 的检测和改写范围。增加含 SVC/TLS 同值常量的程序，检查读出的数据与执行结果。遇到尚未支持的指令或布局时返回可定位的错误 |
| 1：执行区生命周期 | 已准备 RX 地址保持不变；当前通过复制恢复代码 | 先验证扩大固定执行区后，多个 ELF 段、重新映射及写入后执行的语义。结合 Linux VMA 分配代码位置和跳板；动态加载与动态代码必须纳入同一流程。布局不可满足时先调整地址方案 |
| 2：进程与线程 | 第一个程序由 `nce_launch` 创建，PID 1 仍是 LKL 内部初始化逻辑；现有 clone 检查使用独立地址空间 | 建立用户态 init 与 rootfs，覆盖 `CLONE_VM` 线程、每线程 TLS、退出、futex、线程库需要的清理行为；用 shell 的子进程、管道和等待验证实际用户态 |
| 2：异常与信号 | Darwin 信号回调直接调用 Linux 缺页处理；`__access_ok` 固定返回 1；`rt_sigreturn` 仍未实现 | 区分客体访问与宿主调用，建立可恢复的缺页入口和用户指针检查；实现 Linux 信号帧、屏蔽、返回、系统调用中断与重启。无效指针应返回错误，客体故障应按 Linux 语义处理，宿主故障应单独记录 |
| 2：调度 | 单 CPU 串行进入客体；没有异步抢占 | 让无系统调用的计算循环也能被调度中断。验证寄存器恢复、锁与阻塞唤醒，确保一个客体忙循环时其他任务能继续运行 |
| 3：工作集与持续运行 | 切换 mm 时撤销整个窗口并逐页恢复，当前代码只有四页 | 测不同代码量、连续与分散数据、共享页比例和进程数量；记录切换耗时分布、复制字节数、缺页和峰值内存。按测量结果合并连续映射并复用未变化的共享代码；验证修改后内容一致性 |

16 KiB 是当前宿主和 Linux 的共同页大小。先用匹配此页大小的程序完成 N2b，
再检查目标 Android ELF 的实际布局。4 KiB 对齐和子页权限若与布局冲突，需要
另外实现兼容处理。多核涉及同时运行的不同地址空间，后续需要独立设计和验证。

N2b 的本地检查应包含寄存器、ELF、线程、信号和映射失效的功能回归；运行
shell、管道、子进程以及持续计算和内存访问的混合负载。代码复制和映射优化
保留可比较的基线，分别测启用与关闭优化时的正确性和耗时。

下次手机包集中验证扩大后的代码布局、动态代码、异常恢复及持续运行，记录
预热后的性能、峰值内存、热状态和前后台切换结果。若实现中采用 R3 尚未覆盖
的 iOS 内存操作，先单独检查该操作，再将它用于完整流程。取得这些结果后，
再判断能否进入 Android 阶段。

复杂度审查：Linux 继续负责 PID、task/mm、页表、文件、futex 和信号；宿主
负责实际映射、ARM64 上下文与异常入口。保留 `code_backing`，因为改写后的
代码需要写回正确的 Linux 私有页，exec 后 fork 已覆盖这个行为。当前受控
程序继续承担回归检查；普通 ELF 支持完成后，运行入口和测试数据分开管理。

本次完成日志验收、源码检查与实现计划，运行代码仍为 R3。N2b 的范围扩大到
普通 Linux 用户态；完整 Android 与持续性能的验收仍在后续阶段。
