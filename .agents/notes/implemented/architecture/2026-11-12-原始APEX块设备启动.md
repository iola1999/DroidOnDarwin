# 决策记录: 原始 APEX 块设备启动

状态: implemented

## 问题

[信号返回特殊映射](../bug-fix/2026-11-12-内核信号返回特殊映射.md)解除原服务 exec 的 EACCES 后，原 apexd-bootstrap 扫描 `/system/apex`，识别 runtime、i18n、virt 和 tzdata 的四个 bootstrap APEX。CLI/GCD 的首个激活失败为 `/dev/loop-control` 缺失；device-mapper 同样缺失，原 `reboot_on_failure` 请求 `reboot,bootloader,bootstrap-apexd-failed`。

基础内核最终 `.config` 启用了 `CONFIG_BLOCK=y`，但未启用 `CONFIG_BLK_DEV` 和 `CONFIG_MD`，缺少 loop-control 和 device-mapper 驱动。原 ueventd 已完成 coldboot，设备节点必须继续由原 sysfs、ueventd、file_contexts 与 `/dev` tmpfs 流程创建。

## 决策

`probe_lkl.py` 的 process 配置与 `build_lkl_translation_kernel.py` 共用 `BLOCK_OPTIONS`，启用 `BLOCK`、`BLK_DEV`、`BLK_DEV_LOOP`、`BLK_DEV_WRITE_MOUNTED`、`MD`、`BLK_DEV_DM`、`DM_VERITY` 和 `CRYPTO_SHA256`。两个入口在 `olddefconfig` 后检查这些项全部实际为 `y`。内核沿用标准驱动、文件系统与 LSM，原库、policy、enforcing、标签、权限、域转换、rc 和失败重启行为保持原输入。

原 init 实验 runner 新增 `stock_init_block` 记录，观察 ioctl、相关设备的 mknodat/openat 及 mount，保存 PID、六个参数、路径和返回值。记录只进入生成的观察副本，正式执行器源码保留原系统调用路径。报告校验检查字段集合、整数范围和路径十六进制格式；结束记录过滤排除该新记录。

### EBUSY 定位与单变量复验

`stock-init-block-devices-core-v1` 的 CLI/GCD 均成功，各回收 71/71 个上下文。`stock-init-block-devices-original-v1` 的 lifecycle 各回收 2/2，original 各回收 48/48。原 apexd 找到内核预分配的 8 个 loop，并再分配 31 个，共 39 个；对已有设备 0..7 的 `LOOP_CTL_ADD=-17` 为已有设备的返回值。驱动启用后，四个 bootstrap APEX 的 mount 均返回 `-16`，原失败重启仍请求 `reboot,bootloader,bootstrap-apexd-failed`。

`stock-init-block-devices-trace-v3` 实际记录 loop0..3 的 `LOOP_CONFIGURE` 全部成功。随后原 apexd 调用 `mount("/dev/block/loopN", "/apex/<package>@<version>", "ext4", 0x485, NULL)`，四次均返回 `-16`。原 init 对 `/bootstrap-apex` 和 `/apex` 的 namespace、tmpfs 与 bind 操作成功。v2 的 lifecycle 进程返回 0、回收 2/2，但新增记录的 `result` 被旧结束过滤条件计入，校验失败；修正过滤后，v3 四入口通过。当前校验器复验 v2 的原始记录也成功，旧报告及 SHA 保留。

此前配置关闭了 Linux 6.12 `block/Kconfig` 中默认值为 `y` 的 `CONFIG_BLK_DEV_WRITE_MOUNTED`。原 apexd 保持 loop 的 `O_RDWR` 描述符；文件系统打开使用 `BLK_OPEN_RESTRICT_WRITES`，`bdev_may_open()` 因已有写打开的设备返回拒绝。`stock-init-write-mounted-kernel` 的最终配置对照仅有一项变化：`# CONFIG_BLK_DEV_WRITE_MOUNTED is not set` 改为 `CONFIG_BLK_DEV_WRITE_MOUNTED=y`。同一原 init 随后完成四包的 ext4 挂载和 bind，全部返回 0，原日志为 `Activated 4 packages.` 和 `Service 'apexd-bootstrap' ... exited with status 0`。

### 复杂度审阅与偏离

`BLOCK_OPTIONS` 的实际使用方为 process 基础构建和独立 translation 构建，两处共享同一请求列表，各自校验生成配置。移除这些项会恢复设备缺失或 ext4 挂载的 `-16`；没有增加运行时标志、设备模拟、宿主 APEX 解包路径或配置包装接口。`DM_VERITY` 与 `CRYPTO_SHA256` 提供原 apexd 使用的标准设备能力，本次 bootstrap 成功路径使用 loop 上的 ext4，未声称已覆盖独立 verity table 的数据完整性检查。

block 观察复用已有字符串读取、日志与 syscall 调用，不新增持久状态。移除该记录会失去 loop 绑定与文件系统挂载的实际返回值；已有失败记录与修正后的校验复验覆盖结束记录误判。Mach API 改动沿用主线的平台分支，实际使用方为 sparse 宿主映射与高地址宿主指针检查；macOS core 和实际 iOS 观察副本均完成编译或运行检查。没有发现本阶段可删除且不影响这些检查的额外抽象。

实施从驱动缺失推进到块设备写打开与只读文件系统挂载的配置差异，采用 Linux 默认配置。iOS 编译补入旧检查点缺少的既有平台处理；其余执行器、页表及原 Android 用户态保持原检查点。文档、注释和提交描述按技术事实与 humanizer-zh 审阅。

## 曾考虑的替代方案

- 只在 `/dev` 创建节点：缺少内核驱动，节点不能提供 loop 或 device-mapper ioctl。
- 从宿主预先解包并挂载 APEX：改变原 apexd 的激活流程，本阶段使用原容器和内核设备。
- 修改原 rc 的失败重启选项：改变原启动行为，保留 `reboot_on_failure` 并记录实际原因。
- 修改原 apexd 的写打开方式：需要改变原二进制，本阶段保留原二进制，启用 Linux 默认的挂载设备写打开支持。

## 影响

本阶段交付原 bootstrap APEX 的设备创建、loop 配置、ext4 挂载、包目录 bind 和后续配置导入。`BLK_DEV_WRITE_MOUNTED=y` 允许已有写打开的设备同时被文件系统挂载，块层不再使用该选项阻止此类访问；原设备只读属性、DAC、LSM 与挂载权限继续由对应检查决定。原系统盘、metadata、policy、rc 和 service ELF 保持原输入。

原 init 的 mmap entropy 检查、first-stage 分区流程及完整 Android 启动继续单独推进。iOS 结果覆盖编译；设备运行、JIT 授权、资源、持续性能与热状态仍待真机验证。侧分支只做本地提交，主会话将在其当前执行器和页表实现上重建组合。
