# 决策记录: 两端共享 SwiftUI 与产品界面

状态: implemented

## 问题

用户检查 Mac 开发界面后认为排版、交互和操作动线难以理解，要求按对客产品重新设计，并评估两端共用 UI 的价值。原 Mac 使用 AppKit，iOS 使用 SwiftUI，页面、启动状态和日志观察分别维护，修改同一功能需要重复实现。

## 决策

用户于 2026-10-10 选择两栏原型并授权实施。Mac 左侧为设备资料库，右侧为选中设备详情；iPhone 使用列表进入详情。启动作为主要操作，运行后显示打开画面与停止。添加入口选择内置 Android 或镜像包，重命名和删除进入设备菜单，设置包含诊断、日志与高级导入。

`experiments/native-linux/app/` 共用 SwiftUI 页面、DeviceLibrary、SessionModel、ProbeLogReader 和 Foundation DeviceStore。页面、常规文案、设备操作限制和导入规则只维护一份；平台差异包括 Mac 窗口与进程、iOS JIT 与前后台、鼠标与触摸输入。Linux、NCE、Android 和图形核心沿用现有实现。Metal 图像通过原生视图直接显示，帧数据不进入 SwiftUI 状态。

Mac 管理进程使用 ProcessRuntime，每次启动创建独立运行进程；运行进程和 iOS 都使用 LocalRuntime。iOS 停止后提示重开 App，[连续重启规划](../../proposed/feature/2026-10-10-iOS连续重启Android.md)独立保留。修改共用功能后仍需构建两端，并分别验证平台运行行为。

### 实施中的调整

初次使用 SwiftUI App 场景创建 Mac 运行窗口，实际子进程停留在 AppKit 事件循环，未创建显示窗口。改为 AppKit 显式创建 NSWindow，内容继续由 NSHostingController 承载共享 SwiftUI。资料库窗口采用 fullSizeContentView 与紧凑工具栏，修复详情顶部被工具栏遮挡的问题。Android 画面保持独立窗口，返回资料库保留会话；关闭运行窗口会停止设备。

实际停止曾出现 Android 已完成关机、数据盘只读，但宿主持续等待退出。SIGTERM 的主队列回调直接调用 NSApp.terminate，引发嵌套事件循环等待，核心完成回调无法执行。现在通过运行循环发起退出，并以真实 SIGTERM 回归覆盖停止入口尚未注册时的重试和最终退出。

原计划中的交互场景预览未单独建立。当前采用 FakeRuntime 状态回归、原生窗口宿主检查与真实 App 操作检查；覆盖范围见下文。

### 复杂度审查

按 reclaim-code-entropy 检查实际调用方和状态所有权。旧 App.mm 入口与 iOS ProbeModel 已移除，打包脚本只编译共享页面及各自平台入口；旧文件引用检索为空。两个生产运行实现都调用同一 SessionModel，保留 SessionRuntime 协议，使重复启动、停止中操作和失败行为共用。

LocalRuntime.Stage 记录资源准备、等待 JIT、进入核心与资源释放，SessionPhase 记录用户可见运行状态。删除前者会失去准备完成后的取消判断和安全释放条件；删除后者会让两种运行方式再次各自维护页面状态，因此保留。设备目录锁保护跨进程使用，页面按钮限制保护当前交互，两者分别覆盖进程与页面边界。未增加运行后端注册、通用插件或第三方 UI 依赖。

- `python3 scripts/package_native_linux_macos.py --replace` 和 `python3 scripts/package_native_linux_ios.py` 成功。
- `python3 scripts/test_native_linux_macos.py` 成功，结果在 `work/device-macos-tests.log`：存储、显示几何与输入映射、真实 SIGTERM 宿主退出、设备导入与迁移、共享会话状态、签名执行及包内容校验。
- Mac 实际界面完成创建、重命名、设置导航、镜像导入选择器及取消；正常 Android 启动到桌面，停止返回资料库，再次启动及启动中停止成功。启动遮罩与详情排版通过截图检查；桌面就绪后遮罩收起，上滑、Clock 点击、主页导航和按需日志显示成功。检查摘要为 `work/native-linux-nce/macos/product-ui-checks.json`。

## 曾考虑的替代方案

- 分别完善 AppKit 与 SwiftUI：继续重复维护设备流程和状态限制，用户关心的同步问题仍然存在。
- Mac Catalyst：仍需重新验证 Mac 的进程、签名、动态库和窗口集成；共享 SwiftUI 可以直接保留现有原生宿主。
- 为页面迁移执行核心：当前核心已经共用，UI 重构没有产生重写核心的需求。
- 单栏设备列表：用户在两种原型中选择资料库与详情并列。

## 影响

设备、设置、日志和启动状态页面已共用。功能同步的主要工作转为平台构建与体验检查，平台差异仍需各自验证。此次没有进行 HVF 性能比较；共享 UI 的维护收益不用于推断整机性能。
