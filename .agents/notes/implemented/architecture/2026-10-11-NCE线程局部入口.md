# 决策记录: NCE 线程局部入口

状态: implemented

## 问题

[双核内核原型](2026-10-10-LKL双核内核原型.md)已验证 Linux 内核并行，此前 NCE 补丁读取一个全局 `active` 指针。共享机器码上的系统调用和 TLS 读取需要取得各自宿主线程的 `NceState`，才能允许两个客体线程同时执行。宿主 `x18` 由 Darwin 使用，客体 `x18` 已经单独模拟。

## 决策

为 NCE 分配一个进程生命周期内的 pthread key，在进入客体时绑定 `NceState`。补丁用 `TPIDRRO_EL0` 和 key 对应偏移读取当前线程状态，保留现有 80 字节补丁尺寸；系统调用入口和 TLS 快速读取的指令数量均可保持不变。普通单线程原型、Linux 用户线程和后续并行原型使用同一个入口，移除全局状态指针参数及其专用准备函数。

Apple 当前的 [TSD 实现](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/os/tsd.h)通过 `TPIDRRO_EL0` 读取 ARM64 TSD 数组；[libpthread](https://github.com/apple-oss-distributions/libpthread/blob/main/src/pthread_tsd.c)管理动态 key。这依赖系统实现，公开 pthread API 没有承诺寄存器布局。初始化及每个线程进入前用 `pthread_setspecific`、`pthread_getspecific` 和安全的 Mach 内存读取核对实际槽位，检查偏移范围；不匹配时明确失败。手机仍需随阶段包验证。

先完成共享代码、不同 TLS、寄存器/NEON、线程切换与定向信号的本机并行检查，再接入 LKL 的用户态执行。公共 boot image 正式对照先使用独立的已构建版本，避免把入口变化混入镜像对照。

### 后续接入条件

`prepare_resume()` 当前按 PC 哈希选择可覆盖的返回入口；同一程序的两个线程可能选择同一位置。M2 接入时考虑把现有空闲分支区域分给两个 Linux CPU，每个 CPU 只修改自己的区域。必须检查每个程序及动态代码区域至少有两个入口，并验证任务迁移后采用当前 CPU 的区域。这个选择依赖「准备返回到实际执行之间不会发生 Linux 任务切换」，需要在调度与信号回归中确认；暂不修改当前桌面的缓存行为。

抢占目标目前只有一个 pthread。接入双核时，Linux 的 `user_switch` 需同时传递 CPU 编号，宿主按 CPU 更新目标，线程退出清除匹配目标。进入 NCE 的 pthread 绑定自身状态；切换通知由换出线程调用，不能用它给当前 pthread 绑定即将换入的线程状态。

映射的直接故障恢复继续依赖单 Linux CPU，M2/M3 需要停用这条未同步的快速路径，并明确客体执行与映射修改的互斥条件。持有 Linux 锁时等待其他客体停止，还需确认对方能够先离开用户态并释放执行权限，再进入可能需要该锁的内核路径。

## 曾考虑的替代方案

- 在每个补丁中调用 `pthread_getspecific`：调用前需保存客体寄存器和 SIMD，并且尚未取得宿主栈；需要额外的状态保存设计。
- 占用另一个客体寄存器保存宿主状态：扩大原生指令改写范围，并影响已有闭源原生库兼容条件。
- 保留全局指针并串行进入客体：无法满足同地址空间两个线程同时执行的验收条件。
- 按线程标识维护自制索引表：新增表容量、冲突、注销与并发读取规则；当前 pthread key 已能管理线程存储。

## 验证与后续验收

1. 同一份补丁代码由两个宿主线程反复进入，实际计算时间存在重叠，TLS、通用寄存器、NEON 和返回状态分别正确。
2. 线程状态绑定失败时在执行客体前报告错误；普通指令、内存权限、信号及 CLI/GCD 回归成功。
3. Linux 同 mm 双线程、抢占与信号目标后续独立验证。该入口完成后仍需实现映射修改期间的同步，Android 包继续单核。

### 本机进展

共享入口已替换全局 `active` 参数；原 `NceState.self` 与 `nce_prepare_shared()` 已合并到现有准备函数。Linux 用户线程在自身首次进入客体前绑定状态，并在 `pthread_exit` 路径清除；普通 NCE 入口返回时清除。系统调用补丁和 TLS 快速分支保留原指令数量和 80 字节布局。

Apple M5 Ultra / macOS 27.0 (26A428) 上，`scripts/probe_nce_threads.py` 的 CLI/GCD 各四轮通过共享代码并行检查。每线程执行一百万次循环，覆盖独立 TLS、通用寄存器、32 个 NEON 寄存器、FPCR/FPSR/NZCV、定向信号和线程重建。八轮的线程 CPU 时间之和与墙钟时间比值为 1.70–1.95；这里只确认原生客体计算存在重叠，尚未测量 Android 双核性能。

`test_nce_thread_binding.py` 覆盖 key 分配失败、偏移超限、线程绑定失败、无法读取槽位、短读取、初始化值不一致和新线程槽位不一致，七项检查成功。基础 NCE 回归以及独立 NOMMU 双核内核的 CLI/GCD 各三轮均成功；iOS 公共 C/汇编源文件编译成功。完整 Android CLI/GCD/可见窗口分别通过 219/219/220 次命名检查，覆盖 Launcher、Clock、Files、数据持久化与正常退出，ext4 检查成功。原始检查与源码哈希记录在[线程入口结果](../../../../experiments/native-linux/results-macos-nce-threads.json)。

可见窗口本轮 Launcher 曾出现约 15 秒绘制耗时，随后完成首帧和应用检查。等待期间采集五秒宿主调用栈，排除显式等待后的 330 个样本中，映射占 33.94%、信号处理占 33.33%。该值描述采样时刻的调用栈，未测量优化后的加速幅度。原始采样在 `work/native-linux-nce/thread-entry-window-sample.txt`；CLI/GCD 期间与独立 SMP 验证有重叠，可见窗口期间启用了 sample，本轮耗时仅用于故障分析。

两端构建为 `0.23.0-Mac-20261011-003852` 和 `0.23.0-iOS-20261011-003841`。Mac 宿主生命周期、共享配置、Deep Link 请求、内存采样、签名执行及包内资源检查成功；IPA 大小为 485,037,322 字节，SHA-256 为 `9bb43cf1264544f85a84674ddf80a2af62811e76fbd2a2b1593360b8cae6f982`。iPhone 执行待集成版本集中验证。

### 复杂度审查

实际使用方为普通 NCE 程序、LKL 用户线程与并行回归；它们共用同一 pthread key，不保存额外的全局当前线程状态。删除分开的共享准备函数后，所有补丁由同一入口生成。key 的生命周期与已生成代码一致，运行期间释放或重建 key 会使旧代码读错槽位，因此保留进程生命周期。运行检查只发生在线程进入或退出时，系统调用和 TLS 快速分支没有增加 Mach 查询。槽位验证失败回归检查真实边界 API；移除它们可能使平台布局变化直接变成客体执行中的非法访存。

## 影响

Darwin TSD 布局属于平台实现细节，启动检查只能验证当前线程与当前系统。并行执行还需要独立处理返回入口缓存、共享动态代码、映射撤销和进程切换，线程入口成功无法单独确认这些条件。
