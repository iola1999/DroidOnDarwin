# 决策记录: 桌面启动的锁屏解除时序

状态: rejected — 等待期间重试未解决服务初始化超时

## 问题

双核完整 Android 第五轮已报告启动完成，Launcher 也显示并获得焦点，但 `NceSurface` 在原有 180 秒期限结束时仍观察到 `keyguard=true`。日志原文为 `visible desktop activity timed out: com.android.launcher3; top=ComponentInfo{com.android.launcher3/com.android.launcher3.uioverrides.QuickstepLauncher} visible=true keyguard=true`，完整原文与源码配置见[双核记录](../../proposed/architecture/2026-10-11-LKL双核用户态与映射同步.md)和[结构化结果](../../../../experiments/native-linux/results-macos-smp-core.json)的 `library_data_candidate.userspace_attempt5`。

`nce_desktop_start()` 依次唤醒屏幕、调用一次 `window dismiss-keyguard`、启动 Home，再等待桌面。窗口命令使用 `IWindowManager.dismissKeyguard(null, null)` 并立即返回；`WindowManagerService` 将请求交给窗口策略，`KeyguardViewMediator.dismiss()` 将处理加入 Handler 队列。该调用自身没有等待解锁完成。失败时 SystemUI 仍在执行 StartServices，各个组件持续输出完成记录。当前已确认锁屏状态阻止桌面就绪，尚未证明是请求在服务未就绪时丢失，还是服务自身处理过慢。

## 提案

在启动阶段的 Launcher 等待中继续观察锁屏状态；若仍锁定，通过同一 Android API 请求解除，再等待实际状态变化。沿用当前每轮等待和总期限，不修改首帧、焦点、用户解锁和应用内容检查。该行为只覆盖启动期间的 Launcher 等待，桌面就绪后结束；Android 对安全锁屏的认证处理继续由系统完成。

初始 `window dismiss-keyguard` 请求保留，处理服务已经就绪的常规启动。等待期间复用现有 IWindowManager Binder，避免重复启动 `cmd` 进程。每次请求和下一次状态查询之间保留已有等待，服务异常继续报告失败。

### 实施进度

试验中的 `NceSurface` 复用现有 IWindowManager 对象，在 Launcher 可见且仍锁屏时调用 `dismissKeyguard(null, null)`；使用原循环间隔与 180 秒期限。就绪、截图或超时状态记录请求次数，Clock/Files 不发送解除请求。双核第六轮已执行 58 次请求，原期限结束时仍锁定且桌面检查失败；退出清理成功。单核 CLI/GCD 的桌面、两个应用、持久数据与退出检查均成功，两种入口的新增请求数均为 0。该结果尚不能确定请求在服务侧的处理阶段，重复请求未解决双核故障。新增状态只有诊断用的局部计数，生命周期与原等待函数一致；单独引入重试线程或服务没有必要。

第六轮日志进一步显示 `onScreenTurningOn(): no keyguard service!`，直到桌面期限末段才完成 `KeyguardViewMediator` 的初始化；随后出现 `executing service com.android.systemui/.keyguard.KeyguardService, waited 200067ms` 的 ANR 原因。当前可确认 SystemUI/Keyguard 初始化延迟参与了失败。该轮没有读取客体 ANR 线程转储，具体耗时仍按调度与映射方向调查；重试行为不能独立解决这个延迟。

### 试验结论

现有启动代码已在系统服务注册后执行 `lock_settings set-disabled true`。等待期间重试没有解决双核初始化延迟，单核完整流程也没有使用它，因此撤回新增的 Binder 请求与计数，保留既有一次解除请求和实际状态检查。后续按双核调度与地址窗口开销继续调查，完整 Android 的默认时间片回归使用撤回后的源码。试验数据保存在 `scheduler_slice_candidate` 的 `userspace_attempt6` 与 `up_trial`。

## 曾考虑的替代方案

- 增加 180 秒检查期限：会改变已有验收条件，也无法解释请求是否已被处理，先保持期限。
- 只检查 Launcher 可见或获得焦点：当前失败已经同时满足两项，仍处于锁屏状态，因此保留锁屏与首帧检查。
- 等待固定时长后发送一次解除请求：SystemUI 启动耗时随配置变化，固定时长缺少稳定依据，使用实际状态决定后续请求。

## 验收标准

1. 复现配置下继续要求桌面实际解除锁屏、Launcher 获得焦点并完成首帧；核对启动期限、请求次数和失败时的最后状态。
2. 单核与双核分别检查，CLI/GCD 覆盖真实桌面、Clock/Files、持久数据和正常退出；局部成功不表示双核性能已满足交付条件。
3. 取消、辅助程序失败与清理回归保持成功。就绪后的正常用户锁屏行为不受启动等待影响。

## 风险

若 SystemUI 处理速度仍超过总期限，重发解除请求也可能失败。重复请求可能增加 Binder 与 Handler 工作量，应沿用等待间隔并记录实际次数。当前先修正持续确认启动状态的行为，调度和映射成本另按双核记录验证。
