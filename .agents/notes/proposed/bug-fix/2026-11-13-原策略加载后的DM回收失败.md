# 决策记录: 原策略加载后的 DM 回收失败

状态: proposed

## 问题

[原 SDK first-stage](../architecture/2026-11-13-SDK36原始first-stage启动.md)的 16 KiB raw v7 已通过 CLI、GCD lifecycle。首个 original CLI 使用原 `/init`，完成 metadata 与五个逻辑分区挂载、SwitchRoot、原 ramdisk init 删除及动态 init 执行，`first_stage.completed=True`。namespace PID1 的实际 wait 完成后，宿主 sync 返回 0，DM REMOVE_ALL 与 LIST_DEVICES 均返回 -13（EACCES）。原清理函数保留首个错误，控制 fd 4 关闭成功，`empty=False`；C 运行器返回 1，Python 验收失败。原 GCD original、两项 recovery、4 KiB core 与两页 iOS 编译尚未执行。

原 stdout 的第 64283、64284 行分别保存两个 ioctl 的失败，第 64286 行保存最终清理结果。`stock-init-first-stage-dm.h` 保留 REMOVE_ALL 的首个错误，即使失败仍关闭控制 fd 并将保存的 fd 重置为 -1；LIST_DEVICES 失败后，`empty` 保持初值，实际 DM 设备数量尚未确认。`stock-init-runner.h` 的 original 返回条件包含 DM 清理结果；原 observation 的 status 1、`deadline_stop=False` 按现有 original 状态范围保留。

原系统此前已加载 SELinux policy。普通 ioctl 先经过 `security_file_ioctl()`，DM 的 `ctl_ioctl()` 另检查 CAP_SYS_ADMIN；两处均可能返回 EACCES，当前日志尚未区分具体权限检查。临时控制节点在原 policy 加载前创建，父任务持有 fd，节点已删除。该 fd 的有效性、policy 加载后的权限和宿主生命周期职责需要分别核对。

原 v7 summary 的 SHA-256 为 `5ece5bf57b5a4cc0b3e3acdfae64c60bb98907f90dd1b18bf60a2714588998b0`，CLI original stdout 的 SHA-256 为 `cb8fed0177931c48fb8d02b37c3b8f3ce40d131a329e2aef012edd4ed29ebc9a`。阶段记录的 SHA-256 为 `c17978fb8cd2df3ccff5b43546518caeb4711a7560bf6db39f063c9bc293723a`，40 项来源与 scope 保持，进程组为空且没有发送清理信号。166/166 个执行上下文回收成功，halt、宿主磁盘关闭和 kernel release 成功；DM 清理检查继续失败。

候选 data、metadata 在两个 lifecycle 中保持。original 后两盘摘要按实际写入改变，最终均 clean，UUID、容量、文件系统块大小及 metadata GPT 范围保持；data 的 reserved_gid 由 0 改为 1065。后续沿用这两份候选的实际状态，不恢复到首次摘要。

原 vold 的 default-key target 创建返回 EINVAL，随后 `/data` 的原挂载与用户初始化失败，原 init 请求 recovery 并执行重启。该问题继续由[原 vold 与 default-key](../architecture/2026-11-13-SDK36原始vold与default-key.md)处理；本记录负责实际 DM 回收失败，保持 first-stage 与完整 boot 的现有验收范围。

## 提案

新增六参数全零的宿主 syscall248，调用者必须设置 `TIF_HOST_THREAD` 且 `nce_state` 为空；其他调用者返回 ENOSYS，非零参数返回 EINVAL。共享 Linux mutex 覆盖 `nce_launch()` 的 `kernel_clone()` 与宿主清理的扫描至结束区间。扫描全部线程，发现 `nce_state`，或发现同时未设置 HOST 与 PF_KTHREAD 的用户任务，返回 EBUSY。初始 LKL PID1 已在 `syscalls_init()` 设置 HOST，无需按 PID 数字增加例外。扫描使用的 RCU/tasklist 读锁在可睡眠清理前释放。现有任务标志和同一 mutex 已覆盖发布至 `user_start()` 的窗口，不增加 pending 计数或任务注册表。

专用 DM 内部函数复用 `dm_hash_remove_all(true, false, false)`，保持打开设备的保护与同步销毁。随后在 `_hash_lock` 下检查 name、uuid 两棵树；两者均为空返回 0，仍有注册设备返回 EBUSY。调用沿用普通 REMOVE_ALL 完成后额外的一次 `dm_issue_global_event()`，部分删除后返回 busy 也发送该事件；单个设备已有的事件回调继续保留。仅 DM built-in 配置可达，其他配置明确返回 ENOSYS。普通 ioctl 与原 policy 保持。

C 运行器仍在实际 wait/reaped、sync 后执行普通 REMOVE_ALL、LIST_DEVICES 并保存原返回值，再执行 syscall248、保存独立 `stock_init_first_stage_dm_host_cleanup` 行，最后关闭 control fd、halt 与释放资源。新输入登记 `host_dm_cleanup_contract=1`；旧输入保持原契约。新契约要求宿主清理返回 0 并确认空树；当前验收接收普通 ioctl 的成功空列表，或两项均返回 EACCES 且原 header 保持的实际失败形态。其他错误、混合结果、宿主拒绝与关闭失败继续使阶段失败。

终末调用方必须先停止新增与排队 launch，并串行执行宿主 DM 操作；入口解锁后仍允许新 launch。当前 raw 运行器在唯一 namespace 的 wait/reaped 与 sync 后执行清理，随后读取日志并 halt，同盘 recovery 启动新的内核实例。

宿主边界在原 first-stage 运行器内验证：六个单独非零参数均返回 EINVAL；已 launch 的 namespace 返回 EBUSY。客体 PID1、fork 子任务与普通 NCE 任务请求 syscall248 均返回 ENOSYS，guest printf 按[客体 stdout 回读顺序](2026-11-13-first-stage客体stdout回读顺序.md)验收。宿主 fixture 另验证尚未设置 NCE 状态的已发布用户任务、打开 DM 设备、共享 mutex 与事件行为。真实阶段使用新内核来源和独立输出，旧 16 KiB v4 core 不复用。翻译内核 build.json 同时登记实际生成的 `nce_process.c`、`syscalls.c` 与 `dm-ioctl.c` 摘要，供新入口与分派的来源核对。

## 曾考虑的替代方案

- 修改原 policy 或将其设为 permissive：会改变原系统输入和用户态权限检查，本阶段保持原策略。
- 将 EACCES 作为成功，或省略空列表检查：无法确认 DM 设备已经清理，原验收条件继续保留。
- 仅依赖后续 kernel halt：当前阶段要求先确认 DM 清理，再关闭磁盘与释放映射，保留原顺序。
- 只增加等待时间或提前结束原 init：当前两个 ioctl 的实际权限失败仍需处理，原 first-stage 执行条件保持。

## 验收标准

1. 原 v7 失败、stdout、来源和候选 before/after 保持，修复后的运行使用新检查点与独立输出。
2. 原权限失败继续保存，宿主清理完成 REMOVE_ALL，并核对 name、uuid 两棵注册树均为空；清理失败继续返回失败。
3. 宿主入口若有新增，验证调用者、操作、参数、仍有客体任务及 guest 请求的边界；原普通 ioctl 与 policy 语义保持。
4. 两页 CLI/GCD 的 original 均要求 `observation_validated=True` 与 `first_stage.completed=True`，同盘 recovery、回收和 iOS runtime/实际 init 编译完成。完整 boot、原 vold 加密与设备资源继续分别验证。
5. 按 reclaim-code-entropy 核对资源所有权、必要状态、真实使用方、替代实现与移除影响；技术文字按 humanizer-zh 复核。

### 复杂度审查

新增的长期状态只有 `nce_launch_lock`，使用方是 `nce_launch()` 与 `nce_host_dm_cleanup()`。删除该 mutex 或只锁扫描会允许任务发布与 DM 删除并发；仅检查 leader 或 `nce_state` 会遗漏非 leader 与尚未设置 NCE 状态的用户线程。现有线程标志承担任务判断，DM 的两棵注册树承担空列表判断，当前调用方只需要固定清理结果。pending 计数、任务注册表和通用 ioctl 参数会增加状态与接口维护，现有路径无需增加这些对象。

原 DM 删除函数返回 void，不能单独报告打开设备遗留；新增 helper 因此保留同步删除，再检查两棵树并返回 EBUSY。去掉其中一棵树或额外 global 事件会改变空列表合同或原 REMOVE_ALL 通知。C 运行器保留普通失败与宿主结果，Python 在日志输入边界核对两者，二者各自承担执行和验收职责。移除这些检查会失去实际未回收设备、混合普通返回及关闭失败的阶段拒绝条件；宿主回归与后续真实 raw 分别检查这些边界。

## 风险

DM 设备属于当前内核实例，清理时必须确认客体任务与文件系统引用的生命周期。宿主专用请求的范围不能扩大到普通 guest ioctl；LIST_DEVICES 的实际结果仍需核对。原系统已进入后续服务和加密流程，完整 boot 还有独立失败，不能据 first-stage 局部完成得出完整启动结论。
