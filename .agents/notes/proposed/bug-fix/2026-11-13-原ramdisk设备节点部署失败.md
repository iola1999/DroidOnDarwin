# 决策记录: 原 ramdisk 设备节点部署失败

状态: proposed

## 问题

[SDK36 原始 first-stage](../architecture/2026-11-13-SDK36原始first-stage启动.md)的 16 KiB v4 core 与 TCPMSS 核对成功后，完整 raw 命令在第一个 CLI lifecycle 的 ramdisk 部署期间失败。运行器已编译并启动 Linux，客体进程返回 -6；stderr 保存 `runner:127: call(33, make) == 0`。原 `/init` 尚未部署完成或执行，后续 sysfs 缺少观察属于部署中止后的验收结果。

实际失败位置是 `stock-init-ramdisk.h:127` 的字符节点 `mknodat` 调用，旧代码没有记录条目路径和原返回值。固定 archive 的字符节点依次为 `/dev/null`、`/dev/console`、`/dev/urandom`。当前内核关闭 `BLK_DEV_INITRD` 与 `DEVTMPFS`，已消费的 Linux 6.12 `init/noinitramfs.c:27` 在启动中创建 `/dev/console`，设备号为 5:1。原 SDK 的同名节点也是 5:1；是否为实际失败条目及是否返回 EEXIST，需要新日志确认。

原 summary 的 SHA-256 为 `d6dda29d30426bd150d27f759cf3af0b1260006ad48b853035d544c2b4cf1dc8`，failure 的 SHA-256 为 `710698c09403f4a512585ac4b6739f96acef4dbd76aba28839714b7a5827fa3b`，两份位于 CASE 的 `work/native-linux-nce/sdk-first-stage-init-16k-v4/`。两个候选盘的 before/after 全字段相同且 clean，阶段 25 项来源保持，进程组为空且没有清理信号。原失败与首次运行器生成失败分别保留。

## 提案

先记录每个 `mknodat` 的条目、路径、设备号与实际返回，继续要求创建返回 0，通过新的独立输出确认第一失败。诊断使用已成功且来源保持的 v4 core；该 core 的生成入口未消费原 ramdisk 部署头文件，当前只修改 raw 使用的声明。

确认同名字符设备返回 EEXIST 后，再在原部署路径处理已有节点。处理范围限于实际相同的字符设备：使用不跟随符号链接的 statx 核对类型、设备号与链接数，匹配后保留 inode 并恢复原归档的 mode、uid/gid 和 mtime。其余返回或节点差异继续拒绝。部署结束的原 29 项内容与属性核对继续保留；原 ramdisk、fstab、内核与候选盘保持现有来源。

## 曾考虑的替代方案

- 直接接受 EEXIST：当前日志没有原返回，现有节点也可能与归档的类型或设备号不同，需要先记录，再检查实际节点。
- 删除同名节点后重新创建：Linux 启动已打开 console，保留匹配 inode 可以保持该节点的现有引用；错误节点继续由本轮检查拒绝。
- 为设备部署增加通用文件恢复框架：当前只有固定三个字符节点，局部调用和身份检查足以描述需要的行为。

## 验收标准

1. 新日志保存原 `mknodat` 的实际路径与返回；原 v4 stdout、stderr、failure、summary 和候选前后状态保持。
2. 仅在实际 EEXIST 且类型、设备号、链接数匹配后复用节点；错误返回、statx 失败、符号链接、普通文件和错误设备号被拒绝，属性恢复尚未执行。
3. C 回归调用实际部署函数，覆盖新建、匹配已有节点和上述失败边界。实际 raw 的部署记录仍按原 29 项内容、属性、设备号和 stream 顺序验收。
4. 新检查点的 raw CLI/GCD、原 `/init`、同盘恢复与 iOS 实际 runner 编译按原条件继续，首次失败单独保留；完整 boot 与设备运行仍待验证。
5. 按 reclaim-code-entropy 检查局部函数、调用方与临时状态，按 humanizer-zh 复核文字。

## 风险

当前日志只能定位调用，尚不能确认具体条目及返回值。新增节点处理必须在恢复属性前检查实际身份，不能仅依赖路径相同。该阶段仍未执行原 `/init`，设备发现、挂载、停止与恢复继续待验收。
