# 决策记录: 原 ramdisk 设备节点部署失败

状态: proposed

## 问题

[SDK36 原始 first-stage](../architecture/2026-11-13-SDK36原始first-stage启动.md)的 16 KiB v4 core 与 TCPMSS 核对成功后，完整 raw 命令在第一个 CLI lifecycle 的 ramdisk 部署期间失败。运行器已编译并启动 Linux，宿主运行器 abort，subprocess returncode 为 -6；stderr 保存 `runner:127: call(33, make) == 0`。原 `/init` 尚未部署完成或执行，后续 sysfs 缺少观察属于部署中止后的验收结果。

实际失败位置是 `stock-init-ramdisk.h:127` 的字符节点 `mknodat` 调用，旧代码没有记录条目路径和原返回值。固定 archive 的字符节点依次为 `/dev/null`、`/dev/console`、`/dev/urandom`。当前内核关闭 `BLK_DEV_INITRD` 与 `DEVTMPFS`，已消费的 Linux 6.12 `init/noinitramfs.c:27` 在启动中创建 `/dev/console`，设备号为 5:1。原 SDK 的同名节点也是 5:1；是否为实际失败条目及是否返回 EEXIST，需要新日志确认。

原 summary 的 SHA-256 为 `d6dda29d30426bd150d27f759cf3af0b1260006ad48b853035d544c2b4cf1dc8`，failure 的 SHA-256 为 `710698c09403f4a512585ac4b6739f96acef4dbd76aba28839714b7a5827fa3b`，两份位于大小写敏感工作树的 `work/native-linux-nce/sdk-first-stage-init-16k-v4/`。两个候选盘的 before/after 全字段相同且 clean，阶段 25 项来源保持，进程组为空且没有清理信号。原失败与首次运行器生成失败分别保留。

## 提案

诊断已记录每个 `mknodat` 的条目、路径、设备号与实际返回，继续要求创建返回 0，通过新的独立输出确认第一失败。诊断复用已成功的 v4 core，140 项实际输入摘要保持；该报告未消费本轮修改的 raw 部署头文件。

v5 确认同名 console 返回 EEXIST 后，在原部署路径实现已有节点检查。处理范围限于实际相同的字符设备：使用不跟随符号链接的 statx 核对类型、设备号与链接数，匹配后保留 inode 并恢复原归档的 mode、uid/gid 和 mtime。其余返回或节点差异继续拒绝。部署结束的原 29 项内容与属性核对继续保留；原 ramdisk、fstab、内核与候选盘保持现有来源。宿主 C 回归与实际 raw/iOS 验收正在推进。

### v5 实际诊断

诊断检查点为 `556eb081c1911b9bd2d407f030e4520202686c3a`，部署头文件的 SHA-256 为 `115e2391c86994e9a095e27cff754ca0d9f51a60ad21bb1a5c638cab18c2ab00`。`commands-v3.json` 的 SHA-256 为 `b4ff5910a8af12e13b1342046598733e23d7c1478855e99b396c79a8ab1935cc`；新 raw 输出使用 v5，core 报告、内核与四个候选路径保持原值。

实际条目 2 的 `/dev/null`（1:3）创建返回 0，条目 3 的 `/dev/console`（5:1）返回 -17，随后原断言终止宿主运行器。v5 summary 的 SHA-256 为 `beb88c49125fce3015016db1fb89c6add38d431df05ea4416081a5fbac5149aa`，failure 的 SHA-256 为 `690f860cf1091427abdacbdb242a80143eecec77d0482bc22242ea22fdd3f2a7`。候选 before/after 全字段相同且 clean，原 `/init` 与其余五个入口仍未执行。该结果确认具体冲突路径和返回；修复后的实际 statx、属性恢复及回收按新报告核对。

### 宿主回归

真实 C 回归直接包含生产头文件及 v5 生成的 `sdk-ramdisk.h`，Linux syscall 由 fixture 模拟。12 项案例全部成功：三个原字符节点的新建或复用完成属性和设备号核对，已有 console 从 0600 恢复为原归档的 0644，inode 保持；其余九项覆盖创建错误、statx 错误、TYPE/NLINK mask 缺失、符号链接、普通文件及 major/minor/nlink 冲突，均在属性恢复前拒绝。宿主回归没有运行原 `/init`，实际 raw/iOS 验收继续待完成。

结果位于 SDK 工作树的 `work/sdk-first-stage-ramdisk-device-review-v1/host-tests-v1/result.json`，SHA-256 为 `d79bf4cd5015622c0782b23dfc2f2785104ef0563dd84b91bee7474a68d017b8`。生产头文件的 SHA-256 为 `a7a6c0e4897fbbd9e6811ce71acf741e0dba88920da504cb74cd4772a732be79`；测试脚本、C fixture、生产头和原 ramdisk 头的执行前后摘要保持，格式与语法检查成功。测试二进制已删除，源码、输出及删除清单保留。 增量复杂度审阅未发现阻塞项：新增函数仅由原 setup 调用，复用已有 statx ABI 和归档条目，检查状态限于单个调用。最终摘要的 SHA-256 为 `b69cb5b3b1d6829f44744b4d77957c5e8582c919fa4f340f24b133d5e1948395`，同目录的 `summary.json` 保存测试、审阅和清理记录的完整摘要。

### v6 实际部署

检查点 `9a294d76cbaba3fb65a28fb1599d0daa275f473f` 的 16 KiB raw v6 复用输入保持的 v4 core。原 console 创建返回 -17，实际 statx 返回 0，mode 为 0600 的字符设备、设备号为 5:1、链接数为 1；匹配后恢复原归档属性，29 项部署检查全部输出成功。sysfs 设备、停止、DM 回收、三项上下文回收、磁盘关闭与内核释放完成，运行器返回 0，两盘 before/after 全字段相同且 clean。

生产验收仍失败，新增设备创建诊断被纳入结束记录列表，原因和后续修复见[诊断行结束记录筛选](2026-11-13-ramdisk诊断行的结束记录筛选.md)。原 v6 summary 的 SHA-256 为 `b9c0dcb73b292a91b81b233970b8d6dd29160bd6f8fccbcf90be70925c1d7a59`，原 `/init`、其余入口和 iOS 编译继续待验证。

## 曾考虑的替代方案

- 直接接受 EEXIST：路径相同的现有节点可能与归档的类型或设备号不同，实际节点必须先检查。
- 删除同名节点后重新创建：Linux 启动会尝试打开 console，成功后为标准输入、输出和错误保存文件引用；保留匹配 inode 可以保持这些引用。错误节点继续由本轮检查拒绝。
- 为设备部署增加通用文件恢复框架：当前只有固定三个字符节点，局部调用和身份检查足以描述需要的行为。

## 验收标准

1. 新日志保存原 `mknodat` 的实际路径与返回；原 v4 stdout、stderr、failure、summary 和候选前后状态保持。
2. 仅在实际 EEXIST 且类型、设备号、链接数匹配后复用节点；错误返回、statx 失败、符号链接、普通文件和错误设备号被拒绝，属性恢复尚未执行。
3. C 回归调用实际部署函数，覆盖新建、匹配已有节点和上述失败边界。实际 raw 的部署记录仍按原 29 项内容、属性、设备号和 stream 顺序验收。
4. 新检查点的 raw CLI/GCD、原 `/init`、同盘恢复与 iOS 实际 runner 编译按原条件继续，首次失败单独保留；完整 boot 与设备运行仍待验证。
5. 按 reclaim-code-entropy 检查局部函数、调用方与临时状态，按 humanizer-zh 复核文字。

## 风险

v6 已核对匹配 console 的实际身份与原属性恢复。新增节点处理必须在恢复属性前检查实际身份，不能仅依赖路径相同。该阶段仍未执行原 `/init`，设备发现、挂载、停止与恢复继续待验收。
