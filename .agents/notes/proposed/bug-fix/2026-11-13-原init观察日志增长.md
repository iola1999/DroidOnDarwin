# 决策记录: 原 init 观察日志增长

状态: proposed

## 问题

无加密候选的首轮 30 秒观察完成原 first-stage、直接 `/data` 挂载和原 vold 用户初始化。第二轮将 original 观察延长至 180 秒，CLI/GCD 的 JSONL 分别增长到 5,354,044,354 和 5,226,347,214 bytes，报告增长到 13,481,566,497 bytes。`stock_init_trace_result()` 逐次打印全部失败调用；`read_observations()` 随后加载全部行，报告又保存这些行和解码后的客体日志。观察时限结束后，日志解析和报告生成仍持续消耗资源。

根会话已请求停止第二轮，wrapper 最终失败，probe 退出码为 -15，总范围为 692.709333 秒。停止后的 `summary.json` 移为 `summary-log-overflow.json`，停止记录位于 `work/cleanup-2026-11-13/sdk-plain-init-v2-stop-{request,result}.json`，已确认本轮进程组为空。wrapper 只保存两个 lifecycle 与 CLI original 的成功结果，recovery 没有完成，完整 boot 仍待验证。停止后只读检查发现 data 有 journal recovery 和 orphan 标记，metadata 为 clean，结果见 `work/sdk-plain-validation-v1/disks-after-init-v2.json`。随后对本轮实验 data 盘执行离线 `e2fsck -p` 成功，身份、容量和保留块设置保持，data 恢复为 clean，结果见 `work/sdk-plain-validation-v1/data-recovery-after-init-v2/result.json`。该恢复只覆盖宿主离线文件系统检查，后续仍需实际 Android 同盘 recovery。

各 JSONL 末尾只读取 1 MiB。CLI 的 10,204 条 syscall 中有 10,161 条为 `msync`（227）返回 -12；GCD 的 10,199 条中有 10,156 条相同。参数为 16,384-byte 页、flags=0，地址逐页递增，期间出现请求范围回跳。原 ART 的 `libartbase/base/mem_map.cc` 使用同一调用探测未映射页，Linux 对未映射范围返回 ENOMEM。附近的私有可写匿名 `mmap` 请求为 1,074,003,968 bytes，当前客体 RAM 为 1,073,741,824 bytes。提交限制与实际 sysctl、swap 和原库调用方继续调查，`msync` 返回值本身不能确认物理内存耗尽。

## 提案

首轮修复保留失败 `msync` 的前 64 个样本，后续在计数为 2 的幂次时记录，结束后保存失败调用数、已记录数、省略数和最后一组参数。这些计数是单个宿主入口内全部客体进程的合计，覆盖所有失败返回值、页长和 flags；成功调用沿用原来的省略行为。采样索引明确标出未记录范围，省略段可能包含参数变化。该轮保留其他失败系统调用、客体写入和读取等记录的现有行为。汇总在执行上下文已停止后输出，校验器检查样本索引、计数、参数类型及汇总顺序。

无加密观察器每次最多等待 0.1 秒，并检查 stdout/stderr 文件大小。任一文件超过 32 MiB 后记录日志阈值失败并继续原有进程组停止与回收。32 MiB 是停止阈值；检查间隔、识别超限后的进程查询和停止宽限期间，文件字节仍可能增加。解析器在读取前拒绝超过 32 MiB 的日志，并限制单行 64 KiB、JSON 记录 200,000 条，解析错误与大小错误都保留原日志路径、摘要、退出与停止结果。相同限制用于 stderr 读取，解析不得静默截断。

固定 `RLIMIT_FSIZE` 会同时限制候选盘的普通文件写入，因此采用输出文件观察。日志处理修复与候选盘恢复后，使用新目录重跑原 init，先读回默认内存提交配置，再验证[提前设置内存提交策略](2026-11-13-原ART启动的内存提交配置.md)。超出 50 MB 的停止日志按清单压缩，保留来源、失败和有界样本。

### 提前配置后的日志阈值失败

默认 45 秒的 `sdk-plain-init-16k-v3` 六个入口、来源摘要、宿主回收和同盘恢复成功。随后 `sdk-plain-init-16k-v4` 的两个 lifecycle 成功，CLI original 在 stdout 为 33,572,987 bytes 后触发限额，宿主实际退出码 -15，SIGTERM 清理后进程组为空。wrapper 为失败，总范围 124.455411 秒，GCD original 和 recovery 未运行。限额及退出结果见 `work/sdk-plain-validation-v1/init-16k-v4.json` 和该运行目录的 `failure.json`。

停止后 data 有 journal recovery 和 orphan 标记，metadata 有 journal recovery 标记；只读结果见 `work/sdk-plain-validation-v1/disks-after-init-v4.json`。随后复用 v3 的 CLI/GCD 二进制运行原 init 的 mounted-partition lifecycle，两个入口均通过 namespace、generation、盘身份和回收检查，两盘恢复为 clean，来源摘要保持。结果见 `work/native-linux-nce/sdk-plain-recovery-after-v4-v1/result.json`。该检查覆盖原 init 的 lifecycle 与 Linux journal 恢复，完整 Android 重启继续验收。

有界调查读取首 8 MiB 和末 1 MiB，结果见 `work/sdk-plain-validation-v1/log-limit-v4-samples.json`。首段 `component_vm` 为 21,520 条，末段为 2,720 条；末段另有 940 条 `prctl` 失败和 173 条未带「<」前缀的客体写入，包含 OAT/ELF 文件头。具体写入进程和文件路径缺少关联，调查保留这个限制。

现有原 init 校验依赖 block、DM 和 exec 记录，未要求全部小范围 VM 成功记录。v5 生成副本仅保留 mmap/mprotect/munmap 的全部失败，以及至少 1 GiB、可写、私有、匿名 mmap 的成功记录；该次保留 Linux/core 原源码和写入、读取记录。MAP_PRIVATE 按 Linux MAP_TYPE 的低四位判断，避免接收 MAP_SHARED_VALIDATE。该过滤在首段减少 21,518 条、2,379,119 bytes，在末段减少 2,719 条、307,098 bytes。部署清单记录实际跟踪范围，未增加采样计数或内核接口。

v5 的两个 lifecycle 成功，CLI original 在 stdout 为 33,652,812 bytes 后再次触发限额，wrapper 范围 131.965633 秒，宿主组为空且来源摘要保持。该次末 1 MiB 的 259 条 `stock_init_write` 占 811,541 bytes，其中 187 条每次捕获 2048 bytes，全部不带「<」前缀；记录含 OAT/ELF 和 ARM64 指令内容。调查见 `work/sdk-plain-validation-v1/log-limit-v5-tail.json`。随后 mounted-partition lifecycle 的 CLI/GCD 再次通过，两盘恢复为 clean，结果见 `work/native-linux-nce/sdk-plain-recovery-after-v5-v1/result.json`。

现有 `guest_write_text` 只提取以「<」开头的客体写入，二进制编译产物没有该字段的消费方。无加密观察的两个编译入口加入 `NCE_STOCK_INIT_LOG_TEXT_ONLY`，只输出具备上述前缀的 write/writev 向量，2048-byte 捕获上限、向量编号、fd 和结果字段保持。其余 profile 继续使用原完整写入跟踪，成功 read、失败调用、首阶段和回收检查继续保留。该调整减少诊断输出，后续原 ART 和完整 boot 仍需实际运行。

### BPF 接入后的泛用调用记录

2026-11-14 的 `sdk-plain-init-16k-v12` 使用新的 BPF JIT core，CLI original 在 stdout 为 33,704,477 bytes 后触发 32 MiB 停止阈值。原观察器记录实际退出 -15、SIGTERM 清理、进程组为空；失败、输入摘要和盘状态保存在该目录的 `failure.json`。本次只读流式检查 242,346 条完整 JSON：205,615 条泛用 `stock_init_syscall` 占 27,329,643 bytes；其中 read（63）返回 4096 的记录为 91,881 条，prctl（167）返回 -22 的记录为 26,172 条，close（57）返回 -9 的记录为 13,731 条。专用 block、security 和 write 分别为 20,337、12,827 和 3,018 条。末尾原 guest 日志已记录 audioserver 和 surfaceflinger 启动，完整 boot 尚未确认。

泛用诊断按 syscall 和成功/失败类别分别保留前 64 个样本，随后仅在计数为 2 的幂次记录，结束后保存各类计数、记录数、省略数和末次参数。成功类别仍只包含既有 read 和 reboot 记录条件，失败类别覆盖原来的全部失败。分开统计成功与失败可保留 read 首次失败的样本。失败 msync 继续使用已有摘要格式；其他调用新增可校验的采样索引与汇总。ARM64 的 0..511 使用固定槽，范围外编号合并计数并保留每个样本和末次的实际 syscall 编号，避免未知编号造成无限数量的状态。

修改限定在泛用结果跟踪、对应格式校验和实际 C 回归；first-stage、设备、DM、security、guest write 与系统服务观察记录继续按现有条件输出。原 init 的 runner/execution 副本需按最终来源重新生成，复用的 BPF core 继续按原输入摘要严格检查，v12 原失败继续保留；盘恢复由主会话负责。

复杂度审查确认 `stock_init_trace_result()` 是现有泛用记录入口，`stock_init_trace_summary()` 在执行上下文停止后读取同一份计数；Python 的原 init 校验器和回归脚本读取其 JSON。固定表复用原 msync 采样状态的字段，并用现有 stdout 流锁同步更新和整行输出，无需动态分配、额外线程或新的配置项。去掉成功/失败分类会让 read 的首次失败受先前成功调用数影响；去掉末次字段会失去未采样末次调用的参数；独立保留 msync 状态会重复维护相同采样逻辑。历史 msync 汇总格式及未带索引的旧日志继续由对应校验器处理。省略段中参数和失败码的每次变化仍缺少记录。

## 曾考虑的替代方案

- 关闭所有失败调用记录：会失去首次失败的地址、参数和返回值，保留有界样本与结束计数。
- 增加观察时间或日志空间：实际低地址扫描仍持续，解析与报告仍随调用数增长。
- 给整个客体宿主进程设置文件大小限制：限制范围包含 data/metadata 盘的写入，采用 stdout/stderr 阈值检查。
- 把全部原日志存入报告：重复保存详细行和解码文本增加资源消耗；本轮先限制输入与采样，报告格式保持现有使用方。

## 验收标准

1. 真实重复失败 `msync` fixture 的日志数量受限，结束计数与实际失败调用一致，首个和最后参数以及采样索引可核对；并发 JSON 完整性检查继续成功。
2. 超大文件在加载前失败，单行和记录数量边界分别检查；日志限制触发后，真实宿主父子进程停止且 leader 已回收，SIGTERM 中断与清理期间中断回归继续成功。
3. 首次失败保留；新的原 init 运行分别记录首阶段、完整 boot、停止与同盘 recovery，候选盘的实际状态与来源摘要可核对。
4. 记录必要状态、实际使用方和移除影响，按 reclaim-code-entropy 审阅；中文技术文字按 humanizer-zh 审阅。iOS 编译使用最终实际源码，设备验证继续待确认。

## 风险

日志采样会减少逐次调用参数，结束计数与采样索引说明缺失范围。进程在汇总前异常退出会缺少最终计数，报告必须保留该边界。日志阈值触发后，候选盘需要停止后检查及恢复，不能继续宣称本轮持久化成功。ART 的匿名映射失败仍需独立定位。
