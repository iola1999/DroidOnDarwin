# 决策记录: 原 SDK 的 logd 审计初始化

状态: proposed

## 问题

原 SDK36 logd 在 v13 及后续图形诊断中输出 `SocketListener: Failed to start unbound listener`，已有运行位置见[SurfaceFlinger 启动退出记录](2026-11-14-原SDK的SurfaceFlinger启动退出.md)。已结束的原 CLI/GCD 采集确认匹配的 netlink ACK error=-1、audit FD close 返回 0，以及同一失败对象的两次析构 close，结果见[原 init v2 六入口独立解析](../../../../../../../sdk-plain-validation-v1/logd-original-capture-runtime-v2/report.json)。两次析构参数均为 FD0，返回值依次为 0、-9；其与系统服务失败的关系继续待确认。

[静态核对与最小方案](../../../../../../../sdk-plain-validation-v1/logd-audit-namespace-plan-v1/plan.json)确认，冻结 BPF JIT 内核的 AUDIT_GET/AUDIT_SET 要求初始 PID namespace，通过后才检查 socket 创建者和当前发送者的 CAP_AUDIT_CONTROL；失败经 netlink_ack 返回 EPERM。对应 ELF 指令与 lkl-image.bin 的实际字节相同。当前配置启用 PID_NS 和 AUDIT，关闭 USER_NS。原 init 的 launch 参数为 1，使用 CLONE_NEWPID。

实际 SDK logd/libsysutils/libc 的构造路径没有初始化 mCtrlPipe；unbound 失败先于 pipe2，析构仅检查第一项后可能调用两次 close。本轮 CLI/GCD 各自关联的对象中 mSocketName=0、mSock=-1、mCtrlPipe=[0,0]；第一次 close 移除 FD0，第二次返回 EBADF。第一次 close 前的资源名称为 `/dev/null`，其他线程仍可在查询与 close 之间替换 FD。此前 FD25 的 SO_PEERCRED ENOTSOCK 发生在该析构之前，单独保留为未确认。

## 提案

先在[独立 fixture 目录](../../../../../../../sdk-plain-validation-v1/logd-audit-namespace-fixture-v1/)准备单进程 AUDIT_GET+ACK 检查，复用 PLAIN 已验证的 144 项 core 清单、113 项 kernel 清单、16 KiB musl 编译参数及原 CLI/GCD 入口。冻结内核和原 init/策略/rc 保持原输入；隔离 runner 的 launch 参数分别为 0、1，共 initial/private × CLI/GCD 四项。宿主保存真实初始 PID namespace 标识，fixture 比较自身 namespace，并记录开 socket 和发送时的 CAP_AUDIT_CONTROL、请求头、sender、ACK 与状态 payload。

本阶段只执行 prepare、编译和本机消息解析边界检查。guest 运行与原 init printk 诊断分阶段安排，当前不启动 guest。运行 wrapper 复用现有 process_observer，保留超时、中断和失败；独立 host 副本记录 LKL 线程创建、结束、成功 join 和 detach 数量，原 halt、cleanup、timer join、翻译上下文和执行池回收继续检查。

[prepare 报告](../../../../../../../sdk-plain-validation-v1/logd-audit-namespace-fixture-v1/prepare.json)已完成 guest 静态 PIE 编译和 initial/private × CLI/GCD 四个宿主编译，前后 core 144 项、kernel 113 项及冻结方案的 24 项输入全部匹配。消息解析的 35 个本机场景通过普通构建及 ASan/UBSan 检查；wrapper 的 19 个本机边界检查和 Python 语法检查通过。wrapper 逐包核对 rawhex、请求与 ACK 头及 44-byte 状态 payload，v1 实际运行结果见下文。

v1 四项实际运行均失败。AUDIT_GET、CAP30、实际 namespace、close、wait、halt 与进程组回收符合预期；initial 的 LKL created/completed/joined 为 28/28/27，private 为 27/27/26。四份原始失败报告保留在 v1 的 `runs/`。`translation_linux_cleanup` 的 timer 使用直接 pthread_create/pthread_join，其计数范围与 host_ops 分开，移动 host_ops 计数检查无法确认缺少的 join。

[v2 线程检查](../../../../../../../sdk-plain-validation-v1/logd-audit-namespace-fixture-v2/kernel-lifecycle-check.json)核对了冻结 ELF 的八个函数及镜像对应字节。PID1 的 `thread_bootstrap` 调用 `kernel_init`，`lkl_run_init` 经 `syscalls_init` 设置 `TIF_HOST_THREAD`，随后通知启动 semaphore 并退出 native pthread。`lkl_start_kernel` 等待后把该 thread_info.tid 替换为宿主调用方句柄；普通 `kill_thread` 跳过该标志。原 swapper 的 `lkl_run_kernel` pthread 继续参与调度并由 halt 最后 join，两类句柄分别检查。

v2 在独立目录记录最多 64 个 host_ops pthread 的完整句柄、函数来源、创建/开始/结束/join 序号和返回值。fixture 在 start 返回后只对唯一 `kernel_init` 候选做一次诊断 join，检查其真实返回值，再按原 halt 和 timer/translation cleanup 顺序核对全部线程。普通 return、pthread_exit、join 错误和重复/未知句柄由本机检查覆盖。实际句柄确认后，正式启动入口的候选修正在启动 semaphore 等待后保留并 join PID1 原句柄，再替换 tid/CPU owner；生产修复及启动失败分支继续另行验证。

[v2 prepare 报告](../../../../../../../sdk-plain-validation-v1/logd-audit-namespace-fixture-v2/prepare.json)已完成 guest 与四个宿主编译。35 个消息边界、11 个真实 pthread 边界及其 ASan/UBSan、30 个 wrapper 边界检查通过。core144/kernel113/冻结方案24项和v1的29项文件前后匹配。首次编译失败来自派生 linux-execution.c 引用同名 interaction-profile.h 的搜索顺序，独立命令改为优先查找原 translation 头文件；原失败保留。

v2 四项已顺序实际运行。CLI initial/private 通过，created/completed/joined 分别为 28/28/28 和 27/27/27。GCD initial/private 的宿主退出码为 0、进程组为空，ACK、逐线程 join、timer 和 cleanup 均通过；wrapper 额外要求入口前的 `sigusr2_blocked` 为 0，两个 GCD 报告因此保留为失败。`dispatch-test.c` 在 `nce_lkl_run()` 调用前记录该值，原 core 的 GCD 结果为 1 且 `validated=true`，原 `probe_lkl_translation.validate` 没有这项入口前要求。

正式启动修正在[独立候选目录](../../../../../../../sdk-plain-validation-v1/logd-bootstrap-join-kernel-v1/)准备生产差异，当前保持原 patch 脚本和内核产物。候选在 `sem_down(init_sem)` 后用 `lkl_thread_t init_tid` 保留 PID1 的完整句柄，真实 join 成功后再释放 semaphore、替换 tid 和 CPU owner。join 返回非零调用已有 `lkl_bug`，打印诊断后直接调用 `lkl_ops->panic`；原 `host_panic` 调用 `abort`。该位置的 CPU owner 和正在启动的内核仍由原 PID1 持有，失败后继续启动或只释放 semaphore 缺少安全清理条件。初始 semaphore 分配、CPU 初始化和首个线程创建的原失败返回及 `init_sem` 清理保持。

[原 LogAudit 采集副本](../../../../../../../sdk-plain-validation-v1/logd-original-capture-v1/)按成功 exec 和原 argv 识别主 logd，记录其 TGID/TID 与本次 exec；使用现有 `runtime_elf` 的三个 SDK 加载位置解析固定调用帧。AUDIT_SET 的失败 ACK 可包含完整请求 payload，长度为 80 bytes；成功或 capped ACK 为 36 bytes，seq、内嵌头及保留的 payload 分别检查。MSG_PEEK 和消费各保存原结果。两次析构 close 的帧和对象字段在 syscall 前读取，正常分支最多读取 92 bytes，vfork 尾跳分支最多读取 76 bytes；调用后保存原 result。匹配 EPERM 后至多查询一次实际 namespace/CAP，已匹配 close 缺少资源名称后至多查询一次 `/proc/self/fd/<fd>`，查询结果与原 close 结果分别记录。查询使用独立临时映射，释放结果继续检查；读取、基址或固定帧不满足要求则保留未解析。prepare 只核对副本、原策略和 ELF 身份及必要本机边界，实际采集由主会话组合到后续原 init 验证。

## 曾考虑的替代方案

- AUDIT_SET(mask=0) 只收 ACK，当前源码不会修改控制字段；首轮选择公开只读的 AUDIT_GET，解析程序同时处理状态回复和 ACK。
- 原样运行 probe_lkl_translation.py：PTE 分支会调用 kernel builder，guest 和 validator 固定为 core；独立 prepare 复用已保存的命令和依赖，保存派生源码与产物摘要。
- 同时建立通用 netlink 解码器、通用栈回溯和 FD 历史表：当前问题只需要 AUDIT_GET 的两个回复类型及固定 SDK 调用关系，使用有界读取。
- 在 fixture 中长期保留诊断 join：能确认具体句柄，正式入口仍会丢失该 pthread 资源。修正负责启动交接的 `lkl_start_kernel`，fixture 后续只记录实际内核 join。
- join 返回失败后沿用 `out_free_init_sem` 返回：启动中的内核和 CPU owner 已建立，该分支没有停止这些资源的步骤。候选沿用宿主 join 失败会终止进程的要求，额外处理返回错误的 host_ops 实现。
- 为原始 ASLR 新增通用 loader placement 发布接口：固定三个 ELF 的诊断可先使用已有 proc maps 格式，当前没有新增该接口的实际使用方。
- 只替换诊断 syscall 的 no/args：过滤器继续读取原 pt_regs，查询的过滤范围不正确。完整临时帧恢复只覆盖返回的调用；TRAP、KILL 和 USER_NOTIF 的信号、终止及等待还需单独检查，候选在非 0 模式跳过新增查询。

## 风险

ACK 的 EPERM 同时用于 PID namespace 和 CAP 拒绝，需要先核对 namespace。独立 fixture 尚未加载原 Android SELinux 策略；原六入口已经确认私有 namespace 的原 LogAudit 拒绝 ACK、audit FD close、失败对象字节和两次析构 FD 关联。资源名称只描述 readlink 查询时的 FD；其他线程仍可替换 FD，第二项资源名称可能待确认。namespace/CAP 采样位于消费 ACK 后，socket 创建者的凭据仍按原控制请求的检查位置解释。maps 查询会新增短期映射和 FD，查询期间的模式变化及清理失败必须保留实际结果；过滤引发的信号、终止和等待不能仅靠恢复寄存器消除。本轮实际模式为 0，TRAP、KILL、USER_NOTIF 和 TSYNC 的运行边界未覆盖。完整 Android 启动仍失败，logd 与 Java/SystemServer 的关系尚未验证。
