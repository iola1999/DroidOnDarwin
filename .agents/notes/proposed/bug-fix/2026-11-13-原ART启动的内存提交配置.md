# 决策记录: 原 ART 启动的内存提交配置

状态: proposed

## 问题

无加密原 init 的 180 秒观察出现连续失败的 `msync` 探测，日志问题见[对应记录](2026-11-13-原init观察日志增长.md)。附近 PID 188 的两次可写私有匿名 `mmap` 请求均为 1,074,003,968 bytes、flags=34、fd=-1，返回 ENOMEM。请求大小超过当前 1 GiB 客体 RAM 配置的上限。

固定 ART 的 RegionSpace 分配为两倍堆容量并增加对齐空间。`system/build.prop` 的 dex2oat 最大堆为 512 MiB，原 odrefresh 传递该值；该组合与本次请求的 1 GiB+256 KiB 一致。具体 PID 188 的进程名和调用栈仍待核对。固定 Linux 默认 `OVERCOMMIT_GUESS` 在无 swap 且单次请求页数超过 `totalram_pages()` 时拒绝提交；原 SDK init 在 odsign 完成后的 `on boot` 才写 `overcommit_memory=1`。最初失败没有采集实际 sysctl 和 swap 状态，当前来源只支持该拒绝路径与现象匹配。

源码、固定 ELF、原 init 顺序和有界采样记录在 `work/sdk-plain-validation-v1/msync-analysis-v1.json`。`msync(...,16384,0)` 用于检查映射范围，不分配页面；这个返回值不能直接解释为物理内存已经耗尽。

## 提案

先在原 PID 1 启动前读取实际 `/proc/sys/vm/overcommit_memory` 和 `/proc/meminfo`，记录读取结果与原字节。使用日志限额修复后的默认配置观察失败调用，核对当前提交策略、RAM 与 swap，保持原 rc 和系统库。

随后由无加密实验入口显式选择 `sysctl.vm.overcommit_memory=1` 内核命令行。固定 Linux 的 `do_sysctl_args()` 在初始 `/init` 前处理这个参数，当前 LKL 的 `CONFIG_SYSCTL` 和 `CONFIG_PROC_SYSCTL` 已开启，实际 `lkl.so` 含该调用。该候选让原 Android 后续采用的内存提交策略提前生效，RAM 配置仍为 1 GiB；虚拟地址预留与实际页面访问分别记录。

两次运行分别保存实际命令行、启动前 sysctl/meminfo、失败调用数、ART/odsign/zygote 进度、停止与同盘恢复。候选保留原 init、rc、vold、策略及库；两份 fstab 继续使用已声明的无加密改动。本机结果分别描述启动和资源范围，iPhone 的内存预算、持续性能和热状态仍待验证。

### 默认配置读回及提前配置的首次结果

`work/sdk-plain-validation-v1/init-16k-v3.json` 的六个入口成功，源码保持，原 first-stage 完成，两盘在 recovery 后为 clean。本机为 Apple M5 Ultra、macOS 27.0（26A428），16 KiB 页、1 GiB 客体 RAM，原 init 观察 45 秒，wrapper 全范围为 128.881998 秒。CLI/GCD 的实际命令行为 `androidboot.hardware=ranchu`，均读回 `overcommit_memory=0`，MemTotal 为 1,042,880 kB、SwapTotal 为 0 kB、CommitLimit 为 521,440 kB；这些值在客体 namespace 启动前读取。两个 original 都到达 odsign，但该 45 秒范围未观察到目标可写匿名请求或失败 msync，完整 boot 仍待确认。

`sdk-plain-init-16k-v4` 使用显式提前配置，两个 lifecycle 读回 `overcommit_memory=1`。CLI original 的首部记录也读回 1，尾部 PID 228 的 `mmap` 请求为 1,074,003,968 bytes、prot=3、flags=0x100022，返回 33,554,432，该虚拟预留成功。这个结果来自超限日志的有界样本，具体进程名与调用栈仍未确认；默认 45 秒与提前配置的观察范围不同，后续继续核对实际拒绝和原 ART 进度。

v4 的 CLI original 在完整观察结束前触发 stdout 限额，wrapper 失败，GCD original 与 recovery 未运行。日志范围、宿主回收、盘状态和后续 mounted-partition recovery 见[日志增长记录](2026-11-13-原init观察日志增长.md#提前配置后的日志阈值失败)。继续减少生成副本的成功 VM 诊断，再重跑原 init；日志采样和配置调整后的完整启动、应用操作及性能均未交付。

### 日志受控后的 ART 结果

v6 的六入口、宿主回收、源码检查与同盘恢复成功，两个 original 的初始读回策略均为 1。GCD 保存多个 1,074,003,968-byte 可写私有匿名 mmap 成功，原 boot classpath 和 system server 编译的 dex2oat 退出码均为 0；原 odrefresh 内部计时分别为 41,077 和 81,077 ms，测量环境与范围见[日志记录](2026-11-13-原init观察日志增长.md#受限日志后的原-init-结果)。CLI original 未出现该尺寸的成功 mmap，原 odsign 的密钥完成等待为 549 ms；两入口共用实验盘且按顺序运行，这些样本的编译缓存和数据状态不同。

本轮没有失败 msync 记录或汇总。两个原 init 都因 `bpfloader` 退出 1 触发原重启规则，完整 boot 尚未成功。默认 v3 的 45 秒范围未复现旧目标请求和拒绝，提前配置与默认配置的完整同范围比较继续待做；当前结果只确认提前配置的实际读回、目标映射成功与原 ART 的后续编译进度。

## 曾考虑的替代方案

- 增加客体 RAM：能改变默认提交检查的边界，但当前先区分虚拟预留和实际内存需求，再据完整运行选择容量。
- 降低原 dex2oat 的最大堆：会改变原编译器配置及 GC 行为，先验证原 Android 已采用的提交策略。
- 修改或替换 ART 的低地址扫描：当前 Linux 返回未映射范围的语义与固定源码一致，先处理实际匿名映射失败。
- 提前修改原 `init.rc` 的 sysctl 顺序：内核命令行支持在原 init 前设置同一参数，实验保留原 rc 字节。

## 验收标准

1. 默认配置和提前配置均读回实际 sysctl、MemTotal 与 SwapTotal，记录字段类型、单位和读取范围；实际命令行与部署清单一致。
2. 默认配置保留失败样本与计数；提前配置后检查原匿名映射和 ART 后续进度，继续报告新的失败，完整 boot 单独验收。
3. 同盘停止、回收与恢复成功，原来源保持，日志限额与故障回归成功。iOS 编译使用实际最终生成的原 init 副本。
4. 配置入口只用于两项实际比较，状态和数据以部署清单及读取结果为准；按 reclaim-code-entropy 和 humanizer-zh 审阅。

## 风险

允许内存过量提交可以让虚拟预留成功，后续实际访问仍可能触发内存压力。这个实验不能确认 1 GiB 足以完成 Android 或 HyperOS 运行。启动前读数来自宿主 syscall 任务看到的同一 Linux 全局内存配置，PID 188 的实际限制和调用栈仍需后续核对。
