# 决策记录: BPF 首次 JIT 失败的解释器入口

状态: proposed

## 问题

固定 `kernel/bpf/core.c` 的 `bpf_prog_select_runtime()` 先选择解释器，然后尝试 JIT。当前 ARM64 适配的统一错误出口原本清空所有尝试的 `bpf_func`、`jited` 和 `jited_len`；首次发布失败会清空已经选定的解释器入口。原 `codex/sdk-plain-bpf-jit` 的 16 KiB v3 内核仍保留这一条件，plain 工作树已限定为 `extra_pass` 后清空，发布失败回归已完成；RW buffer、offset 与 callback 的实际行为继续验收。

## 提案

复用已通过的两份内核及 core 编译命令，在独立宿主 fixture 的 `bpf_code_publish` 回调注入返回失败。最终发布的 RW header 首字段为本次长度，回收的 invalidate 区域填 ARM64 BRK；fixture 只对最终发布计数。对旧内核运行单函数首次失败，保存实际宿主故障；对修正内核执行正常和失败的单函数、两函数程序，每项重复八次。诊断源码及二进制分别登记摘要，原内核和数据盘保持只读。

使用实际 `lkl.so` 符号中的 `bpf_jit_current` 偏移读取 charge，在 guest 完成且 halt 前检查 charge 为零、宿主分配和归还次数相等。该检查覆盖 pack 和 charge，未直接计数 RW buffer 与 offset；它们的释放由后续独立内核诊断验证。原始 loader、callback 和整机性能仍由[原 BPF 阶段](../architecture/2026-11-13-SDK36原版BPF加载与LKL的ARM64JIT.md)继续验收。

## 曾考虑的替代方案

直接修改正在集成的生产内核添加故障注入，会改变原 init 运行输入和构建身份。本阶段使用独立宿主回调，不增加生产开关。只检查修正后的文本无法确认原 runtime 会实际选择和执行解释器，因此保留旧内核的真实对照。

## 验收标准

- 旧内核在第一次单函数发布失败后实际收到 SIGSEGV，停止检查确认宿主进程组为空。
- 修正内核的单函数与两函数失败均返回预期 42，实际 JIT 长度为零，正常对照的长度非零。
- 重复加载和关闭后 charge 为零，宿主执行池分配与归还相等；普通池释放及完整上下文回收成功。
- 回调注入、编译命令、符号偏移、内核与宿主输入摘要全部保留；首次失败、失败后的状态和修正结果分别保存。

## 风险

固定 verifier 在子程序 JIT 失败后设置原程序 `jit_requested=0`，该轮每个程序只产生一次发布失败；实际发布次数和返回已核对。RW buffer、offset 和 callback 仍需独立检查。此 fixture 的计时包含编译和诊断，不作为 Android 性能结果。

### 接续后的实际结果

最终 `work/sdk-plain-validation-v1/bpf-failure-takeover-v3/summary.json` 的单函数正常/首次发布失败、两函数正常/首次与第二次发布失败，CLI/GCD 共十个入口全部成功，每入口连续八次实际返回 42。失败路径 JIT 长度为零、正常路径为正；halt 前 charge 为零，宿主池分配与归还相等，退出和进程组检查成功。输入前后保持，并包含实际导入的 `process_observer.py`。旧控制结果 `bpf-publication-control-v1` 保留首次发布失败后 CLI/GCD 的实际 SIGSEGV。

最初 `bpf-failure-takeover-v1` 对两函数首次失败预期 16 次注入，实际固定 verifier 在第二轮第一个函数失败后停止本轮 JIT，并设置原程序 `jit_requested=0`；八轮共八次注入。此检查预期已修正，原失败和 v2 结果继续保存。最终 v3 未允许忽略任何变化的基准输入。该检查没有直接测量 RW buffer、offset 或 callback，剩余条件继续按原提案验证。
