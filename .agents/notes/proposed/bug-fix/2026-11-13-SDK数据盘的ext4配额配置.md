# 决策记录: SDK 数据盘的 ext4 配额配置

状态: proposed

## 问题

16 KiB v8 的两个 raw lifecycle 与两个 original 入口均成功；两个 original 均完成 first-stage，原策略后的宿主 DM 回收成功。首个同盘 recovery CLI 在客体启动前中止，返回 -6。`cli-recovery.jsonl` 第 87 行记录 `stock_init_data_mount.mount_result=-22`，stderr 第 2 行为 `runner:19: result == 0`，对应 `stock-init-data.h:19` 的挂载检查。该路径使用 mounted-partition 准备，以 ext4、flags 1030、`errors=panic` 读写挂载 `/dev/block/vdc` 到 `/data`；raw lifecycle 使用原 ramdisk 准备，尚未覆盖这次数据盘挂载。

原 v8 [阶段结果](../../../../work/sdk-first-stage-case-sensitive-validation-v1/raw_original_recovery-16k-v8-stage.json) SHA-256 为 `048dd0f753671691f50da5741d96f92ce9f8df03c3d0c669e8b6af2a150bff97`，实际 init summary 的 SHA-256 为 `9728fc7b9e010a38c1891b8dab02f921f3cea512596314bbac3e8efe2d4f7a48`。失败发生前后，data 与 metadata 的完整字节摘要均保持，文件系统均 clean；只读 inspector 复查的实际状态与保存的 after 一致。[磁盘检查](../../../../work/sdk-first-stage-recovery-mount-review-v1/disk-state-after-v8-v1.json)保留完整状态与 superblock 摘要。data 的 ro_compat 为 `0x256b`，包含 quota `0x0100` 和 project quota `0x2000`。

实际 v8 内核 `build/.config` 关闭 `CONFIG_QUOTA`。固定 Linux `d0f76a77e8c2ca68bd7d96190b8da09040eab072` 的 `fs/ext4/super.c` 第 3611 至 3618 行在缺少 `CONFIG_QUOTA` 或 `CONFIG_QFMT_V2` 且文件系统携带 quota/project 特性时拒绝读写挂载，第 4688 至 4689 行将该结果返回为 EINVAL。当前块设备配置集合没有请求这两项；原系统数据盘需要相应的内核支持。

## 提案

在 `probe_lkl.BLOCK_OPTIONS` 增加 `QUOTA` 和 `QFMT_V2`，由现有 process 与 translation 构建路径启用并检查。`fs/quota/Kconfig` 已分别选择 `QUOTACTL` 和 `QUOTA_TREE`，沿用这些依赖。原数据盘、原 fstab、挂载参数和验收条件保持，后续运行继续使用失败后的实际候选状态。

配置变化需要新内核身份。保存 v8 core 的实际构建记录与必要产物后，冻结新检查点、源码范围和独立输出，重新执行 16 KiB 与 4 KiB core、raw original/recovery、iOS runtime 与实际 init 编译。原 v8 的四个成功入口及 recovery 失败分别保留。原 vold default-key、FBE、fsverity 与完整系统启动继续由[原 vold 记录](../architecture/2026-11-13-SDK36原始vold与default-key.md)负责。

## 曾考虑的替代方案

- 将 recovery 的 `/data` 改为只读：同盘恢复需要写入 generation 并验证持久化，现有验收继续要求读写挂载。
- 移除候选盘 quota/project 特性：会改变原系统的数据格式，内核应支持已有格式。
- 重建候选盘：实际盘与已保存的 after 一致，继续使用原状态检查恢复行为。
- 仅在翻译构建脚本中增加配置：process 和 translation 共同读取现有配置集合，新增独立集合会增加维护位置。

## 验收标准

1. 原失败及四个成功入口、实际 before/after、磁盘状态和来源保留；两页候选连续使用，原镜像保持。
2. 两页生成的内核启用 `CONFIG_QUOTA=y`、`CONFIG_QFMT_V2=y` 及所选依赖，源码、配置、对象和打包文件与新身份一致。
3. 两页 CLI/GCD recovery 实际读写挂载原数据盘成功，generation、同步、卸载、DM 清理、磁盘关闭及上下文回收通过。两个 original 均保留 `observation_validated=True` 与 `first_stage.completed=True`。
4. 两页 core、iOS runtime 与实际 init 编译通过；设备授权、资源、持续性能和热状态继续待真机验证。
5. 按 reclaim-code-entropy 审查配置的真实使用方、替代实现与移除影响；技术文字按 humanizer-zh 复核。

### 复杂度审查

新增配置直接供 `probe_lkl.py` 的 process 构建和 `build_lkl_translation_kernel.py` 使用，沿用同一启用与最终配置检查。移除 `QUOTA` 或 `QFMT_V2` 会再次触发固定 Linux 的读写挂载拒绝条件。没有增加运行状态、外部接口或独立配置集合；quota inode 的实际读写与同步由原盘 recovery 验证。

### 实施进度

两项配置已加入共同集合，Python AST 与差异检查成功。v8 实际构建记录、配置、生成源码、对应对象和打包文件已用同卷 APFS 克隆保存为 22 项固定输入；[归档记录](../../../../work/sdk-first-stage-case-sensitive-validation-v1/core-16k-v8-kernel-archive-v1.json) SHA-256 为 `17cb5751ab263eebbd516b9c4f5c0b30d72fd06ba0d61589ced7f9a0a812722c`。当前准备新检查点与两页验证，新挂载结果尚未产生。

## 风险

挂载通过后，原 quota inode 的读取、写入和同步仍需实际运行验证。当前配置修复解决 recovery 的 ext4 格式支持；原 vold 加密与完整 boot 还有独立失败。
