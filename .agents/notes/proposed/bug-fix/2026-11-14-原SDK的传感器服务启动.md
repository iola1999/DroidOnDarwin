# 决策记录: 原 SDK 的传感器服务启动

状态: proposed

## 问题

ashmem v5 中断前的日志多次记录 `MultihalSensors:64: sensors transport is not opened`。原 vendor 声明 AIDL v3 `android.hardware.sensors.ISensors/default`，MultiHAL 通过 `hals.conf` 加载 HIDL 2.1 ranchu 子 HAL；该库在全局构造期间打开传输，失败后退出。原 rc、VINTF、服务及子 HAL 的六份文件已与固定输入逐字节核对，原盘字节保持，详情见[只读调查](../../../../../../../sdk-plain-validation-v1/sensors-transport-audit-v1/report.md)。

原子 HAL 自身包含 qemud/qemu_pipe，传感器连接使用 AF_VSOCK、HOST CID 2 与 Data 端口 5000，并发送 `pipe:qemud:sensors`。固定传输源码另定义 Ping 端口 5001。实际内核未启用 `CONFIG_VSOCKETS`，宿主当前提供图形设备及 AF_UNIX 图形连接，尚缺少该传输与 sensors 数据提供实现；实际 socket/connect 错误码仍待采集。

固定 SDK `SensorService` 的 native 初始化提交到 `SystemServerInitThreadPool`，phase 200 等待其 future。原 `libsensorservice.so` 在服务已声明的分支调用 `AServiceManager_waitForService`。这项等待与[默认显示阶段 100](2026-11-14-原SDK默认显示等待.md)分别检查；v6 的最后阶段 100 消息尚未确认具体回调，当前不据此认定 sensors 是该轮的等待原因。

## 提案

先按实际 HAL PID/TID 有界记录 syscall 198 的 socket 参数、syscall 203 的地址与原返回值，关联原错误、退出信号、AIDL 服务发布及 phase 200。确认失败位置后比较两项实现：为原 AF_VSOCK 与 qemud 协议提供可用传输、端点和数据；或在实际 `SensorsTransportFactory` 接入本地端点并重编译对应子 HAL。两项均需要保留原 MultiHAL/AIDL 契约、传感器能力、事件时间戳和资源生命周期，实际数据来源独立实现与验证。

## 曾考虑的替代方案

- 只启用 `CONFIG_VSOCKETS`：仍缺少 transport、端点与数据提供，无法完成原连接。
- 只修改独立图形 `libqemupipe.ranchu.so`：原 sensors 子 HAL 已静态包含自己的 qemud/qemu_pipe，实现不经过该动态库。
- 立即修改 phase 100 等待：传感器的已确认等待条件在 phase 200，先保留两个问题的实际范围。

## 验收标准

1. 保存原 socket/connect 的参数、返回值、PID/TID、传输地址及对应原错误，缺少记录保留未确认。
2. 原 AIDL `ISensors/default` 发布，SystemServer 的 native sensor 初始化与 phase 200 完成。
3. 按实际声明能力检查数据、时间戳、set/set-delay、连接与资源回收，重启后能重新工作；性能与设备数据按实际环境分别验收。
4. 原完整 boot、桌面、APK、停止与同盘恢复条件保持，iOS 编译与运行资源继续检查，真机验证按离线目标另行安排。

## 风险

固定参考源码的修订与实际 SDK 子 HAL 的具体编译修订尚未对应；已确认行为以原 ELF、DEX 与运行记录为准。新的诊断继续保持原 SELinux 策略和原调用结果。传输实现需处理短读写、帧长度、断开与重启，单独连接成功无法覆盖传感器事件行为。
