# 决策记录: 客体忙碌期间的宿主请求调度

状态: proposed

## 问题

完整 Android 启动期间，宿主读取日志曾停顿数十秒，随后一次出现大量较早的日志。宿主读取和窗口输入都通过 `lkl_syscall` 请求 Linux CPU。源码显示，客体持续可运行时，原有 idle host task 只在 Linux 空闲后被唤醒。宿主请求可能因此持续等待。独立回归已确认修改后的宿主请求能在持续计算期间完成。

## 提案

利用既有 NCE 定时抢占，在有宿主请求等待时唤醒 idle host task。该任务仅在确有等待者时交出 CPU，普通宿主调用继续使用原有调度规则。保留 LKL 的单 CPU 所有权和任务切换过程。日志读取完成后显式刷新宿主输出。

回归程序持续运行、保持可调度，通过共享文件响应宿主线程的 32 次请求。客体只检查截止时间，不主动睡眠；宿主要求请求在 2 秒内完成，客体 5 秒后失败。这两个时间是测试失败界限，尚无交互延迟承诺。

### 内核回收循环的待处理中断

2026-10-10 04:21 的完整启动复现第二种停顿：SystemUI 因启动超时退出后，`release_task → proc_invalidate_siblings_dcache → d_invalidate → shrink_dcache_parent` 持续遍历 `/proc/351/task/376/stat`。LLDB 读取该 dentry 的引用计数为 -128，清理尚未执行到 `dentry_unlist`；当前线程等待另一线程完成这段清理。此时 Linux IRQ 已启用、`irq_index_status=1`，`TIF_NEED_RESCHED` 尚未设置。LKL 宿主定时器只能登记待处理中断，`__cond_resched()` 的循环没有消费该中断，因此调度状态无法更新。

已在 `CONFIG_LKL` 的 `__cond_resched()` 检查之前调用已有 `cpu_relax()`；该架构实现通过保存和恢复 IRQ 状态处理待处理中断。继续使用内核本来的 `should_resched()` 与 `preempt_schedule_common()`，不修改 dentry 引用计数或回收条件。目录诊断只用于此次调查，完成后撤除。增加并发退出和 `/proc` 遍历回归，并重新执行完整启动与原有调度检查。原始状态保存在 `work/native-linux-nce/dcache-registers.txt`、`dcache-tree.txt`。

## 曾考虑的替代方案

- 只刷新日志输出：无法处理阻塞在 Linux CPU 获取处的宿主输入请求。
- 绕过 Linux 直接写入客体输入状态：需要另建并发协议，且无法覆盖其他宿主系统调用。
- 对所有宿主调用直接跳过调度：改变范围过大，当前只调整既有 idle host task 的交接条件。

## 风险

交接发生在调度边界，必须检查 CPU 所有权、线程退出、信号和地址空间恢复。有大量宿主请求时可能影响客体吞吐，需结合完整桌面负载测量。

复杂度审查：输入与日志共用现有 `lkl_syscall`，未新增请求队列或消息协议。新增状态仅为测试共享文件；运行时继续使用既有 CPU 等待者计数。移除忙碌时的 idle host task 唤醒后，等待者仍只能依赖客体空闲；该判断来自原调度条件，尚未完成单独关闭修改的运行对照。
