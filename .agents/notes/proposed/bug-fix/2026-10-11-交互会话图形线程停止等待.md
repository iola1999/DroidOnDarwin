# 决策记录: 交互会话图形线程停止等待

状态: proposed

## 问题

新单核 Direct Mac 包在长时间窗口检查中出现两项未通过行为：Launcher 应用列表为空；请求停止后 Android 服务退出，宿主仍等待图形连接线程。该轮与独立双核功能检查并行，未用于性能比较。原始报告位于 `work/native-linux-nce/benchmarks/home-navigation-visual/20261011-220448-b2c741/summary.json`，运行编号 `2FE5CD31-2A6B-4E4D-A05B-03AF10473BF6`。控制器到达期限后结束 App。

`sample` 显示宿主运行线程停在 `nce_graphics_stop()` → accept 线程 join；accept 线程停在 `Connection::~Connection()` → reader join。一个 reader 仍在 `Connection::connect()` 调用的 LKL 系统调用中等待调度信号量。按照 vmmap 的 RX 区间和同构建 ELF 符号计算，客体内核地址对应 `switch_to_host_task()`。这些结果尚未说明该线程无法继续运行的原因。

Launcher 日志出现加载任务停止，应用列表填充未完成；目前没有确认它与停止等待之间的因果关系。调试器附加被系统拒绝，现有采样和日志保存在 `work/native-linux-nce/benchmarks/home-navigation-visual-sample.txt`、`home-navigation-visual-vmmap.txt` 和 `home-navigation-kernel-state.txt`。

## 提案

先在没有并行构建或其他 Android 会话时，使用相同包和数据目录复跑。检查应用列表、Clock/Files 首帧及干净退出；需要时使用单独诊断构建观察宿主线程进入 Linux 的状态。明确等待条件后修复相应生命周期，并覆盖触发该等待的线程或连接边界。

## 曾考虑的替代方案

- 在等待期限后直接结束宿主线程：Linux 调度和图形连接仍持有状态，无法保证数据盘正常卸载，因此不采用。
- 清空 Launcher 或整盘数据后继续比较：会丢失当前复现条件，先保留现有数据并检查日志恢复。

## 验收标准

- 实际窗口显示应用列表，能打开 Clock 和 Files，并返回主页。
- 同一数据盘重启后保留应用数据，图形线程结束，数据盘干净卸载。
- 修复后执行对应边界检查及 CLI/GCD 完整桌面；Mac/iOS 包包含匹配实现。

## 风险

当前故障可能与调度时序有关，单次复跑成功无法证明已修复。强制结束后的测试盘仍有待回放日志；离线只读检查报告空闲计数与 orphan 标志差异，退出码为 0，未改动磁盘。下一次正常挂载将进行日志恢复，结束后再次离线检查。

## 调查进展

同一 Mac 包和原数据盘在独立复跑 `20261011-221754-9c7058` 中成功：应用列表已填充，Clock 首帧为 5.527 秒，Files 为 4.895 秒，完整会话正常结束。恢复后离线 `e2fsck -fn` 退出码为 0，日志位于 `home-navigation-isolated-data-check.log`。这些是单轮功能记录，原故障仍未解释。

空闲原生内核的独立小型试验完成 128 轮、每轮 32 个新宿主线程的首次 gettid 调用和退出，未复现等待。该试验没有客体执行，不能覆盖当前怀疑的调度竞争；下一项在 Direct 核心客体运行期间执行相同首次调用负载。共同入口 `new_host_task()` 经 `host0` 创建宿主任务，是否会在 CPU 交接期间发生并发重入仍待运行检查。

Direct 核心负载期间的临时并发首次调用试验也已完成：CLI/GCD 各创建 4096 个宿主线程，分 128 轮、每轮 32 个线程同步开始首次 gettid 调用并退出，两种入口均成功。结果位于 `work/native-linux-nce/lkl-host-admission-core/summary.json`。该负载未复现故障，临时压力代码已从产品 runner 撤回；未据此修改内核调度。

独立诊断包增加 `com.apple.security.get-task-allow` 后，调试附加成功。延长会话 `A9E1CB8B-E12E-4FE7-B621-6AEB0BAB5F1C` 中实际打开 Clock 和 Files，首帧分别为 4.759 / 4.867 秒；随后等待并执行手动导航，会话最终正常结束，图形资源全部释放，停止耗时约 3.75 秒。没有 Java 崩溃或 ANR。原驱动在调试附加时提前记录退出，保留该报告；完成后的 App 文件与补充摘要位于 `work/native-linux-nce/benchmarks/long-diagnostic-final.json`。本轮包含调试与手工操作，不纳入性能统计。

复杂度审查：两项压力试验均未定位失效条件，因此暂不增加首次宿主调用串行锁、额外停止状态或强制线程取消。继续以重复完整会话检查发生条件，原故障保持待查。

下一项使用独立内核诊断变体，检查共享 `host0` 创建任务时发生阻塞的边界：在 `new_host_task()` 切换至 `host0` 后暂时等待一个 Linux 时钟周期，并检测另一个首次调用是否同时进入该函数。`kernel_thread()` 使用可能睡眠的内核分配，因此需明确首次调用在调度期间的互斥条件。该等待仅用于扩大可观察窗口；若检测到重入，也需分别解释它与原图形故障的关系，不能直接认定为原故障原因。诊断构建与正式性能对照顺序执行。

若该诊断确认首次创建重入，候选修复仅串行化尚未建立 TLS 宿主任务的创建过程。等待宿主互斥锁前必须释放 LKL CPU，否则锁持有者无法继续调度；获得锁后重新获取 CPU，并检查内核是否已经停止。已建立任务的系统调用继续使用原有入口，阻塞读写不持有创建锁。关机还需等待已登记的创建请求退出，再释放锁与 TLS key，防止等待中的调用访问已释放状态。实现与保留范围以诊断结果为准。


### 2026-10-12 首次任务创建边界

阻塞诊断已确认共享 `host0` 的重入：在 `new_host_task()` 切换至 `host0` 后等待一个 jiffy，两个首次调用可以同时进入任务创建。原实现以 `concurrent host0 creation` 中止；串行化首次创建后，128 轮、每轮 32 个宿主线程的 4096 次首次调用和退出成功。普通任务的系统调用不持有创建锁；登记请求后释放 CPU，取得创建锁后重新获取 CPU；清理等待已登记请求退出。原图形停止等待与此问题的因果关系仍未确认。

永久回归入口为 `python3 scripts/test_lkl_host_admission.py`，控制组加 `--without-serialization`。两者使用独立诊断内核，控制组仅撤去首次创建互斥，保留同一阻塞与重入检查。2026-10-12 两项预期均满足：控制组返回 -6，并打印重入错误；修复组返回 0，4096 次调用通过。结构化结果位于 `work/native-linux-nce/host-admission-regression/{control,fixed}/result.json`，包含生成源码、内核、测试程序及日志哈希。测试加载复用产品的 `translation/kernel-image.c`，诊断等待未进入产品内核。
