# 决策记录: 原 SDK 默认显示等待

状态: proposed

## 问题

原 SDK ashmem v6 的 CLI/GCD 六入口完成观察、停止回收和同盘恢复，两个 original 均成功创建 `ApplicationSharedMemory`。system_server 的阶段消息均到 `StartDisplayManager` 完成、`WaitForDisplay` 和 `Starting phase 100`，随后没有完成消息，完整 boot 继续 failed。实际运行与设备结果见[ashmem 记录](../architecture/2026-11-14-原SDK的ashmem设备.md)。

`Starting phase 100` 是 SystemServiceManager 的总阶段消息，随后按服务注册顺序逐一调用 `onBootPhase`。它使用原有 `OnBootPhase_100_<服务类名>` 文本记录各回调，当前过滤范围尚未包含这些消息；现有日志无法确认具体等待服务。

固定 SDK 的 `DisplayManagerService.onBootPhase` 在 phase 100 先获取 `mSyncRoot`，随后开始计时，等待 `LogicalDisplayMapper.getDisplayLocked(0)` 与 `mVirtualDisplayAdapter` 均非 null；默认期限为 10000 ms。CLI 的 phase 100 消息后还有约 65 秒其他日志，单独增加观察时长无法解释当前等待。默认 adapter 注册处理也持有 `mSyncRoot`，同步执行 `LocalDisplayAdapter.registerLocked`，查询 SurfaceFlinger 的物理显示信息后创建 VirtualDisplayAdapter。当前尚未确认 DisplayManagerService 回调开始执行；初始化线程持锁等待 SurfaceFlinger/Binder 仅为推断，需各服务阶段、线程栈及调用状态确认。

## 提案

先核对固定 SDK DEX 中实际使用的 DisplayManager 与 LocalDisplayAdapter 标签，并增加原 `OnBootPhase_100_` 服务阶段文本。在独立 v7 扩展现有有界采集，保持共享 128 条预算、原 FATAL/ERROR 和六入口验收。LocalDisplayAdapter 查询静态/动态信息、模式、active mode、color mode 和 desired specs 的六类失败使用 WARN，按固定 DEX 原文采集；DisplayDeviceRepository 的设备增改消息按原 INFO 采集。同步核对原 ART SIGQUIT 线程转储所需的信号权限、SignalCatcher、tombstoned 和写入路径，采用能够保留原策略的实际采集方式。用各服务阶段、线程栈、锁持有关系和对应 Binder 或显示调用确定等待位置，再决定修正范围。

原 system_server、SurfaceFlinger、Composer、Android 属性与 SELinux 策略继续保留，设备读取和资源回收契约沿用 ashmem v6。完整 boot 仍要求 `sys.boot_completed=1`、真实进程、Binder 服务与 `cmd` 查询；原系统完成后的观察器继续按原触发条件运行。

### v7 采集准备

独立 v7 已按固定 `services.jar` 与 `framework.jar` 读回结果增加逐服务阶段、显示设备事件及六类 LocalDisplayAdapter WARN。复用现有 fixture 的普通与 ASan/UBSan 运行均通过旧过滤、原协议、新规则和共享 128 条上限；新增解析反例均拒绝。源码与固定输入保持，[消息来源与选择](../../../../../../../sdk-plain-validation-v1/display-wait-taglog-v7/message-selection.json)和[边界结果](../../../../../../../sdk-plain-validation-v1/display-wait-taglog-v7/validation-report.json)保存实际结果。原启动 runner 位于 `work/sdk-plain-validation-v1/ashmem-original-init-v7/`；当前尚未运行 guest，实际消息与等待位置由下一轮确认。

### v7 实际等待服务与线程转储路径

v7 的[六入口摘要](../../../../../../../sdk-plain-validation-v1/ashmem-original-init-v7/result-summary.json)确认原观察、停止回收、同盘恢复和 SQLite 成功，两盘最后 clean，候选 `03d9465` 与实际来源前后保持。CLI/GCD 各记录 14 个 phase 100 服务完成，最后均为 `OnBootPhase_100_com.android.server.display.DisplayManagerService` 开始，没有对应完成文本。两份标签日志均为 120 条、遗漏 0；选定的 DisplayManagerService、LocalDisplayAdapter 与 DisplayDeviceRepository 消息为 0。DisplayManagerService 的回调已经开始，锁与具体等待调用仍未确认，完整 boot 继续 failed。

[原 ART SIGQUIT 调查](../../../../../../../sdk-plain-validation-v1/art-sigquit-path-audit-v1/README.md)确认固定策略允许 init 向 system_server 发送 signal 并允许 CAP_KILL，原 ART/palette 通过 tombstoned 写 Java trace 至 `/data/anr`。独立 v8 将复用第三次 PID1 有界采样，先确认 PID、UID 与实际域，扫描唯一 system_server 并请求一次 SIGQUIT，记录原返回、临时资源回收与寄存器恢复。为原转储保留 300 秒额外诊断观察窗口；完整 boot、退出与同盘恢复条件保持，实际信号与完整 Java 栈仍待运行验证。

### v8 原 Watchdog 栈与 v9 显式转储

v8 已完成原六入口，停止回收、同盘恢复、SQLite 和来源检查成功，两盘最后 clean，完整 boot 保持 failed。显式 SIGQUIT 诊断在 CLI/GCD 均因 `openat("/proc", 0x90000)` 返回 `-22/EINVAL` 中止，临时 FD、mmap 和完整寄存器恢复成功。实际内核 ARM64 头定义 `O_DIRECTORY=040000`、`O_DIRECT=0200000`，原参数包含 O_DIRECT；独立 v9 改为 `0x84000`，保留原策略、唯一目标、pidfd、原六入口与完整 boot 要求。

v9 的目录 ABI 回归用原 v8 header 复现 EINVAL 与零信号，修正后的 fixture 请求一次信号并回收全部资源。85 项合成场景、11 项格式拒绝、16 项进程退出边界和 Direct 对象摘要回归成功，macOS/iOS 四项编译条件成功。实际六入口的停止回收、恢复、SQLite 与来源检查成功，CLI/GCD 原 system_server PID 492/491 的 pidfd_send_signal 均返回 0，分别关闭全部 80/77 个临时 FD，并解除单页映射、恢复完整寄存器。完整 boot 继续 failed。

v8 原 Watchdog 已生成四份 ANR，CLI PID 493、GCD PID 486 各有 pre_watchdog 与 watchdog 完整 system_server 段；四份快照的 main 均等待 `mSyncRoot`，持锁者为 Java thread 17。`android.display` 在 `registerDefaultDisplayAdapters` 内持有该锁，执行至 `LocalDisplayAdapter` 构造函数的 `SurfaceControl.getBootDisplayModeSupport`，原生栈为 `BpSurfaceComposer::getBootDisplayModeSupport`、`BpBinder::transact`、`IPCThreadState::transact` 与 ioctl。v9 另外取得两份原 tombstoned `trace_00/trace_01`，均包含匹配目标 PID 的 system_server 起止标记。CLI 显式快照已推进到 `BpSurfaceComposer::getPhysicalDisplayIds`，仍持有同锁等待 Binder；GCD 显式快照与 v9 四份 Watchdog 快照仍为启动模式查询。v8 四份另行保存。v9 GCD watchdog 的两个其他 media 服务缺少结束标记，system_server 段完整。

结果见[结构化阶段记录](../../../../experiments/native-linux/results-sdk-art-sigquit-init-20261114.json)、[v8 栈摘要](../../../../../../../sdk-plain-validation-v1/art-sigquit-trace-v8/trace-summary.json)及[v9 栈摘要](../../../../../../../sdk-plain-validation-v1/art-sigquit-trace-v9/trace-summary.json)。原盘 `/anr` 基线为空，停止后逐文件只读导出、大小与盘摘要核对成功。`rdump` 的属主 EPERM、首次导出器未接受 `anr_` 前缀、首次栈分析误要求所有快照为同一 Binder 方法的失败分别保留，修正后按各文件实际内容记录。

固定 SurfaceFlinger ELF 的 `.gnu_debugdata` 已只读解压，ELF 摘要与 runtime 清单一致。原 `getBootDisplayModeSupport` 位于 `0x45dc94`，调用 `Scheduler::schedule` 的实例 `0x45dd34`，随后调用 `future<bool>::get()` 的 `0x37f14c`。源码未修改，记录见[静态来源](../../../../../../../sdk-plain-validation-v1/dms-surfaceflinger-static-v1/report.json)。后续核对 SurfaceFlinger 的 Binder 接收、调度任务处理和回复状态，保留原 DMS 等待条件；当前内核未启用 DEBUG_FS，Binderfs 的日志取决于实际 stats 挂载选项，运行中的入口与权限继续待查。

复杂度审查确认本阶段仅修正独立诊断的 ABI 参数及 fixture，不新增服务、权限、定时器或重复请求状态。完整显示、Android 桌面、APK、HyperOS 与持续性能继续验收。

## 曾考虑的替代方案

- 只增加 180 秒观察期限：phase 100 消息后已有超过默认 10000 ms 期限的后续运行，缺少能够解释等待的依据，先查锁与调用状态。
- 修改默认显示等待条件：会改变原 Framework 的初始化要求，当前未查明实际等待位置，先保留原条件。
- 用部署观察器文件的成功结果判断系统启动：部署与完整系统查询的范围不同，完整 boot 继续采用原实际查询条件。

## 验收标准

1. 原 v6 报告、日志与失败状态保持，新增采集来源对应固定 SDK DEX，缺失和超限结果可辨认。
2. 取得 DisplayManager 的实际初始化位置、锁与 Binder 或显示调用状态；无法采集的路径记录真实失败。
3. 修正后 CLI/GCD 均通过原 phase 100，并完成完整 boot 查询、停止回收及同盘恢复，iOS 编译和最终执行入口链接继续检查。
4. 默认显示与完整系统成功后继续真实桌面、APK 和持续性能验收；设备条件按离线目标保留待真机验证。

## 风险

新日志与线程转储会增加诊断负载，本轮结果用于功能定位。SIGQUIT 转储可能受原域权限、tombstoned 协议或原 ART 的写入路径限制，采用前核对实际行为。锁获取前的等待和已进入定时等待需要分别确认，当前阶段消息不足以区分。
