# 决策记录: LKL 读取 ARM64 寄存器

状态: proposed

## 问题

通用 ptrace 阶段已交付 SEIZE、INTERRUPT、GETEVENTMSG、CONT 和 DETACH，并修复 clone 子任务的初始停止。已停止任务的 GETREGSET 和 SETREGSET 仍返回 EIO，见[通用请求记录](../../implemented/bug-fix/2026-11-14-LKL通用ptrace请求.md)。Android unwindstack 的 `Regs::RemoteGet()` 使用 GETREGSET / NT_PRSTATUS 读取线程寄存器，再按返回的 `iov_len` 识别架构；返回 272 bytes 才进入 ARM64 分支。`crash_dump64` 读取其他线程的 GPR，读取失败后跳过该线程。该阶段可以继续修复多线程转储的寄存器读取，完整 Android 启动和原服务崩溃继续按各自记录处理。

只读调查使用候选提交 `07ca854e9e114701bcb3feb538fe17a3b4766157`、固定 Linux `d0f76a77e8c2ca68bd7d96190b8da09040eab072`，以及仓库已有 Android 源码版本。按现有 `android-sources.json` 的 system/core revision `68be0c2c0006a0740d0b1809abe4717308f90d15` 读取 crash_dump 源码；原 SDK 的 `crash_dump64` 与两份 `libunwindstack.so` 已分别做只读反汇编。来源和接口调查保存于[本轮报告](../../../../../../../sdk-ptrace-generic-v1/regset-readonly-v1/report.json)。源码与 SDK 二进制的精确版本对应尚未建立；两份原 SDK unwindstack 二进制均直接请求 NT_PRSTATUS 并比较 272-byte 返回长度，原 crash_dump 二进制直接请求 8-byte NT_ARM_TLS。

主会话已明确本阶段仅交付 crash_dump 实际使用的只读接口。两个只读 regset、MMU 入口分派和两后端 TLS getter 已加入候选，新独立内核编译与 ELF、镜像、导出偏移检查成功。翻译与原生 CLI/GCD 的寄存器检查和 iOS 编译已完成，原 SDK v15 的六入口也已结束；完整启动与转储继续单独验收，本阶段沿用持续离线开发授权。

## 提案

### 接口范围

在现有 `arch_ptrace()` 增加 MMU 专用的读取入口，仅分派 PTRACE_GETREGSET 的 NT_PRSTATUS 和 NT_ARM_TLS。请求继续经过已有 syscall、凭据、SELinux、附加关系、`ptrace_freeze_traced()` 和 `wait_task_inactive()` 检查；回调读取已停止任务的 `task_pt_regs()` 及真实 TLS 状态。该入口使用 Linux 的 `user_regset_view`、`membuf` 和 `copy_regset_to_user()`。

| 请求 | note | 完整长度 | 元素长度 | 返回内容 |
| --- | --- | --- | --- | --- |
| PTRACE_GETREGSET | NT_PRSTATUS / 1 | 272 bytes | 8 bytes | 31 个 64-bit GPR、SP、PC、PSTATE |
| PTRACE_GETREGSET | NT_ARM_TLS / 0x401 | 16 bytes | 8 bytes | TPIDR_EL0；第二项为 0 |
| PTRACE_GETREGSET | NT_FPREGSET / 2、NT_ARM_TAGGED_ADDR_CTRL / 0x409、NT_ARM_PAC_ENABLED_KEYS / 0x40a 及其他 note | 沿用原请求处理 | 沿用原请求处理 | EIO |
| PTRACE_SETREGSET | 全部 note | 沿用原请求处理 | 沿用原请求处理 | EIO |

固定 Linux 的 ARM64 TLS regset 有两个 64-bit 项；不具备 TPIDR2 的系统读取第二项为 0。Bionic 和本轮原 SDK crash_dump 均只请求第一项的 8 bytes。新入口保留这一短读取行为。原 crash_dump 对 TAGGED_ADDR_CTRL 和 PAC_ENABLED_KEYS 查询失败后继续执行，这两个请求保持当前 EIO。

NT_PRSTATUS 和 NT_ARM_TLS 的 `iov_len` 必须为 8 的倍数，其他长度返回 EINVAL；长度超过完整 regset 后按完整长度截断。零长度返回 0，并保持零长度，客体输出缓冲区不发生内存访问。复制函数为非零读取分配暂存缓冲区，分配失败返回 ENOMEM。iovec 读取失败、输出缓冲区复制失败及最终 `iov_len` 写回失败返回 EFAULT。成功后仅更新 iovec 的长度，`iov_base` 保持。输出复制失败可能已经修改部分输出缓冲区；最终长度写回失败前也可能已完成数据输出。只读请求保持目标执行状态。

### 寄存器与 TLS 来源

[内部 pt_regs](../../../../experiments/native-linux/guest-registers.h) 的保存块为 800 bytes；NCE 的汇编偏移已有编译期断言。公开 GPR 按固定 Linux 的 `user_pt_regs` 字段定义为 272 bytes，逐字段从 `regs.x`、`regs.sp`、`regs.pc` 和 `regs.nzcv` 生成。PSTATE 使用当前保存的 NZCV，保留原始 SP，包括已有 ART 信号恢复所需的 8-byte 偏移。

为 `lkl_host_operations` 增加一个 `user_get_tls(state)` 回调。原生后端读取 `NceState.tls`；翻译后端读取 `Process.tls`。两个后端的 TLS 字段位于不同结构位置，回调直接访问各自已有字段。原生 TLS load 和 TPIDR_EL0 仿真已使用 `NceState.tls`；Unicorn 的批量寄存器保存和恢复使用 `Process.tls`；Direct 从该字段读取 TPIDR_EL0，TPIDR_EL0 写指令进入 Unicorn 执行，随后回写 `Process.tls`。

缺少目标 NCE 状态后，两个已支持 note 的读取返回 EIO；缺少 TLS getter 后，NT_ARM_TLS 返回 EIO。公开结构与原保存块分别保留大小断言。宿主栈、Darwin x18、恢复入口、调用回调和运行统计继续使用原结构位置。

新 getter 追加到 `lkl_host_operations` 的原末尾，既有字段偏移保持。宿主与本轮内核均使用实际生成的 host_ops 头。已交付的通用 ptrace CLI/GCD 保留于[原专项报告](../../../../../../../sdk-ptrace-generic-v1/final-cli-gcd-v1/report.json)，其 `linux-runner.c` 通过 `NCE_TRANSLATION_FILES` 从外部读取 `guest.elf` 和 `late.elf`。本轮 driver 核对该报告的依赖、内核 ABI 和宿主二进制摘要后克隆两入口，让原通用 ptrace 内核与新内核执行同一份本轮 fixture。

### 可执行实现范围与复杂度

新增职责独立的 `lkl-nce-ptrace.c`，提供公开 GPR 转换、两个只读 regset 回调、静态 view 和已有请求的分派。`lkl_nce_patch.py` 将该文件加入 `COPIED_SOURCES` 和 MMU 构建，更新 asm/ptrace.h 的入口声明，并在生成的 host_ops.h 增加 TLS getter。`lkl-process-host.c` 与 `translation/linux-execution.c` 分别实现和注册 getter。现有 ptrace guest 与 driver 更新已支持 GET 请求的预期，并继续验证 SETREGSET 的原 EIO。

`kernel/regset.c` 始终进入内核构建，复制函数可直接复用。当前 HAVE_ARCH_TRACEHOOK 保持关闭；它还关联 syscall entry/exit 跟踪、GET_SYSCALL_INFO、返回用户态的工作处理和 core dump 接口。实际构建已经通过 `lkl-syscall.h` 提供 AArch64 参数和返回值接口，后续完整 tracehook 仍需处理 syscall 跟踪停止、异步停止的 syscall 编号和 TIF_NOTIFY_RESUME。只读 regset 入口只复制已有请求头与长度处理，其余复制和停止逻辑沿用内核实现。

复杂度审查已核对实际使用方、保存状态和复制函数。新增状态仅为 host_ops 的 TLS getter 函数指针；TLS 的数值继续存于原后端。移除该 getter 后，内核无法通过后端私有结构读取 TLS；移除公开 GPR 转换后，unwindstack 无法获得 272-byte ARM64 布局。扩大 tracehook 和寄存器写入范围会增加本阶段实际转储尚未使用的行为，后续按独立契约和回归处理。

本轮内核使用 `work/sdk-vold-linux-v1/mount/regset-read-kernel-v1`，在大小写区分的 APFS 中克隆原已交付源码，新 build 仅复制原 `.config`。按原构建的 NCE、translation、BPF 顺序应用补丁，两次完整重放的源码摘要一致。最终全量源码与原已交付内核比较，仅 asm/ptrace.h、host_ops.h、kernel/Makefile 和新增 nce_ptrace.c 四处不同。原配置、HAVE_ARCH_TRACEHOOK 状态、原输入和冻结的生产源码保持。[独立构建报告](../../../../../../../sdk-ptrace-generic-v1/regset-read-v1/kernel-build.json)保存实际命令、源码清单、NCE 复制阶段摘要、host_ops 头、实际 `.cmd` 和原输入前后摘要；[ABI 检查](../../../../../../../sdk-ptrace-generic-v1/regset-read-v1/kernel-abi-review.json)核对 ELF 与镜像的导出偏移及对应字节。guest 的 prepared 清单由测试侧会话生成，主会话审阅后串行运行。

独立构建脚本首次遗漏 GNU sed 的 PATH，生成 syscall_defs.h 失败；恢复原工具路径后，shared 链接发现 NCE 文件复制覆盖了原内核的翻译修改，报缺少 nce_translation_cleanup。修正脚本中的完整补丁顺序并重新核对全量源码后，构建与 ABI 检查成功。两次失败及最终结果保留于同一构建报告，原内核和 baseline 产物保持。

独立 APFS 克隆测试盘上的 LLDB 复现已确认诊断代码沿用旧 `prctl_get_seccomp` 偏移，跳入新内核 `__seccomp_filter` 的中间指令；具体地址、寄存器和修复范围见[诊断地址更新](2026-11-15-原SDK诊断地址更新.md)。v14 日志未确认 GETREGSET 是否已经调用。原 v14 输入和结果保持，v15 从实际 ELF 生成并校验私有诊断地址后已复验原 SDK。

v15 的 lifecycle、original、recovery CLI/GCD 六入口均退出 0，观察、停止回收、同盘恢复、SQLite 和 4322 项输入检查成功，两盘最终 clean。两个 original 各观察 180 秒，原 450 秒 Binder/SIGQUIT 条件未触发，完整 boot 为 failed。原 ashmem 分析缺少冻结 `pid1_validation.py`，六份 capture 的相应失败与原报告保持，独立来源恢复及离线重分析继续进行。原服务的转储结果继续按实际导出与协议核对；[本阶段汇总](../../../../experiments/native-linux/results-sdk-arm64-read-regset-20261115.json)分别记录寄存器读取、本机验证及 SDK 结果，提案继续为 proposed。

## 曾考虑的替代方案

- 开启 HAVE_ARCH_TRACEHOOK 并完整接入通用请求：配置还要求 syscall 跟踪和用户态返回处理；该范围超过当前只读寄存器需求，留作独立阶段。
- 直接返回内部 800-byte 保存块：公开 GPR 长度与内部布局不同，unwindstack 的架构识别会失败，且内部块包含本阶段未交付的浮点状态。
- 在内核按固定偏移读取 TLS：原生与翻译后端字段位置不同，实际读写已使用各自字段，改用一个真实 getter。
- 同时实现 SETREGSET 和 FPSIMD：本轮 crash_dump 使用方调查未找到对应生产调用；写入还需修复无映射 PC 恢复后发生宿主退出的问题，按公开 Linux ABI 单独推进。

## 验收标准

1. 原内核的已停止线程 GETREGSET / NT_PRSTATUS、NT_ARM_TLS EIO 保留；候选 CLI/GCD 使用同一 guest 检查完整 GPR 返回 272 bytes。GPR 内容与客体汇编保存的寄存器核对，包含 guest x18、SP、PC、NZCV 和停止期间保持原值的通用寄存器。纯用户循环与阻塞 read 均覆盖停止、读取、CONT、DETACH 及回收。
2. CLI/GCD 均检查 8-byte TLS 请求返回真实线程指针，16-byte 请求的第一项相同且第二项为 0；父任务、CLONE_SETTLS 子任务和恢复后的线程分别核对，保持原信号 mask、SP 偏移和 clone 初始停止。
3. 两个读取 note 覆盖零长度、短读取、超长截断、非 8-byte 长度、无效 iovec、输出缓冲区跨越不可读写页面以及只读 iovec 的最终长度写回失败。核对错误码、实际输出范围、`iov_base` 和 `iov_len`；失败后仍可正常读取和恢复目标。
4. SETREGSET、FPSIMD、TAGGED_ADDR_CTRL、PAC_ENABLED_KEYS 和未知 note 的 EIO 保持；原 SEIZE、INTERRUPT、TRACECLONE、GETEVENTMSG、CONT、DETACH 与全部回收检查继续成功。
5. 原生与翻译后端分别核对 TLS getter；翻译检查覆盖 Direct 和 Unicorn 的现有执行路径。生成内核、host_ops 头与实际宿主 `.d`、内核 `.cmd` 及导出偏移关联一致，标准 processes CLI/GCD 与 iOS arm64 编译检查成功。
6. 本阶段结果分别记录寄存器读取、本机验证、完整 SDK 转储及启动结果。完整 boot、桌面、通用 APK、HyperOS、iOS 执行、持续性能和热状态沿用后续验收；当前阶段继续离线验证。

## 风险

原 SDK 服务的 SIGABRT 和 system_server ANR 原因仍需分别处理。读取 GPR 和 TLS 可以让转储继续读取已停止线程，完整转储能否完成需要实际协议结果确认。所有日志与结果保持原失败，后续结果另行记录。

写入调查保存于[后续契约调查](../../../../../../../sdk-ptrace-generic-v1/regset-readonly-v1/write-investigation.json)。固定 Linux 的 GPR setter 不检查 PC 是否已经映射，恢复后的取指故障由客体处理。当前原生 NCE 的恢复跳转范围和 guest PC 识别存在宿主退出风险，后续写入实现需要按该公开契约修复；可恢复代码区域的限制不进入长期寄存器契约。本阶段继续保留 SETREGSET 的 EIO。

调查、实现准备及清理使用本项目 work 目录。已完成 processes 检查的隔离工作树和私有缓存已由主会话清理；本轮使用独立候选源码、原 Android 源码及保留的结构化报告，不再依赖上述临时产物。
