# 决策记录: macOS 原生 NCE 应用

状态: proposed

## 问题

2026-10-10，用户提出让当前 iPhone 应用也能在 macOS 独立运行，并评估 NCE 接近 QEMU + HVF 性能的可能性。本会话明确选择先交付可直接打开的 Mac App，再进行 HVF 对照；NCE 动态代码执行与 ART JIT 继续保留。本轮授权范围为调研和规划，应用实现尚未开始。

本提案增加独立的 Mac 使用场景。iPhone 的独立运行目标继续按[路线决定](../../implemented/architecture/2026-10-08-转向原生Linux与NCE.md)和[桌面提案](2026-10-09-Android可交互桌面.md)执行。Mac 与 iPhone 分别运行完整 Linux / Android，各自保存数据。

## 提案

### 优先决定的范围

建议首版面向 Apple Silicon，交付可从 Finder 打开的原生 macOS `.app`。先沿用当前 SDK Android 桌面、Launcher3、AOSP DeskClock、DocumentsUI 和 gfxstream/ANGLE Metal；HyperOS 3 继续按现有兼容性工作推进。Intel Mac 需要另行选择 ARM64 执行方式，首版验收只覆盖 Apple Silicon。

首版以本机使用为交付条件，运行所需内核、系统镜像、数据盘种子和动态库随包提供。Developer ID 签名、公证与其他机器的下载启动另设发布验收；具体签名身份和分发渠道尚未确定。最低 macOS 版本按依赖部署目标与实际验证确定，当前只核实了开发机 Apple M5 Ultra / macOS 27.0（26A428），没有据此确认其他版本的兼容性。

沿用 1 GiB Linux RAM、4 GiB 客体地址窗口、demand 映射及 360×640 Android 显示作为第一版配置。窗口缩放先保持 Android 的逻辑分辨率和宽高比，按实际显示区域转换输入坐标。高分辨率、动态显示尺寸、多核与扩大内存分别评估，防止在应用打包时同时改变执行条件。

### JIT 与签名

macOS 的启动准备由应用签名和代码内存管理完成。Android ARM64 用户代码继续由 NCE 执行，必要指令适配与运行时生成代码继续使用可执行内存；ART 仍按当前支持范围进行 JIT 编译。

Apple 的 [Apple silicon JIT 文档](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon)说明了 Hardened Runtime 下的 `com.apple.security.cs.allow-jit`、`MAP_JIT` 和写入保护要求。当前 `memory.c` 使用固定执行地址与 `vm_remap` 双地址映射，尚未采用该 `MAP_JIT` 流程。只添加 `allow-jit` 对现有实现是否有效，需要单独验证。

先用现有映射代码检查本机签名包，再在 Hardened Runtime 下验证所需例外。Apple 提供的 [Allow Unsigned Executable Memory](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-unsigned-executable-memory)是候选，具体适用性与最小权限以实验结果为准。验证必须覆盖内核映像、NCE 静态代码区、ART 动态代码区、指令缓存同步、代码权限恢复与数据页重映射。若现有映射在目标签名条件下不可用，再评估 `MAP_JIT` 适配对地址布局和别名关系的影响。

签名检查同时核对 gfxstream、ANGLE 及其传递依赖。应用从自己的 `Contents/Frameworks` 加载库，打包后核对加载路径和实际加载结果。签名实验的通过条件包含实际代码执行与 Android 启动。

### 应用结构与数据

首选复用 AppKit 窗口和同进程 Metal 显示，在现有接口上增加 Mac 应用生命周期。执行核心继续共享 LKL、NCE、Android 用户态、图形与输入实现；平台入口负责资源定位、宿主窗口、数据目录和启动错误。首版只管理一个 Android 会话。

建议将只读内核、系统盘与数据盘种子放入 `Contents/Resources`，图形动态库放入 `Contents/Frameworks`。Mac 可写数据使用独立的 Application Support 目录，具体子目录名随 bundle ID 固定。首次创建 ext4 数据盘时先完整写入临时文件，成功后再启用；更新 App 时继续使用已有数据盘。对数据盘加占用检查，覆盖重复打开应用或两个副本同时启动的情况。构建产物和开发原始日志继续放在项目 `work/`。

启动、运行、停止与失败状态由 Mac 入口维护，Android 就绪以实际系统与显示状态确认。关闭窗口与 Cmd-Q 都通过现有停止接口结束 Android，在 UI 线程之外等待进程、图形通道和磁盘释放。首版可以通过退出并重新打开 App 重启 Android；是否提供同进程重启按钮，取决于重新初始化检查的结果。

首版交互复用已验证的鼠标拖动和系统导航。触控板滚动与拖动手势、物理键盘和中文输入分别记录支持范围，再按具体 Android 输入接口增加。界面实现前提供两种低成本布局供用户选择：以 Android 画面为主的单窗口，以及带启动状态与日志入口的单窗口。视觉选择只影响宿主控件布局。

### 接近 HVF 的可能性与比较方法

基于当前执行方式，长时间执行普通 ARM64 指令、较少进行系统调用和进程切换的负载，有机会接近 HVF 下的计算性能。这是架构判断；本轮没有 NCE/HVF 实测比值。NCE 所需的 Linux 内核已编译为宿主代码，部分系统调用也可能具有较低成本，具体结果受桥接、调度和映射影响。

完整 Android 的限制更明显：当前单 Linux CPU、多进程共用地址窗口、映射与缺页处理、ART 编译覆盖及图形传输都可能增加开销，详见[性能风险](../architecture/2026-10-10-HyperOS性能风险与验证.md)。Mac 的资源与运行条件有利于开发和持续测量，这些执行结构仍需逐项处理。

[Hypervisor.framework](https://developer.apple.com/documentation/hypervisor)提供硬件辅助的 VM 和 vCPU，客体内核与用户态可以在虚拟 CPU 内运行。采用 HVF 的客体可以由自己的内核和硬件页表处理进程地址空间；普通客体系统调用是否触发退出取决于所执行的操作。[QEMU 文档](https://www.qemu.org/docs/master/system/introduction.html)列出了 macOS 上的 HVF 支持，设备与图形仍需要对应实现。桌面帧率也会受到图形后端和同步方式影响。

比较分为两组：先在相同内存预算、单客体 CPU 和匹配负载下分析开销，再与启用多个 vCPU 的实用 HVF 配置比较最终体验。匹配对照与实用配置分别报告。HVF 侧先核对可启动的 Android ARM64 镜像、设备模型和图形后端；同一套 NCE 修改后的内核、Bionic 和 ART 不能直接假定可供 HVF 使用。无法统一的组件与版本逐项列出，CPU 专项与整机比较分别解释。

测量至少覆盖：原生整数与内存计算、Java 冷/热执行、系统调用与 Binder/futex 往返、切换进程时不同工作集的访存、从宿主启动到 Launcher 可接受输入、应用首次与再次打开、连续滑动与应用切换、内存占用及持续运行热状态。每项注明设备、系统、源码与构建标识、镜像与数据盘状态、JIT/AOT 配置、分辨率、CPU 数、内存、图形后端、时间单位与统计范围。先做短测确定重复次数和持续测量时长，固定协议后采集双方样本。

帧时间同时检查 Android 合成与宿主呈现，响应时间使用一致的起止事件；诊断用详细映射统计单独采集，正式计时关闭会明显扰动执行的日志。两种运行方式顺序执行，结束闲置实例，避免相互争用资源。用户尚未指定“接近 HVF”的数值范围，结果先报告各项差距。

按 reclaim-code-entropy 检查现有调用与拟议新增内容，以下为本轮思想实验，尚无代码删改。

| 拟议内容 | 使用方与必要性 | 省略后的影响或取舍 |
| --- | --- | --- |
| Mac 生命周期与资源定位 | Finder 启动没有现有测试脚本传入的参数与环境 | 保留当前窗口原型会继续依赖外部启动命令，需要新增 |

## 曾考虑的替代方案

- 直接使用当前测试 `.app`：已有窗口，但启动需要内核参数与外部库环境，无法满足 Finder 直接打开的条件。
- 运行现有 iOS 包或改为 Mac Catalyst：现有包携带 UIKit 入口和 iOS 二进制依赖，需要逐项调整；仓库已经有原生 AppKit 窗口，优先复用该入口。
- 先完成 HVF 基准再决定是否做 App：用户明确选择 App 优先，基准安排在阶段交付之后。
- 直接以 QEMU + HVF 交付 Mac 版：该方式适合作为对照；用户希望探索共享 NCE 实现的独立 Mac 应用，本提案保留这一目标。
- 在首版加入多宿主进程和多核：可能缓解共用地址窗口的限制，也会改变调度、共享内存和图形资源管理；先测当前 App，再根据主要耗时决定架构调整。

## 验收标准

1. App 在已声明支持的 Apple Silicon/macOS 环境中从 Finder 启动，所需运行文件来自 App 包与用户数据目录；移动安装位置后仍可运行。
2. Launcher、Clock 和 Files 可显示、操作和切换；正常停止并重新打开后，应用数据与密钥保留。鼠标坐标在缩放后正确，首版输入支持范围明确。
3. 覆盖资源缺失、磁盘空间不足、代码执行权限失败、图形初始化失败、数据盘被占用、启动过程中退出与正常 Cmd-Q。强制终止后检查下次启动与 ext4 恢复结果，不宣称未落盘操作已保存。
4. 对最终签名包执行动态代码、Linux 进程/内存/信号、ART 与图形回归；共享执行代码有修改时保留 CLI/GCD 检查及 iOS 编译验证。已有测试结果与新增运行结果分别记录。
5. App 交付完成后执行 HVF 比较；保留配置差异、失败与退化。性能目标按用户后续接受的具体负载与差距确认。

本轮仅检查源码、阶段记录和 Apple/QEMU 官方文档，新增本提案。没有构建 Mac 产品包，也没有验证 Hardened Runtime、签名例外、跨机器分发或 HVF 性能。

## 风险

签名后的固定代码地址与双映射行为可能要求调整内存实现；gfxstream/ANGLE 的包内依赖和签名可能增加打包工作。现有同进程结构中执行核心故障会结束宿主应用，退出和磁盘恢复必须单独验证。

NCE 当前单 CPU 和共用地址窗口可能使多进程负载明显落后于 HVF；ART 与系统组件差异也会影响比较。完整 HyperOS 的厂商兼容、网络及外部存储范围仍按现有主题跟踪，Mac 应用启动成功只确认本阶段交付的系统内容。
