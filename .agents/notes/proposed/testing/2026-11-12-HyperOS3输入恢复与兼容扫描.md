# 决策记录: HyperOS 3 输入恢复与兼容扫描

状态: proposed

## 问题

2026-11-12 用户保留完整 HyperOS 3、手机独立运行和原始签名 APK 的目标，并允许重做执行架构。当前正在恢复 Android 基线，HyperOS 原镜像与旧 `work/hyperos3-import/` 已缺失。本记录明确可取得的输入、需要扫描的依赖和后续验收范围。初查读取本地源码、Git 历史与 GitHub API，随后按主会话授权恢复固定发布包；全程未使用网页搜索，未启动 HyperOS，未修改正在验证的 APK 或系统执行源码。

## 提案

### 输入版本与取得条件

旧[启动记录](../../implemented/testing/2026-10-07-HyperOS启动验证.md)记录 `OS3.0.2.0.WMCCNXM`、Android 16，以及 HyperOS-AVD 的 ext4 系统分区。旧实现保留 Husk 内核、vendor 和启动分区，在 GPT 末尾追加 HyperOS 分区，修改 fstab、CIL 与 init。该轮在 QEMU 进入桌面、设置和关于页面；当前 LKL / Direct 的启动兼容性需单独验证。

旧准备脚本可只读查看：

git show 9738ee4950375959ac4ff873078770af1e111aba:scripts/hyperos3/init.rc
git show 9738ee4950375959ac4ff873078770af1e111aba:scripts/test_hyperos_boot.py

脚本固定 Husk `vda-v12.qcow2` 的 SHA-256 为 `a8dbaecc8fdcd682991b078d6bbb7df6972e459208634fa8dcbad24f17208d6a`，2026-11-12 用 `gh api repos/Leviidev/Husk/releases/tags/lineage-v2` 查询仍存在，发布附件大小为 2,057,568,256 字节。脚本仅检查 HyperOS 输入为 ext4，随后把 `source_system_sha256` 写入输出清单。该清单未进入当前仓库，无法据此确定旧 HyperOS 输入的字节身份。旧脚本对 GPT、Husk vendor_boot 和 metadata 的修改也不适用于当前 LKL 系统盘。

已定位 [HyperOS-AVD OS3 发布](https://github.com/NEORUAA/HyperOS-AVD/releases/tag/v0.1.0-a16-hyperos3-fuxi-r1)，对应代码提交 [`9d7ddd3f046e89d33cb205b5fbbf6dc5b728155c`](https://github.com/NEORUAA/HyperOS-AVD/tree/9d7ddd3f046e89d33cb205b5fbbf6dc5b728155c)。发布信息与源码说明输入来自小米 13 `fuxi` 的 MysticGSI，版本为 HyperOS `3.0.2.0.WMCCNXM`、Android 16 / API 36。这是已移植的 GSI 输入；官方 OTA 内容是否完整保留，当前没有镜像级清单可供核对。

### Android、ABI 与 vendor 的已知差异

当前 DroidOnDarwin 输入为 `arm64-v8a-ps16k-36_r07.zip`，来自 Google APIs 16 KiB 页 SDK 镜像；现有 `system_ext/etc/build.prop` 的指纹为 `google/sdk_gphone16k_arm64/emu64a16k:16/BE2A.250530.026.F3/13894323:userdebug/dev-keys`。HyperOS-AVD 固定版本使用 API 36 Google Play ARM64 revision 7、ranchu Android 15 / 6.6 内核，兼容性范围见其[说明](https://github.com/NEORUAA/HyperOS-AVD/blob/9d7ddd3f046e89d33cb205b5fbbf6dc5b728155c/docs/compatibility.md#L1)。共同的 API 36 仍需逐项核对 Framework、ART、Bionic、APEX、HAL 和内部接口。

固定版本 [`build_image.py`](https://github.com/NEORUAA/HyperOS-AVD/blob/9d7ddd3f046e89d33cb205b5fbbf6dc5b728155c/scripts/build_image.py#L83) 直接执行了下列适配，属于源码事实：

- 从 SDK 复用 vendor 与 system_dlkm；关闭独立 product、system_ext 挂载，因为 GSI 将这些目录放在 system 内；加入 ranchu ADB、radio 和 modem 初始化文件。
- 选择 64 位 mediaserver，将 GSI 内仅有 ARM32 的 drmserver 替换为 SDK ARM64 可执行文件。当前 Direct ELF 入口只接受 ELF64 AArch64，见 [linux-elf.c](../../../../experiments/native-linux/translation/linux-elf.c#L29)。其他必需 ARM32 组件是否存在，等待扫描完整镜像。
- 修改 `services.jar` 中 GNSS 回调的线程执行方式，处理与 ranchu HAL 的锁等待；补充三个小米 CameraServiceProxy 属性标签、logcat 标签与开发者选项日志权限。应根据实际选用 HAL 复现相关行为，再决定继承哪项修改。
- 修改 ramdisk，加载 KernelSU 的 `android15-6.6` 模块；打包 system、vendor、system_dlkm。这些内核模块与启动配置依赖 ranchu，当前 LKL 不可直接装入该模块。

当前 LKL 使用自己的图形 composer、gralloc、音频、网络与安全服务组合，[vendor-manifest.xml](../../../../experiments/native-linux/services/vendor-manifest.xml) 仅声明其中部分接口，其他片段由 [build_nce_userspace.py](../../../../scripts/build_nce_userspace.py#L330) 合并。HyperOS 完整扫描需要列出所有 init 服务、VINTF HAL、动态库、属性和设备节点依赖，再逐项对应当前实现；未知小米服务不能仅靠删除启动项结束兼容检查。

旧[ELF 调查](../../implemented/architecture/2026-10-07-HyperOS执行架构调研.md#本次镜像检查)发现 8 个核心样本的 `p_vaddr-p_offset` 均与 16 KiB 同余，但其中多个样本按 16 KiB 取整后出现不同权限段共页。该记录仅覆盖 8 个文件，原始结果已缺失。本轮应重扫全部 ELF 和 APK 内嵌库，分别报告 ELF 架构、`p_align`、段同余、取整后的段权限冲突、ZIP 数据偏移和压缩方式；仅凭 `p_align=4096` 无法判定当前 Direct 必然拒绝。

### 系统组件与签名检查

最小扫描必须同时覆盖 Framework 与应用关系。当前 [android_data()](../../../../scripts/build_nce_userspace.py#L295) 从 SDK classpath 描述复制 JAR，并固定选择 `framework-res.apk`、SystemUI、Settings、权限 XML、RRO、APEX 与 aconfig 内容。只替换 Launcher、SystemUI 或 Settings 能验证相应组件；完整 HyperOS 阶段需使用同一输入中的 Framework 扩展、系统服务、资源、系统应用及它们要求的模块，记录所有替换和修改。

原镜像取得后，优先为 `framework-res.apk`、Settings、SystemUI、Launcher、SettingsProvider 和其他 `sharedUserId` 包执行 `apksigner verify --verbose --print-certs`，记录文件摘要、签名证书、包名和版本；用 `aapt2 dump xmltree --file AndroidManifest.xml` 读取 shared UID、signature 权限、`uses-library` 与 overlay target。再关联各分区的 `privapp-permissions`、`sysconfig`、`mac_permissions.xml` / `seinfo`、overlay 配置与 Framework 资源。首批五个 APK 的实际检查结果见后文，其他包的签名分组待扫描。复制与安装流程保留发布文件的字节和证书；原厂签名身份仍需另行核对。签名校验失败应保存具体依赖和 PackageManager 日志。

APEX 还需分别记录归档证书、`apex_pubkey`、manifest 模块名与版本、载荷摘要、classpath 和依赖；JAR/DEX、boot image、OAT/VDEX 的兼容由 ART 格式及内容依赖检查。当前 [ApexRegistry](../../../../experiments/native-linux/userspace/apex-service.cpp#L25) 报告构建时选定模块，并检查归档大小和展开 manifest 存在；这项检查没有覆盖真实 apexd 的验证、激活和系统模块更新。完整 HyperOS 的后续验收需明确这些运行行为。

### 最小离线扫描步骤

1. 先核对下载、成员与分区身份。确认 `system.img` 是打包的 GPT / liblp 磁盘还是原始 ext4；固定发布的构建代码使用前一种布局，旧 `prepare_hyperos3.py --system` 要求后一种。提取 system 分区前核对元数据和范围，原镜像只读。
2. 用只读 `debugfs -R`、`dump.erofs --cat --path=...` 取得 build.prop、fstab、init rc、classpath、VINTF、权限与 SELinux 配置，建立路径及摘要清单。记录 Android/API、指纹、ABI、分区布局、sepolicy 版本、Framework JAR 和必须启动的服务。
3. 仅提取首批所需文件，扫描 ELF 的架构、PT_LOAD、DT_NEEDED、符号版本，以及 APK 签名、Manifest、内嵌库。按运行时 linker namespace 解析依赖路径，单独列出未找到和版本不匹配的依赖，不能只按库文件名匹配。
4. 对照当前构建输入，先形成「可直接使用」「需要实现接口」「需要重建或适配」「信息缺失」清单，并为每项给出原文件路径和实际检查输出。首批覆盖 app_process64、linker64、Bionic、ART、SurfaceFlinger、libandroid_runtime、miui-services、framework-res、SystemUI、Settings 和 Launcher；实际文件名以扫描为准。

本机已有 `/opt/homebrew/opt/e2fsprogs/sbin/debugfs`、`/opt/homebrew/bin/dump.erofs`、`/opt/homebrew/opt/llvm/bin/llvm-readelf`、build-tools 36.0.0 的 `aapt2/apksigner` 与 `protoc`。`lpunpack`、`simg2img` 不在 PATH；需要先审阅现有分区解析器和镜像格式，再选择提取工具。本轮没有运行下载源码中的构建或安装脚本。

### 已授权的输入恢复实施

主会话随后授权下载上述三个分卷并实施最小离线扫描，新增占用约束为 12 GiB，另为当前 Android 构建保留空间。先完成 APK 命令与日志契约的独立自查，随后开始固定 tag 下载；源码修改继续限定在独立检查脚本与本记录，不涉及冻结中的 Android/APK 输入。

已新增 `scripts/inspect_hyperos_input.py`，输入为已下载发布目录，输出为项目 `work/` 下的新目录。脚本固定清单摘要，逐卷检查后通过 `cat` 的标准输出顺序读取 gzip/tar；不写串接压缩包，也不展开 userdata。系统磁盘只保留最前 4 MiB 供 GPT/liblp 元数据解析，检查主 GPT 的 CRC、liblp 元数据摘要、条目大小与范围、单设备线性 extents；随后在计算完整成员摘要的同时，写入 `--partition system` 或 `--partition vendor` 选定分区的相应字节。`images/vendor.img` 与选定小型元数据按发布清单提取，来源成员摘要和派生分区摘要分别记录。每次输出预算为 8 GiB，写入前检查预算，超出范围或遇到未支持布局就失败。镜像只保留一份 system 分区，其他文件与配置按实际目录选择提取，继续核对总占用。

这一实现只支持已固定输入，不增加任意固件安装、AVD 注册或写镜像功能。`test_hyperos_input.py` 已检查截断、GPT/liblp 摘要错误、分区越界、重叠、非线性 extent、分区集合错误、输出预算、选定分区字节，以及 4 KiB / 16 KiB ELF 权限共页，6 个测试成功。提取器另检查路径与重复成员。`inspect_hyperos_files.py` 使用只读 `debugfs` 和 `dump.erofs` 选择系统配置及核心 ELF、APK、APEX 样本，记录文件摘要、工具命令与退出码；单次文件输出限 1 GiB。APK 签名、Manifest 和 ELF 检查结果独立记录。DroidOnDarwin 运行兼容性仍待验证。

本轮实际布局中，`images/vendor.img` 为独立 GPT 磁盘，而构建脚本修改的 vendor 位于 `images/system.img` 的 liblp。首次扫描独立 vendor 时，直接执行 `dump.erofs` 返回「cannot find valid erofs superblock」；读取 GPT 后确认其分区从 1 MiB 开始。后续从 system 磁盘补取逻辑 vendor，核对到 fstab 中 product/system_ext 挂载项已注释，扫描使用该逻辑分区。没有保存第二份 system 分区。文件扫描器首次遇到根目录和 toybox 的 `[` 符号链接名，路径白名单过窄导致退出；已调整允许的路径字符，失败记录保留在 `work/`。

ELF 结果需要分开解释：

- 8 个系统 ARM64 样本（app_process64、SurfaceFlinger、mediaserver64、libandroid_runtime、libbinder、libgui、libEGL、libui）包含 `p_align=4096` 的 LOAD，全部满足 `p_vaddr-p_offset` 对 16 KiB 同余，按 16 KiB 取整后有 1–2 组不同权限 LOAD 共页。SDK 替换的 drmserver 使用 16 KiB LOAD，样本未出现权限共页。
- ART 的 `libart.so` 使用 2 MiB LOAD，满足 16 KiB 同余，未出现权限共页；同模块的 libartbase、dex2oat64、artd，以及 runtime 的 linker64、libc、libdl、libm 含 4 KiB LOAD 并有权限共页。后续需验证文件映射、BSS 清零、RELRO 和 mprotect 的相互影响。当前 [Direct ELF 布局](../../../../experiments/native-linux/translation/linux-elf.c#L29)检查段同余，样本还需实际装载执行。
- MiuiHome 的 4 个 ARM64 JNI 库以未压缩 ZIP 成员保存，数据偏移均为 16 KiB 对齐；其 ELF LOAD 为 4 KiB，并出现不同权限段共页。ZIP 对齐检查与 ELF 加载检查分别保留。
- 镜像内存在 ELF32 ARM 的 app_process32，样本未满足全部 LOAD 的 16 KiB 同余；当前 vendor 配置选择 zygote64。尚未扫描全部可执行文件，也未确认必需服务是否仍包含 ARM32 路径。

这些结果给出了可以直接复用的固定输入和配置文件，也列出了需要实现或核对的依赖。首个运行实验应在新数据盘上加载原始 linker64/Bionic 与一个简单 ARM64 ELF，检查实际页大小、段内容及保护；随后验证原始 ART 的 Java/JNI、GC/JIT 和这些 classpath，再启动 HyperOS Framework、SystemUI 与 Launcher。按 linker namespace 核对完整动态依赖、签名轮换、全部 APK 内嵌库和系统服务仍属待做项。

## 曾考虑的替代方案

- 直接恢复旧 QEMU 准备脚本：可以帮助追溯历史分区与启动配置，依赖 Husk v12 的 GPT、vendor_boot 和旧输出，无法作为当前 LKL 安装步骤。
- 先将 HyperOS 桌面 APK 放入 SDK 系统：可以较早暴露签名、资源或 Java 库问题，结论仅限对应组件，仍需完成完整 Framework 与系统服务集成。
- 直接取得手机 OTA：有助于核对原厂组件与改动范围，但当前没有已固定的 OS3 OTA 输入。先使用具有发布清单的相同 OS3 GSI 版本恢复扫描；完整原厂组件目标仍需另核对其覆盖范围。

## 验收标准

输入恢复阶段要求下载与提取摘要匹配，分区与文件清单完整，所选核心 ELF/APK/APEX 的依赖、ABI、签名、页布局和系统配置有可复现结果。本轮已完成固定发布下载、分区恢复和上述选定文件扫描；全量依赖解析与运行兼容仍待验证。

组件阶段分别检查安装、Java/JNI 加载与运行；完整系统阶段检查 HyperOS Framework、system_server、SystemUI、Launcher、Settings、必要系统服务及真实图形输出，保持原始签名 Java/JNI 应用的安装、更新、数据跨重启与错误路径检查。所用虚拟设备实现、缺失或替换的服务、SELinux/AVB/APEX 状态须随结果记录。只有界面显示或 `sys.boot_completed=1` 的结果只满足相应启动检查。

## 风险

旧镜像与可下载发布包的字节身份尚未对齐。第三方 GSI 已改动 Framework 和服务，实际保留了哪些原厂组件需读取镜像后确认。当前 Android 基线的成功也不能确定 OEM 内部接口、ARM32 依赖、16 KiB 页、硬件服务、签名分组或系统模块更新能满足 HyperOS。各项不确定内容在扫描结果中保留，不据此提前删除功能或降低完整系统目标。
