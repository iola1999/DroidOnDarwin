# 决策记录: SDK 无加密启动与性能基线

状态: proposed

## 问题

用户在 2026-11-13 询问加密的必要性及其性能成本。固定 SDK36 的 `/data` 在早期 ramdisk 和 vendor fstab 中设置 `fileencryption=aes-256-xts:aes-256-cts` 与 `keydirectory=/metadata/vold/metadata_encryption`；[原 first-stage 阶段](../../implemented/architecture/2026-11-13-SDK36原始first-stage启动.md)的四个 original 入口均在原 vold 创建 `default-key` 后记录 `DM_TABLE_LOAD=-22`，完整启动尚未通过。[原 vold 与 default-key](../../proposed/architecture/2026-11-13-SDK36原始vold与default-key.md)已完成必要内核修改和 16 KiB 编译，实际加密 I/O、完整系统与性能仍待验证。

当前项目允许依据实际启动和性能结果调整系统及宿主实现。保留原 fstab 的加密要求是此前采用的实现选择，需要和无加密配置下取得完整启动与性能基线的成本比较。软件加密会增加 CPU 运算和缓冲区处理，当前没有整机加密负载的测量结果。

## 提案

在 `codex/sdk-plain-data-baseline` 的独立工作树与磁盘候选中，先移除两份 fstab 的 `/data` 文件加密和密钥目录选项。原 SDK 镜像、原 ramdisk 和已交付四盘保持其字节；候选记录输入摘要、实际变更与部署摘要。原 init、vold、rc、策略、系统库和其余 fstab 选项继续使用固定来源。

固定 system/core `68be0c2c0006a0740d0b1809abe4717308f90d15` 的 `init/builtins.cpp` 在 `IsFbeEnabled()` 后才设置目录加密策略，`installkey` 在 `ro.crypto.type` 不为 `file` 的分支直接成功。`fs_mgr/fs_mgr.cpp` 的 metadata 条件同时要求密钥目录和文件加密；移除两项后按普通挂载分支处理。固定 vold `11760521a2e86389c56620ec50e780e8b17e40ca` 的 `FsCrypt.cpp` 包含非 FBE 的目录准备分支。因此先保持原 `init.rc`，由实际运行确定后续修改。公开源码和 SDK 二进制的精确对应仍未确认。

先生成具有新源码身份的 16 KiB core CLI/GCD，再运行两份 fstab 实际部署的原 PID 1。当前观察器的 30 秒等待与 `first_stage.completed` 只覆盖启动观察和首阶段；完整启动需要原系统实际报告 `sys.boot_completed`，并核对原 Zygote、system_server、系统服务与应用操作。每次运行保存超时、实际退出、停止、进程组和盘状态；停止完成前不得检查或关闭仍由运行进程使用的盘。

运行前审阅用真实宿主父子进程复现了观察器的中断问题：向子组发送 SIGTERM 后，观察器在清理阶段收到 SIGTERM，原 handler 抛出 `InterruptedError`，返回前仍有 parent 和忽略 SIGTERM 的 child，leader 尚未回收。回归 fixture 的 finally 已用 SIGKILL 停止全部测试进程。修复已将 handler 改为记录中断，初始等待以最多 0.1 秒分段检查中断，清理继续检查、停止和回收子组。`work/native-linux-nce/sdk-plain-process-check-v1/after-interrupted-cleanup-fix/result.json` 的 13 项检查成功，初始等待和清理期间的真实 SIGTERM 均已触发，fixture 的 finally 清理前已独立确认进程组为空、leader 已回收。原失败保存在同目录的 `interrupted-cleanup-review/result.json`。

### 本机准备与首轮运行

`stock_init_plain_data.py` 使用 libext2fs 修改独立 APFS 克隆中的原 vendor fstab inode。候选仅改变两个 4096-byte 块：fstab 内容与清零后的尾部，以及原 inode 的文件长度。所有者、模式、SELinux 标签、原 inode、五个 LP 范围和 vendor 外字节均已检查。原 `shared_blocks` 盘的引用检查覆盖 586 个有效目录/文件 inode，块 9413 在这些扫描项中仅由 inode 304 引用；零链接 inode 未纳入该扫描，结论保留这个范围。

`work/native-linux-nce/sdk-plain-input-check-v1/validation-v2.json` 对应模块 `8077a0f5…`，验证候选写入和读回，尚未执行客体。追加同卷前置条件后的模块为 `1fb4a7dc…`；首轮实际启动使用该版本并再次完成候选准备。early 与 vendor 候选 fstab 都为 1528 bytes，SHA-256 为 `1fdcee20dbace778b63ed1c49eafc1f24e12e350e97e5477b1ba0f2e6075dacc`。

新内核沿用 Linux `d0f76a77e8c2ca68bd7d96190b8da09040eab072`。首次 `core-16k-v1` 编译后，在运行前发现 `processes/sigreturn.elf` 引用缺失；补入六份只读 runtime ELF 引用后，`core-16k-v2` 的 CLI/GCD 各 128 项成功，52 项独立内核输入摘要一致。实际配置关闭 FS_ENCRYPTION、BLK_INLINE_ENCRYPTION、FS_VERITY 和 DM_CRYPT，QUOTA 开启。两次结果分别保存在 `work/sdk-plain-validation-v1/core-16k-v{1,2}.json`。

首轮 `sdk-plain-init-16k-v1` 的 lifecycle、original、recovery CLI/GCD 共六个入口成功，源码摘要保持、所有宿主进程组为空。两个 original 都完成原 ramdisk、五个 LP 挂载和 switch_root；原 init 直接以 ext4 挂载 `/dev/block/vdc` 到 `/data`，mount 返回 0，原 `vdc --wait cryptfs init_user0` 退出码为 0。全部 77 条 DM_TABLE_LOAD 返回 0，类型分别为 5 个 linear、48 个 error、24 个 verity，没有 default-key target。同盘恢复后 data/metadata 均 clean，原 metadata 盘、系统镜像和 ramdisk 保持其摘要。首轮摘要中的 `ramdisk_deployment_pending=True` 沿用了准备阶段字段，实际部署结果以原 entry 的逐字节读回记录为准；后续运行会在这些检查成功后更新该字段。

本机为 Apple M5 Ultra、macOS 27.0（26A428），构建起点为 `3a4d470` 的独立工作树。首轮 wrapper 共 96.945533 秒，覆盖准备、编译、六个观察和磁盘检查，不能用作 Android 启动耗时。两个 original 的 30 秒范围均执行 `art_boot` 并成功退出，随后启动 odsign；原 rc 接下来等待 `odsign.key.done=1`，zygote-start 还需要 `odsign.verification.done=1`。该范围没有观察到 Zygote 启动或 `sys.boot_completed`。下一轮先显式延长原 init 观察至 180 秒，保留原 rc 和服务；自定义时限仅用于无加密候选，original 宿主单入口超时为 `max(90, 观察秒数 + 60)` 秒，lifecycle/recovery 仍为 90 秒。原 30 秒默认值与 lifecycle 的两秒检查保持。

第二轮 180 秒观察的日志及报告增长到约 24 GB，停止后 wrapper 失败，probe 退出码 -15，recovery 未完成。失败范围、停止记录、data 的 journal/orphan 标记与离线 `e2fsck -p` 恢复结果见[原 init 观察日志增长](../../proposed/bug-fix/2026-11-13-原init观察日志增长.md)。该轮尾部持续记录 `msync(...,16384,0)=-12`，附近两次私有可写匿名映射请求均为 1 GiB+256 KiB 并失败；原 ART 分配和内核提交检查的对应范围见[内存提交配置](../../proposed/bug-fix/2026-11-13-原ART启动的内存提交配置.md)。具体 PID 188 的进程名及调用栈仍未确认。

日志采样、限额与宿主回收回归已成功。新运行先使用默认内存提交策略观察 45 秒并读取实际 sysctl/meminfo，再显式提前设置原 Android 后续采用的 `overcommit_memory=1`，观察 180 秒。两次配置与时限分别记录，完整启动和性能继续独立验收；原 init、rc、库和 1 GiB RAM 配置保持。该调整由实际匿名映射失败确定，属于初次延长观察后的实现偏离。

本实验用于比较配置与取得完整系统测量条件。原 vold 的加密支持继续保留独立候选，原始签名 APK、同盘持久化、HyperOS 3、iPhone 独立运行和持续性能的最终目标保持。当前只做本机开发及 iOS 编译，设备运行和热状态继续待真机验证。

### 原 BPF 加载器的整合

原 NetBpfLoad v0.47 要求可写的 JIT sysctl 和非零 `jited_prog_len`。独立 `codex/sdk-plain-bpf-jit` 候选已完成 16 KiB / 4 KiB core、九个真实 BPF 程序、ringbuf 与两种页大小的 iOS 运行库编译。最终真实程序检查保存于主工作区 `work/sdk-plain-validation-v1/bpf-jit-syscall16k-v4/` 和 `bpf-jit-syscall4k-v3/`，每个 CLI/GCD 入口均核对实际退出、日志上限、进程组、上下文和执行池归还。上述结果仍未覆盖原网络对象、完整 loader、callback 和发布失败后的回收。

主会话将八份必要生产文件移入无加密工作树，复制前确认目标文件没有其他未提交修改，来源与复制清单位于 `work/sdk-plain-validation-v1/bpf-jit-plain-integration-v1/selected-sources.json`。在该树重新生成 core 报告及输入摘要，再使用原 init、NetBpfLoad、SELinux 与重启规则进行完整启动观察。系统服务观察器采用两份 tmpfs RC 和原 `/system/bin/sh -c`，实际部署与脚本执行继续由原启动验证。每轮仍先停止运行并确认宿主进程组为空，再执行同盘恢复和磁盘检查。

当前优先取得无加密的完整启动、应用操作与同条件性能结果。加密候选后续验证暂缓；APK 签名校验和 Keystore/KeyMint 的原系统功能继续保留。此前慢速结果尚未启用本次新增的加密支持，当前没有可比较的加密与无加密整机性能结果。

## 曾考虑的替代方案

- 继续先完成原加密路径：能验证固定原 fstab，但内核接口、密钥服务、实际加密 I/O 与同盘恢复均需要后续验收。先比较无加密启动的实际成本。
- 只修改宿主 staged vendor fstab：raw first-stage 在 ramdisk 部署后直接执行原 `/init`，随后挂载系统镜像中的 vendor LP，staged 文件不会在该入口部署。
- 同时修改原 `init.rc` 的目录策略和用户初始化：固定源码已有非 FBE 分支，先保持原字节，修改由实际运行结果决定。
- 直接运行此前 v9 二进制：最终保留清单已清理内核和宿主可执行产物，需要按新工作树重建。

## 验收标准

1. 两份实际使用的 fstab 仅移除 `/data` 的指定两项选项；全部其余选项、原 rc 和系统来源可核对。候选与原始输入使用独立 inode，原输入及四份交付盘在实验前后保持。
2. 新 core CLI/GCD 与独立内核构建输入核对成功。原 PID 1 的实际 `/data` 挂载、状态属性、原 vold 用户初始化及首阶段结果分别保存，失败继续保留实际范围。
3. 完整 boot 采用原系统的实际启动完成属性、进程及服务检查；首阶段完成、观察器退出或局部服务运行分别记录各自范围。
4. 同盘重启后的应用数据、安装更新及原始签名保持；性能记录环境、构建、配置、负载、采集范围与失败样本。配置改变后的结果不能直接代替原 fstab 的加密验收。
5. 所有宿主和客体进程停止、回收成功后再检查候选和释放映射；每轮记录清理范围。iOS 编译按实际候选源码执行，手机授权、资源和持续热状态待真机验证。
6. 新增配置入口、候选生成与观察按 reclaim-code-entropy 核对实际使用方及必要状态；技术文字按 humanizer-zh 审阅。

## 风险

固定源码包含非 FBE 分支，原 SDK 二进制的实际路径仍需要运行确认。原启动可能继续受其他内核接口、平台服务、APEX、图形和 framework 依赖阻断。无加密基线会改变数据存储的安全属性，其结果需要明确配置，当前实验不会自行变更最终产品的安全要求。

### 2026-11-14 接续

已按用户要求建立新的 active goal，并保留原目标与工作树。用户明确允许必要的加密与 JIT，当前继续原系统无加密启动和真实 BPF JIT。v11 在观察器 contract 1/2 不一致处停止，原 init 未运行；[版本检查修复](../../implemented/bug-fix/2026-11-14-原系统观察器与first-stage版本检查.md)后 v12 的准备和 lifecycle CLI/GCD 成功。original CLI 的诊断日志增长至 33,704,477 bytes，观察器按 32 MiB 限额停止，实际退出 -15、进程组为空；完整启动 pending。

停止后使用 v12 的实际宿主进行 mounted-partition lifecycle CLI/GCD，journal 恢复、两盘身份、generation 和完整回收检查成功，两盘最终 clean。结果见主工作区 `work/native-linux-nce/sdk-plain-recovery-after-v12-v1/result.json`。该轮没有形成 Android 启动或交互提速结论，后续先限制通用 syscall 诊断，再继续原加载器与系统服务验收。

### 原加载器成功与完整启动验收失败

最终 v13 的 lifecycle、original、同盘 recovery CLI/GCD 共六个入口通过各自观察、停止与回收检查，原 first-stage 完成，两盘最后 clean。CLI 原 NetBpfLoad v0.47 报告 success，bpfloader 退出 0；完整 boot 验收为 failed。原 SurfaceFlinger 的 SIGABRT 及后续 Zygote/netd 重启继续调查。结构化结果见[接续阶段结果](../../../../experiments/native-linux/results-sdk-plain-bpf-takeover-20261114.json)，完整报告按清单压缩保存。

iOS runtime 的 129 项输入与库摘要保持；实际 v13 的 runner/execution 两份 arm64 Mach-O对象编译成功，编译前依赖预扫描和编译后 159 项输入核对保持。上述结果覆盖本机功能和交叉编译，当前没有整机提速或手机运行结论。
