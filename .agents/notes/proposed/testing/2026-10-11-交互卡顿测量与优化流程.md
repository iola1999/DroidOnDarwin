# 决策记录: 交互卡顿测量与优化流程

状态: proposed

## 问题

用户体验 `0.25.0-Mac-20261011-220337-direct1-dual` 后反馈滚动和页面打开仍明显卡顿，要求探索接近原生 iOS、Android 设备的流畅度。此前[完整产品对照](2026-10-11-完整桌面产品性能对照.md)主要覆盖启动、应用首帧、内存和停止。启动中位数减少 31.0%，尚未说明持续交互的表现。当前缺少全部帧、输入到显示以及客体与宿主关联的耗时记录。

方法调查与接口预检完成后，用户于 2026-10-12 授权按本文流程继续实施。工作区已有 `scripts/lkl_nce_patch.py` 的首次宿主任务创建修复候选。该候选仍需完整回归，尚未确认与交互卡顿或此前图形停止等待的关系。

### 已确认的交互表现

环境为 Apple M5 Ultra、macOS 27.0 (26A428)、256 GiB 宿主内存、1 GiB 客体内存、360×640 显示。Direct 单核，每类执行器缓存 128 MiB，nterp、代码页写入跟踪及跨页访存开启；AOT、boot image、快速访存和代码检查/跳转复用关闭。请求调度时间片为系统默认，日志中实际 Linux 基础时间片为 750000 ns。

整轮累计 4554488 次 Direct 调用、250118766 次代码查询、740206 次代码块编译、111717 次 Unicorn 回退和 17 次缓存清空。累计次数覆盖启动、操作和停止，尚未得到交互窗口内的次数增量及时间占比。对这些计数的判断须等分段采集。

当前结论：秒级卡顿已确认；主线程处理及此前等待、渲染命令与缓冲区等待均出现长区间；执行器、Linux 调度、宿主调度、Binder、ART 和 GPU 的具体责任尚未定位。现有结果不足以判断当前性能上限，也不足以承诺接近原生设备。

## 提案

### 目标和路线筛选

完整 Linux / Android、运行期组件和数据处理在 iPhone 内独立完成。macOS 用于构建、调试、离线分析和可复现对照。每个架构候选先列出 iPhone 上所需的执行权限、地址映射、线程、内存和图形接口；缺少手机实现路径的候选只保留为调试参照。集中真机验收继续遵守[协作约定](../../implemented/process/2026-10-07-协作与阶段交付约定.md)。

把滚动、页面切换和触摸响应作为下一阶段的主要性能指标；启动、内存、正常退出及持续热状态同时保留。先以 60 Hz 的 16.67 ms 帧预算观察差距，并记录 100/250/1000 ms 以上停顿，后者是诊断分桶。接近原生的最终验收值需结合 iPhone 实际刷新率、同负载参照和手机实测确定，本文没有新增已承诺的 FPS 或提速倍数。

### 1. 先固定短负载和完成条件

首个实现复用 benchmark 动作序列，增加限定的 `profile` 动作：准备 Settings、开始帧采集、开始调度与帧采集、结束并导出。请求在启动前校验并随运行记录保存；固定命令通过当前临时 `/data/nce` 目录交给 Android 主控进程，确认完成后继续输入。每轮只允许一个采集窗口。帧记录由 `dumpsys gfxinfo` 提供，调度记录使用 tracefs；导出保留原始文件与时钟配对。采集失败使该轮失败，停止请求仍可独立提交。这个阶段尚未覆盖实际屏幕显示时刻。

复用当前设备、配置、输入与结果接口，先定义三个独立场景：Settings 长列表连续往返滚动、Launcher 打开 Settings 并返回、Clock/Files 内页面切换。逐个场景确认初始页面、滚动位置、目标窗口、分辨率和动画设置，再保存操作序列；界面变更导致操作目标失效时，该轮报告失败。

冷启动、首次打开和已预热页面分别统计。完成判定使用焦点 Activity、目标 layer、帧 token 及界面状态；设置有限等待期限，超时保留数据。截图和页面识别优先安排在测量窗口前后，持续截图或像素读回会影响图形负载。手工体验另行保留，正式测量沿用同一操作序列。

每个动作包含运行编号、场景编号、动作编号、宿主输入时间、客体接收时间和完成条件。先做约 10 秒的单场景跟踪，覆盖操作前后的短区间；有初始化干扰时先完成预热再开始。输入编号与帧之间无法建立明确关系时，只报告已覆盖的处理阶段，不输出输入到显示延迟。

### 2. 分层采集，并关联客体与宿主

| 层次 | 最小采集内容 | 解决的问题 |
| --- | --- | --- |
| Android 帧 | `dumpsys gfxinfo <package> framestats`、随后接入 FrameTimeline；保留进程、layer、帧 token、期望/实际时间、有效标志 | 是应用准备帧慢、合成晚、缓冲区阻塞，还是最终显示晚 |
| 客体调度和通信 | `sched_switch`、`sched_waking`、线程生命周期、Binder 事务及接收；需要时加 futex/GC/ART 方法区间 | 主线程真正执行、就绪排队、睡眠等待分别多久，等待的工作由哪个线程承担 |
| 执行器和映射 | Direct 执行、Unicorn 回退、编译、代码缓存清空、映射更新的分段耗时与次数增量 | 哪些开销出现在慢帧的必经工作中，减少计数是否真的减少了等待 |
| 宿主调度与图形 | 对应宿主 TID、CPU 时间、阻塞区间；图形请求入队/开始/完成、读回和上传字节、fence 等待、Metal 提交与显示时间 | LKL 外部的等待、宿主线程竞争及图形传输是否造成卡顿 |

LKL 在宿主进程内执行。客体的 Running 区间中可能包含宿主线程被调度出去或宿主接口阻塞。分析必须记录客体 PID/TID/CPU 与宿主 TID 的对应关系及有效时间；单看 Linux 调度区间无法计算真实宿主 CPU 占用。Mac 的 `sample`/Instruments 用于补充宿主调用栈；iPhone 诊断优先使用包内有限采集和可导出文件，外部调试工具作为辅助。

先使用现有 tracefs 和 dumpsys 完成最小采集；FrameTimeline 在加入 Perfetto 服务后再验证。每轮查询实际数据源，缺失的数据源直接标注。`gfxinfo` 缓冲区容量、Flags、缺失时间、未完成帧及重复记录必须检查；短窗口结束后及时导出。逐 layer 和 frame token 关联，避免把不同窗口或同一显示帧的多层记录合并计数。[FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline)说明帧与 SurfaceFlinger 的对应关系，[调度跟踪](https://perfetto.dev/docs/data-sources/cpu-scheduling)说明线程状态和唤醒信息。

客体提供的 GPU 完成时间和 present fence 要与当前 gfxstream/Composer 实现核对。最终屏幕刷新另接宿主显示完成信息；可评估 ANGLE Metal 路径中的 `MTLDrawable.addPresentedHandler` 与 `presentedTime`，后者为 0 时表示尚未显示或帧被丢弃，不能填作有效时间。`eglSwapBuffers` 返回和图形命令提交只能说明对应阶段完成。[Metal 显示时间](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime)支持两端使用同类观察点，实际接入仍待验证。

当前 gfxstream 的 `setPostCallback` 会配置像素读回，源码位置为 `work/gfxstream-src/host/frame_buffer.cpp` 的 `setPostCallback` 与 `postImpl`。因此低开销帧计时应在现有提交或显示位置记录时间和编号，不能仅为统计帧数启用逐帧读回。

### 3. 先验证数据，再归因

开始和结束时都做客体时钟与宿主单调时钟的配对采样，以调用前后宿主时间夹住客体读数，保存往返时长、偏移和误差范围。需要更长采集时增加中间校准点。统一采用明确的时钟域及单位；休眠、进入后台或误差超出所需精度的区间单独标记。[Perfetto 时钟同步](https://perfetto.dev/docs/concepts/clock-sync)提供跨时钟域记录方式。

采集有效性至少检查：必需数据源存在、测试窗口完整、时钟对应关系有效、目标进程和 layer 正确、事件丢失计数可用、帧记录可解析、正常停止和导出成功。有数据缺失时保留原始文件和失败原因，并限制该轮能支持的结论。Perfetto 的 `stats`、内核每 CPU 缓冲区统计和宿主采集器丢失计数都要保存；日志缺项不能补零。[缓冲区与数据丢失](https://perfetto.dev/docs/concepts/buffers)说明相关检查。

先把慢操作拆为有依赖关系的阶段，再查耗时最大的阶段：

- 就绪但没有执行：检查客体运行队列、宿主调度、CPU 占用和前序任务。若是宿主线程等待，继续查看宿主锁与唤醒路径。
- 主线程执行区间长：通过 ART 区间、客体代码地址与执行器耗时确定 Java、JNI、翻译或编译热点。生成代码地址需保留对应客体 PC、ELF/JIT 标识和有效代次；无法符号化的占比单列。
- Binder、futex 或图形等待长：沿事务、唤醒或 fence 关系找到负责完成工作的线程，测量它的执行与排队。
- 渲染或显示长：分别查看上传/读回、协议往返、渲染线程、GPU 完成和实际显示。只在传输占主要时间时优先研究共享缓冲区。
- 编译与缓存清空集中出现：记录触发 PC、工作集、清空原因和后续重编译，先检查反复失效，再评估缓存与执行策略。

线程之间的重叠工作不重复累加；只计算影响该动作完成的依赖路径。整体上限估计使用该负载的实测比例，并标明假设。计数和单段微基准用于解释，候选收益以完整操作验证。

### 4. 控制采集开销，快速筛选候选

正式性能轮只保留必要帧、动作和低频资源记录；调用栈、详细调度和内部事件在独立诊断轮开启。先交替比较采集关闭、最小采集和详细采集，记录采集自身 CPU、内存、丢失事件和操作耗时变化。未确认开销足够小时，详细诊断耗时只用于定位。

现有代码查询数量很高，不逐次打印字符串或同步写文件。优先在执行入口、退出、编译、清空及慢等待边界累计；需要事件时采用容量受限的采集并在操作之后导出。信号处理入口沿用现有安全约束，不增加锁、堆分配或文件输出。

每个候选先写清五项：可复现症状、定位到的耗时及位置、具体改动、预期改变的指标、失败判据。可共存行为使用启动前设置；涉及 ABI、内核或构建差异时使用明确变体。先做窄负载因果对照，再进入完整交互；收益方向错误或只改善无关计数时，记录结果并停止扩大该候选。

优先尝试最小消融：关闭单个昂贵检查的合法替代路径、保留其余配置，或者构造只改变特定等待条件的诊断版本。任何减少工作或同步的版本都需保持程序语义和图像正确性；禁用正常绘制、删除系统功能或缩短动画的诊断数据不能作为产品提速结果。

### 5. 稳定比较与验收

正式比较固定设备、系统、构建、客体镜像、数据盘起始状态、实际时间片、CPU 数量、分辨率、刷新率、动画和前后台状态。沿用独立实验设备，保留用户日常数据。Mac 比较期间停止并行构建和其他 Android 会话；正式轮次由已启动驱动完成，窗口检查另行执行，防止观察接口重新启动 App。

单项候选先做五对基线/候选交替运行，作为初始样本计划。分别报告每轮帧数、P50/P95/P99、最大值、超过帧预算的比例、长停顿、动作完成时间及内存/热状态。样本不足的高分位数明确标注；扩大样本由轮次波动决定。统计以运行轮次为独立单位，保留全部失败和慢样本；只有明确的外部干扰才能排除，并保存原始结果及原因。

帧间隔和持续刷新率只在标注的滚动、动画区间统计，静止页面另行处理。分别保存新内容帧、重复显示、丢弃和未知状态，防止减少实际绘制后得到失真的帧率改善。采集窗口边缘的未完成帧、预期帧总数和各统计分母均要报告。

回归按改动选择：执行器覆盖指令、缺页/COW/权限、代码更新、信号与抢占；调度覆盖并发、阻塞/唤醒、退出；图形覆盖缓冲区/fence 生命周期、像素和连续更新；内存覆盖回收、峰值和前台应用存活。进入候选产品时完成 CLI/GCD、真实桌面操作、数据持久化和干净停止，两端产物匹配同一实现。

iPhone 最终检查触摸响应、连续滚动、页面切换及持续负载下的帧时间、footprint、热状态和功耗趋势。Mac 用于筛除错误实现和定位瓶颈，手机性能结论使用手机数据。原生 Android 参照尽量采用同版本应用和可比负载；原生 iOS 界面可作为触摸和显示体验参照，系统实现与应用工作不同，比较范围单独说明。

### 2026-10-12 首轮完整场景与采集修正

分析器按窗口检查统计重置、进程/窗口总数、导出历史、Flags、重复帧、未完成帧、采集边界和时钟误差；按 CPU 检查 tracefs 丢失情况。P95/P99 使用线性插值，期望尾部样本少于 10 个时标记样本偏少，帧不能替代独立运行轮次。`FrameCompleted` 仍缺宿主实际显示确认。AOSP Android 16 的 [JankTracker.h](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/libs/hwui/JankTracker.h) 使用 120 帧环形记录；当前包内实现还需按构建来源核对。候选变快后必须重新检查历史完整性，长场景需要连续事件采集。

## 曾考虑的替代方案

- 继续用启动、应用首帧和微基准选择优化方向：已有结果无法解释滚动卡顿，下一阶段增加完整交互与等待归因。
- 先实现更多执行器选项再比较：会扩大组合数量，且无法判断它们是否影响慢帧；先量化主要耗时。
- 一开始集成完整 Perfetto SDK、硬件 PMU 和所有图形事件：当前镜像仍缺采集服务，先复用已验证 tracefs、dumpsys 和现有阶段计数，按缺口接入。
- 只使用 Mac 全线程采样：等待线程和无法符号化的生成代码会影响解释，且不能覆盖 iPhone 显示与热状态；保留为辅助分析。
- 持续屏幕读回统计 FPS：会引入额外图形传输；选择已有显示完成时间和独立的图像正确性检查。

### 复杂度审查

复用现有 benchmark 的运行编号、操作序列、构建/配置记录、停止和导出流程；新增的关联数据只描述现有字段尚未覆盖的动作、帧、客体线程与宿主线程关系。调度事件使用 Linux tracefs，离线查询使用 Perfetto。专用采集限定到诊断场景所需的数据源和边界，继续使用启动前配置与固定工具参数，不增加通用 shell 执行入口。删除动作/帧关联会失去输入延迟，删除两层线程对应会误判运行时间；同时保留这两项。全量指令日志、通用 profiler 框架和新图形回读通道没有本轮使用需求。 显示采集复用已有 Metal layer 和 benchmark 启停，不增加定时器、渲染提交或图像读回。单独文件保存采集状态及离线统计，现有生命周期只调用开始、结束和导出。固定数组索引与 generation 用于处理结束后到达的真实异步回调；删除隔离会使上一轮回调修改新一轮记录。

## 验收标准

1. 同一操作可重复触发卡顿，完成条件可检查；每轮包含实际配置与可匹配的构建、数据和原始结果。
2. 采集开销与数据完整性经过对照；先打通一个场景的输入、主线程、RenderThread、SurfaceFlinger、宿主图形及显示时间，缺失部分逐项注明。
3. 至少对最慢的一类操作给出主要耗时与对应线程/代码/等待对象，区分事实、推断和待验证项。
4. 候选改动在相同交互负载下带来可重复改善，并通过相应行为边界及完整功能回归。收益不满足用户目标时继续评估主要耗时和架构候选。
5. iPhone 上完成集中持续交互检查后，再判断是否接近原生体验；目前没有该结论。

## 风险

FrameTimeline 和 Android GPU 标记可能依赖当前虚拟 Composer 尚未完整实现的时序；需核对最终宿主显示。LKL 与 Darwin 存在两层调度，单层跟踪会遗漏等待来源。详细采集可能改变原有时序，必须有关闭采集的对照。新动态代码、进程重启和缓存清空会改变符号对应关系，旧地址不能复用。

已完成完整 Android 场景采集、帧历史有效性检查、线程对应与执行阶段计时。动作时序和采集开销仍需校准，宿主实际显示计时、候选因果对照和 iPhone 验证继续推进。
