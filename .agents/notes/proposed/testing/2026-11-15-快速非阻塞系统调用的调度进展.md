# 决策记录: 快速非阻塞系统调用的调度进展

状态: proposed

## 问题

原 SDK v12 的 read 负结果汇总很大，独立样本包含请求 `524288 bytes`、返回 `-11/EAGAIN` 的请求。汇总包含全部负值，实际任务和 FD 仍待[读取身份诊断](../bug-fix/2026-11-14-原SDK图形读取忙循环.md)确认，当前无法据此判断调度原因。

固定 v12 内核的 `arch/lkl/kernel/syscalls.c` 中，`nce_run_syscall()` 调用 handler 与 `task_work_run()` 后返回。`nce_user_return()` 处理信号和用户地址准备；`nce_user_preempt()` 另行处理宿主等待者与 `cond_resched()`。宿主 `linux-execution.c` 的 timer 只给 `timer_active` 的执行器请求停止，用户执行结束后清除该标志。连续短系统调用是否仍能及时处理 LKL timer IRQ、其他客体任务与宿主请求，需要独立运行确认。

## 提案

本实验属于持续离线开发范围。先保持 v12 的单 CPU、16 KiB、Direct、BPF JIT 与 timer preemption 配置，运行受控 guest。分别使用纯用户循环、快速 `getpid`、非阻塞 pipe 的 read/EAGAIN 与已有 poll 等待；另一个客体任务延迟写入、记录进展并结束循环。分别记录数据到达、定时与信号处理、其他任务运行，以及退出和回收结果。

guest 与宿主 observer 都设置运行期限，失败保存实际最后状态。先取得原实现结果，再决定是否需要覆盖系统调用返回的调度处理。修复如有必要，复用已有 LKL 调度入口，保留返回值、寄存器、信号重启、阻塞等待和停止语义；用同一 guest 做原实现与候选比较，并核对移除改动后的行为。

## 曾考虑的替代方案

- 依据 read 负值计数直接增加调度调用：未确认实际任务、FD 与其他任务的进展，无法区分用户重试、驱动等待与调度问题。
- 先改原图形库的 EAGAIN 分支：图形读取身份与等待契约仍在核对，受控 guest 可以独立验证系统调用返回的进展。
- 为该问题增加新的 timer 或长期采样状态：当前已存在宿主 timer 与 LKL 调度状态，先验证现有入口，额外状态的必要性尚未确定。

## 验收标准

1. CLI/GCD 使用同一 guest、原内核、配置与实际函数偏移，固定输入前后保持。
2. 每种循环保留其他任务、延迟数据、定时和信号的实际进展；期限失败、缺失样本和进程组回收分别记录。
3. 原实现失败后，候选比较与移除改动的实验须覆盖同一故障。原实现成功则保留该结果，继续调查实际 Android 路径。
4. 必要修复继续检查阻塞 read、信号重启、clone、进程回收与 iOS 构建。完整 boot、应用操作、持续性能和设备条件按原目标分别验收。

## 风险

受控循环与 Android 图形请求的使用方和负载不同，只能确认其自身的进展。宿主调度等待和编译并发会影响耗时，诊断轮次不用于整机性能结论。iOS 实际执行、JIT 授权、设备资源和热状态待真机验证。
