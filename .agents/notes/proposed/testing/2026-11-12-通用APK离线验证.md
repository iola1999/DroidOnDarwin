## 提案

### 先准备独立安装输入

新增 [APK fixture 源码](../../../../experiments/native-linux/apk-fixture/)与[生成脚本](../../../../scripts/build_apk_fixture.py)，直接使用 SDK 35、build-tools 36 和 NDK r29。生成 Java-only 与 JNI 两组 APK，每组包含 v1/v2；四份 APK 使用同一测试证书。版本号写入 Manifest，JNI 库由两个不同常量编译生成；APK 内未压缩库偏移按 16 KiB 对齐，ELF LOAD 段的 `p_align` 为 16384，`p_vaddr-p_offset` 为 16384 的倍数。

应用首次启动写入随机标识、创建版本和启动次数，随后每次启动从应用私有 SharedPreferences 读取并报告。JNI 版本调用原生方法并核对返回值。应用在屏幕与 `DroidApkFixture` 日志中输出同一份 JSON，安装验证可以比较 v1、更新后的 v2 和宿主重启后的标识。构建产物与测试签名密钥保存在 `work/native-linux-nce/apk-fixture/`；生成脚本复用该目录内的密钥，使重复构建保留证书。删除密钥或换用新输出目录会生成新证书，无法更新原证书安装的应用。该密钥仅用于测试。

```sh
python3 scripts/build_apk_fixture.py
```

每次成功构建写出 `manifest.json`，记录源码摘要、工具路径与版本、APK 摘要、签名证书 SHA-256、Manifest 包名与版本、ZIP 原生库位置和 ELF LOAD 段布局。签名、包内容与对齐检查成功后才发布该轮产物；安装、运行、更新和设备结论单独记录。首个输入只覆盖 16 KiB 正例，4 KiB ELF 和 ZIP、压缩库、split APK 与运行时下载代码后续补充。

两组包名分别为 `app.droidondarwin.fixture.java` 与 `app.droidondarwin.fixture.jni`，Activity 完整类名均为 `app.droidondarwin.fixture.MainActivity`。输出包含 `status/package/mode/version/value/marker/created_now/created_version/launch_count`。v1 的预期值为 101，v2 为 102；Java-only 包直接计算，JNI 包实际调用原生函数。v2 首次安装也可以成功运行，因此更新验收必须同时检查 v1/v2 的 `marker` 相同、`created_version=1`，并检查重启后的结果。

### 标准 Android 35 输入检查

本轮在 `work/native-linux-nce/apk-fixture-avd/` 创建独立 AVD，复用上表 Android 35 Google APIs ARM64 镜像。`ANDROID_USER_HOME` 与 `ANDROID_AVD_HOME` 指向该目录内的新路径；adb 使用独立服务端口，每次设备操作指定本次模拟器序列号。模拟器以可见窗口启动，测试结束后关闭实例，保留配置、应用数据和日志供复查。既有 `neb.avd` 与 DroidOnDarwin Application Support 数据保持原样。

先安装 Java-only/JNI v1，启动 Activity 并记录 JSON；再用同证书 v2 执行更新，核对版本、返回值、私有标识与创建版本。随后关闭并重新启动同一 AVD，再次启动两个 Activity，要求 v2 返回 102、`marker` 与 v1 相同、`created_version=1`，启动次数继续增加。临时执行脚本和结果写入该 AVD 工作目录，不采集性能数据。

该检查只验证 fixture 在标准 Android 35 上的安装、Java/JNI 执行、同签名更新与数据保留。DroidOnDarwin 的首轮安装、运行和宿主重启结果独立记录于下文；HyperOS 兼容情况仍需验证。

### 安装入口与当前阻塞

现有 App 没有 APK 文件选择或安装动作，也未找到 adbd 启动。本轮为 Direct 桌面探针增加固定 fixture 的运行时目录与安装检查，首轮 CLI/GCD 的安装、更新和重启检查已成功。`framework-test.cpp` 的 `nce_android_command()` 已能执行客体 `/system/bin/cmd` 并检查退出状态；独立 Java 助手的取舍见下一节。安装验证在宿主构建完成后传入签名 APK，由 PackageManager 完成签名检查、安装和更新；输入 APK 不进入系统构建登记表。

原生 NCE 的 `programs.c` 仍匹配构建期路径、容器偏移及 ELF 头。Direct 的 `translation/linux-elf.c` 已按运行时 ELF 分配布局，但要求容器偏移和 `p_vaddr-p_offset` 按 16 KiB 对齐；`p_align=4096` 本身不会被直接拒绝。原生 NCE 新库登记、Direct 的 4 KiB 边界和安装控制分别验证。

首次启动依次完成 v1 安装执行和 v2 更新执行，随后正常关闭宿主；第二次启动使用同一隔离数据盘，只查询和执行已安装 v2。该步骤已在首轮 Direct CLI/GCD 检查中完成。现有 ART 配置对安装 dexopt 使用 `verify` 并保留解释器/JIT，首轮沿用该配置，未先生成应用 AOT。

### DroidOnDarwin 最小安装检查入口

2026-11-12 主会话确认先接入 Direct 桌面探针，使用可选 APK 目录和两个阶段；产品 UI 后续接入。首次阶段完成 v1 安装与 v2 更新，第二次完整启动沿用同一数据盘，只查询并启动已安装 v2。实现入口只构建一次，运行时传入的 APK 保持原字节与签名，APK 摘要作为该轮测试输入单独记录，不进入宿主或系统镜像的构建输入。原生 NCE 的 `nce_program_layout()` 仍按构建期容器路径、偏移和 ELF 头登记新库；完整 JNI 首轮选择已有运行时 ELF 布局的 Direct，该选择只确定功能验证顺序。

现有调用路径为 `translation/linux-runner.c::android_setup()` 挂载只读系统盘与持久 `/data`，再将 `/data/nce` 挂为会话 tmpfs；`framework-test.cpp` 等待 Android 服务与 `sys.boot_completed`，调用 `nce_desktop_start()`。新增输入复制位于 tmpfs 建立后，检查助手位于 Launcher 首帧检查后、时钟和 Files 既有检查前。Android 安装内容由 PackageManager 写入持久数据盘；重启后的 tmpfs 会重建，因此第二阶段只允许查询与启动，不能重新安装来满足持久化验收。

已增加 `--apk-fixture-dir PATH`，要求 Direct `desktop` 负载、`--persistent-data` 和至少两轮完整启动。输入目录必须位于 `work/native-linux-nce`，`--build-only` 不能启用该检查。运行器通过 `NCE_APK_FIXTURE_DIR` 指定宿主输入目录，通过 `NCE_APK_FIXTURE_STAGE` 指定 `install-update` 或 `verify-restart`。目录使用生成脚本现有的 `manifest.json` 与四个 APK 名称；固定助手从清单读取包名、版本、返回值和摘要。目录内容进入每轮独立的测试输入记录，执行前后重新核对摘要。第一轮要求两个包尚未安装；已有包会失败并保留日志。探针沿用原有隔离数据盘流程，首次从指定 seed 复制，后续复用同一盘；重跑实验应指定新的输出目录，保留前轮数据和日志。

客体助手调用 `/system/bin/cmd package install --user 0 <path>` 安装 v1，使用 `-r` 更新 v2；每次安装要求退出码为 0 且输出独立 `Success` 行。启动前执行 `cmd activity force-stop --user 0 <package>`，记录 `/stderr` 当前偏移，再执行 `cmd activity start-activity -W --user 0 -n <component>`。只有启动命令成功和新的应用 JSON 均符合清单才接受该次执行；命令成功本身不满足应用验收。`cmd package path --user 0 <package>` 必须返回唯一 APK 路径，助手读取已安装 APK 并使用 SHA-256 与输入清单比较。四个输入的证书在宿主再次校验，同证书更新由真实 PackageManager 完成。

项目的 `framework-log.c` 将 Android 日志转发到 stderr，Zygote 将该流绑定到会话 `/stderr`；现有宿主日志线程继续输出这些内容。助手从启动前偏移之后读取 `DroidApkFixture` 标签的完整 UTF-8 行，使用 `org.json` 解析消息，要求包名、模式、版本、返回值、状态和私有数据字段有效。首个合法 JSON 到达后固定文件末尾位置，继续检查该快照内已完成的后续行，重复或失败应用消息使该轮失败。快照后追加的记录及跨越快照终点的半行未检测；尚无合法结果则等待半行补全，超过期限失败。成功结果输出独立 JSON 行，包含测试名、阶段、输入文件名、已安装 APK 摘要和原始应用对象；宿主按阶段检查行数与组合，再比较 v1、更新 v2 和第二次启动的 `marker/created_version/launch_count`。助手不持久化另一份应用数据期望值。

应用 JSON 在 Activity `onCreate()` 中完成 Java/JNI 调用和私有数据写入后输出。当前检查确认 `cmd -W` 的 `Status: ok` 与该 JSON，不关联 fixture 首帧提交；现有桌面图形检查继续执行，fixture 画面仍需单独关联 `nce_surface_check` 或图形输出后验收。

助手使用 Java 标准库与 Android 现有 `org.json`，沿用 `NceAppData` 的 `ProcessBuilder` 调用方式。现有 `nce_android_command()` 返回 `void`，共用固定输出文件，仅用 `strstr()` 检查期望文本，读取上限约 8 KiB，失败会结束检查；直接扩展它还需要增加结果所有权、JSON、摘要与命令期限处理。本次将完整安装检查放在独立 `services/NceApkInstall.java`，`desktop-session.cpp` 只负责检测输入与调用助手。每条命令等待 60 秒，超时强制结束后再等 5 秒回收；应用日志最多等 60 秒，助手进程期限为 360 秒，外层桌面整轮期限为 480 秒。

每条命令使用独立临时输出文件，正常完成或超时回收后，将不超过 64 KiB 的输出和退出码写入宿主 stderr 日志。超过长度上限会失败，当前不会将该临时文件完整转存到宿主；文件位于会话 tmpfs，退出后消失。应用原始日志与 JSON 阶段失败信息由原有宿主日志保存。安装失败会结束该轮检查，失败后同一会话继续交互不属于当前入口的验收范围。

实现范围为 `translation/linux-runner.c` 的运行时文件复制、`services/NceApkInstall.java`、`userspace/desktop-session.cpp` 的调用、`build_nce_userspace.py` 的助手编译清单、`probe_lkl_translation.py` 的可选参数与两阶段调度、`apk_fixture_validation.py` 的输入和结果核对，以及 `test_apk_fixture_result.py` 的解析回归。本阶段复用现有可见窗口探针、系统启动、日志、数据盘和正常退出检查。Mac/iOS UI、adbd、运行中通用命令服务、任意 APK 文件选择及原生 NCE 动态库登记后续分别实现。

### 复杂度审查

按 reclaim-code-entropy 核对，两个包用于分离 Java/PackageManager 和 JNI/ELF 的故障；两版本用于验证真实更新；一个共享 Activity 与一份 JNI 源码足以表达这些差异。测试密钥归输出目录所有，私有标识归已安装应用所有，生成清单只记录构建与检查结果。没有引入 Gradle、网络下载、设备控制或通用应用框架。删去 Java-only 包会失去安装故障与原生库故障的区分；删去 v2 或随机私有标识会失去更新与持久化验收条件。

### 应用日志并发追加边界

独立审查发现，`NceApkInstall.application()` 用 `readLine()` 之后的全文件长度与最后一个字节判断刚读取的行是否完整。具体失败时序是：读取线程在半行 EOF 返回前半段；其他线程随后追加余下内容；当前读取位置小于新的文件长度，主循环跳过半行检查，把前半段交给正则。前半段与后续单独读出的后半段通常都不匹配，实际成功 JSON 因而丢失，最后返回 60 秒超时。读取完整行后又追加其他未换行内容，也可能使旧 `lastByte()` 根据新文件末尾错误地判定该行未完成。

最初候选是在 `readLine()` 后保存固定的 `end`，检查 `end - 1` 的字节并恢复读取游标；半行退回本行 `start` 后重试。首轮完整 APK 检查期间保持助手与系统镜像来源冻结，先保存候选和回归，首轮结束后再修改。

宿主试验使用真实 `RandomAccessFile`、另一线程打开的第二个文件描述符，以及现有 OpenJDK 17 和 SDK 35 `android.jar`。反射只调用生产助手的私有字节检查函数，未调用 Android 或 JSON API。原实现副本确定失败，错误为 `half line accepted after concurrent completion`；临时副本仅把 helper 的参数改为固定 `end`、读取位置改为 `end - 1`，通过半行后补齐、完整行后追加未换行内容、游标保持、CRLF、空行和 EOF 检查。命令、两份源码摘要和完整输出位于 `work/project-audit-2026-11-12/apk-log-boundary-regression/result.json`。该试验只验证候选的字节检查，未验证完整主循环。

另一个静态边界是正确 JSON 已读到后，旧助手仍需遇到整个 `/stderr` 的瞬时 EOF 才返回；持续追加且读取无法赶上，或其他日志留下未完成尾行，均可能延长等待至 60 秒并误报缺少 JSON。`RandomAccessFile.readLine()` 自身没有终点参数，读完后才比较位置无法约束持续增长且没有换行的单行。因此最终实现使用本类私有 `readCompleteLine(file, limit)`，每次最多读取 4 KiB，并将 LF 前的行内容限制为 65536 字节；CRLF 中的 CR 计入该上限，解码时移除。每次读取限制在调用方保存的文件终点内，找到 LF 后恢复到实际行尾，半行或 EOF 恢复到本行起点并返回空值。

主循环在首个合法 JSON 后保存 `scanEnd`，只检查该快照内已完成的后续行；快照后追加的记录及跨越终点的半行未检测。尚无合法结果则继续等待，已有结果后不再等待全局日志 EOF；如果快照处理本身超过期限，单独报告 `Application log snapshot validation timed out`。这两个故障条件未在首轮 Android 运行中触发，宿主回归负责确定性的追加时序检查。
