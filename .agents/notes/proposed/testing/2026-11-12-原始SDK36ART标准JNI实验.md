# 决策记录: 原始 SDK36 ART 标准 JNI 实验

状态: proposed

## 问题

现有 Android 检查使用修改版 ART，其中对象引用和测试编译入口包含项目适配。后续原始系统兼容需要单独运行 SDK36 提供的 ART、Bionic 和匹配类库，先验证标准 `JNI_CreateJavaVM` 与 Java/JNI 行为。原始 Bionic 已请求 8.25 GiB 连续虚拟地址，现有 low 4 GiB 布局不足；运行条件见[稀疏客体地址与原始 Bionic](../architecture/2026-11-12-稀疏客体地址与原始Bionic.md)。

2026-11-12 主会话授权准备独立组件实验。本阶段只编译 fixture、校验原始输入与目录内容；实际 ART 运行等待稀疏客体范围和标准 VM 变更合并。主工作区仅增加本记录，源码在独立工作树实现。输入从现有本机文件读取，不复制完整 Android 磁盘，不运行外来构建脚本。

## 提案

### 输入与目录契约

复用 `work/project-audit-2026-11-12/stock-art-dependencies-expanded.json`，其 SHA-256 为 `c9462a396acb6d39d8052d01220a534ae8483ab6d3977f82413d401ff7e40e5f`。该报告记录 47 个 `DT_NEEDED` 闭包库，共 27,302,856 字节，含 `libart`、`libopenjdk`、`libjavacore`、`libandroidio`、palette、ICU JNI 与 JVM 入口。报告原样保存为实验的固定依赖清单。生成脚本同时核对原始 runtime manifest 和每个输入文件的 SHA-256，复制后重新核对。

原始 runtime manifest 的 SHA-256 为 `4b1a45b0ee51725c68f1c29765958d0b60b45a5f2325bedfc61764cd49232249`，来源为 `arm64-v8a-ps16k-36_r07.zip`，下载地址和归档 SHA-1 保留在清单中。除了报告中的库，只准备原始 linker64、七个 boot classpath JAR、ICU 数据和时区数据。APEX 文件放入 `/apex/<模块>/`，系统库放入 `/system/lib64/`；所有原始文件保持字节不变。

输出为项目 `work/` 下的 staging root 和 manifest，后续 runner 可按 manifest 的 guest 路径逐文件装载。实验生成一个非隔离 linker namespace 配置以查找固定组件目录，并明确它只用于组件验证。实际 Android namespace、动态加载库和系统属性需求仍需运行确认；47 库静态闭包没有覆盖全部运行时动态加载。

### 标准 JNI 与 Java 检查

一个 ARM64 C 程序通过 `dlopen("libart.so")` 取得标准 `JNI_GetCreatedJavaVMs`、`JNI_CreateJavaVM`，使用 NDK 原始 `jni.h`。Java 输入由本机 javac 和 SDK build-tools 36 的 D8 生成 DEX；不引入 Gradle。C 程序与 DEX 均放入 staging root 的实验目录。

- 用 `CallStaticLongMethodA` 检查 `jvalue` 的八种原始类型及对象参数，JNI 结果继续使用标准类型；对象引用只通过 JNI 操作，保留 `jobject` 的不透明句柄契约。
- 用 `RegisterNatives` 检查 Java→C 的参数、对象 identity 和 `ThrowNew`；用 Java 异常检查 C 侧的 `ExceptionOccurred`、类型、消息与清除后的继续执行。
- 创建 JNI global/weak global 引用；Java 分配和 `System.gc()` 后，通过独立 `WeakReference` 的清除及 `ReferenceQueue` 入队观察回收，再检查强全局引用的字段和对象 identity。有限次请求未观察到回收将报告失败，不能只凭 `System.gc()` 返回报告回收成功。
- Java 线程检查同步计数和 `ThreadLocal`；宿主于客体内创建的 pthread 使用自己的 `JNIEnv`，执行 `GetEnv`、`AttachCurrentThread`、Java 调用、`DetachCurrentThread`，主线程只传递 global reference。
- 输出 VM 创建前、创建后、GC 后与热循环后的 `/proc/self/maps`。若检查 primitive array storage，只记录 `GetPrimitiveArrayCritical` 返回值和 `isCopy`，不通过该指针推导 Java 对象起始地址。
- 正常结束释放 JNI 引用、注销测试 native 方法并执行 `DestroyJavaVM`。每项操作输出命名结果；失败保留阶段、错误行和标准异常描述。

初始 VM 参数选择无 boot image、关闭运行时 image dex2oat、64 MiB 最大 Java 堆、开启 CheckJNI 和请求 JIT，boot classpath 使用匹配的七个原始 JAR。选项按当前 Android 16 ART 的解析定义准备；原始 SDK 二进制的接受情况仍待实跑。探针不调用项目的私有 ART 导出，也不解码 ART 内部对象或方法布局。

### JIT 观察边界

Java 热循环检查确定的返回值，报告请求的 JIT 配置和调用次数。该结果只能验证执行语义。`/proc/self/maps` 中出现 JIT 代码区也不能确定指定方法已由 JIT 执行。第一版明确输出 JIT 执行尚未确认；后续考虑用标准 JVMTI `CompiledMethodLoad` 观察方法编译，并将客体执行 PC 与该代码范围关联。原始 ART 的 JVMTI 支持和实际事件仍需独立验证，本阶段不新增模拟运行时 API。

### 文件范围与复杂度审查

新增实验目录包含 C 程序、一个 Java 类和固定依赖清单；新增脚本负责输入核对、编译、目录生成及产物摘要。现有 `stock_bionic` 固定四文件的接口继续服务 Bionic 实验，ART 使用独立 staging root；后续 runner 复用现有逐文件写入和 CLI/GCD 进程运行工具。当前不修改执行器、内核、ART 或现有 Android 镜像生成过程。

按 `reclaim-code-entropy` 审查实际消费者：原始库和 Java 启动输入由创建 VM 路径消费，fixture DEX 由 classpath 消费，生成 manifest 供后续 runner 固定文件来源。JNI global reference 有跨调用和跨线程生命周期，weak reference 用于回收检查；它们分别验证标准 API，不能用整数地址替代。日志和映射只用于组件诊断，不增加产品配置项、第二份运行时对象表或通用测试框架。

## 曾考虑的替代方案

- 使用当前修改版 `art-test.c` 并关闭部分测试。它仍依赖私有编译导出和已有运行时适配，不能单独验证原始 ART 的标准入口，未采用。
- 修改原始二进制以适应 low 4 GiB。原始 Bionic 已给出更大地址需求，继续由稀疏地址实验处理；本任务保留输入字节。
- 复制完整 Android 镜像后直接启动 Zygote。该方案把组件失败与 framework、Binder、图形和属性依赖混在同一轮，本阶段先建立可定位的标准 JNI 实验。
- 通过 `jobject` 数值或 ART 内部方法指针推断对象地址和 JIT 状态。JNI 引用属于不透明句柄，私有布局会重新引入版本依赖，未采用。

## 验收标准

第一版完成 C/Java/DEX 编译，检查 ARM64 ELF 的 16 KiB LOAD 布局、入口/动态依赖/解释器路径、原始 runtime 与 staging 文件摘要，生成可复现命令和 manifest。输入缺失、字节被改动、依赖清单与 manifest 不一致必须失败并说明具体文件；不能仅记录告警后继续。

后续运行使用新组件目录和独立临时数据目录，在稀疏客体布局下执行 CLI/GCD。逐项检查 VM 创建、Java 参数与返回、JNI 双向调用、对象引用、回收观察、Java 与 native 线程、异常恢复和 VM 销毁。原始库字节在运行前后核对；日志记录真实退出码、signal 与未完成阶段。组件成功后再讨论原始 Android/HyperOS framework 集成。

### runner 准备结果

`probe_lkl_translation.py --workload stock-art --stock-art-directory <目录>` 已接入独立组件。脚本运行前校验准备目录，从 manifest 生成目录和文件 TSV，再由 `linux-runner.c` 复用现有 Linux syscall 与 `put_host_file` 装载。准备目录保持原始库字节，guest 内只新增组件需要的目录、设备节点、boot classpath 和临时数据。输入清单、源码和产物均记录 SHA-256；每轮开始和结束重新校验准备目录，避免运行结果关联到已变化的输入。

[stock-art-runner.h](../../../../experiments/native-linux/translation/stock-art-runner.h) 单独保存组件装载及 maps 导出。每轮使用新输出目录，防止读取上次运行的 maps；supervisor 返回后导出四个阶段已生成的文件，缺失文件单独记录。宿主整体崩溃或超过 Python 的 120 秒期限会阻止剩余导出，原始 stdout/stderr 仍保留在该轮目录。解析错误、部分 JNI 结果、失败退出和缺失 maps 均使该轮失败，报告保存已解析记录和错误行号。

[component-supervisor.h](../../../../experiments/native-linux/translation/component-supervisor.h) 有 Bionic 与 ART 两个实际调用方。共用的 `fork/execve` 生命周期实时转发 stdout，stderr 继承宿主日志，分别等待 pipe EOF 与直接子进程退出。每个组件设置 90 秒期限，超时向直接子进程发送 `SIGKILL` 并用 `waitpid` 回收；ART 结果分别保存 `exec_errno`、退出码、signal 和 `timed_out`。Bionic 原 JSON 字段与原始组件校验继续保留，超时也使 success 为 false，并另外输出 `component timeout:` 到 stderr，以便区分外部信号退出。

两个 fixture 当前创建线程，没有创建子进程的调用。本次超时处理只覆盖直接子进程；后续启用 dex2oat 或 Java `Process` 路径前，需重新处理后代进程及继承的 pipe。原始 ART 内部的运行行为仍待确认。90 秒期限触发后应保留真实失败阶段并调查原因。

[stock_art.py](../../../../scripts/stock_art.py) 校验 13 项标准 JNI 检查的顺序、值、类型和完整结束状态，同时核对四份 maps 的导出字节数与实际文件。`warmup_result` 只检查确定的 Java 返回值，报告仍要求 `stock_art_jit: "unverified"` 与 `jit_execution_confirmed: false`。supervisor 返回 0 用于让宿主继续导出诊断，最终组件是否成功由上述完整结果判断。

最终构建只编译单核 PTE、Direct flat、low 地址布局、dual 代码内存下的 CLI/GCD。low 产物用于本阶段编译检查，原始 ART 的运行等待稀疏地址范围与 tagged pointer 支持。复现命令在独立树执行：

```sh
python3 scripts/probe_lkl_translation.py --build-only --mapping pte --execution direct --direct-memory flat --guest-layout low --cpus 1 --code-memory dual --reuse-engine-build --workload stock-art --stock-art-directory work/stock-art-prepared-final --entry both --output work/native-linux-nce/stock-art-runner-final-v2
```

[runner 准备结果](../../../../experiments/native-linux/results-stock-art-runner-preparation-20261112.json)记录最终源码、CLI/GCD、supervisor、LKL 内核与装载清单摘要。ART 和 Bionic 的 `--build-only` 均成功，两个入口均已生成。收尾重建 Bionic 时曾误传 `android36` 父目录，入口在读取 `bin/linker64` 时失败；改为 `android36/com.android.runtime` 后重建，失败日志保存为 `work/stock-bionic-supervisor-wrong-directory.log`。六个 Mac 真实子进程用例覆盖正常输出、退出码 7、`SIGTERM`、`execve` 缺失、pipe 保持打开的超时和 stdout 提前关闭的超时，每项结束均确认直接子进程已回收。Darwin 测试只将 `pipe2(O_CLOEXEC)` 替换为 `pipe` 加 `fcntl`，其余进程控制使用生产 helper。该检查覆盖宿主进程行为，LKL 内的同一行为仍待运行验证。

复杂度复查保留一份共用的子进程生命周期，删除 Bionic 的 `/stock-output` 临时文件与结束后回放过程。若分别实现两个 supervisor，将重复 EOF、退出和超时状态；共用 helper 的返回字段均有真实调用方。组件装载清单从准备 manifest 生成，不增加手工文件表。ART 装载和诊断导出在独立头文件内复用现有 syscall/file helpers；`build_translation_runtime.py` 的既有头文件扫描与探针输入列表均包含新增头文件。当前没有增加通用进程树配置、产品设置或 ART 私有接口。

与最初只准备 fixture 的范围相比，本节增加了已获主会话授权的运行入口、失败日志处理和宿主生命周期验证。实际 ART、JNI fixture 和 LKL 组件均未执行；成功构建与构造日志检查仅完成运行前准备。

## 风险

原始 runtime 的动态加载、APEX namespace、系统属性、信号处理、低 4 GiB 分配、JIT 代码页、GC 与线程同步均可能暴露新的执行条件。准备成功只覆盖输入和编译。Mac 组件结果后续也需与完整 Android、HyperOS 及 iPhone 结果分别记录。
