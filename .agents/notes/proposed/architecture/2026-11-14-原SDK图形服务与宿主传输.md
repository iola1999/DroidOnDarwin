# 决策记录: 原 SDK 图形服务与宿主传输

状态: proposed

## 问题

[原 SDK 启动诊断](../bug-fix/2026-11-14-原SDK的SurfaceFlinger启动退出.md)已取得 SurfaceFlinger 的 `RenderEngine` FATAL：`no suitable EGLConfig found, giving up`。原 SDK36 的 BPF 加载已成功，完整 boot 仍失败。实际 raw init probe 没有启动或链接宿主图形实现，原 mapper 还依赖当前缺少的 Goldfish address-space 设备。

仓库已有 gfxstream/ANGLE 宿主图形、qemu pipe 的 Unix socket 传输、memfd allocator/mapper，以及原 Composer3、emulation EGL 和 `skiaglthreaded` 的本机合成检查。原 init 在私有 mount namespace 中重新挂载 `/dev`，现有 pathname socket 的位置需要调整；raw probe 的生命周期检查和 recovery 也可能没有图形连接。

原 vendor LP 的范围为 offset 3,542,089,728、101,539,840 bytes，来自 `scripts/stock_init_sdk.py` 的固定 `PARTITIONS`。ext4 使用 `shared_blocks`，仅有 79 个 4096-byte 空闲块，共 323,584 bytes。全部解除共享至少需要 3,402 个额外块，共 13,934,592 bytes。原 allocator、mapper 和 qemu pipe 的 inode 分别为 103、610、705；逐块检查确认三者的物理块未被其他 inode 引用，均为单硬链接。来源与块检查保存在 `work/sdk-plain-validation-v1/vendor-image-review-v1/inode-block-review.json`。

## 提案

在已授权的离线范围内继续实施。先保留原 v13、诊断失败和克隆盘恢复结果，再验证以下候选。完整系统、原始签名 APK 和持续性能的验收条件保持原值。

- 图形传输继续使用已有 `pipe:opengles`、`pipe:GLProcessPipe`、`pipe:refcount` 和原 renderControl 协议。host、guest 与实际 GPU 检查同步使用 Linux abstract Unix socket；监听地址的字节数明确排除结构体尾部填充。init 只创建 mount/PID namespace，net namespace 的实际共享与 SELinux `connectto` 权限继续核对。
- 原 `libqemupipe.ranchu.so`、EGL 和 OpenGL common 通过 `/dev/goldfish_pipe_dprctd` 使用同一宿主图形协议。LKL miscdevice 连接固定 abstract socket，保留原 qemupipe 的九个 `qemu_pipe_*` 导出、SONAME 和非图形的上游 vsock 行为。独立库替换的 v3 候选保留为历史对照，当前 v4 使用原 qemupipe ELF。
- 复用 `nce-gralloc-memfd.patch` 的 allocator/mapper，核对当前产物来源及去除调试信息后的文件大小。v4 覆盖原 allocator-service.ranchu 和 mapper.ranchu.so 两个路径。原 uid/gid、mode、SELinux xattr、硬链接和其他文件内容逐项检查，原盘保持。
- 仅在独立 APFS 克隆的系统候选中修改 vendor LP，处理 ext4 共享块、AVB 尾部及原 first-stage fstab 的校验要求。原 plain fstab 双块修改继续保留，通用 ELF 替换通过独立步骤完成。工具选择和空间检查完成后记录实际命令。
- raw init runner 在建立 0/1/2 流后、启动 PID1 前启动宿主 renderer，停止 PID1 及子进程后、停止 Linux 内核前回收 listener、连接线程和 renderer。CLI/GCD 的零连接生命周期和有连接原启动分别验证；图形输入的设备创建和实际显示随后接入。

### 复杂度审查

`host-graphics.cpp`、`guest-pipe.c`、`gpu-test.c` 和 LKL 字符设备是同一传输地址的实际使用方，共享定义只保存需要一致的地址与长度，不增加状态或转发接口。原 vendor ELF 使用字符设备，既有 egl/gralloc/display/framework 检查仍通过 `LD_PRELOAD` 使用 guest pipe；非图形服务的传输继续由原 qemupipe 处理。allocator/mapper 使用现有 memfd 与 Binder 接口；替换原 inode 的内容和保持系统元数据属于制镜像步骤。

省略 abstract 地址会继续依赖原 `/dev` 的可见性；只添加 renderer 调用仍缺少 guest 传输和 mapper；全部解除 vendor 共享块超过当前分区空间。停止检查需要覆盖零连接，已有有连接检查继续核对实际 opened/closed 计数。具体实现按 reclaim-code-entropy 复核使用方、资源所有者和替代实现，按 humanizer-zh 审阅文字。

当前 v4 使用原 qemupipe 后，独立图形库构建入口只剩历史 v3 的复现使用方。本轮已将只读 ELF 契约检查移到唯一 probe 使用方，保存必要历史源码，再移除专用 builder 与补丁；删减后八轮字符设备验证成功。原 `guest-pipe.c` 的四类 `LD_PRELOAD` 使用方继续保留，详细审查与复现条件见[构建入口删减](../../implemented/simplification/2026-11-14-原SDK图形库构建入口删减.md)。

### 本轮新增调查与停止条件

2026-11-14 的只读 ELF 复核确认，原 `/vendor/lib64/egl/libEGL_emulation.so` 与 `/vendor/lib64/libOpenglSystemCommon.so` 均自身定义九个 `qemu_pipe_*`，没有 `DT_NEEDED libqemupipe.ranchu.so`。原 Composer3 依赖 OpenGL common。原 allocator 才存在该 qemupipe 动态依赖。EGL 和 Composer 的实际图形传输仍待建立与验证，先检查原服务环境和 linker namespace 的符号查找规则。

同轮生命周期审阅发现，连接 reader 可能阻塞在 `waitUntilWritable()`；当前析构只关闭 socket 的读写，再等待 reader，channel 的停止位于 reader 循环之后。gfxstream 的 channel `stop()` 会终止待执行的读写。实现将同步 channel 的创建与停止请求，先终止 channel 等待，再等待宿主线程退出；新增回归覆盖满 channel、握手未完成和停止期间创建 channel。该问题尚未在真实原 init 中复现，零连接检查未覆盖此条件。

### 原 EGL 的设备路径

固定 gfxstream guest `qemu_pipe_guest.cpp` 的 `open_verbose()` 对 `opengles`、`GLProcessPipe` 和 `refcount` 直接打开 `/dev/goldfish_pipe_dprctd`；非图形服务才尝试 vsock CID 2 的 5000 端口。原 vendor file_contexts 将该设备标为 `u:object_r:qemu_device:s0`。原 EGL 和 OpenGL common 含有这份 qemu pipe 实现，因此本轮继续验证 Linux 内核提供该字符设备的路径。

候选实现使用一个 LKL miscdevice，在原设备权限检查后连接同一 Linux net namespace 内的宿主 renderer；文件的 read/write、poll、非阻塞行为及最后一个 FD 关闭交给已有 socket 实现。设备仅连接固定图形地址，不引入任意宿主连接参数。实施前继续核对原客户 ioctl、Unix socket 的内核安全检查、ueventd 节点权限和停止顺序。若这些条件可满足，先用原库验证三种图形服务、失败与 FD 生命周期，再运行原 init；原 EGL/Common 字节和原策略保持，实际功能与资源回收分别验收。

服务预加载作为备选继续保留调查结果。原 CIL 对 init 到 SurfaceFlinger 与 Composer 的 noatsecure 只有 dontaudit 条目；Linux secureexec 与原 Bionic 会据此限制 `LD_PRELOAD` 和 `LD_LIBRARY_PATH`。实际服务 `AT_SECURE` 尚未采集，预加载未实施。

字符设备的打开阶段固定使用 `kernel_connect(..., O_NONBLOCK)`。实际内核 `misc_open()` 持有 `misc_mtx` 调用驱动的 open；Unix stream 的阻塞 connect 在监听队列满后可能等待 accept 或信号，默认等待时间为 `MAX_SCHEDULE_TIMEOUT`。队列满的打开操作返回 `-EAGAIN`，后续 read/write 仍按文件的 `O_NONBLOCK` 与 `IOCB_NOWAIT` 处理。这项选择只限制设备打开阶段的等待，实际客户并发打开和失败处理继续由有界探针及原 init 验证。

非零长度读取遇到 socket EOF 返回 `-EIO`，零长度读取返回 0。固定 guest 的 `qemu_pipe_read_fully()` 在非空读取返回 0 后继续循环，原 Goldfish 设备的关闭路径返回 `-EIO`；原 `GLProcessPipe` 的八字节 UID 读取需要覆盖提前关闭。文件使用 `stream_open()`，read/write 可以分别等待；dup/fork 共享的 file 在最后一个引用释放后关闭 socket。原 ueventd 的冷启动、`0666 system system` 权限、`u:object_r:qemu_device:s0` 标签及实际 listener 的 SELinux SID 尚待原 init 运行确认。

v3 memfd allocator 仍有 `DT_NEEDED libqemupipe.ranchu.so`，在 `0xa538` 调用 `qemu_pipe_open("refcount")`，在 `0xa584` 写入四字节 hostHandle；mapper 经原 `libOpenglSystemCommon.so` 的 `HostConnection` 使用图形传输。下一份 v4 候选继续使用相同 allocator/mapper，qemupipe 使用固定 SDK 的原 ELF，SHA-256 为 `bf798c9c9eb9972533260cf47c95df7f3c37f1bac0e6039da4d6bf6466f74169`。原 qemupipe、EGL 和 Common 都打开字符设备，v3 独立库替换及其失败结果保留为对照。v4 在新 APFS 克隆中生成，实际读回、原元数据、其他文件和只读文件系统检查继续采用现有工具；客户端的实际传输、初始化及失败处理由新探针和原 init 验收。

`build_translation_runtime.py` 的 iOS/macOS 运行库编译会使用宿主 graphics 及其头文件，原构建清单只列部分固定头文件。本轮通过编译器 `-MD` 记录各对象实际读取的仓库内头文件，包含共享地址头和 gfxstream API；系统 SDK 继续由构建命令记录。此变更只补充构建输入记录，平台执行仍由对应运行结果验收。

core 报告保存内核 `build.json` 的摘要，内核的复制源码和生成源码位于该清单的 `sha256`。原 init probe 与运行库构建在复用 core 前继续读取内层清单，逐项核对实际来源及 CPU、页大小、BPF JIT 配置，并将这些来源纳入本轮结果。内核二进制保持而复制源码已改变的情况需要在复用前失败；新字符设备的原路径、生成路径和共享地址头均按这项规则复核。

### 本机字符设备、原库与 iOS 编译

`sdk-plain-graphics-core16k-v3` 在 16 KiB 页、单 CPU、1 GiB 客体 RAM、128 MiB 翻译缓存和 BPF JIT 配置下完成 CLI/GCD 核心验证，两入口实际退出 0、进程组回收成功。内层内核清单保存 113 项来源，包含字符设备与共享地址头的原路径及生成路径。内核对象、宿主 C/C++ 和 NDK C/C++ 的地址 ABI 检查成功；详细结果为 `work/sdk-plain-validation-v1/lkl-graphics-pipe-object-v1/result.json`，复杂度审查为同目录 `review.json`。

独立字符设备探针的 no-listener、backlog、protocol 和 original 四种模式在 CLI/GCD 共八轮成功，实际退出 0、进程组清空。检查覆盖 open、read/write、readv/writev、poll、非阻塞、dup/fork 的最后 FD 引用、八字节 UID、提前关闭的 EIO，以及原 allocator 所需的单次四字节 refcount 写入。protocol/original 使用实际 renderer，每轮均报告 `opened=closed=6`；原库模式通过 `dladdr` 核对实际加载路径，最后 FD 释放前后比较 `/proc/net/unix`。异步 ColorBuffer 删除尚未测量。结果与冻结来源保存于 `work/sdk-plain-validation-v1/graphics-pipe-probe-v1/summary.json` 和 `run-v4/result.json`。

构建入口删减后的实际 `run-v5/result.json` 继续通过同一八轮验收，原 `run-v4` 与其摘要保持。最终 liblog fixture 及 v2/v3 四份原日志的协议和 syscall 采样复核成功，结果为 `work/sdk-plain-validation-v1/liblog-final-graphics-v1/result.json`。

vendor v4 使用与 v3 相同的 memfd allocator/mapper，并恢复固定 SDK 的原 qemupipe ELF。新 APFS 系统候选的实际文件读回、inode 元数据、其他文件、LP 布局、外围字节和只读 e2fsck 均成功，原盘保持。结果为 `work/sdk-plain-validation-v1/vendor-graphics-image-v4/sdk-graphics-system.json`。原 init 的 30 秒及 180 秒结果分别见[启动诊断](../bug-fix/2026-11-14-原SDK的SurfaceFlinger启动退出.md#字符设备与原-qemupipe-的原-init-诊断)，EGLConfig FATAL 计数均为 0，180 秒出现 `Can't create AidlComposerClient`；完整系统仍未通过。

iOS 通用运行库以该 core 构建成功，`libtranslation.a` 为 arm64、7,066,448 bytes；331 项清单、24 个编译单元和 1452 项实际编译输入在前后核对一致，一项来源一致输入和 11 项来源及配置拒绝检查成功。结果为 `work/sdk-plain-validation-v1/translation-runtime-ios16k-v1/result.json`。另外从原 init v2 的实际 CLI/GCD 命令分别编译 runner/execution，四份对象均为 arm64 Mach-O、iOS platform 2、minOS 26.0、SDK 27.1；651 项输入前后保持，结果为 `work/sdk-plain-validation-v1/stock-init-entry-ios16k-v1/result.json`。首次 runner 缺少 `ios-jit.h` 的失败日志保留，增加通用 iOS builder 已使用的 `src/ios-jit` 目录后成功。此检查保留原宏及全部 include 参数，尚未覆盖 App 链接、iOS 实际 GCD 调度或设备 JIT 执行。

生成副本的 Composer 诊断在 CLI/GCD 均取得 `create: Failed to allocate drm ahb`，随后客户端显示初始化失败。六入口观察、停止与 recovery 成功，334 项来源和实际 vendor 候选前后保持，完整 boot 继续失败。当前采集尚缺实际分配尺寸和 allocator 返回，下一轮增加原 `GraphicBufferAllocator` 与候选 `allocator-service.nce` 的有界 ERROR 采集；具体结果与验收条件见[缓冲区分配诊断](../bug-fix/2026-11-14-原SDK的SurfaceFlinger启动退出.md#composer-缓冲区分配诊断)。


### system DMA heap 的独立存储候选

原 SDK 的 CLI printk 固定文本观察已出现 Composer 读写 `hal_graphics_allocator_default_tmpfs` 的拒绝，具体快照和文本边界见[启动故障记录](../bug-fix/2026-11-14-原SDK的SurfaceFlinger启动退出.md#静态-printk-快照与日志读取上限)。[共享存储静态复核](../../../../../../../sdk-plain-validation-v1/shared-buffer-review-v1/report.json)完成 33 份源码、73 段内容及 44 个输入的前后检查，支持先采用标准 system DMA heap 作独立候选。候选使用与原内核相同的单 CPU、16 KiB、BPF-JIT 和 high-res-timers 关闭配置，在实际构建入口启用 `DMABUF_HEAPS`、`DMABUF_HEAPS_SYSTEM`，并检查生成配置含 `DMA_SHARED_BUFFER`。独立内核源码由现有原源码作 APFS 克隆，原内核和 core 保持。

先检查至少三页的首末字节、跨页首次写、两个 `MAP_SHARED` 映射、fork 子进程读写、dup、最后 FD 与最后 VMA 的两种关闭顺序，以及 `DMA_BUF_IOCTL_SYNC START/END`。验证内核在 exporter 释放所有页、SG 表和 buffer 后有界记录 inode、size、pages；正式性能构建关闭该诊断。现有 NCE MMU 保持，首次写或共享失败后再按实际边界修改。候选编译可以与 v2 故障定位并行，编译状态进入本轮记录，持续性能另用无并发负载测量。

存储检查成功后，将 allocator 的 `memfd_create/ftruncate` 改为 `/dev/dma_heap/system` 的 `DMA_HEAP_IOCTL_ALLOC`。heap 节点使用 `O_RDONLY|O_CLOEXEC`，返回 `bufferFd` 使用 `O_RDWR|O_CLOEXEC`，长度继续按现有 `mappedSize` 计算。原 NativeHandle、metadata offset、共享映射和 refcount FD 保持，allocator/mapper 的 CPU mapping 生命周期配对标准 SYNC；START 失败后结束该映射，END 失败仍继续 munmap/close 并保留错误。当前宿主 GPU 使用独立 ColorBuffer，后续硬件 FD 导入与设备访问需要重新检查 CPU/GPU 同步。原 SELinux、Binder 和通用 memfd 契约保持，真实域下的两个 FD 回复、图形 client、同盘恢复与完整 boot 继续验收。

复杂度审查沿用已有 bufferFd、VMA 和 refcount FD 的资源所有者。只有一种共享存储实现，不增加 backend 类型字段、存储缓存或新的分配器接口。取消 SYNC 会使 metadata 和 CPU 像素访问缺少 DMA-BUF UAPI 所需的缓存同步；省略最后 VMA 或 exporter 完成检查会留下页释放的验证缺口。具体实验、构建身份和失败结果随候选更新。

首份独立 kernel/NDK fixture 准备只完成编译。审阅发现释放阶段的 inode 可能已由 dentry 回收路径释放，内容检查失败后的 END 和 waitpid 错误后的子进程回收也需要修正。v2 改为在导出成功后保存 inode 号，释放完成后只读取保存值；失败清理保留原错误并尝试结束 CPU scope、解除 VMA、关闭 FD、结束及等待子进程。三种 NDK fixture 和独立内核编译成功；关闭诊断宏的 system_heap 对象不含释放字符串和 counter，原编译与失败分别保留。

[v2 Direct runner](../../../../../../../sdk-plain-validation-v1/system-dmaheap-runner-v2/prepare-result.json)另用同一 fixture 源编译 musl static PIE，复用固定 core 的九个 Direct 对象和运行参数。[首项 normal CLI](../../../../../../../sdk-plain-validation-v1/system-dmaheap-runner-v2/runs/cli-normal-01/report.json)实际发生宿主 SIGSEGV，进程组清空，来源保持；尚无完整 guest、SYNC、release 或线程回收结果，其余五项未执行。后续核对发现实际编译仍使用旧 core 的 `translation-symbols.h`：`nce_copy_user`、`nce_translate_user` 的旧偏移为 `0x116464`、`0x11414c`，新 ELF 为 `0x1172b8`、`0x114fa0`。原准备审阅只核对了来源摘要，未发现这项静态地址关联；独立 runner 重新按 ELF executable PT_LOAD 和 bin 原字节生成偏移，实际修复效果继续验证。

v2 的 release validator 仅核对 inode、size、pages 和总数，从宿主 stderr 查找释放行；guest stdout 在 wait 后整体导出，两份输出的出现顺序无法用于核对最后 VMA/dup 的释放时点。后续用同一内核日志中的有界阶段标记补充检查。child-failure 使用 SIGKILL 回收 fork 子进程，允许子进程的 CPU scope 被终止；该用例只验收子进程、引用与父进程清理，成功 START 后的正常 END 另由 content-failure 检查。

[v3 准备](../../../../../../../sdk-plain-validation-v1/system-dmaheap-runner-v3/prepare-result.json)从同一 v2 内核重新生成回调头，CLI/GCD 编译依赖均使用该新头。[首项 normal CLI](../../../../../../../sdk-plain-validation-v1/system-dmaheap-runner-v3/runs/cli-normal-01/report.json)未再出现 SIGSEGV，guest 退出为 0，两个 49152-byte 分配、跨页读写、共享映射、fork、dup、两种关闭顺序和五组 START/END 的 guest 检查成功；翻译上下文 allocated=freed=2，BPF 执行池回收成功。整体报告仍为 failed，宿主 created/completed/joined=28/28/27、actual exit=1，进程组清空，输入保持。stderr 为 0 bytes，exporter 最终释放尚未确认，原 validator 在宿主退出检查停止，未形成完整 validation。其余五入口尚未执行，后续与正式 PID1 bootstrap 回收组合复验。

4. 原 init CLI/GCD 的 first-stage、停止、同盘 recovery 与完整系统观察器继续验证。分别检查 Composer 注册、RenderEngine 初始化、SurfaceFlinger 服务、实际 `sys.boot_completed=1`、显示及像素。任一未完成项保留为未完成。
5. iOS 宿主编译继续进行，JIT 授权、设备资源、显示延迟、持续性能与热状态待真机验证。诊断配置的启动时间只记录为本机排障结果。

## 风险

abstract socket 的 SELinux 权限、宿主任务标签、原 linker namespace 和图形属性仍需实际验证。局部 ext4 替换需要核对所有共享引用、inode 元数据、分配和校验；原 AVB 信息与候选 fstab 的关系必须明确记录。当前图形尺寸和内容传输成本尚未覆盖完整 Android 桌面与 HyperOS 的持续负载。
