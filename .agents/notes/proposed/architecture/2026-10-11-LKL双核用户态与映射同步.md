# 决策记录: LKL 双核用户态与映射同步

状态: proposed

## 问题

[双核内核原型](../../implemented/architecture/2026-10-10-LKL双核内核原型.md)已验证固定两个 CPU 的 NOMMU 内核，[线程局部入口](../../implemented/architecture/2026-10-11-NCE线程局部入口.md)已验证两个宿主线程共享同一份 NCE 代码。完整 Android 仍使用单 CPU。当前返回入口、抢占目标、用户窗口和 RAM 别名访问均包含单 CPU 条件；直接合并这两个原型会引入竞态。

本记录细化[多核规划](2026-10-10-后续提速与多核可行性评估.md#双核原型的工作分解)中的 M2/M3，授权范围延续用户要求的持续性能开发。每 CPU 抢占目标和返回入口已完成本机验证，独立双核用户态构建已开始执行回归，完整 Android 尚未通过。

## 提案

### 先完成的执行边界

固定两个 Linux CPU，保留独立验证构建。`user_switch` 传递 CPU 编号，宿主分别保存抢占目标；线程退出只清除仍指向自身的目标。线程迁移后采用新的 CPU 编号。状态绑定继续由进入客体的 pthread 自己完成，Linux 调度通知只更新目标与归属。

`prepare_resume()` 将每个程序的现有空闲返回入口区域分给两个 CPU，按当前 CPU 选择区域。每个区域至少包含一个完整入口，PC 哈希仅在该区域内选择位置。需要确认从准备返回入口到实际进入客体之间不会发生 Linux 调度；发生迁移或重入时必须重新选择。先通过共享程序不同 PC、哈希冲突、线程迁移和定向信号检查，再接入普通 ELF 和 ART。

当前实现由 `nce-cpu.c` 保存两个抢占目标，计时器发送信号与线程退出清理共用互斥锁。Linux 回调同时传递 CPU 编号与可能的 CPU 数量；单核继续使用全部返回缓存，双核各用一半。返回入口改写后只执行宿主计数和寄存器恢复；这些路径不会调用 Linux 调度器。CLI/GCD 的独立检查各运行四轮，每个线程每轮执行 20,000 次恢复，并将每 CPU 缓存压缩为一个入口以制造冲突。两线程结果、x16/x17、信号与退出检查均成功；轮次之间交换 CPU 编号。该检查使用宿主线程，真实 Linux 任务迁移仍需后续 MMU 原型覆盖。

移除 CPU 分区的消融版本在实际客体返回值检查中失败，说明检查能够发现另一线程覆盖待执行分支的问题。Apple M5 Ultra / macOS 27.0 (26A428) 上，普通单核 Android 的 CLI/GCD 回归各 219 项成功；配置为 1 GiB RAM、demand、nterp 开启，AOT、公共 boot image、扩展 JIT、快速基线和映射统计关闭。桌面与应用持久化、正常关机和 ext4 检查成功。独立 NOMMU 双核内核的 CLI/GCD 各三轮也成功，iOS 新模块编译成功；本阶段没有新增真机结果。结构化结果见[每 CPU 入口检查](../../../../experiments/native-linux/results-macos-nce-cpus.json)。这些是功能检查，未测量双核 Android 的性能。

首次 Android 回归命令漏设 `NCE_MM_MODE=demand`，日志记录实际使用 `lazy`；该轮首帧辅助程序在 300 秒后收到 SIGALRM，主程序返回失败并完成 2,724 个上下文的释放和只读关机。原始日志保存在 `work/native-linux-nce/cpu-probe/lazy-*`。随后使用前述 demand 配置完成回归；两轮配置不同，无法据此判断本次入口改动的性能影响。

### 用户窗口的所有权

用户态并行先限于同一个 mm。为窗口维护当前所属 mm、正在客体执行的 CPU 集合和待处理的切换请求；使用实际进入/离开客体的边界更新，不能通过 pthread 是否存在来判断。系统调用、缺页和抢占从客体返回宿主时，先退出客体执行集合，再进入可能阻塞的 Linux 路径。返回客体前重新确认当前 mm 的映射和进入条件。

切换到另一个 mm 前，需要请求现有客体执行者停止并等待确认，然后修改窗口。等待期间不能阻止目标线程先退出客体执行集合。不同 mm 的请求需要阻止当前 mm 无限接纳新执行者，Linux 等待/唤醒路径负责让出 CPU，避免占住 CPU owner 等待另一个任务。公平性策略先采用可复现的有界工作负载验证，再决定是否需要进一步调度策略。

同 mm 的数据映射撤销也必须遵守 Linux 的 TLB 语义。Linux [TLB 接口文档](https://cdn.kernel.org/doc/html/latest/core-api/cachetlb.html)要求刷新在所有相关 CPU 上生效；本地固定内核的 `Documentation/core-api/cachetlb.rst` 表述相同。Darwin 的地址映射操作会影响宿主各线程，但 NCE 还维护 `installed`、`desired`、`view_chunks` 和代码副本，必须同步这些状态及代码恢复。首版选择在修改窗口或发布代码前确认相关客体停止；数据映射后续能否缩小停止范围，另按测量判断。

### 窗口停止与返回原型

下一步在独立 SMP/MMU 构建中共用一把窗口写锁，保护 PTE 提交、当前 mm 和宿主映射数组。写入方在禁止中断的区间设置停止请求，再等待两个 CPU 的客体执行标志清空。客体离开只执行原子操作，先于任何可能等待 Linux 锁的调用；否则持有 PTE 锁的写入方可能与退出线程互相等待。首版使用现有宿主抢占计时器促使客体离开，开销待测量。

返回客体前先完成 Linux 准备和中断恢复，再通过带版本的原子比较交换登记 CPU。窗口更新会改变版本，即使 CPU 集合恢复原值，过期的进入请求也会失败并重试。这样允许两个 CPU 使用同一 mm，同时要求不同 mm 的切换等待旧执行者离开。独立检查先使用真实映射和可控的原生读写；完整 NCE 仍需检查信号退出、系统调用与代码发布边界。

窗口写锁与带版本的进入检查已加入独立 SMP/MMU 构建，保护 PTE 提交、映射、mm 释放与代码发布中的映射更新。首版每次写入都等待客体执行集合清空，锁允许同一 Linux CPU 的嵌套调用；退出只清除当前 CPU 的原子标志。普通 Android 构建尚未采用这套同步。

Apple M5 Ultra / macOS 27.0 (26A428) 的 `python3 scripts/probe_lkl_smp.py --mmu` 完成 CLI/GCD 各三轮。共享窗口的两个 CPU 直接访问同一宿主映射，200,000 次累加结果一致，计算时间重叠 504,000–1,077,000 ns；该指标只确认执行重叠。独立 mm 在相同虚拟地址各保存不同内容，每个任务进入窗口 1,000 次，六轮共检查了每轮 1,337,913–1,622,723 次读取，记录 539–796 次停止请求，未读到另一 mm 的值。过期进入版本检查成功。结构化结果见[窗口同步检查](../../../../experiments/native-linux/results-macos-smp-window.json)。

消融实验只在生成源码中跳过等待客体离开的循环，并移除对应内部断言；独立地址空间的实际读取值检查随后触发 `BUG at arch/lkl/kernel/smp-window-test.c:56/exercise_window()`，宿主收到 SIGABRT。恢复源码后重新完成上述六轮，基础内存、futex、调度与退出检查继续成功；补丁重复应用后的输出内容一致。

这项检查由测试程序主动检查停止请求并离开窗口，尚未使用 NCE 信号抢占。剩余工作包括宿主进入/退出回调、信号栈边界、返回入口准备、SMP 下的缺页归类、代码与栈访问，以及实际 Linux 用户线程和 Android 集成。没有新增启动提速、持续交互或真机结论。

### 内核访问客体内存

`nce_copy_user()` 当前先读 PTE，再从 RAM 别名复制；单 CPU 保证这段时间内 PTE 与物理页稳定。SMP 下另一个 CPU 可以取消映射、COW 或回收，内核访问需要保留物理页并检查访问权限。futex 原子操作必须在同一物理页的 RAM 别名上完成，并保留 Linux 对 pagefault-disabled 上下文的约束。宿主主动调用内核的测试仍传入可信宿主指针；客体任务使用经过权限检查的 RAM 别名。

先核对固定 Linux 6.12 的页表锁、GUP 与原子上下文路径。候选为短时页引用，或在 PTE 锁保护下完成受限访问；需要分别处理允许缺页与禁止缺页的调用方。[页引用与固定接口文档](https://www.kernel.org/doc/html/latest/core-api/pin_user_pages.html)和[页表锁文档](https://cdn.kernel.org/doc/html/latest/mm/split_page_table_lock.html)用于核对选择条件，不能将可睡眠的缺页路径直接用于 futex 的原子区间。原型选择与验证结果见下文。

当前原型选择在 PTE 锁内完成每页复制或 futex 原子操作，离开后再允许缺页与调度。页表遍历使用禁止中断的区间，并将页表回收改为 `MMU_GATHER_RCU_TABLE_FREE`；分配回收批次失败时，Linux 通过同步 IPI 等待遍历结束。访问同时检查读写权限、accessed/dirty 和物理页范围，写保护、COW 及文件脏页状态仍由原有缺页路径处理。该实现已通过独立 SMP/MMU 内核的 CLI/GCD 各三轮检查，尚未接入 Android。

`get_user_pages_fast_only()` 也能保留物理页，但短时写入还需处理 fork 的写保护和文件写回；额外引用本身无法让写入与这些操作互斥。固定内核 `mm/gup.c`、`mm/mmu_gather.c` 和 `mm/pgtable-generic.c` 表明，保留 PTE 锁可以覆盖当前短小复制与原子操作所需的访问区间。该选择减少了新增 GUP 接口和引用生命周期，代价是复制期间持有 PTE 锁；后续需要验证锁顺序和并发开销。

### SMP/MMU 本机检查（2026-10-11）

独立构建使用 Linux 固定版本、两个 CPU、1 GiB RAM 和 16 KiB 页，宿主为 Apple M5 Ultra / macOS 27.0 (26A428)。`python3 scripts/probe_lkl_smp.py --mmu` 的 CLI/GCD 各三轮成功；检查涵盖跨页读写、部分复制、禁止访问页、只读页写入失败，以及 futex 比较交换的成功、失败和权限边界。两个任务分别绑定 CPU 0/1，共享同一 mm 的计数器，40,000 次累加结果一致。另一个阶段并发复制、撤销和重建同一页 1,000 次；每轮读线程观察到 148–223 次映射代次变化，成功复制 1,043,846–5,493,177 次，并在空映射期间返回 3,550–5,510 次访问失败。该负载用于并发正确性检查，复制数量不用于性能比较。完成后等待页表 RCU 回收，再停止内核。结构化记录见[双核 MMU 检查](../../../../experiments/native-linux/results-macos-smp-mmu.json)。

测试程序最初在创建第一个任务后立即唤醒，使该任务在等待第二个任务的同时占用 `kthreadd` 所需的 CPU，因而超时。改为创建并绑定全部任务后再唤醒。初次并发循环的读线程又过早完成，尚未覆盖映射变化；现持续读取直到映射线程结束，并每 128 次变化确认读线程已经观察到进展。检查要求跨越至少七个映射代次。普通 NOMMU 的 `python3 scripts/probe_lkl_smp.py` 随后也完成 CLI/GCD 各三轮回归。

当前结果只覆盖内核和 RAM 别名访问。真实 NCE 用户指令、窗口切换、代码发布、fork/COW 与文件写回仍需后续集成检查；没有新增双核 Android 或 iPhone 性能结果。

### 实际 NCE 用户态接入

新增 `probe_lkl.py --processes --smp` 独立构建，复用普通进程、Bionic、ART 与完整系统回归。内核源目录、构建目录和数据盘单独保存；基准 Android 包继续沿用现有构建。实际用户态变体不编译独立内核的测试系统调用和检查模块，避免与正式系统调用混用。新建客体任务允许两个在线 CPU，宿主系统调用任务仍固定 CPU 0。

宿主在系统调用、缺页、抢占或需要 Linux 处理的指令访问前离开窗口；返回时先登记窗口执行者，再准备当前 CPU 的返回入口。SMP 下指令操作数和首次 exec 参数通过受锁保护的 RAM 别名复制，取消对可能由另一个 mm 替换的用户窗口直接复制。普通单核构建保留原有入口；SMP 的直接信号恢复实际设为关闭并记录。跨 CPU 累计计数改为原子更新，信号中的首次日志标志采用无锁原子操作。

该接入已构建并进入实际用户态检查，完整双核 Android 回归尚未通过。需要完成真实线程、futex、信号、fork/COW、动态代码和桌面检查后，才能判断可交付范围及性能收益。

### 功能与开销分开检查

首版 SMP 停用当前信号处理器里的直接缺页恢复，统一在宿主保存栈上的普通路径处理；配置必须记录实际生效值。同步行为验证成功后，再测双核收益以及新同步在单核下增加的开销。若等待和切换抵消并行收益，先改进这些开销，不将增加 CPU 数量视为验收通过。

### 双核用户态首轮失败与处理（2026-10-11）

首轮 `--processes --smp` 已进入实际用户程序，Linux 进程、动态链接和 Binder 检查成功，Bionic 检查退出状态为 11。开启 `NCE_FAULT_TRACE` 后重跑，Bionic 的并发退出检查返回 119，失败点为观察进程退出状态或读取次数检查。两轮失败形式不同，原因仍在定位；重跑的原始结果保存在 `work/native-linux-nce/processes-smp/trace-*`；首轮输出已由后续构建覆盖，重现需使用本段所述配置。

审查同时发现两处跨地址空间切换的读取风险。客体缺页需要先保存当时的已安装映射，再释放客体执行标志，否则另一 CPU 的映射更新可能改变 UDF 的归类；故障发生在动态代码入口时，也需要在释放前保存返回 PC。独立 SMP 构建新增 `nce_guest_fault()` 完成映射快照、离开与缺页处理，入口解码和指令处理拆为两个函数。Bionic 检查改为立即输出检查结果，并在观察进程异常退出时输出状态与读取次数。后续重跑均进入并发退出检查并超时，初轮退出状态为 11 的具体原因仍未确认。

重跑确认 Bionic 的信号、分配器和 128 线程检查成功；并发退出的观察进程已读取 23,634 次状态，随后因超过 20 秒收到 SIGALRM。原型的窗口写锁可能等到下一次 2 ms 定时抢占才获得停止确认。下一步在设置写入请求后立即按活动 CPU 集合发信号，定时抢占继续处理信号落在宿主入口过渡期的情况；测试期限保持原值。

立即通知版本的目标 CPU 选择与退出检查成功，CLI/GCD 的两宿主线程检查也成功；完整用户态重跑仍在并发退出检查超时，观察进程完成 26,547 次读取。该轮的日志保留在 `work/native-linux-nce/processes-smp/attempt3-lkl-*`，包含一次宿主采样，不能用于正式速度比较。

随后将窗口锁拆分为元数据互斥与实际停止。页表查找和非活动 mm 的页表更新只保持互斥；修改客体地址的宿主映射或切换活动 mm 前才等待客体离开。解锁使用原子读改写，保留同时离开的 CPU 状态。此次调整没有增加另一套映射记录或停止状态。独立 SMP/MMU 的 CLI/GCD 各三轮成功，覆盖共享窗口累加、独立地址空间读取、页表访问权限、futex 与并发取消映射。实际用户态重跑的观察进程读取 11,954 次后仍因 20 秒期限收到 SIGALRM；当前没有完整双核 Android 通过结果。

第五轮将 SMP 的窗口准备集中到最终返回入口，移除 `nce_user_return()` 中的两处重复准备。观察进程读取 3,636 次后仍收到 SIGALRM。第六轮复用同一构建，将前置 musl 压力循环设为一轮并加入宿主采样，观察进程读取 926 次后仍超时；两次采样分别覆盖地址空间交换和 Bionic 阶段。`attempt6-kernel-symbols.txt` 与 `attempt6-profile.json` 保存匹配该构建的内核符号、哈希和配置，采样中可见 `nce_window_stop`、抢占信号发送和映射扫描。采样包含等待线程，不能将全部栈次数解释为 CPU 时间；这些诊断运行也不能用于正式性能比较。

共同代码的普通单核 Android 完整回归已通过 CLI/GCD，覆盖桌面、Clock/Files、闹钟数据跨重启保留、图形通道释放和磁盘退出；上下文分配与释放相等。CPU 选择的通知检查、两个宿主线程入口检查与 iOS 核心编译通过。结构化结果、配置和源码哈希见[用户态接入记录](../../../../experiments/native-linux/results-macos-smp-userspace.json)。产品包继续使用单核，当前没有新增 iPhone 或完整双核 Android 性能结果。

### 同地址空间协同调度候选

当前允许两个 CPU 任意选择用户任务，不同 mm 会竞争同一宿主地址窗口。即使每次映射变化都正确等待旧执行者离开，频繁交替仍可能使停止和恢复成本超过并行收益。下一步先测量实际窗口切换及等待，并评估让两个 CPU 同时选择相同 mm 的线程；不同 mm 继续按时间片获得执行机会。

固定 Linux 源码的 `kernel/sched/core.c` 与 `kernel/sched/core_sched.c` 已有 core scheduling：关联的 CPU 按 cookie 协同选择任务，无匹配任务时让相应 CPU 空闲。可以评估复用这套选择和公平性处理，将共享 mm 关联到同一 cookie。需要补充 LKL 的 CPU 关联、mm 创建与销毁、fork/CLONE_VM、exec 后 cookie 更新，并检查宿主任务、内核线程、IPI 和空闲唤醒。该候选尚未实现；窗口停止检查仍然需要保留，调度切换期间也可能存在旧任务尚未离开的区间。

另一候选是在窗口入口增加短时使用期限和等待队列，减少立即切换。它需要独立处理公平性、阻塞系统调用、退出唤醒和 CPU 迁移，可能重复 Linux 调度器已有职责。因此先检查 core scheduling 的接入条件。两种候选都须保留独立 mm 读取、COW、信号、页权限与原有 20 秒期限，并与关闭配置比较同 mm 计算和多进程负载。

## 曾考虑的替代方案

- 只把全局变量改成线程局部：两个线程仍共用 Darwin 地址空间，相同客体地址可以属于不同 mm，地址冲突继续存在。
- 让单 CPU LKL 的多个任务直接同时返回用户态：会改变 UP 内核对 current、调度记账与同步的假设；已有 SMP 内核原型可保留 Linux 的调度语义。
- 所有 Linux 系统调用一直持有一个宿主互斥锁：阻塞调用与跨线程唤醒可能互相等待，并将内核并行重新串行化。
- 不改变 RAM 别名访问，只给映射函数加锁：PTE 查找与后续复制之间仍可能释放或更换物理页。
- 第一版同时支持任意核数和 CPU 热插拔：当前验收只需双核，额外生命周期缺少实际使用方。

## 验收标准

1. 两个真实 Linux 用户线程共享 mm 执行，原生计算有重叠；TLS、通用寄存器、NEON、定向信号、抢占与任务迁移正确。
2. futex wait/wake/原子操作、线程退出、GC 暂停及 JIT 发布可重复完成，无死锁或错误线程状态。
3. 同 mm 的 mprotect、unmap、COW、代码更新与回收交错正确；不同 mm 切换前所有旧窗口执行者已停止，等待者能够继续运行。
4. 整套检查覆盖 CLI/GCD，最后接入真实 Android 桌面、应用操作、持久化与正常退出。手机集中验证两端已经集成的版本。
5. 启动、交互、内存平均值/采样峰值/最新值及热状态分别记录。单核旧路径、新同步单核路径和双核路径按实际可构建组合比较，测试负载与配置一致。

## 风险

TLB 刷新可能发生在 Linux 的锁和原子上下文中，停止确认流程必须能在目标尚未取得这些锁时完成。返回入口、指令缓存、mm 生命周期与页引用各有独立边界，任何一个漏项都可能表现为低概率的 Android 崩溃。全窗口停止可能带来可观开销；当前尚无双核整机收益测量。

### 复杂度审查

每 CPU 入口复用现有返回区域，未增加另一个可执行内存分配器；分区参数来自 Linux 调度通知。抢占目标只由调度切换、任务首次运行与退出修改，计时器消费同一数组。单独的宿主模块承担 CPU 所有权相关状态，使并发检查能够直接执行生产代码。当前最多两个 CPU，超出范围会显式失败。后续增加核数需一起修改内核配置和验证，尚未增加产品设置。

SMP 内存访问由独立原型编译，普通 Android 继续采用既有单核路径。复制和 futex 共用一次 PTE 权限检查及锁定区间，避免分别维护页引用或映射缓存。移除 PTE 锁会允许复制期间发生 COW、写保护和回收；移除 RCU 页表回收会使遍历遇到已释放的页表。测试同步只用于保证两个 CPU 实际交错访问，未进入产品运行路径。

窗口写锁只管理现有映射状态，没有增加第二份页表。CPU 集合描述实际执行，版本描述窗口更新，嵌套深度用于 PTE 提交调用映射函数时复用同一锁；三者各有独立用途。取消等待会触发独立 mm 的实际读取错误，取消版本检查会使过期进入令牌检查失败。完整停止带来的并行损耗尚未测量，继续保留独立构建，等待功能集成后再比较。

实际用户态构建继续复用原有构建、加载、CLI/GCD 与桌面检查，仅增加 `--smp` 和独立产物目录。测试内核保留的系统调用入口由 `tests` 参数限定，实际用户态构建使用标准调用号。故障入口单独承担释放窗口前的映射快照，指令模拟函数消费已经捕获的返回 PC；移除这些读取边界会重新允许其他 CPU 改变故障归类或返回地址。按 CPU 集合通知复用原抢占目标数组，目标更新、发送和退出仍共用互斥锁。
