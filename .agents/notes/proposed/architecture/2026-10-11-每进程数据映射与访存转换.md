# 决策记录: 每进程数据映射与访存转换

状态: proposed

## 问题

[运行时 ARM64 执行器](2026-10-11-运行时ARM64代码块执行.md)已经减少代码校验与回退开销，普通访存仍需检查地址范围并查询 PTE、缓存或平坦地址表。连续访存合并只覆盖局部相邻指令；大部分生成代码仍按每次访问执行这些步骤。CPU 采样中，生成代码占有较高比例，具体分布见该记录的跳转缓存章节。目前没有测量能够直接给出地址转换可消除的完整 CPU 占比。

[独立地址范围候选](2026-10-10-独立地址范围与应用进程重启.md)原先考虑改变进程的执行地址，需要处理 Zygote/fork 继承指针。现在已有运行时访存改写，可以保持 Linux 客体地址不变，仅改变访存实际使用的宿主地址。需要验证这是否能够同时降低软件查表开销与进程切换时的宿主重映射成本。

## 提案

为每个 Linux mm 预留独立的 4 GiB 宿主数据范围，按该 mm 的有效 PTE 安装 RAM 别名。访存生成代码验证客体地址位于当前 4 GiB 用户范围，再计算 `宿主范围起点 + (客体地址 - 客体范围起点)`。各 mm 的映射持续保留，切换只更换执行上下文中的范围起点；Linux 的地址、ELF 指针、fork 和共享内存语义继续由现有页表决定。普通代码仍由运行时执行器处理，保留原始 APK/ELF 输入约定。

首版只实现普通读访问。可读且 young 的 PTE 对应只读 RAM 别名，其他页保持不可访问；写访问继续使用当前转换与代码写别名检查。这样新增映射不会成为代码页的额外可写入口，也暂不增加物理页到所有可写别名的反向索引。PTE 更新、权限撤回、物理存储替换和 mm 销毁必须同步更新或释放对应范围；单 Linux CPU 执行期间映射保持稳定。

宿主缺页需要回到原有 Linux 故障处理。生成器为实际读指令保留宿主 PC 与慢路径入口的对应关系，信号处理器只处理当前执行器、有效生成代码位置及对应数据范围的故障，把执行位置改到原来的读缺页退出路径。该路径继续记录客体地址与客体 PC，保留此前已完成的指令。对应表在执行期间只读，处理器中不分配内存、不修改映射、不调用 Linux；无关异常按原有信号处理约定传递。跨页、对齐、部分完成和组内入口沿用已经验证的逐指令语义，尚未确认的指令形式继续走现有转换。

先在独立 Mac 程序实现两套同客体地址、不同私有页且含共享页的映射，核对隔离、共享、权限变化和故障恢复；再接入 LKL 的 mm 创建、PTE 更新、物理回收与退出。配置使用启动前实验开关，与 flat 读取作同构建对照，记录宿主映射次数、缺页次数、构建/回收成本和阶段内存。只有完整 Android 对照显示实际价值，才扩展写访问或接入手机产品。

连续访存合并的桌面 CLI/GCD 记录中，flat 表实际更新为 1,803,906 / 1,908,621 次，扫描页数为 105,656,406 / 103,949,887；这些计数包含读写表项的变化，尚未分开统计只读指针变化。下一步先区分真正改变可读物理页的更新，测量逐页映射成本及连续范围合并的收益。不能将全部扫描页或全部表项更新直接换成宿主映射调用。

这一候选需要大量虚拟地址空间。Mac 的成功结果只用于本机判断；iPhone 的可预留范围、映射数量限制、页表内存和真实进程数都需要后续确认。范围分配失败应返回明确错误或按明确配置使用已验证路径，不能继续访问不完整映射。手机可执行内存仍由代码缓存单独准备，数据别名无需具有执行权限。

### 独立映射原型

已实现 [read-view.c](../../../../experiments/native-linux/translation/read-view.c) 和 [检查程序](../../../../experiments/native-linux/read-view-probe.c)，使用 Mach 共享重映射建立只读 RAM 别名，撤回时以不可访问映射替换原范围。一个所有者在客体停止执行时更新，源映射保留到别名释放；参数错误保持原范围，宿主映射操作失败后调用方必须销毁该范围，防止使用权限更新未完成的状态。模块自身没有安装信号处理器。

`python3 scripts/probe_read_views.py` 已在 Apple M5 Ultra / macOS 27.0（26A428）、Clang `-O2` 下通过 CLI/GCD 各 6 项检查：两个 4 GiB 范围同时预留、私有页和共享页、最后一页、上下文选择期间保持映射、物理页替换、读权限撤回、写保护、连续范围与部分撤回、越界/未对齐参数、销毁和重新创建。检查程序用 `sigsetjmp` 验证预期页故障，结束后恢复原信号处理设置；此阶段尚未检查生成代码的故障位置识别与无关异常传递，后续集成结果见下节。

初次检查因测试程序假设 `raise(SIGBUS)` 具有 `SI_USER` 类型而提前退出，真实映射与权限检查已完成。该模块没有接管运行时信号；后续去掉这项无实际使用方的合成信号检查，未知故障继续使检查进程失败。正式 CLI/GCD 均已重跑成功。

[结构化结果](../../../../experiments/native-linux/results-macos-read-views.json)保存 16 个内存样本，统计已独立重算。两个入口的别名检查阶段 footprint 均值/采样峰值/最后值分别为 2,138,556 / 2,327,032 / 2,327,032 字节，释放后的最后值为 1,671,552 字节。这里只映射 256 KiB RAM 的少量别名，8 GiB 为虚拟预留；这些短时数据不能推算完整 Android 的页表内存或手机容量。

复杂度审查：范围起点、长度和映射/撤回计数均由一个所有者维护；没有新增物理页副本、后台线程、页目录或持久格式。此阶段的使用方为检查程序，后续在 LKL mm 和 PTE 生命周期中接入，再为 Direct 生成代码增加读取路径与精确故障返回。独立原型没有提供 Linux、ART、桌面及手机的性能结论。

### LKL 与 Direct 集成

已接入候选 `--direct-memory view` / `NCE_DIRECT_MEMORY=view`，默认仍为原值。Linux 在 mm 初始化时建立只读范围，PTE 的可读物理页变化时映射或撤回对应 16 KiB 页，mm 销毁时释放；每次进入用户态时发布当前范围。平坦地址表继续负责写入、独占、有序访存及跨页回退。首版按实际变更逐页更新，另外计数读指针变化、写指针变化、宿主映射/撤回、存活范围与虚拟预留峰值，后续据此判断合并更新是否必要。

Direct 为普通读访问生成范围检查和固定偏移计算，并记录实际宿主读指令与客体指令偏移。故障处理核对当前执行线程、状态帧、生成指令位置、数据范围及读缺页类别后，通过原汇编退出入口保存寄存器、NZCV、向量和客体 PC。记录表仅在编译期间更新，执行期间只读；缓存清空时随代码页释放。代码组中的每条实际读取分别有位置记录，写访问继续使用既有检查。

读故障处理按进程安装，当前同一时刻只允许一个启用该候选的执行入口。代码写入跟踪随后安装，并将无关读故障传给它；退出时按相反顺序恢复处理器。移除时先检查两个信号的当前所有者，后安装的处理器尚未移除时返回 `EBUSY`，保留已有设置。它与当前单 Linux CPU 的执行约束一致，多核仍需单独调整所有权与映射同步。

已有 PTE、权限撤回、跨页、组内故障和保留跳转的检查已扩展到此候选，另增加无处理器时拒绝执行、重复安装、无关信号传递、逆序移除，以及向量单个/成对/结构/字面量读取的真实缺页、状态保存和重试。独立 CLI/GCD 各 75 项检查成功。首轮 Linux CLI/GCD 的 fork/COW、线程、信号和未预登记动态库检查成功；两轮分别创建与销毁 52 个范围，虚拟预留峰值为 16 GiB，结束存活预留为 0。虚拟预留、RSS 与物理 footprint 分别采集。

使用 `scripts/benchmark_android_translation.py --comparison direct-read-views --repeat 2` 完成 Bionic/ART 对照。两组共用构建，固定代码写入跟踪、跨页访问、256 项跳转表和 128 MiB 代码缓存，分别采用 `flat` 与 `view`；相邻访存分组和跨调用跳转复用关闭。

复杂度审查：LKL mm 拥有范围的创建和释放，PTE 更新维护实际可读物理页；Direct 只接收本次执行使用的范围。写入继续使用已有平坦表及代码页保护，故障位置随所属代码页回收。新增的故障位置表用于从宿主指令恢复客体 PC，移除后无法正确处理页故障；信号所有者检查用于保持处理器的安装顺序。当前没有新增持久缓存格式、后台服务或应用专用规则。

### Bionic/ART 与完整桌面对照

环境为 Apple M5 Ultra、macOS 27.0（26A428）、Clang `-O2`、Linux 6.12 单 CPU、1 GiB RAM、16 KiB 页、2 ms 定时抢占、nterp 开启、扩展 JIT/快速基线编译关闭、100 ms 内存采样。Direct 与 Unicorn 回退缓存各 128 MiB。测量期间没有并行构建或 CPU profiler。

八轮 Bionic/ART 按入口和轮次交替切换配置，全部成功。ART VM 四次原始耗时为 flat 1225.880 / 1259.527 / 1219.438 / 1246.885 ms，view 1146.442 / 1416.408 / 1160.949 / 1156.041 ms。中位数从 1236.383 降至 1158.495 ms，减少约 6.3%，其中一次 view 样本明显较慢。ART 阶段 footprint 采样峰值中位数从 273.212 增至 298.767 MiB；阶段均值中位数为 254.726 / 273.472 MiB，最后值中位数为 270.876 / 272.595 MiB。Bionic 阶段耗时中位数为 809.087 / 821.469 ms。

完整桌面沿用同一对宿主二进制、内核与系统盘，每次创建新的 512 MiB ext4 数据盘，顺序为 view CLI/GCD、flat GCD/CLI。四轮均通过 Launcher、Clock 重启、闹钟界面、Files、数据检查与正常退出。下表执行时间包括系统启动、自动操作、等待和退出，每个入口与配置仅一轮；均值为样本算术平均值，峰值可能遗漏采样间隔内的瞬时变化。

首版保留为本机可重复对照，默认配置和手机包继续沿用原值。当前结果不足以将它接入产品或扩大到写访问。后续先判断是否能减少实际映射量，例如首次读取时才建立别名，fork 后直接 exec 的子进程可以跳过未访问页；权限撤回和物理页替换仍须同步处理。只有完整负载同时改善耗时与内存，才继续推进该候选。映射数量与额外内存之间的具体归因尚未测量。

结果检查另外确认原始记录通过校验，并拒绝五份分别改变启用状态、结束存活量、销毁数量、映射计数和实际编译读取数量的记录。阶段结果保存于[结构化记录](../../../../experiments/native-linux/results-macos-direct-read-views.json)，包含 16 轮运行及独立重算的 4,973 个内存样本，源码、依赖和二进制摘要均已核对。成组准备重新生成 Unicorn 静态库后，独立指令与 Linux 功能检查使用最终静态库重跑成功。四个临时数据盘在核对正常退出、摘要和无占用后清理；复现使用同一系统盘创建新的 512 MiB ext4 数据盘。通用 APK 安装与 iPhone 执行集成仍按各自记录验收。

## 曾考虑的替代方案

- 继续合并相邻访存：实现已在单独记录中推进，适用范围有限，仍作为可组合对照。
- 给每个进程重新选择 ELF/ART 指针地址：会改变 fork 继承和 Zygote 布局，当前运行时访存转换允许先保留客体指针。
- 同时将读写都交给宿主页保护：还需同步全部物理代码页的可写别名与代码缓存失效，首版先验证只读路径的收益与映射成本。
- 在每次进程切换时恢复一个宿主窗口：此前完整 Android 已测到大量恢复开销，相关结果见独立地址范围和双核记录。

## 验收标准

1. 两个上下文使用相同客体地址，覆盖私有读、共享页更新、物理页替换、权限撤回和销毁后重建；上下文切换不重建对方映射。
2. 对原生成代码核对全部寄存器、NZCV、向量与客体 PC。权限和页边界失败经原慢路径返回；无关故障不被该处理器接受，CLI/GCD 均需检查。
3. Linux 的 fork/COW、信号、匿名页、文件页、缺页与回收检查成功，关闭选项时仍使用既有实现；比较中的配置和实际采用路径写入结果。
4. Bionic/ART 和完整 Android 使用同一构建交替对照，包含启动、应用操作、更新映射及退出，记录平均、峰值和最后内存值。计算小负载改善不足以确认采用。
5. iPhone 集成前完成本机生命周期和失败检查。手机验证集中于完整阶段产物，实际地址容量或执行权限阻断后续工作时再请求必要验证。

## 风险

持续保留每个 mm 的映射可能增加 Darwin 页表和 VM 元数据；PTE 更新频繁时，新增 `vm_remap`/`mprotect` 成本可能抵消访存收益。信号处理必须识别确切的生成指令和活跃上下文，代码缓存清空后不能留下可用的旧对应项。首版只读路径对写入密集负载的收益有限。本机功能已有结果，尚未测到稳定的桌面收益；iPhone 容量仍待验证。
