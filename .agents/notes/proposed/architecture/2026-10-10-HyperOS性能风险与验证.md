# 决策记录: HyperOS 性能风险与验证

状态: proposed

## 问题

原生 Linux、NCE、ART JIT 和 Metal 图形已经取得本机或真机阶段结果，用户需要判断距离高性能运行完整 HyperOS 还有哪些挑战。当前缺少新路线完整 Android 与旧 HyperOS 的同设备、同负载对照，无法承诺接近 HVF 或原生手机的整体体验。

本记录来自 2026-10-10 侧会话的风险分析，经用户要求保存。方向与[已采用路线](../../implemented/architecture/2026-10-08-转向原生Linux与NCE.md)一致；下列验证建议尚未全部实施，具体改动由主会话根据实际阻塞安排。当前交付范围仍为[方案 A](../feature/2026-10-09-Android可交互桌面.md)。

## 提案

### 判断依据

对完成可交互 Android 桌面保持谨慎乐观。真机已执行原生 Linux、Android ARM64 用户代码与 ART JIT，N4-G1 已使用 Apple A19 GPU；Mac 上完成了原版 SurfaceFlinger 的窗口合成检查。CPU 和 GPU 都已有可能大幅改善性能的执行方式，完整 HyperOS 的兼容性和持续体验仍需验证。

| 已记录的测量 | 条件与结果 | 解释范围 |
| --- | --- | --- |
| N3-S5 原生计算 | iPhone 17 / iOS 27.2；400 万轮汇编计算，5 次中位数：直接调用 7.003 ms、NCE 7.244 ms | 单一受控计算负载；直接调用样本为 3.801–12.830 ms，波动明显 |
| N3-S5 ART | 同一版本、200 万轮算术：解释执行 256.367 ms、JIT 3.646 ms | 新方案内部对照，未与旧 QEMU 的相同 Java 负载比较 |
| N4-G1 GPU | iPhone 17 / iOS 27.2、Apple A19、360×640；120 帧提交 2037.544 ms | 简单场景，包含显示同步等待；真实桌面的滑动帧率未测 |
| SurfaceFlinger 合成 | Mac 上三组普通 Surface 内容更新，检查截图大小与两侧像素 | 确认窗口合成行为；新集成尚无完整桌面的真机性能结果 |

### R1：多进程地址空间切换

当前不同 Android 进程共用一个宿主地址窗口。进程切换时调整映射并恢复相应内容；应用、system_server 和 SurfaceFlinger 的 Binder 往返会频繁经过这些操作。这是当前对性能上限最需要验证的架构问题。

之前手机上，8 MiB 私有工作集、每轮访问所有页的两进程往返为 6.627 ms，同一进程的线程往返为 0.018164 ms。测量同时包含通信、页面访问与切换，无法单独解释为一次调度延迟。后续代码页复用已经减少部分重复复制，不能直接沿用早期数值描述当前桌面。

先记录实际交互中的切换次数、映射与权限操作时间、缺页数量、代码复制量和私有/共享工作集。如果主要耗时集中于地址空间恢复，再评估新的映射或进程地址空间实现；保持共享内存、COW、保护、信号及 fork/exec 语义回归。

### R2：单 Linux CPU 与并行执行

当前 Android 用户态使用单 Linux CPU，应用、系统服务和 GC 会竞争执行时间。宿主图形线程可以独立运行，Android 用户态的并行能力仍受当前设计约束。

两个客体进程的相同虚拟地址可以保存不同内容；现有共用窗口不能直接承载这两个地址空间的同时执行。多核需要处理地址映射、共享页、动态代码与进程隔离的并发语义。单纯修改 CPU 数量不足以实现这些条件。

先测单 CPU 下前台操作与后台服务的等待分布，确认并行需求。新地址空间设计与多核应共同评估，并以真实吞吐、响应时间和正确性决定是否采用；单核能否满足基本体验尚待桌面验证。

### R3：SDK Android 到 HyperOS 的兼容

当前主要运行固定版本的 SDK Android 组件。HyperOS Framework 扩展、系统应用、原生库和厂商服务，需要与修改后的 ART、Bionic 和虚拟设备接口匹配。即使 Android 大版本一致，仍要核对内部接口和模块组合。

原生库还需检查指令覆盖、x18、代码与常量识别、段和页对齐、动态加载以及运行时生成代码。现有构建按已登记 ELF 与执行区域工作，预编译库和 AOT 产物的适配范围尚有限制。APK 内嵌库加载检查成功后，任意新应用仍需独立验证。

迁移时以实际 HyperOS 镜像列出必要模块、依赖和 HAL 声明，逐项检查加载与运行。对修改后的 ART 核对 DEX、boot image、JNI 和相关原生接口；完整系统启动成功后继续检查桌面、设置及系统应用。Android 的 Framework/设备接口关系见 [AOSP VINTF](https://source.android.com/docs/core/architecture/vintf)。

### R4：ART 优化覆盖

目前已接入多种 JIT 路径，仍有方法保留解释执行。当前桌面集成关闭安装预编译和后台 dexopt，AOT 尚未完整接入。这可能增加冷启动、首次操作与后台 CPU 开销。

先测真实系统与应用中的解释执行比例、编译耗时、代码缓存占用、重复编译及 GC 暂停，再扩大热点方法覆盖或接入预编译。标准 ART 组合使用解释执行、JIT 和 AOT，相关行为见 [AOSP ART JIT](https://source.android.com/docs/core/runtime/jit-compiler)。

### R5：图形缓冲区与同步

当前图形验证采用简单场景和较低分辨率，memfd 缓冲区方案仍包含内容传输。真实桌面的多窗口、文字、透明与动画会改变 CPU、GPU、内存带宽和同步负载。

按帧记录上传、读回和复制字节数、合成时间、等待时间及显示提交间隔。如果内容传输或等待占用较多时间，再评估直接共享宿主图形资源及同步实现。优化后继续核对跨进程缓冲区、像素、句柄生命周期和连续更新。系统组件关系见 [Android 图形架构](https://source.android.com/docs/core/graphics/architecture)。

### R6：iPhone 资源与生命周期

当前配置为 512 MiB Linux RAM、4 GiB 客体地址窗口、总预留约 4.58 GiB；ART 动态执行区为 64 MiB。代码、数据、Android 服务和应用增长后，可能出现内存回收、重新编译或应用重启。增加容量需要重新验证设备地址预留及物理占用。

用户已提出当前 512 MiB 难以满足完整系统需求。旧 TCG 的 5 GiB 文件承载配置、宿主预算读数、换页代价及 NCE 扩容候选，见[内存容量与文件映射方案](2026-10-10-NCE内存容量与文件映射方案.md)。1–2 GiB 为讨论中的验证档位，最终容量与文件承载方式尚未确定。

N4-G1 短测峰值 RSS 为 861.73 MiB，回收后 footprint 为 472.13 MiB，二者指标不同。完整桌面与 HyperOS 的峰值、长期增长和实际可用预算仍需设备测量。JIT 准备与重启条件、前后台切换、息屏恢复及持续热状态也需要纳入整包验证。

## 曾考虑的替代方案

- 以原生计算或 JIT/解释器的倍数预测整机收益：负载、比较对象和执行范围不一致，采用完整系统测量后再作判断。
- 每完成一项优化就交付手机测试：用户要求集中交付，先完成本机可推进的工作，仅在设备条件阻断全部可推进路径时单独请求验证。
- 继续只补系统服务，等 HyperOS 全部启动后再检查性能：可能延迟发现地址空间的架构限制；当前先完成 A 的真实交互，再据主要耗时决定下一步。
- 预先把所有高投入候选都实现：缺少真实负载占比可能增加无收益的维护工作；按测量选择地址空间、多核、ART 或图形改动。用户允许大改，实施依据仍需来自具体问题。

## 验收标准

1. 先完成方案 A：真实 Launcher、输入和导航、两个应用启动与切换、跨 Android 及宿主重启的数据保留。
2. 记录冷启动、应用启动、连续滑动与切换的耗时和帧时间分布，并关联原生计算、进程映射、解释执行、GC、图形传输与等待的占比。
3. 本机对照固定构建、系统内容和负载；手机最终对照记录设备、签名/JIT 条件、分辨率、内存、前后台与热状态。旧 QEMU 与新 SDK Android 的差异单独说明。
4. 当主要耗时集中于地址空间恢复时，优先评估相应架构改造；主要耗时在编译覆盖或图形传输时，按对应路径处理，并运行功能回归。
5. HyperOS 集成后再次完成整机测试，保留失败和退化。当前没有用户确认的绝对 FPS、温度或提速倍数阈值，文档不补写保证值。

## 风险

多进程映射和单 CPU 可能共同限制性能；闭源库与 ART 适配可能引入独立兼容问题；图形与系统服务的局部成功尚未覆盖持续交互。平台限制也可能使部分优化无法在当前签名和设备条件下使用。

现有结果支持继续开发，完整 HyperOS 的高性能运行仍未确认。若实际测试表明某条路线难以达到基本可用性，应记录测量、原因和剩余选项，再按用户的产品目标决定投入方向。
