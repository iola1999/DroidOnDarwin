# 决策记录: HyperOS 性能风险与验证

状态: proposed

## 问题

原生 Linux、NCE、ART JIT 和 Metal 图形已经取得本机或真机阶段结果，用户需要判断距离高性能运行完整 HyperOS 还有哪些挑战。当前缺少新路线完整 Android 与旧 HyperOS 的同设备、同负载对照，无法承诺接近 HVF 或原生手机的整体体验。

本记录来自 2026-10-10 侧会话的风险分析，经用户要求保存。方向与[已采用路线](../../implemented/architecture/2026-10-08-转向原生Linux与NCE.md)一致；下列验证建议尚未全部实施，具体改动由主会话根据实际阻塞安排。当前交付范围仍为[方案 A](../feature/2026-10-09-Android可交互桌面.md)。

## 提案

### 判断依据

对完成可交互 Android 桌面保持谨慎乐观。真机已执行原生 Linux、Android ARM64 用户代码与 ART JIT，N4-G1 已使用 Apple A19 GPU；Mac 上完成了原版 SurfaceFlinger 的窗口合成检查。CPU 和 GPU 都已有可能大幅改善性能的执行方式，完整 HyperOS 的兼容性和持续体验仍需验证。

### R1：多进程地址空间切换

当前不同 Android 进程共用一个宿主地址窗口。进程切换时调整映射并恢复相应内容；应用、system_server 和 SurfaceFlinger 的 Binder 往返会频繁经过这些操作。这是当前对性能上限最需要验证的架构问题。

之前手机上，8 MiB 私有工作集、每轮访问所有页的两进程往返为 6.627 ms，同一进程的线程往返为 0.018164 ms。测量同时包含通信、页面访问与切换，无法单独解释为一次调度延迟。后续代码页复用已经减少部分重复复制，不能直接沿用早期数值描述当前桌面。

先记录实际交互中的切换次数、映射与权限操作时间、缺页数量、代码复制量和私有/共享工作集。如果主要耗时集中于地址空间恢复，再评估新的映射或进程地址空间实现；保持共享内存、COW、保护、信号及 fork/exec 语义回归。

#### 桌面启动的宿主映射测量（2026-10-10 04:45）

Mac 完整启动的 1 秒宿主采样中，运行线程多次进入 `vm_remap`、`mmap` 和 `mprotect`。该采样包含大量等待线程，暂不按总采样数推算开销占比。接下来通过可选 `NCE_MAP_PROFILE` 累计数据重映射、代码恢复和访问撤销的调用次数与墙钟时间，每 10 秒输出一次宿主统计；统计通过原子读取，不增加 Linux 系统调用。先保留当前映射行为作为对照，按实际计时决定是否调整切换时机或减少重复权限操作。

采用匹配 SDK 的 BoringSSL 后，Mac 启动前 52.589 秒记录到数据重映射 2,160.8 万次、23.818 秒，代码恢复 292.2 万次、4.900 秒，撤销访问 555.6 万次、7.067 秒。计时为各操作内部墙钟累计，包含宿主调度等待；当前单 Linux CPU 串行执行这些操作。该窗口覆盖系统服务启动，尚无完整桌面数据。

下一步将用户地址窗口的恢复推迟到返回客体用户代码之前。Linux 内核读写用户数据已经通过 PTE 对应的 RAM 别名完成，仅在内核中等待或处理 Binder 的调度不需要恢复整个用户窗口。首次执行、系统调用返回、信号返回、缺页恢复、宿主指令模拟访问及代码发布都必须准备当前进程的窗口；当前映射所属 mm 销毁时清除引用。内核自身 vmalloc 映射仍按原有方式立即更新。先保留现有页面比较和按需恢复算法，只改变切换时机，避免同时修改多项语义。验收使用 fork/exec、COW、共享页、权限、信号和 Binder 回归，以及同一系统启动的映射计时。完整启动结果仍按桌面提案验收。

首轮回归在宿主准备 exec 参数时触发地址访问异常：新分配的 Linux 页面尚未加入按需恢复记录，宿主直接写入前仍不可访问。现为宿主直接访问增加明确的缺页标记，在持有 mmap 读锁时恢复当前窗口并记录所需页面；指令模拟的跨页访问完成后再次确认窗口。该处理只用于宿主直接读写用户地址，内核普通用户数据复制继续使用 RAM 别名。已有 exec 和指令模拟回归覆盖这一差异。

下一项对照针对当前按需映射的学习记录：某页一旦在进程切换后访问，位图会一直保留，后续切换都会恢复它，直到 Linux 撤销该页。完整启动读取过的大量页面因此会长期参与恢复。计划增加仅恢复本次实际访问页的 `demand` 对照，继续沿用现有连续物理页合并；宿主直接访问所需的少量页面仍明确保留。该对照可能增加缺页与信号次数，必须比较完整启动进度、总映射时间和稠密内存回归后再决定默认方式。

`demand` 首轮已通过基础进程、信号、共享页、COW 和 ART 检查，完整启动已进入 Launcher，并执行到 `finishUserUnlocking-0`。前 102.994 秒累计数据重映射 9.500 秒、代码恢复 1.814 秒、撤销访问 7.196 秒；此前 `lazy` 在 105.237 秒时分别为 51.125、6.558、16.091 秒。两次终止原因和启动进度不同，数据仅说明已测映射开销下降。`demand` 轮次因 512 MiB 内存压力杀掉前台 Launcher，最终可见 Activity 检查超时，下一轮增加客体 RAM 后继续验证。结构化记录见 [demand 结果](../../../../experiments/native-linux/results-macos-desktop-demand-mapping.json)；默认映射方式尚未改变。

### R2：单 Linux CPU 与并行执行

2026-10-10 启动检查发现，宿主每 2 ms 投递的抢占事件直接调用 `sys_sched_yield`，即使 Linux 没有请求换出当前任务也会主动调度。当前内核为 `CONFIG_HZ=100`、`CONFIG_PREEMPT_NONE=y`。下一轮改用已有 `cond_resched()` 处理待中断与调度器的换出请求；若存在等待中的宿主系统调用，继续唤醒宿主线程并显式让出 CPU。验证保留 CPU 忙循环的信号抢占和 32 轮宿主请求检查，再观察完整启动的进程切换开销。宿主映射同时根据 `vm_remap` 返回的当前权限，跳过已经具有目标权限的 `mprotect`；只读页、COW 和撤销访问继续执行既有检查。

当前 Android 用户态使用单 Linux CPU，应用、系统服务和 GC 会竞争执行时间。宿主图形线程可以独立运行，Android 用户态的并行能力仍受当前设计约束。

两个客体进程的相同虚拟地址可以保存不同内容；现有共用窗口不能直接承载这两个地址空间的同时执行。多核需要处理地址映射、共享页、动态代码与进程隔离的并发语义。单纯修改 CPU 数量不足以实现这些条件。

先测单 CPU 下前台操作与后台服务的等待分布，确认并行需求。新地址空间设计与多核应共同评估，并以真实吞吐、响应时间和正确性决定是否采用；单核能否满足基本体验尚待桌面验证。

### R3：SDK Android 到 HyperOS 的兼容

当前主要运行固定版本的 SDK Android 组件。HyperOS Framework 扩展、系统应用、原生库和厂商服务，需要与修改后的 ART、Bionic 和虚拟设备接口匹配。即使 Android 大版本一致，仍要核对内部接口和模块组合。

原生库还需检查指令覆盖、x18、代码与常量识别、段和页对齐、动态加载以及运行时生成代码。现有构建按已登记 ELF 与执行区域工作，预编译库和 AOT 产物的适配范围尚有限制。APK 内嵌库加载检查成功后，任意新应用仍需独立验证。

迁移时以实际 HyperOS 镜像列出必要模块、依赖和 HAL 声明，逐项检查加载与运行。对修改后的 ART 核对 DEX、boot image、JNI 和相关原生接口；完整系统启动成功后继续检查桌面、设置及系统应用。Android 的 Framework/设备接口关系见 [AOSP VINTF](https://source.android.com/docs/core/architecture/vintf)。

### R4：ART 优化覆盖

目前已接入多种 JIT 路径，仍有方法保留解释执行。当前桌面集成关闭安装预编译和后台 dexopt，AOT 尚未完整接入。这可能增加冷启动、首次操作与后台 CPU 开销。

先测真实系统与应用中的解释执行比例、编译耗时、代码缓存占用、重复编译及 GC 暂停，再扩大热点方法覆盖或接入预编译。标准 ART 组合使用解释执行、JIT 和 AOT，相关行为见 [AOSP ART JIT](https://source.android.com/docs/core/runtime/jit-compiler)。

### R5：图形缓冲区与同步

当前图形验证采用简单场景和较低分辨率，memfd 缓冲区方案仍包含内容传输。真实桌面的多窗口、文字、透明与动画会改变 CPU、GPU、内存带宽和同步负载。

按帧记录上传、读回和复制字节数、合成时间、等待时间及显示提交间隔。如果内容传输或等待占用较多时间，再评估直接共享宿主图形资源及同步实现。优化后继续核对跨进程缓冲区、像素、句柄生命周期和连续更新。系统组件关系见 [Android 图形架构](https://source.android.com/docs/core/graphics/architecture)。

### R6：iPhone 资源与生命周期

此前配置为 512 MiB Linux RAM、4 GiB 客体地址窗口、总预留约 4.58 GiB；ART 动态执行区为 64 MiB。桌面启动已出现 lmkd 结束前台 Launcher，当前源码已将 Linux RAM 调整为 1 GiB，总预留约 5.08 GiB。Mac 的 640 MiB 写入与 COW 检查通过，新增容量仍需随整包验证设备地址预留及物理占用。

用户已提出 512 MiB 难以满足完整系统需求。旧 TCG 的 5 GiB 文件承载配置、宿主预算读数、换页代价及 NCE 扩容候选，见[内存容量与文件映射方案](2026-10-10-NCE内存容量与文件映射方案.md)。目前先验证 1 GiB 匿名 RAM；最终容量与文件承载方式尚未确定。

N4-G1 短测峰值 RSS 为 861.73 MiB，回收后 footprint 为 472.13 MiB，二者指标不同。完整桌面与 HyperOS 的峰值、长期增长和实际可用预算仍需设备测量。JIT 准备与重启条件、前后台切换、息屏恢复及持续热状态也需要纳入整包验证。

### 返回入口的代码缓存（2026-10-10 06:30）

Android 服务启动时的 3 秒宿主采样反复出现 `prepare_resume`、`nce_write_entry` 和 `sys_icache_invalidate`。当前每次缺页或抢占恢复都线性查找程序、重写该程序唯一的返回入口并刷新指令缓存。采样同时包含大量等待线程，尚不能从平面样本数量直接换算 CPU 占比。原始采样保存在 `work/native-linux-nce/desktop-current-sample.txt`。

计划复用每个程序分支区末尾已对齐的空闲字节，按目标 PC 选择 16 字节入口；原生代码以外的动态区域使用原有保留首页。入口现有的 B 指令编码即为目标校验，命中时直接复用，冲突时按原流程改写并同步。程序查找改用已有二分索引。Linux 单 CPU 继续持有代码执行和修改权限，不增加并发执行或新 JIT 内存。回归检查信号、抢占、缺页、fork/exec 和完整桌面，记录命中次数及实际启动结果。

### TLS 读取的直接指令实现

当前 `TPIDR_EL0` 读取经过完整 NCE 分派，保存并恢复通用寄存器、SIMD 和浮点状态。计划将目标寄存器为普通 ARM64 寄存器的 MRS 改写为三个 LDR 与一个 B：从已有 active 指针取得当前 NceState，再读取该线程的 TLS。只写原指令的目标寄存器，保持 SP、标志及其他寄存器；guest x18 和 XZR 继续使用已验证的通用处理。TLS 写入继续走原处理。

实现复用现有 80 字节分支区及 active 指针，不增加 TLS 副本。独立回归检查低位寄存器、x16/x17、guest x18、LR、XZR、读后写和状态保持，再运行 Linux 线程与完整 Android。原有 `tls_accesses` 只用于核对分派次数，将随实现移除；功能检查保留实际读出的值和最终 TLS 状态。`python3 scripts/probe_native_linux.py` 已通过上述寄存器、TLS 与现有共享代码状态检查，并编译同一实现的 iOS 静态库。收益及完整系统行为待 Android 启动验证。

### 有容量限制的页面恢复（2026-10-10 06:52）

TLS 直接读取和返回入口缓存通过本机指令与 Linux 回归；完整启动仍出现 SystemUI 服务超时。可见窗口从启动到停止累计发生约 1555 万次延迟缺页、1477 万次数据映射。窗口中的系统错误提示和自动息屏另行修复，当前尚无可交互桌面的性能结论。

下一项对照在 `demand` 基础上记录每个地址空间最近发生缺页的最多 512 个页面，切换回来时提前恢复这些有效 PTE。使用固定大小直接映射表，冲突替换旧记录；每个 mm 增加 2 KiB，销毁时释放，fork 创建独立空表。页面权限与内容仍以当前 Linux PTE 为准，撤销页同时清除记录。既有宿主直接访问位图继续承担其原职责。

此修改在长期保留全部已访问页与逐次缺页恢复之间增加有限容量的选择。预期减少 ART 栈、TLS 与常用堆页重复触发宿主信号；可能增加未再次使用页面的映射。先作为 `hot` 对照模式，检查 COW、mprotect、取消映射、代码发布和信号，再比较同一 Android 启动及稠密内存测试。未测出收益前保留默认方式。

## 曾考虑的替代方案

- 以原生计算或 JIT/解释器的倍数预测整机收益：负载、比较对象和执行范围不一致，采用完整系统测量后再作判断。
- 每完成一项优化就交付手机测试：用户要求集中交付，先完成本机可推进的工作，仅在设备条件阻断全部可推进路径时单独请求验证。
- 继续只补系统服务，等 HyperOS 全部启动后再检查性能：可能延迟发现地址空间的架构限制；当前先完成 A 的真实交互，再据主要耗时决定下一步。
- 预先把所有高投入候选都实现：缺少真实负载占比可能增加无收益的维护工作；按测量选择地址空间、多核、ART 或图形改动。用户允许大改，实施依据仍需来自具体问题。

## 验收标准

1. 先完成方案 A：真实 Launcher、输入和导航、两个应用启动与切换、跨 Android 及宿主重启的数据保留。
2. 记录冷启动、应用启动、连续滑动与切换的耗时和帧时间分布，并关联原生计算、进程映射、解释执行、GC、图形传输与等待的占比。
3. 本机对照固定构建、系统内容和负载；手机最终对照记录设备、签名/JIT 条件、分辨率、内存、前后台与热状态。旧 QEMU 与新 SDK Android 的差异单独说明。
4. 当主要耗时集中于地址空间恢复时，优先评估相应架构改造；主要耗时在编译覆盖或图形传输时，按对应路径处理，并运行功能回归。
5. HyperOS 集成后再次完成整机测试，保留失败和退化。当前没有用户确认的绝对 FPS、温度或提速倍数阈值，文档不补写保证值。

## 风险

多进程映射和单 CPU 可能共同限制性能；闭源库与 ART 适配可能引入独立兼容问题；图形与系统服务的局部成功尚未覆盖持续交互。平台限制也可能使部分优化无法在当前签名和设备条件下使用。

现有结果支持继续开发，完整 HyperOS 的高性能运行仍未确认。若实际测试表明某条路线难以达到基本可用性，应记录测量、原因和剩余选项，再按用户的产品目标决定投入方向。

### 页面恢复对照的结论（2026-10-10 07:25）

512 页缓存的启动对照增加映射用时，尚无完整桌面收益；其代码已撤下。后续批量数据视图的独立原型通过，但完整 Android 映射成本进一步增加，具体结果与取舍见[批量切换记录](../../rejected/architecture/2026-10-10-进程数据视图批量切换.md)。当前交付继续验证 `demand`，保留测量结果，不保留这两项未采用的执行模式。

### 无 boot image 启动的 JIT 对照（2026-10-10 07:31）

当前完整系统设置 `dalvik.vm.jitthreshold=65535`，ART 的默认 warmup threshold 同为 65535。系统没有 boot image，首次加载的方法需要解释执行、验证并积累热点；AndroidRuntime 支持通过 extra-opts 传入 `-Xjitwarmupthreshold`。下一轮将 warmup 和优化 threshold 同时设为 1024，检查提前编译是否减少 SystemUI 初始化与首次桌面等待。1024 是本次实验配置，尚未确认其完整系统收益。

此对照只改变完整 Framework 启动的参数，保留指令与 ART 专项测试自己的编译控制。需要核对 JIT 动态代码权限、Java 异常、应用窗口和跨进程切换；若编译竞争或代码缓存开销增加，按实测调整或恢复。CPU 分组权限修复同时验证，因此两项改动后的整机变化不能直接归因于单个参数。

2026-10-10 07:33 的本机对照通过 CPU 分组权限回归，随后 system_server 在启动阶段收到 SIGABRT。终止前 JIT 编译了 SystemServer.startOtherServices 等方法，现有日志未输出终止原因；两者的因果关系尚未确认。先在 Linux 信号返回路径记录主动发送 SIGABRT 的线程及有限长度的帧指针调用栈，使用 copy_from_user 检查客体页面，定位后再决定修复或参数取舍。该配置尚未通过完整系统验收。

07:47 的低阈值对照中 SystemUI StartServices 用时 90,701 ms，出现服务 ANR；同时若干应用的 JIT 线程因第二处临时寄存器耗尽终止。修复记录见 [ART 字段与字符串编译问题](../bug-fix/2026-10-10-ART-volatile浮点字段编译终止.md)。当前配置还包含重复进程启动和编译失败，尚不能据此选择阈值。另发现 Pixel Launcher 持续请求未安装的 AiAi Smartspace/ContentCapture 服务；开始检查 Android SDK 的 AOSP 桌面组件是否与当前 API 36 Framework 兼容，尚未替换系统内容。

### 更早的热点编译对照（2026-10-10 08:25）

VDEX 对照仍出现 SystemUI 初始化 ANR，详细结果见[验证缓存记录](2026-10-10-复用SDK字节码验证缓存.md)。下一轮将完整系统的 JIT warmup 和优化阈值从 1024 调为 16，检查重复构造、属性访问和集合操作是否更早进入已实现的编译路径。16 为实验参数，继续保持 32 MiB JIT 缓存和原有启动期限；比较初始化耗时、编译错误、代码缓存压力与真实窗口。其他回归用例仍使用各自显式编译配置。

16 阈值的本机轮次中，SystemUI StartServices 为 99,978 ms，仍发生服务 ANR；相比 1024 的 87,772 ms 没有改善，完整系统阈值恢复 1024。SystemUI 已提前编译多个 Dagger SwitchingProvider 方法，说明参数已生效，单独降低阈值未解决当前初始化延迟。

下一轮通过 `NCE_TRACE_SYSTEMUI=1` 在启动 Home 时向 SystemUI 和 system_server 发送一次 SIGQUIT，读取 ART 自身的线程调用栈。NCE 当前没有 tombstoned，SignalCatcher 输出改接已有 stderr 会话日志；普通构建继续使用原来的 tombstoned 路径。诊断开关默认关闭，含线程栈采集的轮次单独记录，不用于性能比较。应用检查及超时条件保留。

### 已有页恢复与减少扫描（2026-10-10）

后续的[启动定位](../../implemented/testing/2026-10-10-桌面启动性能定位.md)与可选 MM 统计确认，已有 Linux 页在宿主窗口被撤销后产生大量重复故障。当前已实现受限的信号内数据页恢复和按现有视图减少扫描，整套回归已成功；首轮快速恢复开关对照的 SystemUI StartServices 为 79,635 / 14,303 ms。该数字来自 Mac 上同构建单轮组件计时，手机与持续交互收益尚待验证。实现、上游调研、统计边界和后续 nterp/AOT 条件统一记录在[桌面性能优化实施](../../implemented/architecture/2026-10-10-桌面性能优化实施.md)。
