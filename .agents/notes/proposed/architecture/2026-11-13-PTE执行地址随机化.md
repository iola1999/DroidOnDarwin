# 决策记录: PTE 执行地址随机化

状态: proposed

## 问题

主线 `25675143b45288714dd9e2b8ba275d7447e0614c` 已有 Linux mmap 和 stack ASLR。translation 生成内核仍通过 `NCE_ELF_LAYOUT`、`NCE_ELF_INTERP_LAYOUT` 和 `NCE_ELF_BRK` 使用登记基址。sigreturn 代码页也使用全局固定映射地址；ELF 改用随机地址后，固定页可能与新 ELF VMA 冲突。共享路径登记另有原生 NCE、window、Android linker syscall 245 和动态代码 syscall 243/244 的真实使用方。

2026-11-13 主会话已授权本阶段实施。独立工作树为 `work/exec-aslr`，分支为 `codex/pte-exec-aslr`。源码、输出和可变构建缓存均只写该树；主会话负责接收、组合验证和推送。

## 提案

最可能改变的选择是 PTE ELF 基准与每个 mm 的 sigreturn 地址。仅在现有 translation 生成层移除三个固定 ELF 覆盖，并将 `ELF_ET_DYN_BASE` 设为 `TASK_UNMAPPED_BASE`。这个值相对 `nce_user_base`，位于已有登记程序和 243 窗口上方。PIE、无 interpreter 的 ET_DYN、interpreter 和 brk 使用 Linux 现有随机源、`PF_RANDOMIZE`、`randomize_va_space`、personality 与 mmap 布局。brk 的 1 GiB 随机区间限制到实际 guest 上界内。

范围检查放在所有 `vm_mmap()` 和 `vm_brk_flags()` 都会经过的 `__get_unmapped_area()`。长度先按实际 guest 容量检查；低非固定 hint 清为零；固定映射与分配后的最终地址均检查 guest 下界和上界。Linux ELF 按最大 `p_align` 向下对齐后仍经过这项检查。检查覆盖全部 PT_LOAD 的文件段和匿名尾段，保留 Linux 的 VMA、权限、文件偏移、冲突与回收规则。执行结束设置的 brk 也必须在实际范围内，brk syscall 在页对齐前检查客体边界。

固定 Linux 的 `load_elf_interp()` 使用普通 mmap 地址，尚未按 interpreter 的最大 `p_align` 调整基址。4 KiB guest 中的现有 musl interpreter 使用 16 KiB ELF 对齐，关闭固定覆盖后需要保留这项约束。PTE 生成层复用主 ELF 已有的「映射、释放、向下对齐、`MAP_FIXED_NOREPLACE`」步骤，随后继续原 interpreter 装载流程。

sigreturn 保留共享代码页、文件校验、初始化 mutex 和内核 RAM 生命周期。全局只保存页内入口偏移；每次 exec 使用 Linux 空闲地址安装一页 special mapping，将实际入口写入已有 `mm->context.sigreturn`。fork 沿 `dup_mm()` 继承该入口；mremap 用所属 mm 的入口检查地址和页长。页权限继续为 `VM_READ | VM_EXEC | VM_MAYREAD | VM_MAYEXEC`。

### 复杂度审查

`translation/linux-elf.c` 的 `(path, source_offset)` 登记仍由 syscall 245 和原生 window 调用。保留 source offset、精确 span、`MAP_FIXED_NOREPLACE`、重复预留 `EEXIST`、后续 `MAP_FIXED` 装载、最低 256 KiB CFI 对齐、2 MiB 对齐和 reload 合同。243/244 保留固定执行窗口、共享写入别名、发布与页生命周期。原生 `lkl-elf.h`、执行准备和 fixed sigreturn 的原合同保持原值。

删除 PTE 的三个覆盖后，PTE 的普通 exec 不再消费登记回调；原生生成源码与 syscall 245 继续消费它。移除共享登记将破坏 window 和改编 linker。sigreturn 的全局固定地址由现有 mm 字段承担，保留一个代码页和页内偏移即可，不增加随机状态对象、开关或另一组布局配置。删除共同范围检查会使内核内部 ELF/brk 绕过 syscall 的地址检查；验收包含低 hint、向下对齐与边界映射。

## 曾考虑的替代方案

- 在共享 `lkl-elf.h` 移除固定覆盖：原生执行准备和 window 仍要求登记地址，本阶段仅修改 PTE 生成层。
- 在宿主增加每次 exec 的随机登记表：与 Linux 的 load bias、mmap 和 mm 生命周期重复，继续使用现有 Linux 状态。
- 为每个 mm 分配另一份 sigreturn 代码页：代码字节相同，保留共享代码页和每个 mm 的实际入口。
- 只检查 translation mmap syscall：Linux ELF 的 `vm_mmap()` 与匿名尾段不经过该包装，检查放到共同分配位置。

## 验收标准

1. 生成的 `asm/elf.h`、`fs/binfmt_elf.c`、MMU、mmap 和 util 源码摘要进入本树构建报告；核对固定 Linux revision `d0f76a77e8c2ca68bd7d96190b8da09040eab072`。
2. 用真实 ELF 和 `AT_PHDR`、`AT_ENTRY`、`AT_BASE`、`brk(0)` 记录 PIE、无 interpreter ET_DYN、直接 loader 与有效 ET_EXEC 的实际地址。检查每个 PT_LOAD、guest 页、256 KiB 与 2 MiB 对齐、非零首段 vaddr 和文件偏移。ET_EXEC 保留链接地址。
3. 实跑 `randomize_va_space=0/1/2`、`ADDR_NO_RANDOMIZE` 和现有 mmap 位数上下界；核对地址范围和实际变化，采样结果只说明已观察到变化，精确随机区间由 Linux 算术与对齐决定。
4. 覆盖低 hint、低固定地址、上下界、长度与地址溢出、p_align 向下对齐及内部 ELF/brk 失败回收。fork 继承 ELF、heap 与 sigreturn 地址，私有页保持 COW；子进程 exec 后父进程内容与地址保持原值。
5. 复用已有信号寄存器、sigreturn 权限/mremap、245、CFI reload/APK offset/fork reload、243/244 使用方。检查每个 mm 的 sigreturn 入口、fork 继承和重新 exec 的地址变化。
6. 两种页大小顺序构建、运行 PTE Direct CLI/GCD core，检查完整 allocated/freed 相等与页表释放告警。随后运行匹配页大小的固定原库与原 SDK init，并完成两页 iOS 编译。HyperOS 的解压和 BPF callback/JIT 调查按主会话指令保持停止。报告注明实际 libc 覆盖与完整 Android/真机的未验证边界。

实施先完成源码与窄检查，再按 16 KiB、4 KiB 顺序验证。首次失败使用独立结果目录保存，修复后另存结果。外部固定资产缺失先汇报，同时继续其余验收。

### 首次本机结果

`work/native-linux-nce/exec-aslr-core-16k-v1/summary.json` 保存首次 CLI 失败。新增 PIE fixture 以绝对路径链接无 SONAME 的 musl `libc.so`，`DT_NEEDED` 包含本机构建目录，guest 报告 `No such file or directory` 和符号缺失。静态 PIE 样本已运行，动态 ELF/brk 验收尚未完成。修复使用 `-L` 和 `-lc` 生成库名依赖，后续结果另存目录。

`exec-aslr-core-16k-v2` 与 `v3` 保留动态 PIE 的 brk 断言失败。v3 在断言前输出完整样本，关闭 ASLR 的 PIE 段末页为 `738328576`，`brk(0)` 为 `738361344`，差值为两页。固定 musl 1.2.5 的 `src/malloc/mallocng/malloc.c` 首次 metadata 分配会增加 guard 页与 metadata 页，动态 loader 的分配已经在 `main` 前发生。验收改为同时记录 `/proc/self/stat` 第 47 字段的 `mm->start_brk` 与 `brk(0)`，严格检查内核起点，并检查实际 heap 范围、变化和 fork/COW。失败记录继续保留原字节。

16 KiB 生成树此前按输入摘要变化原地重放补丁，新增范围检查改变了旧补丁的完整匹配片段，重复生成出现两份 `NCE_ELF_BRK` 条件段。构建工具现在对全部页大小和 CPU 变体使用已有的「删除生成源码、复制固定来源、应用补丁」流程，build objects 仍单独保留。brk 范围检查放在旧条件段前，保留其匹配边界。

`exec-aslr-core-16k-v4` 已通过关闭 ASLR 的 static、static-2m、pie、pie-256k、pie-2m、pie-nonzero 和 ET_EXEC，回收为 76/76。直接运行 musl loader 的程序样本失败；固定 `ldso/dynlink.c` 在这个入口用 mmap 装载程序，原始 auxv 仍指向执行的 loader。验收保留原始 `AT_PHDR`、`AT_ENTRY` 和 `AT_BASE`，按 loader 的真实 headers 校验 auxv，再按 VMA 校验其加载的程序；普通 exec 继续按程序校验 auxv。

### Core 与 iOS 阶段

`exec-aslr-core-16k-v6` 的 CLI/GCD 各完成 128 个 ELF 样本与 253/253 上下文回收，报告摘要为 `38289373b0a982f9e8de21a5320b7cef965d1f02f55bee7455fe954429b1538b`。随后 `exec-aslr-core-4k-v1` 在旧 `linux_mmap_aslr_fork_same_mm` 的紧邻断言处失败，回收为 5/5，失败报告保持原字节。16 KiB ELF 对齐可能留下一个 4 KiB 空闲页，后续 mmap 需要跨过已有 VMA。检查改为保留父子进程的下一次分配地址一致、分配方向和非重叠要求，并读取 `/proc/self/maps`，确认两次分配之间的整个区间已有映射。普通 mmap 采样也执行该检查。

## 风险

普通随机 VMA 与固定 245/243 区域仍可能竞争同一 mm 的地址；保留 Linux 冲突返回，不新增宿主预留状态。大的 p_align 会减少对齐后的可选基址，异常大的 ELF span 可能无法放入当前 guest 窗口。brk 上界限制使用剩余容量，靠近边界的 ELF 可能没有可增长空间。设备资源、iOS JIT 授权、持续性能和热状态继续待真机验证。本阶段不连接手机，不做网页搜索。
