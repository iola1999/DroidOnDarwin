# 决策记录: 4 KiB 系统服务与 BPF 环形缓冲

状态: proposed

## 问题

[Direct 的 4 KiB 客体页](../../implemented/architecture/2026-11-12-Direct的4KiB客体页.md)已完成原始 HyperOS Bionic/ART 组件。当前运行探针的 4 KiB 负载白名单限制在 core/Bionic/stock-art，Linux runner 的 services 挂载与服务启动代码没有专属页大小拒绝。扩大系统负载前需要检查受限 VMALLOC 对实际内核调用者的影响。

当前 `framework-test.cpp` 的 system_server 分支运行 `netbpfload`；镜像构建实际包含 `/apex/com.android.tethering/etc/bpf/netd_shared/netd.o`。该文件声明 `packet_trace_ringbuf`，类型 27、容量 32768 字节，loader 下限 44、内核下限 5.10，ignore 标志为 0。原始 HyperOS `/system/etc/bpf/memevents/bpfMemEvents.o` 声明 `ams_rb` 和 `lmkd_rb`，各 4096 字节；`/system/etc/bpf/miui/MiuiBpfDefineset.o` 声明 4 MiB 的 `ringbuf_map`。原始文件的 map 声明已静态读取，完整加载状态仍需实际运行确认。

真实 4 KiB 内核源码的编译断言确认 `RINGBUF_NR_META_PAGES=3`。`bpf_ringbuf_area_alloc()` 为每个页使用 order 0 分配，再按「metadata + data + 同一份 data」请求 vmap。长度为 `(3 + 2 * (max_entries / 4096)) * 4096`，合法容量均使该长度不满足 16 KiB 完整组条件。独立物理页也未满足当前连续组条件。小于 16 KiB 的环形缓冲还要求一个宿主页内重复映射同一 4 KiB 页，单纯补齐 metadata 或增大物理分配不能保留原双映射。

## 提案

已复用已验证真实内核和宿主 binary，另编小型 guest，通过 BPF_MAP_CREATE 请求 ARRAY 作为成功对照，再请求 4096、32768、4 MiB 的 RINGBUF。失败复现与分批清理检查已完成，原始加载器和完整系统尚未运行。独立目录保留全部输入身份和原始输出，原始 core 结果保持原状。

修复需保留 map 容量、用户态 mmap 页偏移、权限及数据双映射共享。先核对实际当前 type 27 的 producer/consumer 和 reserve/pending/notification 行为，再比较局部 ringbuf 实现调整与通用 kernel vmap 实现的代价。任何修改均需覆盖环尾记录、discard、reserve/submit、用户态两份数据映射和关闭清理；type 31 的用户 producer 单独核对。复制同步不能满足本阶段共享语义。

### 原始记录与 mmap ABI

静态扫描覆盖原始 SDK/HyperOS 的 25 个 ELF、70 个 map 声明，其中未找到 type 31。原始 `bpfMemEvents.o` 的 7 个 producer 入口都调用 helper 131（`bpf_ringbuf_reserve`），申请 88 字节；SDK 的 memevents 测试对象同样使用 88 字节。含 8 字节头部及对齐后的记录为 96 字节。32 KiB `packet_trace_ringbuf` 的 4 处 reserve 使用 32 字节，含头记录为 40 字节。HyperOS 4 MiB `ringbuf_map` 的 4 处 reserve 分别使用 32、48、40、56 字节，含头记录为 40、56、48、64 字节。上述值来自原始 ELF 反汇编，map 参数和程序字节均未调整。

4 KiB memevents 环从 producer_pos=0 开始，每条记录及时消费，第 43 条成功记录从 4032 开始，88 字节 payload 跨尾 32 字节。`tp_ams` 直接执行 BPF stores，最大写入偏移为 payload+0x50，并调用 `bpf_probe_read_str(payload+0x20, 16, ...)`。内核返回的 reservation 指针会被 BPF 指令和 helper 直接使用；只修改 `bpf_ringbuf_output()` 的 memcpy 无法覆盖这些入口。原始 SDK 与 HyperOS `libmemevents.so` 均按 88 字节事件读取，消费端根据头部长度推进 consumer_pos，跳过 discard，遇到 busy 停止。

以下偏移以 mmap 文件偏移计，PAGE_SIZE=4096。内核自身不可映射的 metadata 页数由 `RINGBUF_PGOFF` 表示，用户偏移不包含这部分。

| 区域 | 页偏移 | type 27 | type 31 |
| --- | --- | --- | --- |
| consumer_pos | 0 | 可写映射仅允许 offset=0 且 length=4096 | 禁止可写映射 |
| producer_pos | 1 | 只读 | 可写 |
| data 第一次映射 | 2 | 只读 | 可写 |
| data 第二次映射 | 2 + max_entries/4096 | 与第一次使用同一物理页 | 与第一次使用同一物理页 |

只读映射清除 `VM_MAYWRITE`，后续 mprotect 也不能增加写权限。常规 consumer 将 consumer 页单独 mmap，再从 offset=4096 映射 `4096 + 2*max_entries` 字节。两份原始 `libmemevents.so` 的 mmap 调用符合这组权限和页偏移。内核 type 31 consumer 可从用户写入的位置取得跨尾 dynptr，用户 producer 同样依赖连续的双映射数据。

### 下一步实现范围

主会话已授权先处理容量至少 16 KiB 的 ringbuf：在 consumer 前补齐内核 metadata，使 data 起点落在 16 KiB 边界，物理页按 16 KiB 组分配。consumer、producer、data 的相对页偏移继续为 0、1、2，原 mmap 参数、权限与双映射共享保持原值。该范围使用 SDK 32768 字节与 HyperOS 4194304 字节实际参数检查 type 27/31、跨尾记录和关闭清理。原始 BPF 对象和 max_entries 保持原值。

4096/8192 字节容量另行设计。在 Darwin 16 KiB 映射粒度下，单个宿主页内重复映射一份 4 KiB/8 KiB 数据需要额外的内核访问处理。当前提案仍需比较内核访存转换与局部跨尾 reservation 处理的成本和语义。跨尾临时连续记录仅作为待审备选，必须逐项检查 busy、commit、discard、嵌套 reservation、容量失败条件及 mmap 观察；原共享 mmap 仍使用同一物理页，临时记录方案也会引入提交复制。

## 曾考虑的替代方案

直接开放 services/desktop 后依赖启动失败定位。已经找到实际配置下会出现的 ringbuf 请求，先复现其调用可缩小排查范围。统一把 ringbuf 容量提高到 16 KiB 会改变原始 map 参数和用户态契约，当前不采用。只增大 metadata 到完整宿主页仍无法支持 4 KiB 数据区的重复 alias。

在环尾插入 discard padding 会改变可用容量和 reserve 失败条件。原内核可到达的状态 `consumer_pos=96, producer_pos=4032, pending_pos=4032` 表示已提交 42 条 96 字节记录并消费第一条。下一条 88 字节 payload 使 `new_prod_pos-consumer_pos=4032`，满足 mask=4095；增加 64 字节尾部 padding 后差值为 4096，请求失败。即使 consumer 及时消费，额外 padding 仍改变 query 返回的位置和可用数据量。该方案保留在比较记录中，当前未采用。

复杂度审查按 reclaim-code-entropy 完成。真实使用方已定位到现有 tethering 构建和原始 memevents/MIUI 对象，通用任意页 vmap 会扩大内核访存范围，当前先实现满足宿主完整组条件的 ringbuf 分配。调查脚本和源码随结构化结果保留，未新增产品配置、通用诊断框架或中间数据同步服务。容量较小的 map 仍需独立解决，不能用现有较大 map 的结果扩大结论。

## 验收标准

实际 BPF 系统调用的返回、失败原因与重复调用后状态可复现。修复前后保留同一原始 BPF 文件和 map 参数，用户态 mmap 权限及双映射内容一致；失败清理检查能发现遗漏。静态声明、系统调用、原加载器与完整系统分别记录，只有对应范围完成才更新其状态。

### 失败复现与清理检查

[结构化结果](../../../../experiments/native-linux/results-4k-bpf-ringbuf-20261112.json)保留原始 ELF/map 声明、指令片段、编译命令、guest/runner 源码、全部基础输入哈希及原始日志哈希。运行采用 Mac17,15、macOS 27.0（26A428）、已验证的 `1ceb1b0` 构建，4 KiB guest、1 GiB RAM、64 GiB sparse、TBI、单 CPU Direct flat/code-watch。此次检查不测性能。

- 首轮 `python3 -B work/guest-4k-services-scan/run.py`：CLI/GCD 各 48 次 type 27 请求全部返回 ENOMEM，前后 ARRAY 对照成功。CLI 因 VmallocUsed 从 80 降至 64 KiB 触发测试内的相等判断，guest 退出 95；GCD 的 80 KiB 保持不变，检查成功。两入口 Linux 上下文均 1/1 清理。该首轮失败保持原记录。
- 后续 `python3 -B work/guest-4k-services-scan/run-batches.py`：先预热，再执行四批请求；CLI/GCD 各 3168 次 type 27/31 请求全部返回 ENOMEM，每类容量各 528 次。各批 ARRAY 对照成功。预热后 MemFree 固定为 1015608 KiB、VmallocUsed 固定为 64 KiB；Slab 从预热后的 5028 KiB 增至第二批 5040 KiB，后三批保持不变。两入口进程退出成功，上下文均 1/1 清理。
- 所有基础 119 项输入和原始 ELF 哈希再次核对一致。原始日志位于 `work/native-linux-nce/guest-4k-ringbuf-failure/` 与 `guest-4k-ringbuf-failure-batches/`；静态产物位于 `work/guest-4k-services-scan/`。

分批结果覆盖当前拒绝路径的重复请求，尚未对每个物理页分配位置注入失败。计数稳定支持本次负载中未出现累计内存增长；首次内存变化的每一项分配归属仍未追踪。原始加载器、BPF 程序触发、完整 services/desktop 与 iPhone 执行继续待验证。

## 风险

Binder 的实际缓冲分配使用 `kvcalloc(GFP_KERNEL)`、`alloc_page`、`vm_insert_page` 与 `kmap_local_page`，本轮未发现其直接调用任意 vmap。SELinux 策略数组和 ext4 组表可能经 kvmalloc 进入 vmalloc；显式 NOFAIL 多见于 slab 与 page cache，当前尚未定位 services 必经的 NOFAIL VMALLOC 调用。`__kvmalloc_node_noprof()` 会把原 flags 传给 vmalloc fallback，因此 NOFAIL 条件仍需在真实负载与故障注入中检查。页面回收 reporter 当前 order 4，在 4 KiB 下报告至少 64 KiB buddy 块；当前组件还未触发该回调。
