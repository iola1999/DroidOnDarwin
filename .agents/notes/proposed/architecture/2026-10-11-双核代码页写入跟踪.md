# 决策记录: 双核代码页写入跟踪

状态: proposed

## 问题

[双核运行时执行器](2026-10-11-运行时执行器与双核Linux.md)的完整桌面已经成功，代码缓存设置也完成局部对照。调用内校验复用没有覆盖大多数代码查询，下一次调用仍需比较代码内容。单核已有 `NceCodeWatch`，通过 RAM 的两个宿主映射跟踪写入，额外别名保留内容比较；双核目前禁止启用该设置。

现有版本字段和写异常计数使用原子变量，但普通查询计数及首次页面保护未处理两个查询同时进入的情况。磁盘读取前的失效也在双核排他区间之外。直接移除配置限制会违反现有并发约定。

## 提案

复用现有 `--direct-code-watch` 设置和版本回调。查询计数改为原子累加；已经受保护页面继续直接读取原子版本。首次保护或写入后的重新保护使用一个短时互斥区间，取得锁后重新读取版本，防止两个查询的部分保护失败相互影响。异常处理器继续不获取这个锁。

查询允许并发，调用方必须保证被查询页面没有并发写入。双核的共享代码标记与执行登记负责这一约束；失效、物理存储替换及额外 RAM 别名发布前停止全部客体。额外别名继续返回零版本，不新增一套基于内核通知的版本数组。初版继续关闭跨调用跳转复用，先单独检查内容比较减少后的收益。

## 曾考虑的替代方案

- 每次版本查询都获取互斥锁：已保护页面只需读取版本，所有查询加锁会增加两个 CPU 的等待。
- 根据内核写入通知维护另一套版本：还需完整核对所有内核写入和额外别名，现有宿主页保护已经覆盖直接 RAM 写入，先复用已验证的处理。
- 直接允许双核使用原实现：并发首次保护和查询计数尚未满足并发契约，磁盘失效顺序也需要调整。

## 验收标准

- 并发查询同页和不同页返回稳定版本，首次保护、查询计数、部分保护失败后的恢复均正确。
- 保留两份 RAM 别名写入、额外别名、存储替换、文件读取、并发写异常和销毁检查，CLI/GCD 成功。
- 双核 Linux 核心覆盖共享代码修改、用户复制、取消映射和退出；服务与 Bionic/ART 在 CLI/GCD 中成功。
- 同一构建交替关闭和开启跟踪，记录内容比较、版本命中、保护失败、阶段耗时及内存，完整桌面完成应用和正常退出后才能评价收益。

## 风险

宿主页面保护是进程范围的操作，额外 RAM 别名和查询期间的同页写入必须遵守上述约束。新增锁仅用于尚未受保护页面，不能进入信号处理路径，也不能在持锁期间调用 Linux。iOS 内存准备及完整产品集成继续单独验证。

## 本机进展

并发页面查询、其他页同时写入、部分保护失败恢复等独立检查已在 CLI/GCD 成功，结果在 `work/native-linux-nce/code-watch-smp-tests/summary.json`。双核核心与服务的两个入口均成功，结果分别在 `lkl-direct-smp-code-watch-core-verified` 和 `lkl-direct-smp-code-watch-services`。查询统计使用进程范围，各 CPU 的记录显式标记 `scope: process`。报告检查核对两份总计相同，并将查询数与全部 CPU 的代码查询总数比较；错误范围、总数不一致、超限和保护失败的负例均被拒绝。

首次 Android 交替对照遇到[proc 退出检查的错误码范围问题](../../implemented/testing/2026-10-11-proc退出竞态错误码.md)，修复后的八轮全部成功。Apple M5 Ultra / macOS 27.0（26A428）、`-O2`、双 Linux CPU、1 GiB RAM、16 KiB 页、每 CPU 的 Direct/Unicorn 各 128 MiB 缓存、flat 访存、256 项跳转表、跨页处理和原生独占指令、2 ms 定时抢占、100 ms 内存采样；nterp 开启，扩展 JIT 和快速基线关闭。两组使用同一构建，仅切换写入跟踪。关闭/开启时，Bionic 阶段中位数为 1.336512 / 1.216362 秒，ART 为 1.799308 / 1.474580 秒，分别减少约 9.0% / 18.0%。完整记录在 `work/native-linux-nce/android-direct-smp-code-watch-corrected-matrix/summary.json`。

随后启动可见桌面交替对照，准备阶段的关闭配置在 480 秒上限内未完成应用检查；Android 已启动，但完整检查未完成。数据盘正常卸载，838 个用户上下文和 66 个图形通道全部释放。该组正式开关对照尚未开始，保留于 `work/native-linux-nce/desktop-direct-smp-code-watch-matrix/runtime/summary.json`。约 60 秒时 system_server 检查完成，与之前单轮结果接近；启动完成检查附近的采样位置约为 266 秒，之前约为 105 秒。原因尚未确认，后台调度仅是待查因素。后续单独验证开启配置，并保留原来的时间上限。

开启配置的完整可见桌面随后成功，结果在 `work/native-linux-nce/lkl-direct-smp-code-watch-desktop/summary.json`。Launcher、Clock、闹钟、Files 和持久数据检查成功，1110 个用户上下文与 128 个图形通道全部释放，数据盘正常卸载。环境与前述 Android 对照相同，桌面执行阶段 263.783034 秒、清理 0.675435 秒，footprint 采样峰值 3,475,886,016 字节。进程共查询版本 373,699,859 次，两个 CPU 合计内容比较 55,896 次、版本命中 373,498,080 次，页面保护失败为零。该阶段包含启动、操作检查、等待和停止；首次关闭配置超时，因此尚无同构建桌面提速结论，后续先检查关闭配置的启动失败。结构化结果见[macOS 汇总](../../../../experiments/native-linux/results-macos-smp-code-watch.json)。

## 复杂度审查

跟踪器继续使用原有页面版本和写异常处理，只增加一个用于首次保护的互斥锁。版本查询来自各 CPU 的 Direct 执行器；失效与额外别名由 Linux 宿主映射、磁盘读取和回收调用。去掉锁会允许两个首次查询的保护与失败恢复交错；去掉双核排他区间会使查询与失效同时发生。已经受保护的页面仍直接读取原子版本。没有增加第二套页面状态数组，也没有启用跨调用跳转保留。

## 第二次桌面准备失败

`work/native-linux-nce/desktop-direct-smp-code-watch-repeat-matrix/runtime/summary.json` 的关闭配置在 Android 的 240 秒启动轮询上限失败，宿主返回 1，客体测试状态为 27904（退出码 109）。system_server 检查约在 64 秒完成，未观察到 boot completed。正式交替样本仍未开始，保持原时间上限。准备过程的三秒 `sample` 保存在同目录上级的 `baseline.sample.txt`；非等待栈包含 Unicorn 的访存与状态恢复，尚不足以确定启动延迟的单一原因。采样和后台进程观察均不纳入性能对照。两个关闭配置失败及一个开启配置成功尚不能支持完整桌面的提速结论。
