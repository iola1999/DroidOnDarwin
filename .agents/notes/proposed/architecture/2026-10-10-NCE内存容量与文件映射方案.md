# 决策记录: NCE 内存容量与文件映射方案

状态: proposed

## 问题

用户在另一会话中询问 NCE 的 Android 可用内存、旧 TCG 为何能提供 5 GiB，以及文件映射的性能代价，并明确认为当前 512 MiB 难以满足完整系统的使用需求。本记录于 2026-10-10 根据用户粘贴的会话补录，并核对当前源码、历史真机日志与平台文档。原会话未提供可访问的链接或完整日期。

当前工作仍按[Android 可交互桌面方案 A](../feature/2026-10-09-Android可交互桌面.md)推进。本文记录内存扩容需求、候选实现与验收条件；1–2 GiB 是讨论中的验证档位，最终容量、文件映射方式及其性能尚未确定。本次整理只更新文档。

## 提案

### 已核对的容量与适用范围

| 项目 | 2026-10-10 核对值 | 适用范围与来源 |
| --- | --- | --- |
| NCE 的 Linux RAM | 512 MiB | `NCE_RAM_SIZE = 0x20000000UL`；由内核、Android 服务、应用及文件缓存共同使用。见 [layout.h](../../../../experiments/native-linux/layout.h) |
| 客体用户虚拟地址窗口 | 4 GiB | `NCE_USER_SIZE`；用于程序、堆、线程栈等地址安排。虚拟地址预留与实际驻留内存分别统计；多个进程切换使用这个窗口 |
| Framework 测试的 Java 堆配置 | 初始 16 MiB、默认上限 128 MiB | `dalvik.vm.heapstartsize=16m`、`dalvik.vm.heapsize=128m`，见 [framework-test.cpp](../../../../experiments/native-linux/userspace/framework-test.cpp)；这是当前启动属性，Java 堆之外还有原生内存与图形资源 |
| NCE RAM 承载 | 匿名私有映射 | `shmem_init()` 使用 `MAP_ANON \| MAP_PRIVATE`，并要求大小等于 `NCE_RAM_SIZE`，见 [lkl-process-host.c](../../../../experiments/native-linux/lkl-process-host.c) |
| 旧 TCG 本次对照日志的客体 RAM | 5120 MiB，即 5 GiB | `/Users/fan/Downloads/husk-log/husk.log:202` 记录 `GUEST GETS 5120 MiB from a file-backed block`；容量为当前配置的 10 倍 |
| 旧 TCG RAM 承载 | 共享文件映射、按需分配 | 同一日志第 257 行记录 `memory-backend-file`、`size=5120M`、`share=on`、`prealloc=off`；承载文件名为 `guest-ram.bin` |

512 MiB 是当前原型的配置值。NCE 执行方式本身没有固有的 512 MiB 容量上限，但现有地址布局、映射和回收实现仍需随扩容检查。4 GiB 用户地址窗口、512 MiB 客体 RAM 与每个 Java VM 的堆配置属于不同约束，不能直接相加得到进程物理占用，也不能仅按其中一个数值推算可运行应用数量。

当前完整桌面的峰值尚待测量。512 MiB 可能增加 GC、文件缓存回收和后台进程退出；具体影响需要在目标负载中区分。扩容应与 CPU 执行、进程映射及图形开销分别分析，相关问题见[性能风险与验证](2026-10-10-HyperOS性能风险与验证.md)。

### 旧 TCG 的 5 GiB 如何工作

历史版本 `c93cd7a:src/app/Husk/QemuRunner.swift` 的文件映射候选从 5120 MiB 开始，后续为 4096、3584、3072、2560、2048 MiB；选择过程还参考映射探测与先前失败记录。这是旧实现的容量选择方式，不能据此确定 NCE 的可用容量。

QEMU 为客体提供 5 GiB RAM 地址范围，宿主通过共享文件映射提供其内容。`prealloc=off` 使页面按访问需要分配；`share=on` 使修改可写回承载文件。客体看到的容量、当前驻留在 DRAM 的容量，以及 iOS 计入进程的内存占用需要分别观察。配置说明见 [QEMU 内存后端参数](https://www.qemu.org/docs/master/system/qemu-manpage.html)及[共享映射说明](https://www.qemu.org/docs/master/system/vm-templating.html)。

文件承载页面仍可驻留在 DRAM。已经映射且驻留的页面由 CPU 直接读写，正常访问无需文件 I/O；页面被回收后再次访问可能需要从文件读入；修改过的页面需要保存内容后才能回收。频繁访问的数据超过可驻留容量时，重复读入与回写可能造成明显延迟和发热。文件映射与 swap 都可能产生换页 I/O，各自的承载和管理方式需要区分。机制说明见 Apple 的[虚拟内存说明](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/ManagingMemory/Articles/AboutMemory.html)及[文件映射说明](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemAdvancedPT/MappingFilesIntoMemory/MappingFilesIntoMemory.html)。这两份存档文档用于解释基本行为，当前 iOS 的回收策略仍需实测。

旧日志中的预算读数也有时间条件：

| 采样点 | phys footprint | resident | 当时可继续分配的读数 |
| --- | --- | --- | --- |
| `app-launch`，日志第 58 行 | 2.9 MiB | 12.0 MiB | 3373.1 MiB |
| `before-qemu-init`，日志第 270 行 | 541.8 MiB | 608.3 MiB | 2834.2 MiB |

两次 footprint 与可继续分配读数相加均约 3376 MiB，即 3.30 GiB，可用于描述当时估计的进程限额。该值不能作为长期固定预算。旧日志确认客体配置了 5 GiB；本次核对没有找到足以量化该负载换入、回写及缺页等待的测量，无法确定文件映射对当时卡顿的贡献。

### NCE 与旧 QEMU／TCG 的执行差异

| 层面 | 旧 QEMU／TCG | 当前原生 Linux＋NCE |
| --- | --- | --- |
| Android ARM64 代码 | 经过 TCG 翻译并缓存执行 | 支持的普通指令在宿主 CPU 执行，系统调用、TLS 和特殊指令由 NCE 适配 |
| Linux 内核 | 客体内核经过模拟 CPU 执行 | 修改后的 Linux 6.12 LKL 编译为宿主代码执行 |
| 系统调用 | 经过模拟 CPU 的异常处理进入客体内核 | 改写后的入口交给嵌入的 Linux 内核 |
| 用户内存访问 | QEMU 软件 MMU 处理客体地址 | 建立宿主映射供 CPU 访问；进程切换仍需保存状态和调整映射 |
| CPU 与进程 | 虚拟 CPU 由 TCG 执行 | 当前单 Linux CPU 调度；多个客体进程共同消耗 宿主进程的宿主资源 |
| 设备接口 | QEMU 虚拟主板及设备 | 按 Android 需要适配存储、输入、显示等接口 |
| 图形 | 本次历史真机日志已使用 ANGLE Metal | gfxstream → ANGLE → Metal；缓冲区传输、合成和同步仍有开销 |
| 系统镜像 | 使用适配虚拟机的内核和系统镜像 | 需要适配内核、Bionic、ART 与设备接口；当前集成为 Android 16，完整 HyperOS 尚未迁入 |

依据见[路线决定](../../implemented/architecture/2026-10-08-转向原生Linux与NCE.md)及[Android 阶段记录](../../implemented/architecture/2026-10-09-Android用户态与Metal阶段记录.md)。NCE 测试应用在 [NativeLinuxApp.swift](../../../../experiments/native-linux/ios/NativeLinuxApp.swift) 中调用 `nce_lkl_run()`，这条执行路径已移除 QEMU 的 CPU 翻译和整机模拟层；当前共享界面与设备管理位于 `experiments/native-linux/app/`，内置 JIT 沿用上游实现并保留来源声明，图形使用 gfxstream / ANGLE。`qemu_pipe_open_ns()` 是图形客户端兼容入口，当前经 Linux Unix socket 连接 `/dev/nce-render`，见 [guest-pipe.c](../../../../experiments/native-linux/graphics/guest-pipe.c)。

用户提供的对话将此前卡顿测试描述为 CPU 渲染。核对所引用的 `husk.log:282`，其 `GL_RENDERER` 明确包含 `ANGLE Metal Renderer: Apple A19 GPU`，因此本文按该次运行记录为 Metal。其他历史构建需按各自日志确认。NCE 的预期收益主要来自减少 CPU 翻译和软件访存处理，仍需测量系统调用、缺页、地址空间切换和图形传输等剩余开销。

### 扩容候选与实施前检查

#### 首个 1 GiB 验证档位（2026-10-10 05:24）

Mac 的 `demand` 映射启动已显示 Launcher，随后原版 lmkd 在 21:22:16 UTC 先杀掉 PermissionController，再杀掉前台 Launcher，日志原因为 `min watermark is breached even after kill`，释放的 Launcher RSS 为 89,152 KiB。SystemUI 也出现启动 ANR。此次运行明确触及 512 MiB 客体容量，下一轮将匿名 RAM 提到 1 GiB，继续使用现有回收和别名映射方式。Java 堆暂维持 128 MiB，以便区分客体总容量变化的影响。

扩容回归将在 Android 启动前实际写入超过旧容量的私有页，检查内容与 fork 后的 COW，释放后继续运行既有进程、共享页、代码和回收检查。宿主 RAM 映射检查已经覆盖承载区域首尾页面，会随配置读取新的最高偏移。完整启动记录 lmkd 行为与宿主内存占用。新增容量的 iPhone 地址预留和预算随阶段 IPA 集中测试，当前尚无设备结果。

首轮已实际分配并写入 640 MiB，子进程检查全部页并修改三个 COW 页，父进程内容保持正确。Launcher 的真实画面检查通过，日志未见 lmkd 结束应用；后续时钟检查因用户解锁和可见状态失败。该轮数据见 [1 GiB 结果](../../../../experiments/native-linux/results-macos-desktop-demand-1g.json)。完整持续交互与设备预算仍未验证。

完整系统需要评估更大的可用内存。可先以 1 GiB、2 GiB 作为容量验证档位，结合真实桌面和应用工作集选择后续配置；5 GiB 的 NCE 配置、稳定驻留容量及性能尚未验证。扩容同时检查 Java 堆属性，分别记录 Java、原生和图形内存增长，避免只扩大其中一项。

先测量整个 宿主进程的 footprint、resident、`os_proc_available_memory()` 与峰值，给 LKL/NCE、JIT、图形资源和宿主自身留出空间。Android 分出多个 Linux 进程后仍共享同一份宿主预算。`os_proc_available_memory()` 返回当时还能分配的估计字节数，读数可能随生命周期和系统情况变化；物理内存总量及单次读数不足以决定最终客体容量。见 [Apple API 文档](https://developer.apple.com/documentation/os/os_proc_available_memory)。

提高内存上限的 entitlement 可以作为平台条件调查项，是否适用于设备和实际侧载签名环境需要确认。构建配置包含该声明后，仍需读取已签名包及运行读数。Apple 说明该权限只适用于部分设备，并要求应用兼容其不可用的情况，见 [Increased Memory Limit Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.kernel.increased-memory-limit)。

文件承载 RAM 是扩容候选，需要一起处理以下问题：

- RAM 承载、Linux 直接映射和客体用户映射必须引用正确的页面，并保持共享、COW、fork/exec 和访问保护语义。
- 现有 `shmem_reclaim()` 通过重新建立匿名 RAM 与直接映射归还 Linux 空闲页。引入文件承载后需要重新设计这段行为，防止不同映射引用不同内容。Linux 空闲页可归还与仍有有效内容的页面由宿主换出，分别处理。
- 检查容量扩大后的地址预留、偏移运算、页管理数据及映射范围。每进程虚拟地址范围与客体物理容量可以分别配置；当前布局与平台限制需要实际验证。
- 可执行代码继续遵守 iOS JIT 和页面权限要求；普通 RAM 改为文件映射不能直接解决代码页执行问题。
- 处理承载文件空间不足、映射失败、读写故障及文件生命周期。文件承担运行内存用途，持久 Android 数据仍按现有系统盘和数据盘管理。
- Android 可能在宿主内存紧张时继续保留缓存。需要测量并评估宿主压力如何传递给 Linux 回收与 Android 进程管理，防止两层内存管理各自判断充足而持续换页。

目标是让频繁使用的页面有足够驻留空间，让较少使用的页面具备回收条件。共享文件映射本身没有给出热页驻留保证；如果实际交互依赖持续存储读写维持，容量增加仍可能伴随严重卡顿。

## 曾考虑的替代方案

- 维持 512 MiB 作为完整系统最终配置：用户明确认为容量过小。保留其现有原型用途，扩容需求进入后续评估。
- 扩大匿名 RAM：可沿用现有承载方式，但仍需核对宿主预算、地址预留与回收；尚无更大容量的真机结果。
- 使用共享文件承载 RAM：旧 TCG 已使用 5 GiB 配置，NCE 可调查相同的宿主机制；映射语义、代码页及回收路径需要单独适配，性能取决于实际工作集与换页情况。
- 直接按旧 TCG 设置 5 GiB 并依靠文件回收运行：缺少 NCE 容量和持续交互测量，本文保留为待验证容量，不确认为交付默认值。

## 验收标准

1. 每档容量记录构建、设备、系统、签名/JIT 条件、客体 `MemTotal`、Java 堆属性、地址预留与宿主内存峰值；说明内核保留空间与配置容量的差异。
2. 扩容后验证私有页、共享页、COW、fork/exec、保护、进程切换、代码页和回收后再次访问。覆盖大于旧容量的分配与释放，以及高偏移地址，检查内容和隔离语义。
3. 如果引入文件承载，同负载比较匿名与文件承载配置，记录存储占用、可获取的换入/回写量、缺页与等待时间。指标不可获取时明确记录测量限制。
4. 完整桌面负载覆盖冷启动、连续滑动、两个应用切换、后台运行与恢复，关联 GC、Linux 回收、进程退出、宿主 footprint/resident、内存压力与热状态；持续运行和重复轮次的方法随测试记录。
5. 处理宿主内存压力和文件故障时，检查活跃数据、共享映射与文件生命周期；容量选择须给运行时和 GPU 留出实测余量。单次启动成功不足以完成内存验收。
6. 保持阶段性整包真机交付安排。本机能够完成的功能与边界检查先完成，再与桌面阶段合并验证。最终容量与性能结论来自真实负载，本文未设定未经用户确认的容量保证或帧率阈值。

## 风险

增加客体可见内存可能使 Android 扩大缓存与后台工作集，宿主压力和发热同时上升。共享文件页的内存计费、回收时机及可驻留容量受平台影响；文件映射仍消耗地址空间和物理资源，不能据此承诺越过 iOS 的运行限制。实际签名权限也可能使提高内存上限的选项无法使用。

地址空间切换、单 Linux CPU、ART 覆盖和图形传输仍可能独立限制性能。内存扩容有助于处理容量不足造成的开销，完整 HyperOS 的高性能运行仍需通过系统集成与持续交互确认。
