# 决策记录: 独立地址范围与应用进程重启

状态: proposed

## 问题

用户要求考虑有较大性能收益可能的改动，并关注逐应用预编译对 APK 复用的影响。当前 NCE 在一个宿主窗口内切换 Linux mm，已有页恢复仍会产生大量信号与宿主映射操作，测量见[后续提速规划](2026-10-10-后续提速与多核可行性评估.md#当前映射诊断与连续页恢复候选)。独立地址范围仍待实现；用户代码翻译已完成独立指令、真实 LKL 用户进程和 Bionic/ART 原型，尚无 Android 桌面、整机提速或通用 APK 兼容性结果。

## 提案

为独立创建的 Linux 进程分配互不重叠的宿主地址范围，可能使各自的数据映射持续保留，减少切换时的撤销与缺页恢复。这要求修改当前全局用户布局、ELF 装载、执行区授权和 NCE 上下文；fork 子进程继承父进程指针，不能直接改变其地址。先验证两个 exec 进程的隔离、共享页和生命周期，再决定如何处理 Android 应用的 Zygote 继承。

一个需要验证的 Android 入口是 `WrapperInit`。已核对 Android 16 的[源码](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/core/java/com/android/internal/os/WrapperInit.java)：`execApplication()` 构造 app_process 命令，`main()` 向 Zygote 报告 PID、执行 `ZygoteInit.preload()`，随后经过 `Zygote.nativePreApplicationInit()` 和 `RuntimeInit.applicationInit()` 进入应用。Android 的 [wrap.sh 文档](https://developer.android.com/ndk/guides/wrap-script)说明这种调试入口用于启动新的运行时进程，并要求 debuggable APK。若用于本项目通用启动，应在受控 Framework 内验证等价初始化，保留原始 APK、签名与 UID/GID；现有调试入口不能直接作为通用安装完成的依据。

该候选可与公共 boot image 配合：新运行时会重复执行类与资源预加载，可能增加启动时间和内存。匹配的公共镜像或其他初始化复用是否足以抵消这些成本，必须实际测量。先保持单个 Linux CPU，仅比较移除地址重映射后的变化；SMP、线程局部 NCE 状态和并发代码更新另按[多核规划](2026-10-10-后续提速与多核可行性评估.md#多核的实际阻塞)推进。

普通原生 ELF 与 ART 生成代码仍需为每个执行地址准备可执行区域。手机上多个地址范围能否成功预留、准备耗时及 footprint 尚未测量；不能从 Mac 的虚拟地址容量推断 iPhone 的可用规模。应用后续主动 fork 的行为需要保留原有隔离与写时复制，父子共享地址语义的处理仍是本候选的未解决项。

### 结合双核结果的后续原型

2026-10-11 的[双核试验](2026-10-11-LKL双核用户态与映射同步.md)已确认真实用户线程可并行计算，完整 Android 仍在大量窗口恢复和调度中延迟，Keyguard 初始化发生 ANR。较长基础时间片未使双核桌面检查通过。完成当前单核参数对照后，继续在独立原型中评估地址范围和访存转换，不直接替换已验证的单核产品。

当前 `layout.h` 为一个用户窗口预留 4 GiB；为多个进程重复预留完整窗口会增加虚拟地址需求，手机是否可容纳仍未知。exec 候选先只验证两个小型位置无关 ELF，在不同范围加载相同代码、私有数据和共享页，并确认每次切换无需撤销对方映射。随后才调整 Android 的全局布局、Zygote 初始化和应用启动协议。

另一个可独立测量的候选为原生 LKL 加用户代码动态翻译。用户访存经软件 TLB 解析到现有 RAM，不要求每个进程占用完整宿主窗口；Linux 继续承担进程、系统调用、文件和设备，运行仍由手机独立完成。其代价包括普通访存、分支和寄存器处理开销，需要实际比较。QEMU 的[多线程 TCG 文档](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html)描述了翻译代码内的软件 TLB 与跨 CPU 失效约束。[Unicorn 的 FAQ](https://github.com/unicorn-engine/unicorn/blob/master/docs/FAQ.md)和[头文件](https://github.com/unicorn-engine/unicorn/blob/master/include/unicorn/unicorn.h)提供 `UC_TLB_VIRTUAL`、`UC_HOOK_TLB_FILL` 与刷新入口，可用于独立测量；本项目尚未验证这个执行引擎的 Android 整机性能或 iPhone 可执行内存适配。

原型先使用相同 ARM64 指令负载比较原生执行与翻译执行的整数、访存和原子操作，核对计算结果。再让两个地址空间在同一客体地址读取不同内容，并检查代码修改、权限变化与缓存失效。库复用和试验依赖放在 `work/`，原型不引入产品依赖。只有纯计算损耗、软件访存成本与取消重映射的收益有可比较结果后，再决定是否继续接入 LKL；该候选没有整机提速承诺。

### 用户代码翻译的独立测量

2026-10-11 实现 [ARM64 执行原型](../../../../experiments/native-linux/translation/benchmark.c)和[运行脚本](../../../../scripts/probe_user_translation.py)，使用本地 venv 的 Unicorn 2.1.4 静态库。原生函数和翻译器执行相同汇编字节，比较固定整数依赖循环、64 KiB 数组读写及单线程 LDAXR/STLXR 循环。翻译代码在计时前预热，三轮交替执行顺序；数据初始化和核对排除在计时之外，一次引擎进入和寄存器传递包含在内。原生与翻译结果及全部数组字节一致。

Apple M5 Ultra / macOS 27.0 (26A428)，16 KiB 客体页、16 MiB 翻译缓存上限，命令为 `python3 scripts/probe_user_translation.py`。原生/翻译的墙钟中位数分别为：整数 426.586 / 440.109 ms，数组读写 107.310 / 459.607 ms，原子循环 141.827 / 164.827 ms。对应翻译耗时为原生的 1.032 / 4.283 / 1.162 倍。该结果仅覆盖三个小型循环，分支复杂度、代码工作集、共享原子争用和真实 Android 均未覆盖。逐行测量、源码与依赖摘要见[结构化结果](../../../../experiments/native-linux/results-macos-user-translation.json)。

两个地址空间在同一客体虚拟地址读写不同物理缓冲区的检查通过；256 次交替、每次 64 次原子递增、TLB 刷新与引擎进入合计 1.485 ms。只读权限拒绝写入，恢复权限后正确写入，动态代码替换后执行新结果。这些检查尚未接入 Linux 的 PTE、COW、fork、信号或多核。首次试验在替换代码后继续使用旧翻译块，随后补充显式 `uc_ctl_flush_tb()`：固定版本 `uc.c` 的 `UC_CTL_TLB_FLUSH` 仅调用 `tcg_flush_tlb()`，头文件注释不足以保证翻译块同时失效。现有代码替换检查覆盖这个故障。

两个 CPU 寄存器上下文交替复用同一引擎，TLS、x18、SIMD 与条件标志检查成功；256 次保存、恢复、执行和结果读取合计 1.408 ms。固定版本报告每份 CPU 上下文为 12,640 字节，未包括客体栈、Linux task 或代码缓存。该检查只切换寄存器状态，尚未验证抢占与真实 Linux 线程调度。

内存记录包括每个检查阶段的 physical footprint、最新 RSS 和进程生命周期 RSS 峰值。该轮引擎准备后 footprint 为 3,228,056 字节，边界检查后为 3,719,576 字节；具体数值以结构化记录为准。采样仅发生在阶段边界，没有时间加权平均值，也不能表示完整 Android 的代码缓存或内存需要。

当前结果支持继续比较取消重映射与增加软件访存的成本。访存循环已显示明显损耗，不能只依据整数循环接近原生就选择该执行架构。随后扩大到真实 LKL 进程和地址切换负载，结果见下方记录。

### Linux 集成的约束与剩余边界

集成先保持单 Linux CPU，用小型 ELF 检查系统调用、TLS、fork/COW、共享页、权限和信号。需要 Linux 缺页处理或调度时，先停止引擎并返回普通宿主栈，完成处理后恢复客体 PC。当前实现已覆盖这种退出与恢复，并增加直接读取当前 mm 的 PTE 变体；保留用户窗口回调维护的软件页表作为对照。

执行引擎按单个虚拟 CPU 复用，Linux 线程只保存客体寄存器和 TLS。为每个 Linux 线程建立独立翻译引擎会复制代码缓存与内部状态；当前 Android 回归会创建数千个 NCE 上下文。原型在每次进入前从初始 CPU 上下文恢复，再写入该线程寄存器，清除前次执行留下的独占访问状态；跨系统调用的信号与浮点寄存器检查成功。后续多核仍需独立验证并发代码更新、共享原子操作和引擎生命周期。

地址空间切换需要失效旧的地址转换；代码内容变化还需要独立处理翻译块失效。来自内核写入、共享可写页、fork/COW 和应用动态代码发布的修改都可能影响执行，必须分别验证。最初的指令原型只覆盖宿主显式修改代码，Linux 原型随后覆盖了现有代码发布协议；其他代码修改方式仍待检查。iOS 的翻译缓存执行授权、写入方式和抢占也要继续适配，Mac 原型成功不足以确认设备端可用。

通用 ELF 装载的验收使用宿主构建完成后才提供的 ARM64 二进制，保留原文件，不查找预生成的程序登记项。先完成独立进程的加载与指令执行，再接入 JNI APK。该阶段沿用完整 Linux/Android 目标；DEX 和公共 ART 优化继续按原规划处理。

### Linux 软件访存原型（2026-10-11）

已实现 [Linux 执行入口](../../../../experiments/native-linux/translation/linux-execution.c)和[运行脚本](../../../../scripts/probe_lkl_translation.py)。复用已验证的单核 LKL 镜像，将用户页的宿主映射回调改为更新软件页表；内核 RAM 和 vmalloc 继续使用原有宿主映射。Unicorn 的软件 TLB 从该表取地址和权限，发生缺页时退出引擎，再由 Linux 处理缺页或发送信号。系统调用同样先保存寄存器并退出引擎，允许 Linux 阻塞和切换线程后恢复。这个阶段保留内核现有的用户窗口扫描与页表比较，测量范围包括取消用户页的 Darwin 映射与增加翻译执行的共同影响。

原型与产品构建分开。ELF 在运行时依据文件头和程序头安排地址，客体文件在宿主构建之后提供；宿主不引用 `program-images.h`。裁剪符号的 ELF、共享库构造函数、`dlopen`、动态 TLS、8 个线程及 fork 后的库状态检查成功。动态代码沿用现有代码发布系统调用，128 次更新、共享代码修改、相同地址替换物理页、代码撤销和再授权检查成功。已有信号回归覆盖 x18、SIMD、FPCR/FPSR、嵌套信号、备用栈、EINTR/重启、线程取消和定时器抢占。

初始实现使用每批 50,000 条指令抢占。核对 Unicorn 2.1.4 的 `uc.c` 后确认 `count` 参数通过逐指令回调实现，因此加入 `--preemption timer`：专用线程每 2 ms 请求 `uc_emu_stop()`，引擎退出后才进入 Linux 调度。上游同版本的超时线程也使用这个入口；原型用互斥锁隔开引擎运行与寄存器、缓存和销毁操作。两种方式分别通过 CLI/GCD 各三轮，保留 `--batch-instructions` 供指令模式对照。一次原型运行创建并释放 57 个 Linux 用户上下文，共享一个翻译引擎；定时线程在销毁引擎前停止并完成 join。

结构化结果见 [Linux 翻译原型结果](../../../../experiments/native-linux/results-macos-lkl-translation.json)。环境为 Apple M5 Ultra / macOS 27.0 (26A428)、单 Linux CPU、16 KiB 页、1 GiB Linux RAM、16 MiB 翻译缓存、FP/ASIMD HWCAP。原生与翻译均执行 `memory_exchange_benchmarks()` 的 28 种组合：2/4/8/16 MiB 数据、0/50/100% 共享、只访问一页或访问全部页，以及同 mm 线程；每组计时 128 次管道往返，初始化和首次 COW 排除在外。原生组使用关闭映射统计与缺页诊断的 CLI/GCD 各一轮，翻译组每种抢占方式各六轮。以下为 16 MiB、访问全部页的往返耗时中位数，单位为 ms：

| 负载 | 原生窗口 | 翻译＋指令计数 | 翻译＋2 ms 定时器 |
| --- | ---: | ---: | ---: |
| 进程，全部私有页 | 13.783605 | 2.878117 | 2.688577 |
| 进程，50% 共享页 | 6.556417 | 2.424171 | 2.278773 |
| 进程，全部共享页 | 0.149949 | 0.359648 | 0.302687 |
| 同 mm 的线程 | 0.017437 | 0.230816 | 0.111261 |

这组结果显示跨进程私有页切换存在继续优化的空间，同 mm 和全部共享页的负载仍有损耗。原生测试携带完整 NCE 程序集合，并在页切换前执行内存边界和 640 MiB 容量检查；翻译测试携带小型 ELF 集合，先运行代码与信号检查。两组工作集不同，执行顺序也未随机交错，因此当前用于判断方向，不能据此给出 Android 整机提速倍数。定时器减少了逐指令计数成本，16 MiB 同 mm 线程仍比原生慢约 6.38 倍。

内存采样默认每 100 ms 一次，`--memory-interval-ms 0` 关闭周期采样。记录内核准备、客体文件准备、客体执行和清理阶段的 footprint/RSS 样本均值、采样峰值、最新值，以及独立的进程生命周期 RSS 峰值。指令/定时器两组共 288 个原始样本，均值、峰值、最新值和样本数重新计算后全部一致；关闭采样的 CLI/GCD 也成功。定时器组六轮客体执行阶段的 footprint 均值中位数为 73,854,890.574 字节，采样峰值与阶段最新值中位数均为 98,738,824 字节。采集函数累计耗时中位数为 0.645 ms，同阶段持续时间中位数为 1,517.4225 ms；这个采集耗时未覆盖宿主线程唤醒对调度的全部影响，采样峰值也可能遗漏短暂峰值。

执行脚本会拒绝内核镜像与验证清单不一致、私有导出地址与 ELF 不一致、运行期间输入变化、缺少检查项或内存统计不一致。额外验证已确认损坏的均值、最新值、缺失 benchmark 组合、缺失功能检查和失败结束状态均被拒绝；无效指令批次在构建前拒绝。两项原生测试函数提取后，原生 CLI/GCD 基础回归成功，覆盖原有动态代码、信号、内存和 Android 服务检查；本轮该回归未打开 `NCE_SYSTEM_SERVER_PROBE`，未重跑 Launcher、Clock 和 Files 桌面阶段。

复现使用 `python3 scripts/probe_lkl_translation.py --repeat 3`，定时器变体增加 `--preemption timer --output work/native-linux-nce/lkl-translation-timer`。先完成 `probe_lkl.py --processes --graphics-angle work/angle-macos/prefix/lib` 的单核验证，保持该镜像、头文件及 `lkl.so` 匹配；Python 环境依赖仍为 `work/native-linux-nce/user-translation-venv` 中的 Unicorn 2.1.4。脚本记录构建命令、配置、源文件、客体 ELF、引擎与宿主可执行文件的摘要。

这一阶段仅覆盖 AArch64 ET_DYN、16 KiB 段布局，运行时地址表上限 64 项；当时尚未处理 4 KiB ELF、APK 内库、应用更新后的地址复用与手机 JIT 准备。后续 Bionic 接入增加了 ZIP 内库检查，见下方 Android 运行时记录。动态代码检查覆盖现有显式发布协议，其他引擎通过可写别名或文件修改代码的全部方式仍待验证。后续 PTE 变体见下方记录。原生与翻译执行的整体工作集仍有差异，Android 与 iPhone 继续作为后续阶段验收项。

### 直接读取 Linux PTE（2026-10-11）

已建立独立单核内核变体，让软件 TLB 查询当前 Linux mm 的 PTE，省去 installed/desired 用户窗口表、撤销与恢复。查询只读页表，不分配内存、不获取 Linux 锁、不调度；缺页、COW、accessed/dirty 更新仍退出翻译引擎后由 Linux 处理。内核与宿主共享映射、代码变更计数，在下次进入引擎前分别刷新 TLB 和翻译块。内核 RAM 与 vmalloc 继续使用宿主映射。`--mapping window|pte` 选择实验构建，产品内核与产物继续独立保存。

客体检查增加已有的内存边界、文件访问、栈增长、2 GiB 稀疏空间、640 MiB 容量与 fork/COW，原生测试仍按原顺序调用同一容量函数。PTE 变体每轮创建、释放 66 个 Linux 用户上下文，用户窗口映射和撤销回调均为零。计数抢占和周期内存采样关闭的 CLI/GCD 分别通过，默认采样仍为 100 ms，阶段字段沿用前述定义。

扩大负载发现了[定时抢占后的指令状态问题](../../implemented/bug-fix/2026-10-11-翻译器定时抢占后的指令状态.md)。现改为固定 Unicorn 2.1.4 源码加本地补丁，定时器只请求在翻译块入口停止；普通系统调用、缺页与错误继续使用原有退出路径。四类访存的确定性回归验证指令完成、地址回写和恢复执行。原版入口复现状态不一致，修复版连续 20 轮成功。前一阶段使用原版停止入口的数据保留为历史实验，其正确性范围限于当时的小型负载。

构建脚本校验固定源码压缩包的 SHA-256，记录补丁、静态库和内核摘要。Linux 构建标识固定，Darwin 静态归档使用 `ZERO_AR_DATE=1`，使重复构建的产物可逐字节比较；这些固定值用于可复现构建，实际运行环境与配置另记在测量报告中。每次实验仍核对运行前后摘要，拒绝来源或产物在测试期间变化。额外检查确认，非零用户映射/撤销次数、损坏的内存均值/峰值/最新值、缺失容量检查项均会被拒绝；对照脚本拒绝不平衡的奇数轮次。

正式对照使用 `python3 scripts/benchmark_lkl_translation.py --repeat 8`。脚本重新构建两种变体，核对全部客体文件逐字节相同，再按相反顺序交替运行窗口表和 PTE，覆盖 CLI/GCD 共 32 次独立进程。环境为 Apple M5 Ultra / macOS 27.0 (26A428)、单 Linux CPU、16 KiB 页、1 GiB Linux RAM、16 MiB 翻译缓存、2 ms 抢占请求和 100 ms 内存采样。每个变体 16 轮，均通过前述全部功能检查。原始结构化行、构建摘要与配置见 [PTE 对照结果](../../../../experiments/native-linux/results-macos-lkl-translation-pte.json)。

| --- | ---: | ---: |
| 进程，全部私有页 | 2.467898 | 0.309433 |
| 进程，50% 共享页 | 2.295496 | 0.319488 |

全部私有页的中位数比约 7.98，50% 共享页约 7.18；全部共享页与同 mm 线程接近。各轮仍有波动：私有页窗口表范围 0.879250～2.584460 ms，PTE 范围 0.296460～0.439835 ms。整段客体执行包含代码、信号、容量和内存边界检查，中位数由 1,401.864 ms 降至 749.850 ms，耗时比约 1.87。该对照只比较两种用户代码翻译映射方式；原生产品与完整 Android 的工作集、前置步骤不同，目前没有 Android 整机提速结论。

### 原型复杂度审查

汇编文件定义供两种执行路径共同使用的三个负载，以及仅供客体寄存器切换检查使用的函数；C 文件承担引擎生命周期、功能边界和计时；Python 只负责构建、进程期限、配置与结果保存。Unicorn 只在 `work/` 的实验依赖中存在，产品构建未引用。两个数据缓冲区对应实际地址空间隔离检查，删除第二份会失去同地址不同内容的验证；翻译缓存刷新对应已复现的旧代码执行问题。当前不增加通用翻译器接口、策略注册表或持久缓存格式。

PTE 变体复用现有 MMU 源码，经严格匹配的独立构建补丁修改，当前没有复制整份 MMU 实现。共享状态只包含映射和代码两个计数；移除任一个会失去对应缓存失效判断。原型的窗口表仅供对照使用，PTE 运行时不分配。Unicorn 补丁限定 ARM64 单核原型，保留单独停止入口是为了区分定时异步请求和回调中的同步停止；同时删除翻译块入口的请求处理会使持续计算无法被抢占，恢复异步线程直接修改 CPU 退出状态会重新引入指令内部退出风险。最小指令回归与完整 Linux 定时信号分别检查状态恢复与持续运行时的调度。

Linux 原型按执行与映射、宿主加载与文件准备、周期内存采集、客体行为检查分文件。现有 `lkl-host.c` 直接复用，`nce_process_thread_exit()` 由它在 Linux 线程退出时调用；当前原型没有该回调需要释放的线程局部宿主资源，保留空实现满足实际调用接口。`dynamic_code_tests()` 和 `memory_exchange_benchmarks()` 从已有测试中提取，原生入口仍按原顺序调用，翻译原型复用同一负载，删除了首轮原型自行编写的交换负载。初始 CPU 上下文用于清除独占访问状态，映射变更计数用于判断 TLB 失效，代码变更计数用于独立判断翻译块失效，三者的用途不同。去掉定时器锁会使跨线程停止请求与引擎销毁或寄存器操作并发；去掉内存采集线程会失去阶段中的采样峰值。两个小型头文件分别只有对应运行程序实际调用的三个函数，没有引入执行策略注册层或产品设置项。

### Bionic 与 ART 接入计划

下一阶段让独立翻译入口挂载现有只读 Android 系统镜像，在临时 Linux 文件系统内准备测试 DEX 和配置，运行 Bionic、CFI/ZIP 内库和 ART 回归。宿主继续不链接程序登记表；系统镜像中的原始 ELF 在运行时解析，测试数据不使用持久 Android 数据盘。复用已有负载，先检查信号、128 个线程、分配器、CFI、APK 内库、Java/JNI、JIT 代码发布和 VM 销毁，再根据实际失败调整执行路径。这个阶段覆盖运行时基础，完整 APK 安装、Android 桌面与手机执行内存继续作为后续验收。

验收分别记录 CLI/GCD、解释器选择与 JIT 配置、各阶段时间和内存均值/采样峰值/最新值。失败时保留客体日志和返回状态。修改翻译器后重新运行已有信号、内存、动态代码与抢占检查，确认基础行为保持正确。

### Android 翻译入口与缓存处理

2026-10-11 已接入 Bionic、CFI 与 ART。`probe_lkl_translation.py --workload android` 直接挂载现有只读 `system.img`，运行 `/bionic-test`、`/system/bin/cfi-test` 和 `/system/bin/art-test`。配置和测试 DEX 写入临时 Linux 文件系统，宿主不链接 `program-images.h`。已适配的 Bionic/ART 仍来自产品系统镜像；目前没有验证未经适配的 Android 系统镜像。

运行时 ELF 布局沿用 Bionic 的 256 KiB CFI 地址对齐要求。`BRK` 按指令编码交给 Linux 生成 `SIGTRAP`，其余未处理指令异常交给 `SIGILL`。原有 CFI 负例、反复卸载/加载、ZIP 内两份库和 fork 后重新加载均参与验收。

首次 ART 检查成功，但 CLI/GCD 的 VM 测试分别耗时 13,766.887 / 17,045.459 ms，原始结果为 `work/native-linux-nce/lkl-translation-android/summary.json`。本机 `sample` 显示普通数据写入反复进入 `store_helper`、`notdirty_write` 与代码失效处理。核对固定版本源码后发现，全范围 `UC_HOOK_MEM_INVALID` 会使 `uc_mem_hook_installed()` 返回 true，阻止数据写入恢复直接路径。该回调已移除；客体地址和权限仍由 `UC_HOOK_TLB_FILL` 查询 Linux PTE，失败时退出引擎交给 Linux。

PTE 变体新增 8 KiB 代码页位图，每个 bit 对应一页 16 KiB Linux RAM。内核在可执行 PTE 变化、代码发布时标记物理页；宿主在 RAM 归还时标记对应页，进入翻译引擎前使这些物理页关联的翻译块失效。执行文件切换保留全量清空。原有两个计数仍分别判断 TLB 与代码变化；位图由唯一 Linux CPU 写入和消费，不新增工作线程。`--cache-invalidation full|pages` 保留对照方式。

`--linux-fastpath 0|1` 控制专用于当前 Linux 接口的生成代码调整：缺页从软件 TLB 失败路径恢复寄存器并退出；定时器只请求在翻译块入口停止；访存之后不再重复调用停止检查；翻译块入口读取停止标志，仅在有请求时调用 C 处理函数。这个选项要求执行期间没有物理内存回调和异步指令内部停止。`preemption-test.c` 增加读取目标与地址重合、单次读取后地址更新、成对读取后地址更新及写入后地址更新的缺页恢复检查，同时保留停止时的指令状态检查。

`--cache-mib 16|64|128`、`--art-nterp 0|1`、`--art-expanded-jit 0|1`、`--art-fast-baseline 0|1` 用于测量缓存容量与 ART 配置。参数、实际运行配置、源码/二进制摘要、CLI/GCD 返回状态和阶段内存统计均写入结果；内存采样可用 `--memory-interval-ms 0` 关闭。`benchmark_android_translation.py` 用同一宿主、内核、系统镜像和 DEX 交替比较全量清空、按页失效、Linux 访存执行调整和更大缓存。该阶段的产品默认值保持原有 NCE 路径，Android 桌面及 iPhone 的翻译执行仍待验证。

### Android 运行时对照结果

命令为 `python3 scripts/benchmark_android_translation.py --repeat 2`。环境为 Apple M5 Ultra / macOS 27.0 (26A428)、单 Linux CPU、16 KiB 页、1 GiB RAM、2 ms 抢占请求、100 ms 内存采样；ART nterp 开启，expanded JIT 和 fast baseline 关闭，无应用 AOT 或 boot image。四组各含 CLI/GCD 各两轮，使用相同宿主、内核、只读系统镜像和 DEX；执行前后核对全部输入摘要。16 次执行均成功。

下表耗时为 `android_art_vm_destroyed.elapsed_ms` 的四轮中位数，覆盖创建 VM、Java/JNI、GC、解释器与 JIT 检查及 VM 销毁。内存为整个 `art_execution` 阶段各轮统计的中位数，包含 ART 进程开始装载到退出；均值为含阶段边界的算术采样均值，峰值可能遗漏短暂高点。完整配置、结果与源码摘要见 [Android 翻译运行时结果](../../../../experiments/native-linux/results-macos-android-translation.json)。

| --- | ---: | ---: | ---: | ---: |
| 全量代码失效，16 MiB 缓存 | 10,162.068 | 201.410 | 204.899 | 204.805 |
| 按物理页失效，16 MiB 缓存 | 4,997.967 | 229.840 | 242.540 | 242.540 |

16 MiB 缓存下，全量代码失效与按页失效加 Linux 执行调整的耗时中位数比约 4.25，采样峰值中位数增加约 35.2 MiB。64 MiB 相对 16 MiB 的耗时降低约 3.9%，四轮仍有波动，当前继续保留 16 MiB 实验默认容量。这个默认只属于独立原型。全量清空组的第一轮有 846 次宿主显式清空，按页组为 4 次；`invalidated_pages` 记录按页失效请求数量，未统计实际移除的翻译块数量，也未包括引擎因缓存容量触发的内部清空。

原生产品此前相同 ART 测试的 CLI/GCD 耗时为 231.278 / 313.855 ms，来自本阶段开始时的 `work/native-linux-nce/processes/lkl-summary.json`。两条路径的前置负载和内存工作集不同，尚未做严格交替的原生/翻译对照。当前翻译路径的 ART 计算仍明显偏慢，后续必须同时评估多进程映射成本与用户态计算开销。上述 4.25 比值只比较本次翻译配置，完整 Android 提速仍待测量。

复杂度审查：删除物理内存错误回调后，地址错误仍由实际 PTE 查询处理，已有权限和缺页回归继续覆盖该边界。代码位图用于跨地址空间和可写别名的物理代码失效；去掉它就需要恢复全量清空，或者增加其他等价的变更跟踪。固定 8 KiB 位图没有队列容量或溢出分支。两个私有 Unicorn 入口分别用于物理代码失效和有明确前置条件的 Linux 执行调整，不新增执行后端接口层。Android 测试继续调用已有程序，新增宿主逻辑只准备文件系统和按阶段运行；没有再维护一套 Java/JNI 测试实现。配置保留用于消融对照，当前均有测试或 benchmark 使用方。

其他检查：PTE＋定时抢占＋Linux 执行调整的基础负载 CLI/GCD 各两轮成功；窗口表和 PTE 两种映射方式的指令计数配置各通过 CLI/GCD，后者关闭周期内存采样。128 MiB 缓存、关闭 nterp、开启 expanded JIT/fast baseline、关闭采样的 Android 配置也通过 CLI/GCD。四类访存分别在原版停止入口、修复后的停止入口、Linux 执行调整、普通缺页和 Linux 执行调整下的缺页进行检查：原版四项复现中间指令状态，其他四种模式各 20 轮共 320 项成功。原型保留的窗口表用于回归和性能对照，产品执行路径未引用本次新增私有接口。

## 曾考虑的替代方案

- 保留 Zygote fork，在所有客体数据访存中转换地址：可以保留客体指针值，要求处理普通访存、原子指令、间接跳转、信号恢复和其他 JIT 引擎；覆盖范围与每次访存成本都很大，先建立独立原型再与 exec 方案比较。
- 仅把当前全局变量改为线程局部存储：各进程的同一地址仍可能对应不同物理页，地址冲突依旧存在。
- 为每个 APK 修改源码或签名后预编译：不符合通用安装的使用方式；当前解释器/JIT 路径继续保留，原生库处理由手机完成的目标见[安装规划](../feature/2026-10-10-APK安装与原生库加载.md)。

## 验收标准

1. 两个未共享 mm 的进程使用独立地址范围，核对相同库加载、私有写入、共享内存、权限、进程退出和地址回收，测量切换操作与实际驻留内存。
2. 用保留原始签名的 APK 验证新运行时入口，检查 Binder 身份、应用参数、异常、JNI、生命周期、更新及数据保留。当前已有桌面与应用回归继续成功。
3. 记录每次启动新增的预加载时间、编译时间和内存；同负载比较启动、交互与总映射成本。多核前后分别验证，减少同时变化的条件。
4. 本机实现与边界检查成功后，集中验证 iPhone 的多个执行区域准备与持续运行；独立地址范围分配成功仍需完整 Android 使用结果。

## 风险

重新启动 ART 可能损失 Zygote 的内存共享与启动优势。Framework 的应用进程协议、继承文件描述符、隔离进程、WebView/应用专属 Zygote 和主动 fork 均可能需要额外适配；当前尚无覆盖结果。该候选保留在架构规划中，连续页恢复实验完成后再按实际收益和已知缺口确定实施顺序。
