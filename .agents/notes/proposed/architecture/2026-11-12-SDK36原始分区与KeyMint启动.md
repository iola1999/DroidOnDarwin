# 决策记录: SDK36 原始分区与 KeyMint 启动

状态: proposed

## 问题

ASLR 固定阶段 `964984508d27c2b120b7636df2d490e0243ab51e` 的两种页大小原 init 均通过 mmap entropy 检查。随后 servicemanager 读取 device HAL manifest 失败，记录 `Cannot read /vendor/manifest.xml: No such file or directory`；keystore2 记录 `Failed to construct mandatory security level TEE`、`Cannot connect to Keymint`、Legacy wrapper 的 `Error::Km(r#HARDWARE_TYPE_UNAVAILABLE)`，最后触发原 critical 重启。报告为 `work/stock-init-aslr/work/native-linux-nce/stock-init-aslr-{16k,4k}-original-v2/summary.json`。

现有原 init 观察入口只挂载原 system ext4，vendor/product/system_ext 的 rc 和部分配置由固定提取目录部署。vendor VINTF、原 KeyMint 可执行文件及依赖未进入实际挂载目录。固定 SDK desktop 的原服务为 `/vendor/bin/hw/android.hardware.security.keymint-service`，原 rc 声明 `vendor.keymint-default`、`class early_hal`、`user nobody`；VINTF 声明 `IKeyMintDevice/default` v4、`IRemotelyProvisionedComponent/default` v3，以及 SecureClock/SharedSecret 的 default 实例。

固定 Android 16 比较源码为 system/security `android-16.0.0_r2`、`ce2aa0ef49158d0d45fb133fd42ab1deff210f8c`，hardware/interfaces 同 tag、`5688f7eb1e117ed26e642a695de300b7683acb87`。`globals.rs` 的 `keymint_service_name()` 根据 VINTF 的 default 声明选择 TEE 请求的连接名；缺少声明才转入 Legacy wrapper。`connect_keymint()` 保留原 `getHardwareInfo()` 返回。原 default `service.cpp` 使用 `SecurityLevel::SOFTWARE`，与固定二进制 `0x4888` 传入零值相符。原二进制与这些源码的精确构建提交对应尚未确认；后续实际连接和硬件信息检查继续保留。

SDK desktop 提取脚本从原 `system.img` 的 liblp 提取各逻辑分区。独立 `vendor.img` 是另一张 GPT 磁盘，本轮使用与现有文件清单相符的 LP vendor 来源。原 system.img SHA-256 为 `54a96f82a138e0919686cefffead8861e10c6189bf94188fef4fa08e24dc3ed1`，五个所需分区各有一个线性 extent；system_ext 为 242,716,672 bytes，product 为 2,345,381,888 bytes，vendor 为 101,539,840 bytes。原 system ext4 根的 `/product`、`/system_ext`、`/vendor` 为挂载目录，各分区内容不在 system 目录中。

## 提案

已获主会话授权，在 `work/stock-init-keymint`、`codex/stock-init-keymint` 从 ASLR 固定阶段接续。ASLR 工作树与报告保持原输入。构建、镜像和日志写入新树的 `work/`。

与 HyperOS 侧会话共用宿主槽职责：slot 0 为持久数据，slot 1 为只读 system 输入，slot 2/3 为只读 vendor/system_dlkm 输入。复用 `aafac70`、`bd43b83`、`b46b945` 的原盘和元数据观察入口。SDK 的 slot 1 可以直接打开完整固定 GPT/liblp 盘；在现有 ext4 挂载之前，使用标准 loop offset/sizelimit 将五个已校验的线性 extent 映射为只读分区设备。SDK 的 product/system_ext 由这些标准设备挂载，不增加宿主槽；HyperOS 保留其固定 ext4 根内的 product/system_ext bind 和 EROFS 输入。

先核对原 LP 元数据、分区摘要和原 KeyMint 文件清单，再扩展现有原 init 入口部署完整原分区。原 rc、policy/enforcing、标签、权限、域转换、安全级别、VINTF 和 critical 重启规则保持原值。实际记录 KeyMint exec、服务发布、keystore2 连接及原硬件信息，出现失败后定位首个系统调用或原日志。设备接口需求由原服务和实际调用决定。

### 固定分区范围

`keymint-sdk36-loop-lifecycle16-v1` 在准备阶段将 system_dlkm 交给 ext4 读取器，返回 `2133571347`。原盘该 extent 的 superblock magic 为 `e2e1f5e0`，实际使用 EROFS；其余四个分区为 ext4。实现随后保留原格式，复用 `ErofsMetadata(...).read('/')` 读取其根元数据。读取器要求起始偏移为零，使用共享提取函数生成 7,393,280 bytes 的宿主元数据输入并核对原分区 SHA；客体继续通过 slot 1 原盘与标准 loop 访问该分区。

原盘为 4,415,553,536 bytes，GPT super 起点为 2,097,152 bytes。下表 offset 为原盘的绝对字节偏移，sizelimit 为 loop 的可访问字节数。每个分区保留原来的单一线性 extent。

| --- | ---: | ---: | --- |
| system | 3145728 | 940838912 | `993193cfffd9b1a2ea034bfce5ec18fbb2856e259398ad6c1eb10b689b524e7d` |
| system_dlkm | 944766976 | 7393280 | `2e5a72b5d94fd53f2dfcaa8bb75f10f26b0962f0774f49f6aa130b97910b1af1` |
| system_ext | 953155584 | 242716672 | `1323de63e2197fadd226725d98bbf81c9d2ee563820e6d91c56950c4bcac785a` |

LP header SHA-256 为 `c5698c2e8467a25aefe8f77f0c844a7fa016431b877a3c8d422e2a187ac28dae`，tables SHA-256 为 `6a82919b994b845889935875337210c6fabc908001a7e9184bd2993846a12f33`。实际扫描结果保存在 `work/keymint-investigation/sdk36-extents.json`。已有提取函数与新的挂载准备共用原 GPT/liblp 解析，继续检查 header/tables 摘要、线性 device 0、表索引和原盘范围。

正式挂载前，用 vendor extent 创建临时只读 loop，核对 LOOP_GET_STATUS64 的 offset/sizelimit/flags、BLKGETSIZE64、边界读取和写方式打开的拒绝；按标准 umount2、LOOP_CLR_FD、close、LOOP_GET_STATUS64/LOOP_CTL_REMOVE 验证清除。正式五个挂载同样记录只读参数；原 init 在独立 mount namespace 中读取原服务与元数据。

新树 core 复制依赖时，`keymint-core16-v1` 缺少 Unicorn `platform.h`，v2 缺少 musl `errno.h`，v3 缺少 compiler-rt `libbuiltins.a`。完整安装目录复制到新树后，`keymint-core16-v4/summary.json` 的 CLI/GCD 均成功，各回收 116/116 上下文，120 项输入摘要与当前文件一致；报告 SHA-256 为 `fabe857f6ed79870f881031553a320185f9e5be052e68c5328b4e8c290b3797a`。原 ASLR 工作树未修改。

### 原策略加载后的首次失败

`keymint-sdk36-loop-lifecycle16-v2` 立即检查 LOOP_CLR_FD 后状态，system_dlkm 仍返回 status=0、flags=5。Linux `fput()` 对 PF_KTHREAD 任务使用 `delayed_fput_work`；最后一次 close 后需要该工作完成。v3 关闭每轮查询 fd，并在两秒界限内等待 GET_STATUS64=-ENXIO 与 LOOP_CTL_REMOVE=0。CLI/GCD 的临时 vendor loop 和正式五个 loop 均成功清除，各回收 2/2 上下文，页表告警为零。v3 报告 SHA-256 为 `3fa3b0e014094b2ff537f76ac7389ca38763bed3df2216d177ed79bce9a6e156`。

`keymint-sdk36-original16-v1` 的 lifecycle 两入口成功，CLI original 在原 policy 加载后读取 `/system/etc/selinux/plat_property_contexts` 失败：openat=4，两次 mmap 成功，随后 `read(fd=4, count=4096)=-5`。此前 plat_file_contexts 与 vendor_file_contexts 也在策略加载后返回同样的读错误。原 init 记录 `Failed to initialize property area`、`InitFatalReboot: signal 6` 与 `InitFatalReboot: signal 11`，尚未执行 KeyMint。主线直接挂载 system 分区的 ASLR 报告没有这些 read=-5。

宿主 kernel 域读取 kernel log 返回 -13，显式卸载 `/init.environ.rc` 返回 -1；v1 在该卸载的 REQUIRE 中终止。观察行随后提前记录，lifecycle 仍严格检查显式卸载、loop 清除与移除。original 在首次卸载返回 EPERM/EACCES 后记录该结果并关闭已持有 loop fd，再核对标准内核 halt、所有 guest 上下文回收、host disk close 与内核映射释放。v3 的 CLI/GCD 均保留 umount=-1，关闭 5 个 loop fd，halt=0、host disks close 完成、kernel release=0，各回收 3/3 上下文；原 PID 1 的 status=11，未按 deadline 停止。正式 loop 的显式清除与移除没有执行。lifecycle 两入口仍各回收 2/2 上下文，六个 loop 的显式清除和移除全部成功。

`loop-read-diagnostic16-original-v1` 的独立生成内核仅追加失败输出，原成功内核、LSM 返回值与策略保持原输入。CLI/GCD 均记录 `security_file_permission()` 对 kworker 的 MAY_READ=4 返回 -13，scontext 为 `u:r:kernel:s0`，backing `/dev/ncesystem` 的 tcontext 为 `u:object_r:tmpfs:s0`；紧邻 `lo_read_simple()` 的同一偏移和长度读取也返回 -13。loop 将该拒绝传为块 I/O 错误，原 init 收到 read=-5。原 plat CIL 有 `dontaudit kernel tmpfs (blk_file (read open))`。诊断脚本和两个生成源码纳入其 build.json，build.json 摘要纳入 core 与 original 报告。后续分区映射转向[标准 DM linear 阶段](../../implemented/architecture/2026-11-13-SDK36原盘的DMlinear映射.md)，原策略和分区内容继续保留。

### 本机阶段验证与复杂度审阅

本阶段交付原 LP 解析、摘要、只读 loop 生命周期、原根链接与元数据，以及原策略下的实际首次失败和完整宿主结束观察。完整原 init 与 KeyMint 尚未通过。最终 `keymint-sdk36-original16-v3/summary.json` 的四入口均通过观察校验，138 项输入与当前文件一致，SHA-256 为 `04bed541892bf99a75f2e7602086679e9877951d5281859419ac1084360c660b`。两种调度入口均保留 property read=-5、signal 6/11 和显式卸载拒绝，页表释放告警为零。

本机为 Apple M5 Ultra、macOS 27.0（26A428）；使用 Xcode 27.1 和 iPhoneOS 27.1 SDK。`keymint-runtime16-ios-v1/build.json` 编译 16 KiB iOS runtime，113 项输入一致，SHA-256 为 `f4855bf9de5022f829257fb489ef9236adbc3c4cc5674e299c96f774a622e45f`。实际生成的原 init runner/execution 副本也通过 iOS 编译，`keymint-init-copy16-ios-v1/init-copy-build.json` 的 169 项输入一致，SHA-256 为 `c41cb5639ede8edd406de32a21d1b9bf70051911486adf3150e7ce115db2b806`。设备执行和持续性能继续保留为待验证项。

`test_stock_init_sdk.py` 用最终实际报告检查 27 项原盘、只读、边界、loop 释放和原策略后的完整结束条件；`test_stock_init_hyperos.py` 使用固定 4 KiB SDK 报告检查 24 项共享观察与 HyperOS 输入条件，HyperOS 实际执行仍由独立阶段验收。`test_hyperos_init.py` 的 3 项检查、改动 C 文件格式检查、Python 编译检查和 `git diff --check` 均成功。[结构化阶段结果](../../../../experiments/native-linux/results-stock-init-sdk36-loop-20261113.json)为 4,456,741 bytes，SHA-256 为 `aa21a1003debcb1031498a45d9bce0fad2684a008d76f55bc88d84ac197225d8`，保存首次失败、最终报告、诊断源和 iOS 输入；原始大日志保留在本树 work。

按 reclaim-code-entropy 核对实际调用方。`partition_extents()` 同时供原提取入口和 SDK 原盘准备使用，原解析与原分区范围校验只保留一份；原 image SHA 和 LP header/tables SHA 分别检查发布输入与内部格式。`read_partition_metadata(..., offset=...)` 使用 libext2fs 已有偏移接口，EROFS 元数据继续由既有读取器负责。新增 SDK 模块仅处理固定五分区、原服务与 loop 报告校验，共享 init 验证器使用 `original_input` 传入 SDK 或 HyperOS 的现有准备结果。

loop 结构的 offset/sizelimit、fd 和 id 分别供配置、边界读取和实际清除使用。删除每轮查询 fd 的 close 会持续持有 backing 引用；删除等待会恢复 v2 的立即清除失败。original 的 EPERM/EACCES 分支仅接受首次根文件卸载拒绝，保留拒绝、关闭计数与最终 halt/host close/kernel release 检查；lifecycle 的全部显式清除要求保持。诊断只在 work 的生成内核记录返回与标签，没有加入产品检查分支。下一阶段使用 DM linear 后，将按实际调用方重新检查这组 loop 准备代码。

### 主线接受

2026-11-13 主线从 `d4ea643` 接收固定 LP 阶段。共同 init 验证器使用 `original_input`，继续从单条实际布局记录检查 guest 下界、上界和历史 64 GiB/512 GiB 报告；HyperOS original 仍要求 4 KiB 与 512 GiB，lifecycle 保留原历史报告读取。主线的 bootstrap 节点检查、binfmt 注销和 4 KiB EROFS gbuf 分配保持原实现。

原 `keymint-sdk36-original16-v3/summary.json` 通过主线 27 项 LP contract 检查，结果为 `work/native-linux-nce/sdk-lp-main-acceptance-v1.json`。共享 HyperOS 输入与主线 SDK36 4 KiB 四入口报告通过 27 项检查。两页主线 core 的 121/120 项输入摘要重新核对一致；正式 DM 组合的实际原 init 与 iOS 编译继续由 DM 记录验收。

## 曾考虑的替代方案

- 仅复制 KeyMint 可执行文件：无法同时保留原 VINTF、依赖、所有者、SELinux 标签和分区内配置。
- 为 product/system_ext 分别增加宿主槽：会与当前四槽职责产生另一组资源映射；固定 LP 的单一线性 extent 可复用原只读盘和标准 loop 设备。
- 将这些大分区作为 RAM 文件部署：增加客体 RAM 需求，并重复已有原盘内容；使用原块设备的分区映射。
- 改写原安全级别或 critical 行为：会改变当前启动契约；先让完整原服务输入进入实验。

## 验收标准

1. 原盘、各分区元数据和关键服务文件与固定来源一致，原盘通过 O_RDONLY、宿主共享锁和 Linux 只读设备/挂载约束访问，运行后摘要保持一致。
2. SDK 的 system/vendor/product/system_ext ext4 与 system_dlkm EROFS 实际挂载成功。CLI/GCD 读取关键服务、rc、VINTF 的原所有者、模式和 SELinux 标签，并核对原 mount namespace 内的路径。
3. 原 init/APEX/ASLR 成功行为保持；KeyMint 原 exec、声明、服务连接及下一处失败写入报告，原安全级别与重启规则保持。
4. 有关 loop 生命周期、边界与错误输入完成必要回归。涉及四槽代码的变更复用现有宿主回归，iOS runtime 与实际 init 副本继续编译。
5. 文档与代码同次阶段提交，按 reclaim-code-entropy 核对实际使用方、必要状态和移除影响，再按 humanizer-zh 审阅。

## 风险

完整原分区会启动此前未部署的服务。[DM 阶段](../../implemented/architecture/2026-11-13-SDK36原盘的DMlinear映射.md)的 16 KiB CLI/GCD 已执行原 KeyMint；原 init 后续在 `/data` 数据库创建和 BPF JIT sysctl 处失败，原 reboot 规则保持。固定比较源码和原二进制参数对应 `SOFTWARE`，实际 `getHardwareInfo()` 响应继续待记录；物理硬件隔离未验收。首次 init 与原 fstab 的设备发现仍沿用现有观察范围，完整 Android 启动未完成。当前只做离线本机检查与 iOS 编译。
