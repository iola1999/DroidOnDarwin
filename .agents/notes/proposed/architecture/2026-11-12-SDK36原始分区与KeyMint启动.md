# 决策记录: SDK36 原始分区与 KeyMint 启动

状态: proposed

## 问题

ASLR 固定阶段 `964984508d27c2b120b7636df2d490e0243ab51e` 的两种页大小原 init 均通过 mmap entropy 检查。随后 servicemanager 读取 device HAL manifest 失败，记录 `Cannot read /vendor/manifest.xml: No such file or directory`；keystore2 记录 `Failed to construct mandatory security level TEE`、`Cannot connect to Keymint`、Legacy wrapper 的 `Error::Km(r#HARDWARE_TYPE_UNAVAILABLE)`，最后触发原 critical 重启。报告为 `work/stock-init-aslr/work/native-linux-nce/stock-init-aslr-{16k,4k}-original-v2/summary.json`。

现有原 init 观察入口只挂载原 system ext4，vendor/product/system_ext 的 rc 和部分配置由固定提取目录部署。vendor VINTF、原 KeyMint 可执行文件及依赖未进入实际挂载目录。固定 SDK desktop 的原服务为 `/vendor/bin/hw/android.hardware.security.keymint-service`，原 rc 声明 `vendor.keymint-default`、`class early_hal`、`user nobody`；VINTF 声明 `IKeyMintDevice/default` v4、`IRemotelyProvisionedComponent/default` v3，以及 SecureClock/SharedSecret 的 default 实例。

固定 Android 16 比较源码为 system/security `android-16.0.0_r2`、`ce2aa0ef49158d0d45fb133fd42ab1deff210f8c`，hardware/interfaces 同 tag、`5688f7eb1e117ed26e642a695de300b7683acb87`。`globals.rs` 的 `keymint_service_name()` 根据 VINTF 的 default 声明选择 TEE 请求的连接名；缺少声明才转入 Legacy wrapper。`connect_keymint()` 保留原 `getHardwareInfo()` 返回。原 default `service.cpp` 使用 `SecurityLevel::SOFTWARE`，与固定二进制 `0x4888` 传入零值相符。原二进制与这些源码的精确构建提交对应尚未确认；后续实际连接和硬件信息检查继续保留。

SDK desktop 提取脚本从原 `system.img` 的 liblp 提取各逻辑分区。独立 `vendor.img` 是另一张 GPT 磁盘，本轮使用与现有文件清单相符的 LP vendor 来源。原 system.img SHA-256 为 `54a96f82a138e0919686cefffead8861e10c6189bf94188fef4fa08e24dc3ed1`，五个所需分区各有一个线性 extent；system_ext 为 242,716,672 bytes，product 为 2,345,381,888 bytes，vendor 为 101,539,840 bytes。原 system ext4 根的 `/product`、`/system_ext`、`/vendor` 为挂载目录，各分区内容不在 system 目录中。

## 提案

已获主会话授权，在 `work/stock-init-keymint`、`codex/stock-init-keymint` 从 ASLR 固定阶段接续。ASLR 工作树与报告保持原输入。构建、镜像和日志写入新树的 `work/`。

与 HyperOS 侧会话共用宿主槽职责：slot 0 为持久数据，slot 1 为只读 system 输入，slot 2/3 为只读 vendor/system_dlkm 输入。复用 `aafac70`、`bd43b83`、`b46b945` 的原盘和元数据观察入口。SDK 的 slot 1 可以直接打开完整固定 GPT/liblp 盘；在现有 ext4 挂载之前，使用标准 loop offset/sizelimit 将五个已校验的线性 extent 映射为只读分区设备。SDK 的 product/system_ext 由这些标准设备挂载，不增加宿主槽；HyperOS 保留其固定 ext4 根内的 product/system_ext bind 和 EROFS 输入。

先核对原 LP 元数据、分区摘要和原 KeyMint 文件清单，再扩展现有原 init 入口部署完整原分区。原 rc、policy/enforcing、标签、权限、域转换、安全级别、VINTF 和 critical 重启规则保持原值。实际记录 KeyMint exec、服务发布、keystore2 连接及原硬件信息，出现失败后定位首个系统调用或原日志。设备接口需求由原服务和实际调用决定。

## 曾考虑的替代方案

- 仅复制 KeyMint 可执行文件：无法同时保留原 VINTF、依赖、所有者、SELinux 标签和分区内配置。
- 为 product/system_ext 分别增加宿主槽：会与当前四槽职责产生另一组资源映射；固定 LP 的单一线性 extent 可复用原只读盘和标准 loop 设备。
- 将这些大分区作为 RAM 文件部署：增加客体 RAM 需求，并重复已有原盘内容；使用原块设备的分区映射。
- 改写原安全级别或 critical 行为：会改变当前启动契约；先让完整原服务输入进入实验。

## 验收标准

1. 原盘、各分区元数据和关键服务文件与固定来源一致，原盘通过 O_RDONLY、宿主共享锁和 Linux 只读设备/挂载约束访问，运行后摘要保持一致。
2. SDK 的 system/vendor/product/system_ext/system_dlkm 实际挂载成功。CLI/GCD 读取关键服务、rc、VINTF 的原所有者、模式和 SELinux 标签，并核对原 mount namespace 内的路径。
3. 原 init/APEX/ASLR 成功行为保持；KeyMint 原 exec、声明、服务连接及下一处失败写入报告，原安全级别与重启规则保持。
4. 有关 loop 生命周期、边界与错误输入完成必要回归。涉及四槽代码的变更复用现有宿主回归，iOS runtime 与实际 init 副本继续编译。
5. 文档与代码同次阶段提交，按 reclaim-code-entropy 核对实际使用方、必要状态和移除影响，再按 humanizer-zh 审阅。

## 风险

完整原分区会启动此前未部署的服务。原 init 的实际后续设备、挂载与安全检查尚待实跑定位。软件 KeyMint 原服务保持自身的 `SOFTWARE` 返回；物理硬件隔离未验收。首次 init 与原 fstab 的设备发现仍沿用现有观察范围，完整 Android 启动未完成。当前只做离线本机检查与 iOS 编译。
