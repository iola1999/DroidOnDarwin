# 决策记录: 原始 SDK36 init 与 rc 启动实验

状态: proposed

用户已要求暂停。本次保存已完成的 PID 1 回收与原 init 首轮观察，实验尚未完成；后续标签调查、实现和复验均已停止。此检查点保存在 `codex/offline-address-domains` 分支。

## 问题

原始 SDK36 Bionic、ART 与 JNI 已分别运行，当前 services 入口仍由项目的 `android-services-test` 装载简化 SELinux 策略、创建属性服务并启动 Binder 服务。完整 Android 需要核对原始 init 的策略加载、属性区、挂载命名空间与 rc 顺序。当前阶段先在 Mac 执行固定 SDK36 输入，保留原始 rc，记录实际首个失败。本文覆盖实验启动与回收；分配策略及高地址 PTE 成本继续保留为后续调查。

主工作区 `b0a1961` 的 4 KiB 与地址域组合已只读检查，暂未发现阻断问题。本实验基于独立树 `e30f41015e92f07faa2cbbe6f9b34122778b6e45`，使用已有 16 KiB、单 CPU、sparse 64 GiB、Direct flat/PTE、双映射与 data TBI 构建。期间主工作区保持原状。结果只用于功能调查。

## 提案

### 输入与启动范围

原始 `/system/bin/init` 的 SHA-256 为 `c27d13897025ad72d68f5d9a57e3c76cd250f53e82817cf2b5eb04d3e01ec12a`，Build ID 为 `649038d41dde87a6f7a29d2c84a63468`，PT_INTERP 指向 `/system/bin/bootstrap/linker64`。原 bootstrap linker 的 SHA-256 为 `69accdc2bd8a964b7747709fdfba4145a390bcfeb0395710e93fb471723b81f9`。从这两个文件遍历 DT_NEEDED，并优先选择 `lib64/bootstrap`，得到 34 个文件、13,810,664 字节，全部与 `android36-runtime.json` 的逐文件摘要相符。这个集合包含 `libcrypto.so`。实施前将 FIPS 检查列为可能的装载阻塞；本轮原 init 已进入 `selinux_setup`，实际终止原因为后续 exec 返回 `EACCES`。

现有 `build_nce_userspace.py:1219` 将 bootstrap linker 设置为项目 linker 的符号链接，`prepare_stock_android.py` 的候选只替换原 ART 依赖集合。因此本轮先独立部署原 init、原 bootstrap linker 及其运行库，保留原始字节和路径；使用独立 staging 与现有文件复制接口，暂不复制系统盘。

本地 SDK 固定为 Android 36 ps16k r07，归档 SHA-1 `dda632745023567113d9954101709c6526a3c250`。运行库清单 SHA-256 `4b1a45b0ee51725c68f1c29765958d0b60b45a5f2325bedfc61764cd49232249`。原 rc 采用 `/system/etc/init/hw/init.rc` 以及 system、system_ext、product、vendor 的完整 init 配置目录。缺失二进制、APEX 或设备必须记录在报告中，不通过减少 rc 服务来获得阶段成功。

本次使用仓库已固定的 AOSP system/core 提交 `68be0c2c0006a0740d0b1809abe4717308f90d15` 检查启动顺序；该提交用于理解接口，尚未建立它与 SDK init 二进制的精确源码对应。实际阶段判断仍使用原二进制日志、syscall 返回值与退出状态。

### PID 1 与停止契约

`translation/linux-runner.c` 的 `run_program()` 调用 syscall 246，传入 `launch[1]=1`。`lkl-nce-process.c:18` 的 `nce_launch()` 使用 `kernel_clone(CLONE_NEWPID)`，返回祖先 PID 命名空间可见的 PID。`user_start()` 设置 `nce_state`，`translation/linux-execution.c:user_run()` 执行 `execve()`。独立 guest helper 必须首先验证 `getpid()==1`，随后 `unshare(CLONE_NEWNS)`、将根挂载设置为 private、重新挂载 procfs，并校验 `/proc/self` 与 getpid/gettid 对应。helper 通过 `execv("/system/bin/init", {"/system/bin/init", "selinux_setup"})` 保持同一 PID 1；原 init 的后续流程调用 exec 进入 `second_stage`，本轮该调用失败。

普通 SIGTERM 无法作为可靠结束条件：上游 `init.cpp:702` 忽略普通来源 SIGTERM。LKL `kernel/signal.c:1214` 对来自祖先 PID 命名空间的 SIGKILL 设置 `force`；目标为子命名空间 init，独立于全局 init 的不可终止规则。实施前先验证最小 PID 1 与后代探针：宿主保留 syscall 246 返回的 PID，以 `kill(returned_pid, SIGKILL)` 结束，再用 `wait4` 回收，核对该命名空间全部翻译上下文释放。此项实际成功后才能使用同一路径结束原 init。

观察器使用固定期限，循环执行 `wait4(..., WNOHANG)`，进程退出后读取独立日志；期限结束只记录停止原因，不记 init 启动成功。外部 Python `subprocess` timeout 只保护宿主测试进程，触发后本轮观察与正常回收均记失败。结束顺序保持 wait4、LKL halt/cleanup、翻译上下文回收与宿主映射释放。保留正常退出、信号退出、观察到期限三种结果。

### 原 init 前置状态与原 rc 依赖

| 顺序 | 当前来源与最小处理 | 验证边界 |
| --- | --- | --- |
| 原 bootstrap 装载 | 独立 staging 原 init 与 34 文件依赖集合；使用真实 PT_INTERP | 记录装载日志、实际映射路径及 exec 返回；后续动态加载仍可能需要额外库 |
| `selinux_setup` | 保留原 vendor `precompiled_sepolicy`、平台/产品/system_ext 摘要与 contexts；挂载 selinuxfs | 原策略为版本 30，LKL 上限 33；三个配套摘要文本一致。本轮 policy write 返回完整字节数；标签、权限与 exec 域转换仍待检查 |
| `second_stage` | 保留 `/dev/socket`、可写 `/dev/__properties__`、tmpfs `/apex`、`/bootstrap-apex`、独立 tmpfs `/linkerconfig`，以及匹配当前 PID 命名空间的 proc | 原 init 创建属性区与两个属性服务线程。项目 `nce_property_service` 与简化策略不参与此实验 |
| 挂载命名空间 | `mount_namespace.cpp:90` 将根改为 shared，`/apex` 与 `/linkerconfig` 改为 private，再创建 default namespace 并回到 bootstrap namespace | `/linkerconfig` 必须是挂载点；当前 services 只创建目录，不能直接复用该状态 |
| rc `early-init` | 原 `init.rc:6` 导入 root environ、USB、hardware 和 zygote 配置；随后启动 ueventd、执行 `apexd-bootstrap` | 必须记录原 rc 导入失败与执行失败；保持完整文件 |
| APEX 与设备 | 原 `init.rc:81` 使用 `exec_start apexd-bootstrap`；原 apexd.rc 设置失败重启；后续等待 `ro.cold_boot_done` | 现有展开后的 APEX 目录没有原 `.apex/.capex` 封装，当前 LKL `CONFIG_BLK_DEV` 关闭，loop/device-mapper 尚不可用；这一阶段预计需要补原 APEX 激活与设备驱动，实际首个失败待运行 |
| first-stage mount | 原 ranchu fstab 使用 logical partition、virtio data/metadata、加密与 verity 选项 | 本轮直接从 selinux_setup 开始。原 ramdisk `/init`、GPT/LP、原 fstab 挂载尚未运行，需后续单独推进 |

原 SDK ramdisk 为 2 MiB LZ4，SHA-256 `5eff5ed46490588b7576716741e19709b8a99dccd5a7f1e7ee1256c027dacf1d`；只读解压得到 12 个 cpio 条目，包含独立 first-stage `/init`，未包含 `/init.environ.rc`。本轮使用 libext2fs 的只读 offset 输入，从已有 SDK system.img 的 system 分区偏移 3,145,728 提取了 621 字节 `/init.environ.rc` 与 5,292 字节 `/system/build.prop`，未复制系统盘。提取摘要保存在结果文件的 `static_investigation`。

### 最小实现范围

复用已通过的 sparse 核心构建、编译命令与现有原始组件文件复制方法。新增独立 guest helper、独立 init 观察入口与脚本，不增加产品配置，不改变执行器和内核默认。现有同步 `run_program()` 保持原有验收；init 实验使用有期限的 wait4 路径。输入报告记录源码、内核、执行器、原文件和生成文件摘要，区分「观察流程完成」与「init 到达的阶段」。

静态调查材料保存在独立树 `work/init-investigation/`，包括 system/core 源文件、ramdisk 清单和 DT_NEEDED 清单。脚本在已校验的核心构建基础上生成独立运行器与执行器源码副本，加入限时 wait4 和 write/writev 记录；产品源码保持原状。后者记录原 init 尝试写出的内容及 syscall 返回值，因为原策略加载后宿主读取 kernel ring buffer 返回 `EACCES`。

### 实现范围与剩余差异

原始二进制和 rc 内容保持原字节。两个 BoringSSL rc 符号链接和 `ueventd -> init` 在 staging 中保存为目标内容对应的普通文件，报告记录原链接目标、校验使用的目标路径及 `staged_as`。staging 复制了文件内容与基本 mode，未恢复原文件系统的 SELinux 扩展属性、所有者和全部文件元数据。

当前只部署 init/ueventd 及 init 依赖库，完整 rc 的其他服务二进制、原始 APEX 封装和全部设备仍待部署。实验使用已经准备好的挂载目录，原 first-stage init 与 fstab 挂载未运行。执行脚本、[guest helper](../../../../experiments/native-linux/translation/stock-init-guest.c)、[运行器](../../../../experiments/native-linux/translation/stock-init-runner.h)和[write/writev 观察代码](../../../../experiments/native-linux/translation/stock-init-trace.h)各自用于输入与报告、PID 1 入口、期限停止和权限拒绝后的日志记录；没有增加产品配置或公共执行接口。

暂停位置是原 SELinux 策略下的 second-stage exec 权限拒绝。恢复工作后首先需要读取原 init 的实际进程域、可执行文件与解释器标签，检查 ramfs 的 `security.selinux` 支持和 exec 域转换，并按原 file_contexts 恢复所需标签。根因尚未确认；本轮未关闭 SELinux、未修改原策略，也未实施标签修复。

## 曾考虑的替代方案

- 直接运行完整 first-stage ramdisk init：还需要原 logical partition、设备发现、verity 和 metadata 挂载条件；本轮先验证已部署分区之后的原 init 入口，并保留 first-stage 后续目标。
- 直接执行 `second_stage`：会跳过原策略加载与 init 域转换；只在 `selinux_setup` 得到实际失败后作为明确标记的定位对照。
- 使用最小自定义 rc：可以隔离服务启动问题，本轮要求保留完整原 rc，因此先记录原顺序的首个失败。
- 复用现有 services 初始化后启动原 init：属性区、SELinux 策略和属性服务已有项目实现，会改变原 init 前置状态；首轮采用独立根目录和挂载状态。

## 验收标准

1. 所有原输入与固定清单摘要相符，实际二进制及 rc 保留原始字节，额外生成内容逐项标记。
2. CLI/GCD 的 PID 1 与后代探针验证祖先命名空间停止、wait4 回收及上下文释放；停止失败必须阻止原 init 运行。
3. 原 init 实验保留全量 stdout、stderr 与 kernel 日志、exec 结果、阶段日志、等待状态及期限停止结果。阶段失败可以完成调查；启动成功要求记录原 init 到达的明确阶段。
4. 完整 Android、桌面、APK、持续性能和 iPhone 分别保留独立验收。
5. 原 rc 后续依赖按实际失败推进：policy load、属性服务、命名空间、ueventd/APEX、init/late-init、原 zygote。每项保留失败与修复后的对照。

## 风险

原 init 引入新的 syscall、SELinux 策略、标准运行库和长生命周期任务；既有 Bionic/ART 成功未覆盖这些路径。原 init 的首轮已停在 SELinux 策略加载后的 exec 权限拒绝，实际标签与拒绝原因尚未核对。完整原 rc 会访问 ranchu 设备与平台服务，LKL 缺失设备应保留实际错误。原 AOSP 源码与二进制的编译对应尚未核实。单核、64 GiB 客体、宿主地址分离只覆盖本机原型；iOS 资源、JIT 授权和持续性能均待真机验证。
