# 决策记录: 运行时执行器与双核 Linux

状态: proposed

## 问题

双核原生 NCE 已确认同 mm 用户线程能够并行，完整 Android 仍在共享窗口切换期间产生大量映射和等待，详见[双核记录](2026-10-11-LKL双核用户态与映射同步.md)。单核 [Direct 执行器](2026-10-11-运行时ARM64代码块执行.md)已经用客体地址转换访问 RAM，并完成真实桌面检查；它具备为不同进程同时使用相同客体地址的实现基础。

上一项每进程只读映射没有显示稳定的桌面收益，且提高了内存峰值。下一阶段优先评估双核 LKL 与 Direct 的组合，继续沿用平坦地址表。不同进程的客体指针保持原值，每 CPU 使用当前任务的地址表与独立执行状态；减少共享窗口限制后，实际并行收益仍需完整系统测量。

## 提案

### 执行和同步约定

先固定两个 CPU，采用独立构建。每 CPU 拥有 Direct 和必要的回退执行器、代码缓存、当前任务状态与停止请求。任务迁移后使用目标 CPU 的执行器，任务只保存客体寄存器。Linux、RAM、文件和设备仍在同一宿主进程内，运行组件随手机包交付。

首先检查两个执行器同时编译和执行、相同客体地址下的私有数据、共享原子数据、独立抢占和代码更新。现有 Direct 用 LDAR/CAS 模拟独占访问；另一个 CPU 将值改动后恢复时，CAS 可能成功。增加原生 LDXR/STXR 候选，检查竞争重试、远端写入、地址变化、寄存器状态与执行边界。已有单核选项继续作为对照。

随后复用 LKL SMP 的 CPU 身份、IRQ、调度与 RAM 别名访问保护，增加按 CPU 发布的页表与映射状态。客体进入后，页表及代码映射必须在执行区间保持稳定；修改前请求相关执行器停止，确认离开后提交更新。退出执行区间先于任何可能等待 Linux 锁的操作，防止持锁方与执行器相互等待。初版可先停止全部两个 CPU，确认正确性后再按实际 mm 缩小范围。

每 CPU 的代码缓存可以独立编译与回收，共享物理代码的写入与失效仍需要跨 CPU 通知。原子指令和回退执行器必须使用同一 RAM，不能用互不共享的副本完成原子更新。当前只读宿主范围的信号处理只允许一个活跃执行者，本阶段使用 `flat`，该候选的并发改造不作为前置条件。

停止请求必须覆盖登记客体后、真正进入生成代码前的区间。检查该边界后再决定复用周期请求或增加持续停止标志；不能依赖一次可能被新执行入口清除的通知。计时线程只请求停止，执行器缓存仍由所属 CPU 修改。

### 参考与实施顺序

2026-10-11 核对 [QEMU MTTCG 文档](https://www.qemu.org/docs/master/devel/multi-thread-tcg.html)：每 CPU 的执行状态、跨 CPU TLB/代码失效和原子操作分别需要同步；其同步原语一节也记录了 CAS 模拟独占访问的 ABA 限制。本项目使用 ARM64 宿主，可直接评估硬件独占指令，实际行为由本机检查确认。

顺序为独立双执行器与原子检查、SMP/PTE 进入退出与核心 Linux 回归、Bionic/ART 和完整桌面，再进行同构建或明确构建变体的单核/双核对照。记录阶段耗时、每线程 CPU 时间、实际重叠、停止等待、代码缓存及内存平均值/峰值/最后值。微基准只确认并行与语义，完整系统结果决定产品集成。

## 曾考虑的替代方案

- 继续延长共享窗口的调度时间片：已有 12 ms 对照仅显示有限启动变化，双核完整桌面仍失败，无法消除两个 mm 共用相同宿主地址的问题。
- 继续扩大每进程只读宿主范围：首轮完整桌面的 footprint 峰值增加约一半，未显示稳定提速，先保留对照记录。
- 多个 Linux CPU 共用一个 Direct 实例并加互斥锁：会把用户代码再次串行执行，不满足本阶段并行验收。

## 验收标准

1. 两个独立执行器可以同时编译与执行，私有地址隔离、共享原子更新、TLS/x18/向量、定向停止和退出正确；CLI/GCD 均覆盖。
2. 原生独占指令处理竞争重试与远端写入，不将已失效的预留用于成功写入；明确记录跨宿主返回的允许失败行为。
3. 两核 Linux 的线程迁移、系统调用、信号、futex、fork/COW、mprotect/unmap、代码发布与正常退出检查成功；两个不同 mm 可以实际同时执行。
4. Bionic/ART 与真实 Android 桌面、Clock/Files、数据保留及干净关机成功；随后比较单核/双核耗时、交互和内存，不以线程数量或微基准倍数判定完成。
5. 本机结果通过后再推进 iOS 执行内存和 App 集成，集中交付有完整体验的阶段包。当前产品继续使用已验证的执行路径。

## 风险

每 CPU 缓存增加内存；过多全局停止可能抵消并行收益。代码写入、页表回收、宿主线程与 Linux CPU 迁移之间存在不同的生命周期。独占指令可在宿主调度后失败，生成代码必须允许正常重试；执行器之间的原子语义还需覆盖回退路径。Mac 并行成功后，iPhone 的 JIT 写保护、容量及热状态仍需验证。


## 实施进展

### Linux 集成中的状态与停止边界

翻译内核接口已拆为公共配置、公共内存统计和每 CPU 的页表快照、失效范围、代码页位图。每 CPU 独立消费失效通知，mm 销毁时清除仍指向该页表的快照，防止页表地址复用后保留旧状态。单核 CLI/GCD 回归成功后，已接入独立双核构建。每 CPU 拥有 Direct、Unicorn、客体退出事件及缓存统计；ELF 布局登记共用互斥锁，单独由 `linux-elf.c` 管理。

停止请求需要由客体登记协议管理：登记前清除旧请求，登记后收到的请求必须保持到执行器观察到为止。普通独立调用继续使用原来的单次停止语义；Linux 并发入口采用显式准备接口。内核表更新使用现有停止区间，进入客体期间保持 IRQ 关闭，离开客体后再恢复 IRQ。此阶段的验收仍包括实际双核 Linux、Android 和桌面测量。

### 双核 Linux 的资源释放与代码写入

双核核心测试首轮完成功能检查，但停机时 66 个用户上下文只释放 3 个。将 `rcu_barrier()` 放在 CPU 停止之前后，上下文全部释放；仍有 4 MiB 平坦地址表保留。Linux 空闲 CPU 可以继续持有 `active_mm`，原先只遍历活任务 `mm` 的清理没有覆盖它。现在由 mm 生命周期维护地址表所有者列表，所有 Linux 线程退出后排空；最后一轮核心及 Bionic/ART 的上下文分配和释放相等，平坦表 live 字节为 0。

物理代码页使用共享标记。Linux 安装可执行 PTE 时设置标记，Direct 对已标记物理页的写入返回，进入与其他客体互斥的 Unicorn 区间；内核用户复制、磁盘读取和 Unicorn 写入通知所有 CPU 的代码缓存。RAM 回收时清理标记并通知失效。这个版本先对全部内核用户复制暂停客体。已加入 `--smp-uaccess-stop all|code` 候选，保留 PTE 锁和 IRQ 保护，读取普通数据时继续允许客体执行；写入时持有现有 writer 锁，与 Unicorn 回退互斥，仅命中物理代码页标记时暂停其他 Direct 客体。这样仍覆盖 COW、权限变化、页表回收与代码更新。通过启动开关保留全部暂停的对照，验证普通数据访问、futex、取消映射和代码别名修改后，再比较完整桌面。

新增跨 CPU 代码别名检查：父进程先缓存 RX 页面，子进程在另一个 CPU 交替通过普通存储和管道 `read()` 修改 RW 别名，每次核对新返回值，共 128 次。首轮失败，原因是 Unicorn 的 `UC_HOOK_MEM_WRITE` 回调参数为物理地址，宿主错误地再次查询客体页表，丢失写入通知。按其物理 RAM 偏移发送失效后，CLI/GCD 各两轮成功，原始失败在 `work/native-linux-nce/lkl-direct-smp-core-code-sync/`，修复后在 `work/native-linux-nce/lkl-direct-smp-core-physical-hook/`。测试每轮修改后没有调用显式代码发布，覆盖实际写入通知。

首轮可见桌面触发 240 秒启动检查期限，原始结果在 `work/native-linux-nce/lkl-direct-smp-desktop-initial/`；包含 3 秒宿主采样，只用于功能与诊断。CPU 0 记录 51,023 次代码写入回退和 28,405 次跨页回退。共享代码标记此前直到物理 RAM 回收才清除，已取消执行映射的页面复用为数据页后仍可能触发串行回退。现在根据可执行 PTE 引用数量维护 0/1 标记，覆盖 fork 别名、权限替换和取消映射。移除其中一个执行映射时，其余映射继续保留保护；所有执行映射消失后，普通数据写入可以继续并行。生成内核函数的回归已覆盖别名引用、物理页复用、每 CPU 失效位图和停止条件。

跨页普通 RAM 访问复用 Direct 现有实现。两个地址映射由客体登记与 IRQ 保护保持有效，写入前检查两页的共享代码标记；有序访问与独占访问仍使用其原有路径。独立检查新增双执行器跨页读写及第二页代码保护，失败存储不得先修改第一页。Linux 核心检查另加入两核间并发用户复制、取消映射与 `mprotect`，允许合法的 `EFAULT`，要求已复制内容来自有效 RAM。

可选 `--parallel-profile 1` 记录执行区间并集、双 CPU 区间交集与各执行线程 CPU 时间；关闭时跳过这些时钟查询。区间包含 Direct 编译、代码查询与回退，排除 Linux 系统调用和缺页处理。它用于判断执行重叠，持续帧时间和整机收益仍需分别测量。此时完整桌面验证进行中，iPhone 产品保持原构建。

### 独立双执行器与原生独占指令

已增加 `NceDirectConfig.native_exclusive` 和 Linux 实验开关 `--direct-native-exclusive 0|1`，默认关闭。原生候选使用 LDXR/LDAXR、STXR/STLXR 和 CLREX；进入和离开生成代码时清除宿主预留。原来的 LDAR/CAS 路径保留为单核对照。共享普通数据可以并发访问，代码、地址表及引擎销毁仍由调用者保证生命周期；此时还未允许两个 Linux CPU 进入当前集成。

独立检查覆盖两个引擎同时编译、相同客体 VA 对应不同 RAM、共享计数的 8/16/32/64 位独占操作及两种顺序、TLS/x18/向量、代码替换与定向停止。另有两类 ABA 检查：客体返回宿主后，和客体一直在同一生成代码页等待远端写入期间。原生候选报告写入失败；LDAR/CAS 对照仍可能报告成功，保留这一差异用于验证测试的区分能力。

首版通过独立 CLI/GCD 和单核 Linux 核心检查，但 Bionic/ART 对照的原生候选触发 ART 内部 90 秒期限。该轮累计约 19.88 亿次代码查询与 19.88 亿次跨块返回；采样集中在生成代码入口、出口和代码查询。代码分析确认：原生预留会在返回宿主查询目标页时失效；两个目标发生跳转表冲突时，反复查询会使同一独占序列持续失败。原始日志在 `work/native-linux-nce/android-direct-native-exclusive-matrix/`，该轮按失败保留。

先实现同页控制流预扫描：从 LDXR 到 STXR/CLREX 只接受限定指令，其他片段从加载处整体回退。八轮 Bionic/ART 检查成功，但该规则使单轮回退次数由约 53 增至约 344,338，ART 阶段耗时中位数增加约 26.5%，Bionic 阶段增加约 33.7%。该预扫描已撤回；结果保留在 `work/native-linux-nce/android-direct-native-exclusive-local-matrix/`。

当前实现只增加每次执行调用内的 `exclusive_interrupted` 标志：持有客体预留期间返回宿主时设置；STXR 按硬件结果返回失败；下一次 LDXR 在开始新重试前返回 UNSUPPORTED，交由回退执行器继续。这样保留了程序已执行的副作用及当前寄存器，无须复制寄存器快照或回滚内存。新增两个 4 KiB 代码页相距 1 MiB、占用同一跳转表项的回归，要求第一次受中断的重试返回，且共享数据未写入。后续双核集成时，含回退执行器的区间需与其他客体执行互斥，直到其并发原子语义另行验证。

当前实现的独立 CLI/GCD 各 83 项命名检查、Linux 核心 CLI/GCD 及八轮 Bionic/ART 交替对照成功。关闭 `exclusive_interrupted` 更新的对照构建会在代码页冲突检查失败，结果保存在独立检查的 `negative-control/result.json`。完整 Linux 双核、完整桌面和 iPhone 均待后续接入，当前阶段没有新的整机提速结论。

### 本机测量

环境为 Apple M5 Ultra、macOS 27.0 / 26A428、Clang `-O2`。独立执行器使用每引擎 2 MiB 代码缓存、256 项跳转表、16 KiB 数据页和 `flat` 访存；每个线程执行 4,000,000 次数组更新。CLI 的墙钟耗时为 5.121 ms、两个线程 CPU 时间合计 10.217 ms、重叠 5.097 ms；GCD 分别为 5.086 / 10.156 / 5.074 ms。这些数据确认两个引擎实际同时工作，测量包含首次编译，仅覆盖独立数组负载。

Linux 与 Android 对照仍使用单个 Linux CPU、1 GiB RAM、16 KiB 页、2 ms 定时抢占、每执行器 128 MiB 缓存、256 项跳转表、`flat`、代码写入跟踪和跨页处理；跳转复用与访存合并关闭。Android 使用 nterp，expanded JIT / fast baseline 关闭。相同二进制交替开启和关闭原生独占，每种设置四轮，结果为中位数：

| 阶段 / 指标 | LDAR/CAS | 原生独占 |
| --- | ---: | ---: |
| Bionic 阶段耗时（ms） | 851.968 | 697.778 |
| ART 阶段耗时（ms） | 1242.235 | 1250.824 |
| ART footprint 平均值（MiB） | 253.898 | 252.750 |
| ART footprint 采样峰值（MiB） | 272.727 | 272.712 |
| ART footprint 最后值（MiB） | 270.384 | 271.259 |

最终这组 ART 耗时增加约 0.7%，内存峰值接近；此前相同实现的一组结果为增加约 0.4%。Bionic 两组结果的方向不同，先前为增加约 3.3%，最终为减少约 18.1%；当前样本不足以确认其稳定收益。最终每轮回退次数：LDAR/CAS 为 49–51，原生独占为 55–60，低于已撤回预扫描版本的约 344,338 次。

[结构化结果](../../../../experiments/native-linux/results-macos-direct-parallel.json)保留 12 轮结果、126 个输入与产物摘要；303 个内存样本已重新计算平均值、采样峰值和最后值。并行独立检查另有 `parallel_execution` 内存阶段；该阶段约 20 ms，在 100 ms 采样下仅取得阶段边界值，未覆盖瞬时 footprint 峰值。宿主进程 lifetime RSS peak 单独保留。

### 复杂度审查

按 reclaim-code-entropy 核对实际使用方：新增布尔设置由 Linux 实验入口和双执行器回归使用，并由 benchmark 同构建对照记录；没有新增产品设置、持久格式或另一套代码缓存。每引擎仍使用现有状态与缓存所有者，独立并发检查单独成文件，复用既有汇编负载、构建和内存采样。执行调用内的中断标志只用于结束受宿主影响的独占重试；删除它会恢复已观察到的重试停顿。已撤回控制流预扫描，减少了指令类别与范围判断。当前保留原 LDAR/CAS 对照，以便量化原生候选的开销与兼容性边界。


### 双核 Bionic/ART 对照

共享代码标记的生命周期修复和跨页处理开启后，使用同一双核内核与宿主二进制，按 CLI/GCD 平衡顺序交替运行 `all` / `code` 两种用户复制停止策略，各四轮，全部成功。环境仍为 Apple M5 Ultra / macOS 27.0 (26A428)、Clang `-O2`、1 GiB RAM、16 KiB 页，每 CPU 的 Direct 和 Unicorn 各有 128 MiB 缓存；flat、原生独占、跨页处理开启，代码页信号跟踪关闭。定时抢占为 2 ms，内存采样为 100 ms，额外并行计时关闭。ART 使用 nterp，expanded JIT / fast baseline 关闭。

| 阶段 / 指标中位数 | 全部复制暂停 | 仅代码写入暂停 |
| --- | ---: | ---: |
| Bionic 耗时（ms） | 1229.903 | 1127.527 |
| ART 耗时（ms） | 1614.942 | 1617.198 |
| ART footprint 平均值（MiB） | 305.078 | 304.196 |
| ART footprint 采样峰值（MiB） | 343.852 | 343.813 |
| ART footprint 最后值（MiB） | 336.267 | 342.235 |

Bionic 耗时中位数减少约 8.3%，ART 增加约 0.14%。这组结果只比较用户复制停止策略，未比较 CPU 数量；不能据此推算双核整机收益。原始结果在 `work/native-linux-nce/android-direct-smp-uaccess-matrix/summary.json`。复现命令为 `python3 scripts/benchmark_android_translation.py --comparison direct-smp-uaccess --reuse-engine-build --output work/native-linux-nce/android-direct-smp-uaccess-matrix`。

### 本轮复杂度审查

每 CPU 的寄存器执行入口、退出事件、TLB/代码失效通知与缓存分别由实际运行它的 CPU 管理；合用这些状态会覆盖另一 CPU 尚未消费的通知。任务本身保留寄存器，迁移后选择目标 CPU 的执行器。公共 RAM、ELF 布局与平坦表内存统计继续共享；没有为每线程分配执行器。

mm 资源列表解决停机时仍被空闲 CPU 持有的地址空间清理，移除后可复现 4 MiB 平坦表遗留。可执行 PTE 计数处理同一物理页的多个执行映射，0/1 标记供生成代码直接读取；仅保留 0/1 标记会丢失其他执行映射是否仍在使用的信息。复制停止设置直接进入现有构建、日志和交替对照入口；额外计时由一个关闭即跳过时钟的开关控制。ELF 布局的独立文件承载登记、查找和释放，保留原宿主回调 ABI，没有新增转发层。


### 完整桌面与关机中的待修问题

源码审查发现，任务离开 Direct 后可能迁移到另一 CPU，进入 Unicorn 时应重新清除新 CPU 的退出事件；原清除位置只覆盖离开前的 CPU。已将初始化加入 `prepare_unicorn()`。RAM 回收也改为核对该范围已无执行映射，代码标记继续由 PTE 生命周期维护。

`lkl-direct-smp-services-cleanup-debug` 的宿主采样显示，停机等待期间仍有网络命名空间清理线程执行 `rcu_barrier()`。据此增加停机前的 `netns_wq` 排空，并在排空前后等待 RCU 回调。随后 `work/native-linux-nce/lkl-direct-smp-services-netns-drain/summary.json` 的 CLI 检查仍触发 120 秒期限，`linux_data_readonly_shutdown` 成功，但宿主未完成退出，未继续执行 GCD。该修改尚未解决停机问题，仍需定位等待关系。

### 同一 SMP 构建的单 CPU 对照

下一阶段增加启动前的在线 CPU 数量选择，使用 Linux 的 `maxcpus` 启动参数。SMP 内核、两个 Direct/Unicorn 实例及缓存容量保持相同，分别启用一个或两个 CPU，以测量并行执行对同一负载的影响。该设置只在启动前生效，运行期间不改变 CPU 集合。原生入口保留现有调用契约，翻译入口使用单独的带 CPU 数量参数的启动函数。

验收要求记录构建容量、请求数量和启动后实际可调度 CPU 集合；仅启用一个 CPU 时，CPU 1 的执行与编译计数必须为零。CLI/GCD 均需完成核心、Android 和正常关机检查，再进行同一 SMP 二进制、相同初始盘和交替顺序的服务及桌面对照。两核专用并发用例继续在两个 CPU 在线时运行，单 CPU 轮次明确检查调度集合，保留通用线程、信号、映射和动态代码回归。应用设置在上述验证通过后接入。


首次单 CPU 核心 CLI/GCD 成功，CPU 1 计数为零。随后双 CPU 轮次在启动检查中失败：宿主系统调用线程按既有设计固定在 CPU 0，它的调度亲和性只能反映该线程的限制。启动检查改为读取 `/proc/stat` 的在线 CPU 行；客体核心检查先请求完整 CPU 集合，再核对内核允许的集合。失败轮次保留在 `lkl-smp-online-two-core`，后续重新检查两个配置。


修正后的单、双 CPU 核心 CLI/GCD 均成功。单 CPU 轮次的第二个执行器调用、编译和代码查询均为零；执行区间采样中的 CPU 1 时间及双核重叠均为零。双 CPU 轮次的执行区间重叠为 CLI 10.667 ms、GCD 10.576 ms，两个 CPU 都实际运行。这里的区间包含执行器工作，用于检查并行状态。报告回归会拒绝缺失或错误的在线集合、闲置 CPU 的非零执行计数和错误的采样汇总。

同一 SMP 内核与宿主二进制的 Android 交替对照共八轮成功，各配置含 CLI/GCD 两轮。单 / 双 CPU 的 Bionic 执行中位数为 1.179704 / 1.393688 秒，ART 为 1.843218 / 1.772979 秒。设备为 Apple M5 Ultra、macOS 27.0（26A428），1 GiB RAM、16 KiB 页、每 CPU 的 Direct/Unicorn 各 128 MiB、双映射、flat、原生独占、代码页写入跟踪、跨页访存、2 ms 抢占，nterp 开启；快速路径、扩展 JIT、快速基线关闭。原始配置和数据见[在线 CPU 对照](../../../../experiments/native-linux/results-translation-online-cpus.json)。本组只说明上述负载的结果，完整桌面和设备性能继续待测。

启动设置与 benchmark 已加入在线 CPU 数量，拒绝 0、超出构建容量及单核运行库请求两个 CPU。设置只影响下次启动；打包默认启用全部 CPU，因此打包校验要求全部 CPU 在线的完整桌面报告。复杂度审查：两个执行器和缓存的所有权保持原样，在线数量交给 Linux 启动参数管理；新增原生兼容包装保留现有 ABI，省去包装会要求无关原生调用方同步修改。未增加运行期间 CPU 热插拔状态。


核对上一组 Android 日志时发现，Linux 随在线 CPU 数量将默认时间片从 750,000 ns 调整为 1,500,000 ns。因此上述单 / 双 CPU 数字同时包含这一默认策略的影响。后续同构建对照显式请求两组均为 750 μs，报告保存请求值并检查实际值为 750,000 ns；此前结果继续保留并按原配置解释。
