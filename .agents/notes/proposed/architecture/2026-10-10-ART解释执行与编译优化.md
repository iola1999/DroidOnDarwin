# 决策记录: ART 解释执行与编译优化

状态: proposed

## 问题

用户已授权按[后续提速规划](2026-10-10-后续提速与多核可行性评估.md)持续实现，先核对最新工作区。实施基于 `a6d00d6`，开始时工作区干净。该版本已更名为 DroidOnDarwin，采用两端共享界面、设备管理和阶段反馈；普通启动已经跳过专项诊断。ART 构建与 NCE 引用约定沿用上一阶段。

当前 ART 编入 ARM64 nterp 汇编解释器，但 restricted mode 下关闭运行入口。编译暂未覆盖或尚未达到编译阈值的方法继续使用 C++ 解释器。nterp 上游假设对象指针可放入 32 位寄存器，本项目对象地址需要加上运行时基址；直接打开入口会在对象访问处失败。

## 提案

### 实施顺序与接口

先适配 nterp，再根据真实热点推进 JIT 覆盖和快速基线编译，随后评估匹配的 boot image/AOT。每个阶段保留完整系统启动对照，性能数字随实际结果更新。

nterp 保留现有 DEX 寄存器、Quick 参数和返回值中的 32 位编码引用。在数组、对象、类与字段访问处解码，在返回 C++ 对象的位置编码；保留 null 语义、GC 根和异常展开契约。当前构建使用 MS GC，带读屏障的 GC 需要单独适配后才能启用。

同一包保留 C++ 解释器与 nterp，启动前选择，下次会话生效。初期默认沿用 C++ 解释器。实际入口通过回归检查，配置与测试结果进入日志；仅输出请求值不足以确认 nterp 已执行。运行中的切换暂不实现。

上游适配使用独立补丁，纳入现有构建哈希和源文件恢复流程。复用现有 Java/JNI 回归与宿主测试入口，根据失败补充必要边界；实验设置复用共享界面和启动配置，不增加通用插件或策略注册框架。

### 进展

- 2026-10-10：核对最新提交，建立持续优化 goal。nterp 已完成高地址引用适配，增加启动前开关和实际方法入口检查。
- 增加 MethodHandle、VarHandle、引用数组、volatile 字段、GC 根、异常与 monitor 回归。首次启用时发现 Quick 多态调用将编码引用直接交给 C++；保存 Quick 参数后解码 receiver，恢复调用约定。关闭 nterp 的对照又发现 MethodHandle 参数复制仍比较完整指针，已改为比较编码引用；两种解释器均通过新增回归。
- 部分指令处理器超过上游 128 字节槽位。采用上游 `add_slow_path` 将对应处理体移出固定槽位，保留 dispatch 表格式。构建输入哈希包括新增补丁。
- 同步编译后，本机 CLI/GCD 的完整桌面回归均成功，记录包含 209 次通过的命名检查；可见窗口也已完成 nterp 配置的完整回归。该窗口检查早于 MethodHandle 参数复制修复，后续用正式 App 的组合实验继续覆盖。
- 同构建的解释器关闭/开启已交替运行各三次，六轮完整桌面诊断均成功。结构化结果见[ART nterp 本机结果](../../../../experiments/native-linux/results-macos-art-nterp.json)。在 Apple M5 Ultra、macOS 27.0 (26A428)、1 GiB 客体 RAM、demand、默认快速恢复/稀疏扫描、关闭统计条件下，200 万次整数循环的解释执行中位数为 55.344 / 9.302 ms，范围为 55.307–55.905 / 8.787–9.333 ms；20 万次常用运算循环为 18.136 / 4.309 ms，范围为 18.012–19.077 / 4.291–4.492 ms。每个进程内取三次中最快值，再统计三个进程样本。
- 整段诊断时间中位数为 175.471 / 156.937 秒，但期间部分 App 构建和预热重叠，且包含专项测试；这些时间仅保留为本轮记录，普通启动收益另用无并行构建的正式 App 对照。默认解释器暂不改变。
- 按用户补充要求实施[两端性能实验自动化](../../implemented/testing/2026-10-10-两端性能实验自动化.md)，统一启动配置，增加 Mac CLI、iPhone Deep Link、设备内操作及结果收集。`0.15.0 (84)` iOS 包已完成构建，当前继续本机验证，尚未要求设备测试。

- 无并行构建的正式 Mac App 已完成六轮交替实验，自动操作、停止、日志配置检查和最终 ext4 清理检查均成功；所有样本热状态为 nominal，低电量模式关闭。核心启动至桌面就绪的中位数为 C++ 112.018 秒、nterp 102.061 秒，耗时减少 8.9%；范围分别为 111.041–112.083 秒、99.004–104.072 秒。首次数据初始化在此前单独完成，六轮沿用数据盘与宿主缓存。测量包含现有一秒日志观察延迟，操作序列时间只统计输入提交。完整配置、构建与每轮结果见[普通 App 对照](../../../../experiments/native-linux/results-macos-desktop-nterp.json)。该结果支持继续保留 nterp；默认值等待后续集成和手机验证。

### 后续编译覆盖调查

nterp 的本机功能成立后，已经实现按需记录优化编译器的过滤通过次数及每个被拒绝方法的第一个 IR 原因，已完成本机完整运行验证。采集随性能诊断开启，普通运行不做逐方法记录；采用累计计数、按 2 的幂次输出及每类至多两个方法样例，SIGQUIT 提供完整计数快照。过滤通过之后仍可能在后续编译阶段失败，计数只说明过滤结果。后续按 Android 实际命中的类型扩展。不能仅根据支持的 IR 数量判断运行收益。

首次带统计的 CLI/GCD 完整桌面回归均成功，[编译过滤快照](../../../../experiments/native-linux/results-macos-compiler-filter.json)中 system_server 在启动期有 470 次 InvokeStaticOrDirect、426 次 Max、51 次 StringBuilderAppend 和 18 次 InvokePolymorphic 拒绝，过滤通过 2772 次；这些计数包含 fork 时继承的父进程状态，不能解释为独立方法数量或执行时间。样例涉及 StringBuilder、字符串构造、系统配置解析及属性通知。后续日志增加运行期编号，区分复用 PID 的独立 ART 执行。

据此先适配字符串构造、字符串拼接、Min/Max 与多态调用，增加 `expandedJIT` 启动选项，默认关闭。Quick 参数继续保存编码引用，StringBuilderAppend 返回的完整指针在生成代码中转换；多态入口沿用已修复的 receiver 转换。回归强制编译对应方法后检查 Unicode、null、数值边界、GC、VarHandle 和异常。Deoptimize/ShouldDeoptimizeFlag 需要单独核对栈恢复及类层次变化，继续保留原限制。

扩展 JIT 已通过本机 CLI/GCD 完整桌面检查，十个被测方法均确认安装了编译入口，结果见[扩展 JIT 回归](../../../../experiments/native-linux/results-macos-expanded-jit.json)。首次强制 MethodHandle 编译发现 LoadMethodType 尚未开放，补上 JIT 根加载与 runtime 返回引用转换后成功。原有字符串构造的拒绝检查随选项更新，继续检查关闭配置保持原解释执行。关闭 nterp/扩展 JIT/统计后的 CLI/GCD 对照也成功，各有 211 次通过记录，确认日志未出现编译过滤统计。`0.16.0` 的 Mac 构建 5 与 iOS 构建 85 已完成打包；Mac 的配置、自动化、停止、资源哈希、签名和动态库检查成功。正式 App 的启动对照正在执行，手机验证仍集中到后续阶段。

快速基线编译器有独立的对象访问、JIT 根地址和隐式 null 检查代码，需与当前编码引用及显式异常约定共同适配。上游 boot image 头仍使用 32 位镜像地址；本项目堆基址在高地址，生成与装载需要相同的地址编码约定。两项都保留在后续步骤，当前没有可用性结论。

### 复杂度检查

nterp 使用现有 Quick/DEX 的编码引用、上游指令生成器和固定 dispatch 格式。直接扩大所有槽位会增加整个解释器体积；当前仅将超出的处理体移到上游已有的慢路径区。回归里的 MethodHandle/VarHandle 能发现实际返回值和 GC 引用问题，因此保留；单纯检查汇编文本的测试不能覆盖这些行为。

扩展 JIT 的开关复用现有启动快照与客体配置文件，编译统计复用性能诊断选项。每张优化图只记一次过滤结果；关闭时跳过原子计数、计时和日志。回归需要验证实际编译入口及 GC 后的值，单独扩大 IR 白名单不能完成验证。ART 源码恢复使用 `patch --posix`，防止补丁工具生成 `.orig` 文件；此前生成的两份文件已清理。

## 曾考虑的替代方案

- 只取消 `ART_USE_RESTRICTED_MODE`：该宏还约束编译器覆盖和执行入口，直接取消会同时改变多个未验证条件。保留宏，为适配后的 nterp 单独确定可用条件。
- 将所有 DEX 寄存器扩大到 64 位：整数寄存器布局、调用参数和根数组都会改变，无法直接复用现有 JIT ABI。保持现有编码，在需要指针的位置转换。
- 一开始改变默认解释器：先在同构建下验证功能和启动耗时，再决定默认值。

## 验收标准

- 两种配置均通过真实 Java/JNI 执行，涵盖引用与 null、数组及字段、继承和接口调用、异常、监视器、GC、JIT/解释器相互调用；确认被测方法实际使用选定入口。
- 完成本机 CLI/GCD 与桌面启动、应用操作、停止检查；基准与候选使用相同构建、负载及数据状态，统计默认关闭。
- 性能记录说明设备、系统、配置、负载、时间单位和测量范围；单个方法结果与系统启动分别说明。
- 阶段产物沿用现有 macOS/iOS 打包校验和来源记录。设备测试集中到有重大进展的完整版本，局部适配通过后继续开发。

## 风险

对象偏移与完整指针混用可能造成崩溃或 GC 错误；固定长度指令处理器也可能因转换指令超出容量。调用转换、异常栈恢复和编译入口需要一并检查。nterp 的收益取决于实际解释执行占比，当前完整诊断仍不能说明手机上的持续交互收益。
