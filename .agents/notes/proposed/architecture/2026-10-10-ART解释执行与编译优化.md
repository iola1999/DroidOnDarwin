# 决策记录: ART 解释执行与编译优化

状态: proposed

## 问题

用户已授权按[后续提速规划](2026-10-10-后续提速与多核可行性评估.md)持续实现，先核对最新工作区。实施基于 `a6d00d6`，开始时工作区干净。该版本已更名为 DroidOnDarwin，采用两端共享界面、设备管理和阶段反馈；普通启动已经跳过专项诊断。ART 构建与 NCE 引用约定沿用上一阶段。

当前 ART 编入 ARM64 nterp 汇编解释器，但 restricted mode 下关闭运行入口。编译暂未覆盖或尚未达到编译阈值的方法继续使用 C++ 解释器。nterp 上游假设对象指针可放入 32 位寄存器，本项目对象地址需要加上运行时基址；直接打开入口会在对象访问处失败。

## 提案

### 实施顺序与接口

先适配 nterp，再根据真实热点推进 JIT 覆盖和快速基线编译，随后评估匹配的 boot image/AOT。每个阶段保留完整系统启动对照，性能数字随实际结果更新。

nterp 保留现有 DEX 寄存器、Quick 参数和返回值中的 32 位编码引用。在数组、对象、类与字段访问处解码，在返回 C++ 对象的位置编码；保留 null 语义、GC 根和异常展开契约。当前构建使用 MS GC，带读屏障的 GC 需要单独适配后才能启用。

同一包保留 C++ 解释器与 nterp，启动前选择，下次会话生效。初期默认沿用 C++ 解释器。实际入口通过回归检查，配置与测试结果进入日志；仅输出请求值不足以确认 nterp 已执行。运行中的切换暂不实现。

上游适配使用独立补丁，纳入现有构建哈希和源文件恢复流程。复用现有 Java/JNI 回归与宿主测试入口，根据失败补充必要边界；实验设置复用共享界面和启动配置，不增加通用插件或策略注册框架。

### 进展

- 2026-10-10：核对最新提交，建立持续优化 goal。nterp 已完成高地址引用适配，增加启动前开关和实际方法入口检查。
- 增加 MethodHandle、VarHandle、引用数组、volatile 字段、GC 根、异常与 monitor 回归。首次启用时发现 Quick 多态调用将编码引用直接交给 C++；保存 Quick 参数后解码 receiver，恢复调用约定。关闭 nterp 的对照又发现 MethodHandle 参数复制仍比较完整指针，已改为比较编码引用；两种解释器均通过新增回归。
- 部分指令处理器超过上游 128 字节槽位。采用上游 `add_slow_path` 将对应处理体移出固定槽位，保留 dispatch 表格式。构建输入哈希包括新增补丁。
- 同步编译后，本机 CLI/GCD 的完整桌面回归均成功，记录包含 209 次通过的命名检查；可见窗口也已完成 nterp 配置的完整回归。该窗口检查早于 MethodHandle 参数复制修复，后续用正式 App 的组合实验继续覆盖。
- 同构建的解释器关闭/开启已交替运行各三次，六轮完整桌面诊断均成功。结构化结果见[ART nterp 本机结果](../../../../experiments/native-linux/results-macos-art-nterp.json)。在 Apple M5 Ultra、macOS 27.0 (26A428)、1 GiB 客体 RAM、demand、默认快速恢复/稀疏扫描、关闭统计条件下，200 万次整数循环的解释执行中位数为 55.344 / 9.302 ms，范围为 55.307–55.905 / 8.787–9.333 ms；20 万次常用运算循环为 18.136 / 4.309 ms，范围为 18.012–19.077 / 4.291–4.492 ms。每个进程内取三次中最快值，再统计三个进程样本。
- 整段诊断时间中位数为 175.471 / 156.937 秒，但期间部分 App 构建和预热重叠，且包含专项测试；这些时间仅保留为本轮记录，普通启动收益另用无并行构建的正式 App 对照。默认解释器暂不改变。
- 按用户补充要求实施[两端性能实验自动化](../../implemented/testing/2026-10-10-两端性能实验自动化.md)，统一启动配置，增加 Mac CLI、iPhone Deep Link、设备内操作及结果收集。`0.15.0 (84)` iOS 包已完成构建，当前继续本机验证，尚未要求设备测试。

- 无并行构建的正式 Mac App 已完成六轮交替实验，自动操作、停止、日志配置检查和最终 ext4 清理检查均成功；所有样本热状态为 nominal，低电量模式关闭。核心启动至桌面就绪的中位数为 C++ 112.018 秒、nterp 102.061 秒，耗时减少 8.9%；范围分别为 111.041–112.083 秒、99.004–104.072 秒。首次数据初始化在此前单独完成，六轮沿用数据盘与宿主缓存。测量包含现有一秒日志观察延迟，操作序列时间只统计输入提交。完整配置、构建与每轮结果见[普通 App 对照](../../../../experiments/native-linux/results-macos-desktop-nterp.json)。该结果支持继续保留 nterp；默认值等待后续集成和手机验证。

### 后续编译覆盖调查

nterp 的本机功能成立后，已经实现按需记录优化编译器的过滤通过次数及每个被拒绝方法的第一个 IR 原因，已完成本机完整运行验证。采集随性能诊断开启，普通运行不做逐方法记录；采用累计计数、按 2 的幂次输出及每类至多两个方法样例，SIGQUIT 提供完整计数快照。过滤通过之后仍可能在后续编译阶段失败，计数只说明过滤结果。后续按 Android 实际命中的类型扩展。不能仅根据支持的 IR 数量判断运行收益。

首次带统计的 CLI/GCD 完整桌面回归均成功，[编译过滤快照](../../../../experiments/native-linux/results-macos-compiler-filter.json)中 system_server 在启动期有 470 次 InvokeStaticOrDirect、426 次 Max、51 次 StringBuilderAppend 和 18 次 InvokePolymorphic 拒绝，过滤通过 2772 次；这些计数包含 fork 时继承的父进程状态，不能解释为独立方法数量或执行时间。样例涉及 StringBuilder、字符串构造、系统配置解析及属性通知。后续日志增加运行期编号，区分复用 PID 的独立 ART 执行。

据此先适配字符串构造、字符串拼接、Min/Max 与多态调用，增加 `expandedJIT` 启动选项，默认关闭。Quick 参数继续保存编码引用，StringBuilderAppend 返回的完整指针在生成代码中转换；多态入口沿用已修复的 receiver 转换。回归强制编译对应方法后检查 Unicode、null、数值边界、GC、VarHandle 和异常。Deoptimize/ShouldDeoptimizeFlag 需要单独核对栈恢复及类层次变化，继续保留原限制。

扩展 JIT 已通过本机 CLI/GCD 完整桌面检查，十个被测方法均确认安装了编译入口，结果见[扩展 JIT 回归](../../../../experiments/native-linux/results-macos-expanded-jit.json)。首次强制 MethodHandle 编译发现 LoadMethodType 尚未开放，补上 JIT 根加载与 runtime 返回引用转换后成功。原有字符串构造的拒绝检查随选项更新，继续检查关闭配置保持原解释执行。关闭 nterp/扩展 JIT/统计后的 CLI/GCD 对照也成功，各有 211 次通过记录，确认日志未出现编译过滤统计。`0.16.0` 的 Mac 构建 5 与 iOS 构建 85 已完成打包；Mac 的配置、自动化、停止、资源哈希、签名和动态库检查成功。正式 App 的启动对照见下文，手机验证仍集中到后续阶段。

快速基线编译器有独立的对象访问、JIT 根地址和隐式 null 检查代码，需与当前编码引用及显式异常约定共同适配。上游 boot image 头仍使用 32 位镜像地址；本项目堆基址在高地址，生成与装载需要相同的地址编码约定。两项的实现与验证分别见下文。

正式 App 的扩展 JIT 六轮对照已经完成。在 Apple M5 Ultra、macOS 27.0 (26A428)、`0.16.0` Mac 构建 5、1 GiB/单 CPU、360×640、demand、nterp 开启、统计关闭、沿用数据与缓存的条件下，关闭/开启扩展 JIT 的启动中位数为 99.043 / 99.057 秒，范围为 98.990–102.041 / 98.015–101.028 秒。全部样本成功，热状态 nominal，末轮 ext4 正常卸载；见[完整对照](../../../../experiments/native-linux/results-macos-desktop-expanded-jit.json)。本轮没有测到启动提速，扩展选项继续默认关闭。编译覆盖已通过功能验证，后续应用负载是否受益仍需分别测量。

### 快速基线编译原型

下一阶段适配上游 ARM64 单遍编译器，提供独立的 `fastBaseline` 启动设置，默认关闭，与扩展 JIT 开关独立对照。先覆盖现有上游支持的字段、引用、分配、类型检查、调用与抛出异常；尚未支持的 DEX 指令和同步方法继续交给优化编译器。此阶段不扩展上游快速编译器的指令集合。

两个编译器共享高地址引用转换函数。快速编译器补显式 null 检查、完整宽度的 JIT 根地址、runtime 参数/返回值转换及 card table 地址计算。强制基线编译的回归同时检查实际采用的编译器，防止退回优化编译器后误判为快速路径成功；编译成功计数按编译线程保存，每次编译更新一次，不在生成的客体方法里计数。可选统计按 2 的幂次报告，包含进程、运行编号和线程编号。

验收覆盖关闭/开启组合、GC 期间的寄存器根、字段存储屏障、显式异常、虚方法/接口调用及不支持指令的回退。之后比较同构建的实际桌面启动和 JIT 编译时间；若尝试编译的额外开销超过收益，保留测量并重新选择默认与实施方向。

开启和关闭快速基线编译的 CLI/GCD 检查均成功，每轮包含 213 次通过记录。开启时 20 个强制编译方法中 19 个使用快速编译器，volatile 回退使用优化编译器；关闭时 20 个均使用优化编译器。记录见[快速基线编译检查](../../../../experiments/native-linux/results-macos-fast-baseline.json)。`0.17.0` 的 Mac 构建 6 与 iOS 构建 86 已完成，Mac 宿主、配置查询、自动化、内存聚合及包内哈希检查成功。同构建的正式桌面对照和阶段内存采集结果见下文。

正式 Mac App 六轮交替实验均完成。Apple M5 Ultra、macOS 27.0 (26A428)、`0.17.0` 构建 6、1 GiB/单 CPU、360×640、demand、nterp 开启、扩展 JIT 与详细统计关闭；数据盘和宿主缓存沿用，期间未并行构建或运行其他 NCE。关闭/开启快速基线编译的桌面就绪中位数为 104.035 / 105.009 秒，范围为 100.999–104.036 / 101.081–250.096 秒。全部样本热状态 nominal、低电量模式关闭，无 Java fatal exception 或 ANR，最终 ext4 正常卸载。完整配置、原始样本与内存统计见[正式 App 快速基线对照](../../../../experiments/native-linux/results-macos-desktop-fast-baseline.json)。本轮没有测到启动提速，快速基线编译继续默认关闭。

250.096 秒的样本在启动已经延迟后追加三秒宿主线程采样，该样本完整保留并标为诊断轮。SystemUI StartServices 为 14.623 秒；Launcher 的 Displayed 日志为 2 分 12.093 秒。1154 个非等待样本中，缺页处理与映射操作合计 69.2%，只描述这次短时调用栈分布。启动延迟原因尚未确定，不能归因于编译选项。其余两次快速编译样本为 101.081 和 105.009 秒；仍不足以确认启动收益。

启动阶段的 footprint 平均值中位数为关闭 1329.5 MiB、开启 1338.6 MiB；采样峰值中位数为 1989.3 / 1976.5 MiB。停止后最新值中位数为 403.7 / 402.6 MiB。这些是 Mac 运行进程数据；采样均值包含边界样本，进程生命周期峰值另列，iPhone 内存和持续交互仍待集中验证。后续继续匹配的 boot image/AOT，同时保留映射与调度方向的投入。

### Boot image / AOT 实施准备

下一步先生成与当前 ART 同源码、同引用约定的 `dex2oat` 工具，在 Mac 的 NCE 环境中运行，编译产物随后随手机包交付。先检查工具启动与 verify-only 产物，再适配预初始化 boot image，最后检查可复用的 AOT 机器码。每一步单独验证，普通启动在产物验证完成前继续使用已有路径。

源码中的 image header 保留 32 位 image/oat 地址，`ImageWriter` 对镜像根和映射地址调用 `PointerToLowMemUInt32`；装载器又分别修改压缩引用与原生指针。实施时要明确记录镜像内的引用偏移、原生地址与重定位范围，并版本化 NCE 产物。当前 JIT 生成代码可嵌入进程堆基址，持久 AOT 必须改用可重定位的基址访问，不能沿用上一进程的地址。先分别验证预初始化对象和机器码，便于定位收益与失败。

已在独立产物目录完成匹配 `dex2oat` 的编译和链接，正在验证 NCE 内执行。工具构建先复用已有 ART 编译参数及对象文件，在独立产物目录验证依赖；正式集成时复用构建逻辑，不能维护另一份手工复制的 ART 编译选项。暂不增加尚无运行实现的 App 设置。

正式构建新增可选编译工具，复用当前源文件、编译参数与缓存，不从对象缓存目录枚举历史对象。`probe_lkl.py --processes --art-compiler` 使用独立系统盘与测试数据目录，依次运行 CLI/GCD 的编译检查，覆盖 verify 产物和损坏输入错误；普通 App 构建不包含该工具。工具入口与 runtime 一起放入测试变体的 `libart.so`，可执行文件只调用该入口；这样 JNI 依赖的 `libopenjdkjvm.so` 与工具共享 Runtime、Thread 和锁状态。最初将 runtime 对象直接链接到可执行文件的原型未进入正式运行，因双份 runtime 风险调整。verify 产物已通过下述实际装载检查，机器码和 boot image 的重定位仍需后续验证。

首次运行在 `ThreadLocalHashOverride` 创建 AtomicInteger 时崩溃。工具将完整对象地址直接截断成 32 位构造参数，解释器按堆内偏移解码后访问越界；已改用现有编码引用函数。该路径发生在编译工具内，原有普通 runtime 回归未覆盖；编译工具执行回归将持续覆盖它。

CLI/GCD 编译工具回归均成功，每轮通过 145 次命名检查。工具生成 17,248 字节 OAT 和 944 字节 VDEX，新进程通过 `GetOatDexFile()` 确认方法关联的文件路径与 verify 编译过滤器，并完成 Java、GC、异常和 JIT 行为检查。损坏 DEX 返回 1，数据盘正常卸载，当前编译目录的 21 项 ELF/APK 边界检查成功。记录见[编译工具检查](../../../../experiments/native-linux/results-macos-art-compiler-verify.json)。这些产物只保留验证信息，尚未包含 AOT 方法机器码。上游会跳过不存在的 DEX 路径，外部批量构建在调用工具前必须核对输入清单；负面回归使用实际存在但内容损坏的文件。

实施顺序调整为先验证普通 DEX 的可重定位 AOT 机器码，再处理 boot image。原因是线程堆基址和 BSS 根访问同时影响两者；先用现有 Java 回归检查代码生成，能够减少镜像地址重定位与代码生成同时失败时的排查范围。下一步在 ART Thread 中保存进程堆基址，生成代码从线程读取，产物版本与上游 OAT 区分；保留尚未适配的编译过滤限制。

### 复杂度检查

nterp 使用现有 Quick/DEX 的编码引用、上游指令生成器和固定 dispatch 格式。直接扩大所有槽位会增加整个解释器体积；当前仅将超出的处理体移到上游已有的慢路径区。回归里的 MethodHandle/VarHandle 能发现实际返回值和 GC 引用问题，因此保留；单纯检查汇编文本的测试不能覆盖这些行为。

扩展 JIT 的开关复用现有启动快照与客体配置文件，编译统计复用性能诊断选项。每张优化图只记一次过滤结果；关闭时跳过原子计数、计时和日志。回归需要验证实际编译入口及 GC 后的值，单独扩大 IR 白名单不能完成验证。ART 源码恢复使用 `patch --posix`，防止补丁工具生成 `.orig` 文件；此前生成的两份文件已清理。

快速编译器与优化编译器复用引用转换函数，保留上游指令支持范围与回退。接口调用回归需要精确构造 DEX 指令，改用 SDK 的 dexlib2 后已移除手写 DEX 索引解析；只重写三个指定方法，输入形状变化时构建失败。编译入口计数只在方法安装时更新，用于确认选择结果，不增加生成代码的执行统计。

编译工具复用同一构建函数和源码缓存，仅工具变体增加入口与链接依赖。独立测试磁盘使编译回归可以重复运行；装载检查复用已有 Java/JNI 回归，不新增第二套虚拟机测试程序。`test_nce_userspace.py --fixtures` 指向本轮产物，防止编译工具检查读取普通构建目录的旧 ELF。去掉实际 OAT 关联检查会允许 ART 退回原 DEX 后仍通过测试，因此保留该检查。

## 曾考虑的替代方案

- 只取消 `ART_USE_RESTRICTED_MODE`：该宏还约束编译器覆盖和执行入口，直接取消会同时改变多个未验证条件。保留宏，为适配后的 nterp 单独确定可用条件。
- 将所有 DEX 寄存器扩大到 64 位：整数寄存器布局、调用参数和根数组都会改变，无法直接复用现有 JIT ABI。保持现有编码，在需要指针的位置转换。
- 一开始改变默认解释器：先在同构建下验证功能和启动耗时，再决定默认值。

## 验收标准

- 两种配置均通过真实 Java/JNI 执行，涵盖引用与 null、数组及字段、继承和接口调用、异常、监视器、GC、JIT/解释器相互调用；确认被测方法实际使用选定入口。
- 完成本机 CLI/GCD 与桌面启动、应用操作、停止检查；基准与候选使用相同构建、负载及数据状态，统计默认关闭。

## 风险

对象偏移与完整指针混用可能造成崩溃或 GC 错误；固定长度指令处理器也可能因转换指令超出容量。调用转换、异常栈恢复和编译入口需要一并检查。nterp 的收益取决于实际解释执行占比，当前完整诊断仍不能说明手机上的持续交互收益。

快速基线编译首次回归在强制编译 `NceFastBaseline.number` 时失败，方法回退到优化编译器。诊断定位到 `CanDoImplicitNullCheckOn` 在 restricted runtime 下始终返回 false；快速编译器仍用它筛选可为空的字段访问。NCE 路径已经生成显式空检查，现仅在其他构建保留隐式检查的偏移限制。临时诊断日志已移除，实际编译入口与异常路径重新验证成功。

快速编译入口回归成功后，完整启动出现 SystemUI 的 `UnsupportedOperationException`，远端栈由 `Alarm.matches` 进入 `IBinder.addFrozenStateChangeCallback`。检查发现快速编译器对接口解析到 `java.lang.Object` 的方法仍使用 IMT；优化编译器在 `instruction_builder.cc` 中将同类调用转换为 virtual。快速编译器采用相同处理，回归新增接口引用的 equals/hashCode/toString 和 null。修复后 CLI/GCD 的完整桌面启动、时钟操作和停止检查均成功，日志未出现 Java fatal exception 或 ANR。

新增接口回归的 Java 源码经 D8 生成的是 `invoke-virtual Object`，无法触发本次错误。构建测试 DEX 时，使用 Android SDK 自带的 dexlib2，将三个指定方法的首条调用改为 `invoke-interface Reader.equals/hashCode/toString`；Reader 不声明这些方法，解析结果为 Object 的公开方法。保留调用参数与指令宽度，由库重建索引和校验和；方法或指令形状不符合预期时构建失败。转换工具只用于回归 DEX，不处理系统或应用内容。三个接口方法的编译和行为检查已成功。
