# 决策记录: 原始 init 的数据分区与回收

状态: proposed

## 问题

SDK36 原 DM 分区观察已越过 property_contexts 读取，执行原 KeyMint 并通过 VINTF 实例检查。侧树 `work/stock-init-keymint/work/native-linux-nce/keymint-sdk36-dm16-original-v1/summary.json` 的 CLI/GCD 随后记录 `/data/misc/keystore/persistent.sqlite` 的创建返回 `-30`，SQLite 错误码 14，原 keystore2 panic/signal 6。该报告 SHA-256 为 `d1e1f44e65d911e5c43318be40e026a29b2e9aee8790f638bda2eb1859e90be6`，固定阶段与主线接受结果继续由 [SDK36 原始分区与 KeyMint](2026-11-12-SDK36原始分区与KeyMint启动.md)记录。

现有原 init setup 只创建 `/data` 与 `/metadata` 目录。正式 translation runner 的 slot 0 打开和 ext4 挂载在 services/desktop 分支，原 init 的 bionic 观察分支未使用它。原 `/system/etc/init/hw/init.rc` 的 post-fs 执行 `mount rootfs rootfs / remount bind ro nodev`；两入口实际 mount syscall 的 flags 为 4133，返回 0。目录继续属于只读根文件系统，后续 chown、chmod、mkdir 与 SQLite 创建返回 EROFS。

固定 SDK 的发布目录包含 system.img、vendor.img、ramdisk.img 和 encryptionkey.img，没有独立 userdata 初始镜像。原 `/vendor/etc/fstab.ranchu` 规定 `/dev/block/vdc` 挂载 `/data`，使用 ext4、quota、fileencryption、fsverity 和 metadata keydirectory。当前生成内核关闭 FS_ENCRYPTION、FS_VERITY、QUOTA 与 DM_CRYPT；完整 first-stage 和启动硬件/fstab 输入尚未验证。可写数据盘、原加密/配额要求与完整 first-stage 需要分别记录实际范围。

## 提案

沿用离线开发授权，先在现有 SDK36 mounted-partition 观察入口通过可选 `--data-image` 接收显式数据盘路径。复用 slot 0 的可写 ext4、排他锁、关闭前 fsync 和标准 host disk close；原五个 LP 分区继续由只读 slot 1 和 DM linear 使用。两种页大小各使用一份独立的 512 MiB 数据盘，容量沿用 `probe_lkl.py` 的现有 data seed。实验在新的 `work/` 目录创建镜像，记录大小、格式、初始摘要及每次运行后的摘要，现有应用数据盘与 Android 参照数据继续保留。

Linux 启动前打开数据盘，在原 init setup 中将 slot 0 对应的 `/dev/block/vdc` 挂载到 `/data`，使用原 fstab 的 noatime、nosuid、nodev 挂载标志；原加密、配额和 metadata 要求继续单独验收。随后由原 rc 完成所有者、mode、标签与 Keystore 目录准备。使用 guest 实际创建、读取、文件及目录 fsync 和跨入口 generation 检查持久写入；按每次 Linux 停止后的数据盘读取核对 Keystore SQLite 的实际生成程度。

`stock_init_run()` 完成 0..2 标准流准备后，在 launch 前打开 `/data` 的 O_RDONLY|O_DIRECTORY|O_CLOEXEC fd，要求编号至少为 3，核对 ext4 类型。该 fd 属于父任务，子任务独立复制文件表，exec 关闭其 CLOEXEC 副本；父任务保留实际文件系统引用到 namespace wait 完成。Linux worker 仍运行期间执行 syncfs(267)，随后关闭目录 fd，再尝试卸载 `/data`。lifecycle 严格卸载；original 保留原策略的卸载拒绝，分别记录 syncfs、fd 关闭、内核 halt、host fsync 和映射释放。同步错误使该入口验收失败，同时继续标准关闭和停止。

现有 DM 分区 fd 可占用 1/2，后续标准流 dup3 会提前关闭这些 fd 并使用相同编号。数据阶段用 F_DUPFD_CLOEXEC 将保存的分区 fd 放到编号至少为 3 的位置，保留它们到明确 cleanup，避免保存的编号对应到标准流。继续通过容量、边界读取和最终设备移除验证原持有关系。

每次运行后读取 ext4 state、needs_recovery 与 orphan_present。syncfs 会等待 ext4 日志提交，正常 put_super 才清除 needs_recovery；original 保留未回放 journal 的实际状态。完成两入口 original 后，再从同盘运行 lifecycle，通过标准 Linux 挂载回放，读取 generation 和实际 SQLite，然后严格卸载。数据库导出在回放后的干净文件系统上进行，核对 SQLite header、quick_check、schema，以及实际存在的 -wal/-journal/-shm 文件摘要。

先完成 DM 固定阶段的主线接受，再实施数据分区变更。两种页大小的 CLI/GCD 覆盖生命周期、原 init、写入和重启恢复，并编译实际生成 runner/execution 与 iOS runtime。原 policy、rc、APEX 和服务行为继续使用固定字节，报告原 KeyMint、Keystore 的实际进入程度及首个失败；完整 boot 成功继续按系统和桌面结果验收。

## 曾考虑的替代方案

- 把 `/data` 改为 tmpfs：能够检查当前写入，但无法验证停机后的数据恢复。
- 修改原 rc 的根只读挂载：会改变原启动行为，独立数据文件系统可以继续按原 rc 工作。
- 使用已有 Android 参照 AVD 或应用数据盘：这些文件承担已有实验和用户数据，采用新实验目录的数据盘。
- 同时扩展加密、quota、metadata 设备与 first-stage：这些要求涉及额外内核配置、启动输入和原 vold 路径。先检查当前明确的可写数据盘缺失，后续按原 fstab 验证这些实际依赖。

## 验收标准

1. 数据盘显式路径、大小和初始摘要可核对；只读、越界、重复打开及锁冲突保持现有 host contract，原只读分区摘要保持。
2. lifecycle CLI/GCD 在 guest Linux 挂载 ext4 并完成写入、fsync、跨入口读取和严格卸载，全部上下文回收。
3. original CLI/GCD 的 `/data` 写入越过 EROFS，原 Keystore SQLite 创建的实际返回及输出文件保持；原 policy、域转换和服务首个失败继续保存。
4. 原策略后的卸载结果、sync、fd 关闭、halt、host close 与内核释放分别可核对，原盘的 ext4 state/journal 和同盘恢复分别报告。
5. 实际生成 runner/execution 与两页 iOS 运行库编译成功；已有无数据参数的 SDK36/HyperOS 报告 contract 保持。
6. 按 reclaim-code-entropy 检查生命周期状态和输入表示，使用已有 slot 与 Linux 文件系统接口；技术文字按 humanizer-zh 审阅。

## 风险

原 PID 1 在已有系统服务失败后请求 namespace reboot，数据盘可能需要下次挂载回放 journal；宿主 fsync 只能提交已经传到 host block 接口的写入。持久化结论必须同时覆盖 Linux 同步、实际原盘内容与下次挂载。原 `/metadata` 分区、加密、quota、fsverity 和 fstab 启动条件继续作为完整系统的验收项。设备执行、资源和持续热状态按[离线开发目标](../../implemented/process/2026-11-12-离线开发目标与持续推送.md)保留待验证。
