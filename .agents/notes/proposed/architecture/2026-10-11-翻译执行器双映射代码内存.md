# 决策记录: 翻译执行器双映射代码内存

状态: proposed

## 问题

独立翻译执行器已在 Mac 运行完整 Android 桌面，iOS 产品仍使用原生 NCE。Linux 装载、Direct 和 Unicorn 当前分别创建可执行内存，尚未共同满足手机已有的 JIT 准备流程。具体缺口见[双核集成记录](2026-10-11-运行时执行器与双核Linux.md#ios-集成的当前缺口)。

`dod_ios_jit_prepare_range()` 要求在调试连接期间准备 16 KiB 对齐的 RX 映射，返回独立 RW 别名，然后断开连接并检查实际执行。Unicorn 2.1.4 的生成代码区同时保存 `TranslationBlock`、ARM64 指令、常量池和恢复状态表；只修改缓存分配函数会遗漏这些写入。Direct 用 Oaknut 在临时数组生成指令，最后统一复制，写入位置较集中。

## 提案

保留当前原生产品默认路径，翻译后端使用明确构建变体。先在 macOS 的 RX/RW 双映射上验证全部代码写入；本机成功后接入 iOS 的现有准备与断开连接流程。单核与双核是否采用该变体继续以完整桌面测量为准。

代码段的执行地址参与分支、恢复状态和函数指针计算，保持其含义。Direct 生成器继续按 RX 地址计算指令，通过对应 RW 地址复制。Linux 按 ELF 段区分代码与数据，重定位使用最终执行地址；数据保持普通可写映射。

Unicorn 先核对全部写入调用方，包括 `tcg_out*`、重定位、常量池、分支修改、`TranslationBlock` 分配、恢复状态表和缓存清理。指令生成指针保留 RX 地址语义，实际写入显式转为对应 RW 地址；块元数据和恢复状态表保存在普通数据内存，并随对应代码缓存清理。所有代码缓存须在启动 Linux 前准备，运行期间复用既有容量。iOS 断开调试连接后不临时申请新的可执行缓存。

## 曾考虑的替代方案

- 仅交叉编译当前 Mac 代码：仍依赖 `MAP_JIT` 或同址读写执行，缺少手机执行内存验收。
- 先扩展 Direct 覆盖并移除 Unicorn：现有桌面仍实际使用回退，需要另行实现指令与异常语义，无法直接删去。
- 运行期间按需向调试服务准备代码：改变已验证的手机生命周期，也增加执行期间的外部依赖。

## 验收标准

- Mac 的 RX 映射不可写，RW 映射不可执行；通过 RW 多次更新后，从 RX 执行得到当前结果。
- 覆盖两个缓存并存、边界失败、缓存复用、分支修补和销毁；Direct 与 Unicorn 的 CLI/GCD 回归均成功。
- 相同构建变体完成 Linux 核心、Bionic/ART、服务及真实可见桌面，记录配置、输入哈希和阶段耗时。
- iOS 包含匹配内核、执行器及系统镜像，全部代码区在断开调试连接前准备；实际设备检查集中到完整阶段产物。

## 风险

Unicorn 中代码指针兼用于写入和执行，遗漏任一写入会在只读映射上失败；错误转换分支目标还会跳转到错误地址。ARM64 宿主范围先单独验证，其他宿主不新增支持承诺。缓存容量和准备时间可能增加启动与内存成本，需保留测量结果后再选择产品配置。

## 本机进展

`nce_code_prepare_range()` 已从原生内存实现提取，继续保留原来的 iOS 准备调用。Mac 的独立测试检查 RX/RW 权限、相邻数据页、两个线程分别更新并执行代码、跨区域间接分支及准备失败，CLI/GCD 成功，结果在 `work/native-linux-nce/code-memory-tests/summary.json`。

Direct 和 Unicorn 通过 `--code-memory dual` 选择独立构建。Unicorn 使用单独源码、构建和安装目录，构建记录包含补丁及库的摘要。TCG 的执行指针保持 RX 地址，代码写入通过 RW 别名，最初 `TranslationBlock` 元数据也通过 RW 地址访问；后续服务检查暴露了该布局的性能问题，处理见下节。恢复状态表的偏移值保持原有含义。`work/native-linux-nce/direct-unicorn-dual-code-tests/summary.json` 的 CLI/GCD 独立检查全部成功。

独立执行器测试原先使用 `dispatch_sync_f`，调用可能在主线程内完成。此次改用异步 GCD 派发并断言所在线程。最初的两个软件信号转发检查失败；显式检查确认信号未被屏蔽，GCD 工作线程的 `pthread_kill(pthread_self(), …)` 返回 45（`ENOTSUP`）。这两项改用普通 pthread 发送信号并等待退出；实际读视图异常仍在 GCD 工作线程验证。失败产物分别保留于 `direct-dual-code-tests`、`direct-dual-code-worker-tests` 和 `direct-dual-code-thread-signal-tests`，成功结果见前述组合检查。

Linux 装载按生成的 ELF 段准备代码内存，保存原始字节后经 RW 别名恢复代码，再按最终执行地址重定位。该顺序保留 iOS 准备过程写入短测试代码之前的内核内容。`lkl-direct-dual-core/summary.json` 的双核核心 CLI/GCD 成功；`lkl-direct-dual-android/summary.json` 的 Bionic/ART CLI/GCD 成功。核心检查时写入跟踪关闭，Android 检查开启。均为本机功能检查，尚未评价完整桌面性能或手机运行。

## 复杂度审查

公共准备函数供原生代码、Direct 缓存、Unicorn 缓存及 Linux 代码段调用，返回已有 `NceCode` 类型。Linux 装载单独负责文件、重定位和段权限；执行入口继续负责 Linux 生命周期。Unicorn 的区域表只记录它实际拥有的缓存，分配、查找和释放通过互斥锁保护，缓存关闭要求对应执行器已停止。移除该表会失去上游写入位置到 RW 别名的转换依据；将每条写入改成依赖全局固定偏移则无法同时容纳两个独立缓存。当前先验证完整写入范围，转换锁的成本随后通过同负载对照评价。

## 服务失败与代码页数据布局调整

首次双映射服务检查和采样复现均在加密测试的既定期限内失败，数据盘正常卸载，用户上下文全部释放。结果在 `lkl-direct-dual-services` 和 `lkl-direct-dual-service-diagnostic`。同源 MAP_JIT 对照的服务 CLI/GCD 均成功，执行阶段分别为 22.184220 / 19.626310 秒，64 MiB AES-GCM 检查约为 6.818190 / 6.986311 秒；结果在 `lkl-direct-mapjit-service-control`。保留双映射内核和 Direct、仅使用原 Unicorn 的隔离构建也成功，AES-GCM 约为 7.089512 秒，构建参数记录在 `dual-code-isolation/summary.json`。以上用于定位失败，尚未作为成组产品性能结论。

开启 Direct 向量查表、恢复 Darwin 的线程代码权限切换，双映射服务仍失败，分别保留在 `lkl-direct-dual-service-tbl` 和 `lkl-direct-dual-service-permissions`。普通 Unicorn 整数、访存和原子微基准未出现明显差距。缩小到一百万次循环和写内存回调时，原构建约 0.06 秒，双映射约 7 秒；去掉 TBL 后差距仍在，去掉内存回调后两组均约 0.02 秒。采样主要停在读取块元数据和恢复状态表的位置，未集中在代码写入转换函数。

只将恢复表读取改到 RW 别名后，该用例约为 3.6 秒。进一步把块元数据和恢复表放到普通数据内存，用例降到约 0.034 秒，计算结果一致。当前确认的是该数据布局对本机回调用例的影响，尚未确定底层硬件或虚拟内存原因。最终实现保留 RX 执行地址和 RW 指令写入地址，数据分配归属各自的 Unicorn 缓存；清空块索引后释放对应数据，关闭一个执行器时不影响另一个。恢复表在生成时复制一次，运行期间直接读取普通内存。新增回归逐次核对内存回调中的 PC、寄存器和写入值，并检查块边界停止、缓存清空和两个执行器的独立关闭。

该选择增加了每个缓存的数据分配记录。调用方只有上游块分配和恢复表生成，释放点只有缓存清空和关闭；省去这些记录会失去失效块数据的统一释放时机。按块失效立即释放会违反 Unicorn 在当前块退出前继续持有元数据的生命周期，因此沿用代码缓存的整体回收边界。内存增量和完整服务/桌面结果继续测量。


## 当前验证结果与边界

最终构建的公共代码内存、原生执行回归、Direct/Unicorn 独立检查、双核核心、Bionic/ART 和服务均成功；支持的独立与 Linux 检查覆盖 CLI/GCD。服务执行阶段为 23.707202 / 22.935076 秒。可见桌面完成 Launcher、Clock、闹钟及 Files 检查，执行阶段为 334.124302 秒、清理 0.823640 秒，footprint 采样峰值为 3,470,758,304 字节；135 个图形连接和 1,130 个用户上下文全部释放，数据盘正常卸载。测量使用 Apple M5 Ultra、macOS 27.0（26A428）、双 CPU、1 GiB 客体 RAM，每 CPU 分别配置 128 MiB Direct 与 Unicorn 缓存，开启代码页写入跟踪，采用 2 ms 定时抢占。桌面执行时间包含启动、应用操作和等待。

结构化结果、配置、构建与产物摘要见 [macOS 双映射结果](../../../../experiments/native-linux/results-macos-dual-code-memory.json)。先前失败轮次也保留在该结果中。当前完成的是 macOS 功能及生命周期检查；桌面尚无相同构建的交替成组对照，不能据此确认性能收益。iOS 交叉构建、断开调试连接后的执行检查和完整产品集成继续推进，产品默认设置保持原值。
