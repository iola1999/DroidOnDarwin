# 决策记录: 后续提速与多核可行性评估

状态: proposed

## 问题

用户要求核对尚未实施的提速方向，并评估多核的可行性与复杂度。随后要求将可手动启停的实验设置纳入规划，便于比较可能产生收益或损耗的实现。本记录基于 2026-10-10 的 `94cf60a` 源码、现有测量和本轮上游调查；本轮交付为评估与规划，下面的候选尚未实施。

当前目标继续采用[原生 Linux 与 NCE](../../implemented/architecture/2026-10-08-转向原生Linux与NCE.md)，在 iPhone 内运行完整 Android，随后集成 HyperOS。Mac 承担构建、离线产物生成和本机验证。设备测试集中到可体验的阶段版本。

N4-D2 已实现已有数据页的快速恢复、减少页表扫描、程序二分查找及可选 MM 统计；之前也已实现 TLS 直接读取、返回入口缓存、代码页复用、Metal 图形和部分 ART JIT。它们的状态与测量见[桌面性能优化实施](../../implemented/architecture/2026-10-10-桌面性能优化实施.md)。本轮继续寻找这些改动之外的收益。

## 提案

### 优先判断

优先推进 ART 执行覆盖和匹配的预编译，并为同地址空间双核建立独立原型。完整跨进程并行需要额外的地址空间设计，复杂度最高。当前已经具备原生执行普通 ARM64 指令的路径，后续更大的收益主要来自减少解释执行、重复初始化、映射与同步开销，以及允许实际可并行的工作同时执行。

N4-D2 的 Mac 同构建单轮对照中，宿主进程创建至桌面就绪为 168.914 / 118.191 秒，条件为 Apple M5 Ultra、macOS 27.0 (26A428)、1 GiB 客体 RAM、360×640、demand、JIT 阈值 1024、关闭统计，沿用数据盘且未清除宿主文件缓存。该结果说明 MM 改动减少了启动等待；优化后各类 CPU 工作的占比仍需重新测量。现有累计映射墙钟、旧采样和组件计时无法给出当前可并行比例，也无法推算手机的持续帧率。

### 当前映射诊断与连续页恢复候选

桌面组件 AOT 对照未测到稳定启动收益，后续先复查优化后的主要开销，再确定 boot image 的实施范围。使用 `0.18.0` Mac 构建 7、nterp 开启、AOT 关闭的独立诊断轮，启用可选映射统计并采集宿主调用栈；其耗时单独记录，不参与关闭诊断的性能比较。原始文件暂存于 `work/native-linux-nce/profile-current/`。

该诊断轮已正常停止，无 Java fatal exception 或 ANR。五次采样均为 5 秒、间隔参数 5 ms；四个启动前段片段的非等待样本中，信号处理占 36.9%–44.0%，宿主映射占 29.9%–33.6%，两者合计 67.7%–73.9%。这些是采样分类，尚有 20.8%–28.0% 未解析原生地址；不能据此直接计算优化上限。整轮含就绪后的等待与操作，累计快速恢复 11,112,042 次、数据映射 11,530,281 次、映射窗口切换 42,795 次。详细结果见[当前映射诊断](../../../../experiments/native-linux/results-macos-current-mapping-profile.json)。核心至就绪为 281.094 秒，该轮开启了诊断，耗时仅作为运行记录保留。

当前 `restore_present_data()` 每次只恢复一页。下一项候选是在这个入口中一次恢复最多 8 页，即 128 KiB，限于普通堆与线程栈地址区间。相邻页面必须已有 PTE、物理页连续、权限一致、访问位已设置，且可写页已置脏；遇到空洞、权限变化、已安装映射或范围末尾立即停止。单个 Linux CPU 仍独占窗口，信号处理过程不分配 Linux 页面、不获取 Linux 锁、不调度。静态程序和动态执行区沿用现有单页入口。

该候选由 `faultPrefetch` 启动开关选择，初始默认关闭，沿用共享配置、Deep Link、环境变量与结果记录。只在实际缺页时检查后续页面，不新增每进程常用页缓存或完整宿主视图。已有页快速恢复和这一选项可以分别关闭；未满足快速恢复条件时继续走原缺页处理。新增统计只在性能日志开启时记录恢复页数。

验收覆盖 fork/COW、只读页、PROT_NONE、未分配页、取消映射后的再次访问，以及 CLI/GCD 完整桌面。功能成功后，按同包交替配置比较启动、阶段内存、映射次数和缺页次数；不以局部密集读写测试决定默认配置。公共 boot image 的重定位准备继续保留在 ART 记录中。

连续页恢复已实现。开启选项的 CLI/GCD 各通过 214 次命名检查，关闭选项后，同一核心的 GCD 也通过 214 次；均包含相邻页访问权限、fork/COW、完整桌面、Clock、Files、持久数据与正常退出。最后一次只读 ext4 检查成功。`0.19.0` 的 Mac 构建 8 与 iOS 构建 88 已生成，宿主界面生命周期、共享设置、Deep Link 请求、内存采样、签名及资源检查成功。两端本轮未加入 SystemUI/Launcher AOT 文件，IPA 为 473,424,128 字节，SHA-256 为 `a1f1dac7ab21c047768d332d224f233720adcd6028235a5745b98ecd07c9583c`；手机执行待集中验证。[功能结果](../../../../experiments/native-linux/results-macos-fault-prefetch-functional.json)保留实际配置、源码/资源哈希与三轮检查。正式同包性能对照已完成，选项保持默认关闭。

正式对照使用同一 `0.19.0` Mac 构建 8、Apple M5 Ultra / macOS 27.0 (26A428)、1 GiB/单 CPU、360×640、demand、JIT 阈值 1024，开启 nterp 和内存采样，关闭 AOT、扩展 JIT、快速基线及详细诊断。首次系列的关闭配置耗时 108.991 秒，随后开启配置约 300 秒时因 Launcher 未报告完成绘制而中止。窗口已可见且获得焦点，但 `reportedDrawn=false`、`firstWindowDrawn=false`；宿主正确识别进程退出并停止矩阵。数据盘随后由 `e2fsck -p` 恢复日志与孤立 inode，`-fn` 检查成功，再沿用该盘完成六轮交替对照。首次失败单独保留，尚未确认是否由连续页恢复引起。

重跑顺序为关闭、开启、开启、关闭、关闭、开启；各轮都完成就绪、输入提交和正常停止。关闭时启动为 123.185 / 269.113 / 220.180 秒，开启为 173.992 / 192.187 / 226.156 秒，中位数为 220.180 / 192.187 秒。关闭/开启的启动 footprint 采样平均值中位数为 1390.342 / 1408.713 MiB，采样峰值为 1976.395 / 1971.989 MiB。两组波动均大，当前样本不足以确定稳定收益；不据此改变默认配置。一次关闭配置记录 `binding to KeyChainService timeout`，最终仍启动成功。所有事件中的宿主热状态为 nominal、低电量模式关闭，末次 ext4 只读检查成功。

[正式 App 对照](../../../../experiments/native-linux/results-macos-fault-prefetch.json)保存首次失败、重跑样本、各阶段内存、组件计时及原始文件哈希。两组均沿用数据盘与宿主文件缓存，期间没有并行构建或其他 NCE 会话；本轮没有帧率、应用响应延迟或 iPhone 性能结论。后续继续公共 boot image 与地址空间设计，慢启动原因仍需独立诊断。

复杂度检查：实现继续以 Linux PTE 和现有 installed/desired 为准，只增加一个启动布尔值与一个可关闭计数，不新增每进程缓存。页数上限固定为 8，先用启停对照确认收益，再决定是否需要扩大参数范围。移除相邻页权限和访问/脏页检查会扩大信号入口承担的内存语义，因此保留；新回归在邻页访问后实际触发禁止读写，并核对父进程私有值。统计 `fast_restored_pages` 与 `fast_faults` 的差值仅说明额外恢复了多少页，不能说明这些页后来都被使用。

### 实施状态

用户已授权依次实现。本轮从 `a6d00d6` 开始，nterp 和两端 benchmark 入口已完成本机验证；普通 Mac App 六轮交替实验的启动中位耗时减少 8.9%。扩展 JIT 已完成本机功能检查；普通 App 六轮对照中，启动中位数为关闭 99.043 秒、开启 99.057 秒，本轮没有测到启动提速。快速基线编译已完成 CLI/GCD 与正式 App 检查，本轮未测到启动提速，继续默认关闭。benchmark 已加入各阶段内存的平均值、峰值和最新值，876 个正式 App 样本与原始序列核对成功，用于比较后续参数。 后续已完成可重定位 AOT 和两个桌面组件的实际装载；同包 AOT 开关已通过功能回归，正式 Mac App 六轮对照的启动中位数为关闭 93.039 秒、开启 94.033 秒，开启时启动内存较高，本轮未测到稳定启动收益。后续先推进公共 boot image 与映射、调度，停止扩大逐应用 AOT 实验。具体实现、测量范围与剩余工作见 [ART 优化记录](2026-10-10-ART解释执行与编译优化.md)和[实验自动化记录](../../implemented/testing/2026-10-10-两端性能实验自动化.md)。下表保留最初缺口，用于跟踪后续顺序。

用户进一步要求评估 AOT 对 APK 复用与兼容性的影响。后续保留通用解释/JIT 路径；系统组件预编译先做有限对照，是否扩大按整机收益决定。公共 boot image、JIT 覆盖、映射与调度继续作为通用方向。新 APK 携带的原生库需在手机内动态准备，详见[应用复用约定](2026-10-10-ART解释执行与编译优化.md#应用复用与运行时编译)。

### 尚未实施的方向

复杂度按需要共同改变的契约与验证范围判断。表中收益描述为适用条件下的可能结果，尚无相应整机对照。

| 方向 | 当前缺口与具体工作 | 可能改善的部分 | 复杂度与顺序 |
| --- | --- | --- | --- |
| ARM64 nterp 汇编解释器 | 构建启用 `ART_USE_RESTRICTED_MODE=1`，`IsNterpSupported()` 返回 false。适配 32 位对象引用加高地址基址、数组、调用、异常、JNI、栈扫描和标记寄存器约定 | 首次执行、尚未达到 JIT 阈值的方法、编译未覆盖的方法；若这些路径占用较多 CPU，有较大收益空间 | 高；优先。涉及解释器、Quick ABI、GC 和现有 JIT 的共同约定 |
| 扩大 JIT 覆盖、接入快速基线编译 | `CompilationFilterForRestrictedMode` 仍拒绝部分 IR，`ART_NCE` 下快速基线编译被显式关闭。先统计热点方法的拒绝原因，再适配实际命中的路径与对应 intrinsic；单独评估快速生成机器码的编译器 | 热点方法的稳态执行、较早进入机器码、减少编译线程占用；更积极编译也会增加内存与 CPU 开销 | 高；与 nterp 共用引用及调用回归，按真实热点推进 |
| 匹配修改版 ART 的 boot image、AOT 与持久编译结果 | 当前使用 `/data/no-boot-image.art`、`-Xnoimage-dex2oat`，系统缺少完整 AOT 接入。生成并装载匹配的 boot image/oat，处理高地址引用、重定位、方法入口、执行区登记及构建失效条件 | 冷启动、应用启动、反复执行相同初始化和重复编译，可能同时减少耗电 | 高；优先。AOT 仍受编译覆盖限制，不能只更换现成文件 |
| 按地址空间组织执行，减少切换和权限操作 | Linux 内核已经通过 RAM 别名复制用户数据；宿主用户窗口仍在不同 mm 之间反复恢复。评估有限的同 mm 调度偏好、Binder 往返与窗口恢复时机，以及旧别名释放后采用更少的保护操作 | 服务交互、频繁 Binder 往返和应用切换；可能减少大量映射，过度偏好同 mm 会增加其他进程等待 | 中至高；保持服务优先级和公平性，先记录等待与切换关联 |
| 同地址空间的客体线程并行 | 当前单 Linux CPU、共享 active 状态和信号目标仅允许一个客体线程执行；具体路线见后文 | 单个 Android 进程中的主线程、RenderThread、GC、JIT 和工作线程在确实可同时执行时的吞吐与响应 | 很高；值得做双核原型，整机收益待测 |
| 为不同进程重做地址转换，支持跨进程并行 | 让同一客体地址在不同 mm 下解析为不同宿主地址，覆盖数据访存、代码地址、原子指令、信号、JNI 和 JIT 生成代码 | 应用、system_server、SurfaceFlinger 同时执行，并可能减少进程切换重映射 | 最高；需要独立验证转换开销，暂不直接替换当前执行方式 |
| 共享图形缓冲区和更少的同步往返 | 现有 gralloc 使用 memfd，CPU 读写经 `rcReadColorBuffer` / `rcUpdateColorBuffer` 传输。评估与宿主 Metal/IOSurface 的共享资源及 fence 生命周期 | 内容传输占比较高时的帧时间、带宽和 CPU 开销；对以 Java 初始化为主的等待作用有限 | 高；先测实际帧的传输字节与等待，当前已使用硬件 GPU |
| RAM、文件承载与回收协同 | 当前 RAM 已从 512 MiB 增至 1 GiB；更大容量、文件承载及别名回收仍待实施 | 内存压力导致的回收、GC、应用结束及重新启动；访存换页也可能增加延迟 | 中至高；依赖手机预算，详见[容量方案](2026-10-10-NCE内存容量与文件映射方案.md) |
| 启动服务与产物加载 | 测量 ELF/资源装载、重复类初始化、服务重试及实际等待；对不影响依赖的工作评估延迟初始化或批量处理 | 缩短启动准备和无效等待；依赖真实阶段计时 | 中；保留系统功能和错误可见性，与 ART 启动对照结合 |

boot image 的预初始化对象与 AOT 的机器码可以分别验证。Mac 构建时预生成匹配产物，随 IPA 交付后由手机独立运行，符合现有目标。NCE 的实际地址基址与对象编码必须纳入重定位设计；在 Mac 上生成包含宿主绝对地址的代码后直接复制到手机会产生错误。优先使用 ART 的标准 profile/AOT 产物，不另建未经验证的 JIT 堆内存序列化格式。[AOSP ART 配置](https://source.android.com/docs/core/runtime/configure)与[JIT/AOT 工作方式](https://source.android.com/docs/core/runtime/jit-compiler)提供产物职责与选择条件。

### 多核的实际阻塞

**iPhone 上运行多个宿主线程具备实现基础，当前限制集中在 LKL/NCE 的执行设计。** 多核原型可以先在 Mac 验证并发正确性；iOS 的多线程 JIT、信号与热状态最终仍需集中验证。

本地 LKL 源码由 [probe_lkl.py](../../../../scripts/probe_lkl.py) 固定到 `d0f76a77e8c2ca68bd7d96190b8da09040eab072`，并由 [lkl_nce_patch.py](../../../../scripts/lkl_nce_patch.py) 加入本项目扩展。本轮检查了生成树中的 `arch/lkl/kernel/cpu.c`、`threads.c`、`include/asm/thread_info.h` 和 `Kconfig`：

1. **单 CPU 内核入口。** `struct lkl_cpu cpu` 保存单一 owner 和等待队列，`_current_thread_info`、`abs_prev` 为全局状态，`__switch_to()` 通过信号量移交运行权。Kconfig 仍依赖 `!SMP`。现有 pthread 数量可以很多，但客体执行由一个 Linux CPU 串行调度。
2. **共享用户虚拟地址。** `active_mm`、`installed`、`desired` 和 `view_chunks` 描述唯一宿主窗口。进程 A 与 B 的同一地址可以对应不同物理页；宿主进程的一套页表无法让两个线程同时以该地址读取不同内容。为 C 变量增加线程局部存储，仍需另外解决这一地址冲突。
3. **共享 NCE 上下文入口。** [lkl-process-host.c](../../../../experiments/native-linux/lkl-process-host.c) 有单一 `active`、`target_thread`、恢复入口与代码缓存。[nce.c](../../../../experiments/native-linux/nce.c) 生成的系统调用/TLS 分支还嵌入 `active` 槽地址。并行化要同时改变生成代码、抢占目标、返回入口和资源生命周期。
4. **依赖单 CPU 的内存与代码更新。** 当前信号内快速恢复依赖 PTE 在恢复期间稳定；用户数据复制和代码恢复也写有单 CPU 条件。SMP 后必须协调缺页、COW、取消映射、内存回收、JIT 写入及指令缓存同步。信号处理器中等待一个可能被该信号打断的线程所持有的锁，会产生死锁风险。
5. **Android 多线程语义。** futex、线程退出、定向信号、抢占、GC 暂停、方法替换与内存屏障都需要在真实同时执行下检查。用户态和内核态之间必须有明确的所有权交接，阻塞调用不能占住其他线程完成工作所需的运行权。

### 可以复用的 SMP 历史实现

找到 [Rover-Yu/lkl-linux 的 smp 分支](https://github.com/Rover-Yu/lkl-linux/tree/smp)，本轮经 GitHub API 核对其提交为 `f731f30a95e5006dd94e4e1e16969a9589206318`，日期为 2017-11-06，Makefile 为 Linux 4.13.0。源码包含每 CPU 的 `cpus[NR_CPUS]`、TLS CPU 编号、每 CPU current、IPI 及原子操作/自旋锁适配。[作者 2018 年演讲](https://events19.linuxfoundation.cn/wp-content/uploads/2017/11/LKL_-Another-Way-to-Reuse-the-Linux-Kernel_Yu-Li.pdf)说明原型曾运行于 x86_64 与 AArch64，并列出时钟、IPI、RCU 和宿主接口改动。

这些内容可作为移植参考。当前项目基于 Linux 6.12，并新增了用户进程、MMU、Darwin 信号和 NCE；历史原型主要复用网络与文件系统，未覆盖这里的 Android 多地址空间。需要在当前内核上重新实现与验证，不能直接合入旧分支后承诺完整系统多核。

### 多核路线比较

| 路线 | 可行性判断 | 主要工作与限制 |
| --- | --- | --- |
| 单 CPU 内核继续串行，允许同 mm 用户线程并行 | 原理上可行，适合作为候选原型；内核入口仍有串行限制 | 必须改变 Linux 对当前运行任务的记账、用户态离开/返回内核的交接、阻塞和唤醒语义。不能只在 `nce_enter()` 前释放 CPU 锁；需要核对调度器与同步代码对 UP 的假设 |
| LKL SMP，加同 mm 的用户态并行约束 | 推荐的长期双核原型方向；已有内核 SMP 工作可参考 | 先完成每 CPU 内核状态、时钟、IPI、原子/锁及 RCU，再允许同 mm 的客体线程并行。换到其他 mm 前必须使当前窗口使用者全部停止并确认，公平性和 Binder 唤醒需要一起设计 |
| LKL SMP，加每进程软件地址转换 | 原理上可行，尚缺低开销原型 | 在加载/生成 ARM64 代码时改写访存与相关地址操作，让不同 mm 使用各自宿主映射。覆盖普通、成对、SIMD、原子及跨页访问，动态代码和故障恢复也要适配；额外指令可能抵消并行收益 |
| 每个 Android 进程使用独立宿主进程 | 宿主页表适合承担隔离，但当前普通侧载 iPhone 缺少适用的进程创建路径 | Apple DTS 明确说明 iOS App 不能自行派生子进程。Mac 上的实现无法直接作为手机交付路线，现有内置 JIT 授权也未提供该权限 |

平台限制来源：[Apple DTS 对 iOS 子进程的说明](https://developer.apple.com/forums/thread/747499)。这里描述普通 App 运行条件，尚未在本轮尝试其他系统权限环境。

同 mm 并行可以让同一应用的主线程与 RenderThread/JIT/GC 工作线程同时执行，也可以服务 system_server 内部的线程池。实际受益还取决于这些线程是否就绪、是否争用锁、是否在等待其他进程。应用与独立 SurfaceFlinger 的同时执行仍受窗口限制。

给每个进程分配不同的加载基址只能处理部分装载问题。fork 后内存中的绝对指针、匿名映射、JNI 指针和已有代码仍保留原地址。若要保留任意 Android 二进制和 fork 语义，需要完整的指针/访存转换或独立宿主页表；仅调整 ASLR 或 ELF relocation 覆盖不足。

### 双核原型的工作分解

推荐沿 LKL SMP 路线递进，先限制为两个虚拟 CPU。虚拟 CPU 使用宿主线程，实际硬件调度继续由 iOS/macOS 管理。

| 阶段 | 可交付结果 | 主要验证 |
| --- | --- | --- |
| M0：测量并行需求 | 按需记录就绪线程、所属 mm、运行/等待与窗口切换，得到同 mm 可重叠执行的时间范围 | 关闭采集时的开销；墙钟、线程 CPU 时间和并行区间分开统计 |
| M1：LKL 双 CPU | 当前内核的两个 CPU 能运行内核任务，完成系统调用、时钟和 IPI；客体用户代码继续串行 | per-CPU/current、任务迁移、锁与原子操作、RCU、阻塞 I/O、退出与关机 |
| M2：同 mm NCE 并行 | 两个 Linux 用户线程真实同时执行，线程局部入口/TLS、信号目标和返回状态正确 | 原生计算重叠、futex、寄存器/NEON、定向信号、抢占、JIT 发布；不能只根据宿主线程数判断成功 |
| M3：映射并发与进程切换 | 同 mm 并行期间安全处理权限、COW、unmap、回收与代码修改；可公平切换到其他 mm | 取消映射竞态、fork/exec、mprotect、缺页与线程退出交错、跨进程 Binder、饥饿和死锁 |
| M4：Android 与设备集成 | ART GC/JIT 与真实桌面在双核下运行，保留单核对照配置，形成一个集中验证版本 | 启动、应用操作、帧时间、内存、持续功耗与热状态，以及 CLI/GCD/手机生命周期 |

M1 之前先完成最小的每 CPU 执行上下文边界；避免为尚未验证的任意核数、CPU 热插拔或可插拔调度器增加公共配置。M2 阶段若现有快速故障路径无法满足并发条件，应使用已同步的普通路径，待正确性检查成功后重新优化。

M0 的首轮实现计划使用可关闭的低频就绪线程采样：在 Linux 返回用户态的安全位置，统计当前 mm 之外、同一 mm 之内的其他就绪线程，以及就绪内核线程。采集关闭时跳过时钟查询与线程遍历；开启时限制采样频率，复用现有性能日志输出累计结果，记录采集自身耗时。线程列表读取遵守 Linux 的生命周期约定，不在宿主信号栈中遍历，也不新增调度策略。用计算线程和阻塞线程的受控负载检查分类，再采集真实桌面启动与应用操作。

这种采样只描述被采样时刻的就绪情况。线程可能随后争用锁或等待其他进程，Linux 仍在执行的系统调用也会影响采样间隔，因此不能直接将同 mm 有其他就绪线程的样本比例代入加速比公式。先与窗口切换、访存恢复和组件耗时一起判断双核与调度改动的优先级，再实现 M1；目前尚无采样实现或结果。

同 mm 调度还需要处理等待顺序：当该 mm 的线程进入阻塞系统调用后，必须允许完成其依赖的其他进程运行；更换窗口不能在持有对方所需的内核锁时等待全部线程退出。内核可通过 RAM 别名访问其他 mm 的用户页，但当前 PTE 生命周期和复制实现也必须按 SMP 重新检查。

复杂度主要在 M2/M3 的跨层并发语义，以及 M4 的 GC/JIT 与热状态回归。编写双核计数器示例无法覆盖这些条件。工作量以这些可验收阶段跟踪，当前缺少支持精确工期或整机倍数的测量。

### 多核收益的上限与热状态

如果当前耗时中可并行部分占比为 p，串行部分保持不变，n 个等速核心且没有协调成本时，理想加速比为 `1 / ((1-p) + p/n)`：

| 假设可并行占比 | 双核理想加速比 | 四核理想加速比 |
| --- | ---: | ---: |
| 50% | 1.33× | 1.60× |
| 80% | 1.67× | 2.50× |
| 90% | 1.82× | 3.08× |

这些是公式示例，当前 Android 的 p 尚未测得。同 mm 限制会缩小可并行范围；映射协调、锁争用、宿主调度及发热降频还会增加耗时。多核可能缩短完成时间，也可能增加持续功耗；需要记录相同工作量的耗时和热状态，不能根据瞬时 CPU 使用率选择默认核数。

### 实验设置与 benchmark

用户于本轮要求为收益尚不确定的优化保留手动启停方式。规划采用以下规则：

1. **设置在会话启动前应用。** 解释器选择、CPU 数量、映射策略、RAM 与图形缓冲路径在 Android 停止后更改，下次启动生效。已启动时显示实际生效配置；避免在仍有客体线程和资源时替换执行策略。
2. **同包对照优先。** 能在同一二进制、相同 ABI 下共存的实现提供实验设置和对应 CLI 参数，复用现有 `NCE_DIRECT_FAULT`、`NCE_SPARSE_SCAN`、`NCE_MAP_PROFILE` 的对照方式。界面与 CLI 使用同一组取值与默认值；代码中只保留一份生效配置。
3. **编译约束明确显示。** 内核 UP/SMP、ART 对象布局、寄存器约定或无法共存的执行区设计通过构建变体比较。只有两个路径共同满足运行契约后，才提供普通启动开关；仅改变布尔值不足以安全启用 nterp、AOT 或多核。
4. **候选逐项接入。** 预计候选包括汇编解释器、快速基线编译、AOT/boot image、单/双 CPU、映射策略、图形共享缓冲与 RAM 容量。实际名称和是否能同包切换由实现决定；尚未实现的设置不加入可操作界面。boot image 与 AOT 分别标识，缺少匹配产物时说明所需构建。
5. **校验依赖和实际状态。** 例如并行 NCE 需要并发安全的 MM 和代码发布；AOT 需要匹配的 ART、DEX、ISA 与引用布局。无效组合在启动前报告，不能静默忽略请求。由运行时决定退回某条路径时，日志记录请求值、生效值和原因。
6. **保留固定对照。** 一组实验只改变一个独立变量，先比较同包开/关；有依赖的改动按完整组合比较并注明组成。SMP 应分别比较现有 UP、SMP 构建只运行一个 CPU、SMP 构建运行两个 CPU，以区分 SMP 自身开销和并行收益。
7. **记录可复现配置。** benchmark 输出构建 ID/源码与产物哈希、设备/系统、请求与生效设置、负载、分辨率、RAM、ART 产物、数据盘冷热状态、统计状态及测量范围。允许导出当前配置，离线分析按配置分组；热状态、前后台和缓存无法固定时一并记录。
8. **统计按需开启。** 默认关闭高频计时、逐方法日志和调度跟踪。优先使用按线程或按 CPU 累计的计数、稀疏采样和低频汇总，避免每次访存或每条解释器指令进行原子计数。需要低级时间源时在开启分支内读取。诊断轮次与关闭诊断的性能轮次分开，实际测量统计开销。
9. **以成组样本判断。** 同负载交替运行基准与实验配置，记录各轮结果、中位数和范围；首次运行、重复运行和持续交互分别比较。后台温度或宿主负载变化时保留原始结果并注明。实验组合数量按依赖限制，避免枚举全部开关组合。
10. **设置生命周期随结论更新。** 未确认收益的实验默认保持当前已验证实现；有稳定收益且完成兼容回归后再改变默认值。失败实现的源码移除时，其设置、测试专用分支和文案一起清理，实验结论留在记录中。可再生成 AOT 等产物按构建失效规则替换并清理旧版本。

这些设置用于验证已经实现的不同执行方式。多核中的锁、权限校验、GC 屏障等正确性要求不作为可独立关闭的性能选项。当前桌面模式已经跳过基础进程、ART 和图形专项回归，继续保留独立回归入口；无须把跳过这些测试重新列为启动提速候选。

### 复杂度审查

按 reclaim-code-entropy 核对新增状态的实际使用方和必要性：

- 多 CPU 的 current、运行权、抢占目标及入口状态分别服务正在执行的 CPU/线程，必须有明确所有者；仅把全局结构复制两份无法建立正确的地址空间关系。
- 唯一宿主窗口仍只需一个所属 mm 与使用者集合。额外增加每 CPU 的独立窗口标记却继续操作同一地址，会形成不一致状态，应排除。
- 采用 Linux 现有 SMP 调度、同步与标准 ART profile/AOT 格式，减少自建调度器、私有持久 JIT 格式和第二套对象引用规则。
- 先做双核与明确的开关组合；任意核数、策略插件和通用配置框架没有当前使用方。本轮不为规划添加这些代码。
- 思想实验：移除同 mm 使用者退出确认后，另一个进程映射会改变仍在运行线程的数据；该同步必需。移除复杂策略注册表后，固定的单/双核和现有映射对照仍可运行；该抽象暂不需要。

## 曾考虑的替代方案

- 只开启 `CONFIG_SMP` 或新增 pthread：缺少每 CPU 状态、并发入口和地址隔离，无法形成正确的 Android 多核执行。
- 从单 CPU 内核解锁后直接运行多个用户线程：保留为研究候选，但需要改写 Linux 任务运行与返回约定；长期优先比较标准 SMP 结构的维护成本。
- 同时启动多个独立 LKL 内核：各自拥有进程、Binder、文件与内存状态，无法直接组成当前 Android 系统；需要额外重做系统共享语义，暂不采用。
- 为每个进程更换 ELF 基址：不能处理任意已存储指针与 fork 后地址相同的语义，单独使用时覆盖不足。
- 每次开机重新降低 JIT 阈值：已有 16/1024 对照未改善启动，优先处理执行覆盖与预编译。
- 继续扩大热页预恢复：512 页缓存和批量数据视图已出现退化，见[批量切换记录](../../rejected/architecture/2026-10-10-进程数据视图批量切换.md)。新的方案必须说明解决了当时的哪项成本。
- 把所有实验都做成运行中切换：当前映射、代码和对象布局有会话级约束；启动前配置与明确的构建变体更易验证和维护。

## 验收标准

本轮评估完成条件为：核对当前开关和执行限制，给出未实施方向、适用负载、复杂度、上游参考及原型顺序，并记录用户提出的实验设置要求。本轮未执行新的性能实验，未改变运行代码。

后续实施按以下结果推进：

1. ART 原型覆盖对象、数组、方法调用、异常、JNI、GC 根与线程暂停；检查热点方法实际进入候选执行方式，比较真实 SystemUI/Launcher 启动和操作。不同方案独立对照。
2. 多核先完成 M1–M3，本机验证真实执行重叠、并发正确性及与单核相同的语义，再集成 ART/Android。保留 CPU 时间与墙钟区别，并检查调度公平性。
3. 图形候选记录每帧上传/读回字节、CPU/GPU 等待和显示提交间隔，检查跨进程句柄、像素及释放；内存候选检查 footprint、回收、前台应用存活和持续操作。
4. 实验设置检查默认值、依赖冲突、重启生效、配置导出和日志中的实际值；CLI 与 iOS 使用相同配置含义。关闭诊断的性能对照独立运行。
5. 完整集成后交付一个阶段 IPA，集中检查手机启动、应用切换、帧时间、内存与热状态。已有目标没有绝对 FPS 或倍数阈值，新增保证值需要用户确认。

## 风险

nterp、AOT、SMP 都会改变现有 ABI、引用或并发约定，单一计算测试通过仅覆盖对应路径。多核还会使现有单 CPU 下难以出现的竞态实际发生，并可能增加峰值内存与发热。软件地址转换的性能方向尚不确定，需先测单核新增开销，再评估跨进程并行能否抵消它。

现有 SDK Android 的结果只覆盖当前系统内容。HyperOS 组件、原生库和工作负载加入后，热点与资源需求可能改变；届时用同一套可复现实验配置重新评估优先级。
