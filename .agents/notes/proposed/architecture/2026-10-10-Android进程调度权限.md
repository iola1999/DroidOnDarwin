# 决策记录: Android 进程调度权限

状态: proposed

## 问题

完整 Android 日志反复报告 system_server 写入 `/dev/cpuctl/top-app/tasks`、foreground 和 background 分组失败，错误为 Permission denied。文件已设为 system 所有、0664。LKL 固定源码的 `__cgroup1_procs_write` 只允许 root 或目标进程相同 UID，system_server 使用 UID 1000，应用使用独立 UID，因此跨 UID 操作仍被拒绝。

## 提案

移植 [Android 16 / 6.12 的权限条件](https://android.googlesource.com/kernel/common/+/e65d894191a4f781c98ca3fe40d147d058483419/kernel/cgroup/cgroup-v1.c)：保留原有 UID 检查，并允许在目标用户命名空间拥有 `CAP_SYS_NICE` 的调用者操作。文件打开权限、SELinux 和控制器的迁移检查继续执行。

在已有 cgroup 初始化后运行行为回归：应用进程使用 UID 20001；管理进程使用 UID 1000，先确认无有效 capability 时跨 UID 写入失败，启用 `CAP_SYS_NICE` 后成功，移除后再次失败。读取实际 `/proc/<pid>/cgroup` 确认目标位于已选择的分组，结束全部测试子进程。

## 曾考虑的替代方案

- 修改 tasks 文件权限：现有文件权限已允许 system 写入，不能解决内核迁移的 UID 检查。
- system_server 使用 root：扩大权限且改变 Android 进程身份，未采用。
- 直接允许 UID 1000：绕过了 Android 原有 capability 条件，未采用。

## 验收标准

跨 UID 成功与失败边界均通过；完整启动中的 CPU 分组权限错误消失。前台响应是否改善需要实际交互测量，暂不预估幅度。

## 风险

该条件涉及调度权限，必须保留无 capability 的拒绝检查。修复权限后，分组的默认 CPU 权重仍需根据实际需求独立评估。

### 首轮回归（2026-10-10 07:33）

`android_cgroup_cross_uid_permissions` 已通过：管理进程使用 UID 1000，有效 `CAP_SYS_NICE` 开启时成功移动 UID 20001 的进程，关闭时两次写入均被拒绝，`/proc/<pid>/cgroup` 显示目标位于 foreground。完整 system_server 启动继续验证。

实现只增加 Android 内核已有的 capability 条件。回归使用实际进程、现有 cgroup 文件与 capset，测试进程结束前均被回收；未增加产品配置或独立调度服务。
