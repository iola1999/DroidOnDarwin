# 决策记录: 运行时 ARM64 代码块执行

状态: proposed

## 问题

运行时 ELF 解析与 Unicorn 软件 TLB 已经通过 Android 桌面检查，宿主不再需要登记该轮装载的每个 ELF。然而实际 128 MiB 缓存下，完整桌面检查仍耗时约四分钟、footprint 采样峰值约 2.7 GiB。ART 中全量/按页 TLB 对照的耗时中位数仅相差约 4%，说明减少地址转换缓存刷新只能处理一部分成本。当前产品继续使用原生 NCE；两种执行路径尚无同条件整机比较。

用户要求通用 APK 安装不依赖逐 APK 的源码或宿主重新构建，同时允许大规模改动以改善性能。下一项执行器候选应同时验证运行时新代码与真实 Android 计算，不能只改善小型循环后就更换产品默认路径。

## 提案

先在独立 Mac 原型中评估直接生成 ARM64 代码块的执行器，复用当前原生 Linux 内核、运行时 ELF 解析、PTE 查询、信号及代码发布协议。普通整数、浮点和 SIMD 指令直接生成等价 ARM64 指令；PC 相对寻址、控制转移、x18、系统调用和访存按客体语义处理。访存继续转换客体地址，保留 fork/COW 的原始指针值和 Linux 进程语义。这个候选需要与普通访存直接使用宿主地址的 NCE 区分，后者继续面临用户窗口切换成本。

当前 Git 历史保留了旧 Direct 执行器：整理提交 `825735e` 的父提交中，`src/arm64-exec/husk-arm64-direct.cpp`、入口汇编和对应检查仍可读取。先按新调用方检查可复用的指令处理、寄存器同步与代码缓存部分；旧 QEMU 接口、EL1、PAC、bulk、构建及无调用方的选项不自动重新引入。缺少的指令可先由现有解释器执行并记录出现次数，常见指令再按实际负载补齐。执行器对所有 APK 使用相同规则，保留输入文件和签名。

旧阶段已有整数/访存、FP/SIMD、原子、内存异常、代码失效和代码缓存检查；其执行条件是 QEMU 内核与旧映射接口，详见[历史实验](../../implemented/testing/2026-10-07-QEMU与早期NCE实验记录.md)。旧整机未达到可用性要求。本次评估的变化是 Linux 内核和系统调用原生执行，用户页已能直接通过 Linux PTE 转换；需要重新测量这些条件下的执行成本。

### 本轮补充资料

- [Frida Stalker 的 ARM64 说明](https://frida.re/docs/stalker/)与[当前 Stalker API](https://frida.re/docs/gum/class.Stalker.html)提供运行时基本块解码、重定位、缓存和分支连接的实现参考。默认缓存按线程维护，与当前单个 Linux CPU 复用执行器的生命周期不同；直接接入需重新处理线程、代码授权和缓存回收。
- [Frida 16.1.3 的独占访存修复说明](https://frida.re/news/2023/07/14/frida-16-1-3-released/)说明，块边界和插入回调会影响独占访问序列，可能导致循环无法结束。新执行器必须继续覆盖原子循环与抢占，不能只检查单条 LDXR/STXR 的结果。
- [Dynarmic A64 配置](https://github.com/azahar-emu/dynarmic/blob/master/src/dynarmic/interface/A64/config.h)提供页表、fastmem、跨页检查及访存后停止等选项。旧阶段已修复过它的访存异常状态问题，重用时必须核对原修复及当前实现，不能依据配置项名称推断完整 Linux 信号恢复正确。

这些资料于 2026-10-11 核对，说明已有可参考的实现。独立执行器与 Android 本机检查的进度见下节。

### 独立执行器实施

2026-10-11，在 `experiments/native-linux/direct/` 复用历史 Direct 的指令校验、寄存器分配和 ARM64 生成部分，按解码、代码生成、执行缓存、汇编入口和检查程序拆分。新调用接口接收客体状态、RAM/代码页映射及映射代次；数据页支持 4 KiB 和 16 KiB，代码按 4 KiB 处理。当前使用单 Linux CPU 的执行约束，Mac `MAP_JIT` 内存先用于独立测量。

生成器依赖固定版本的 Oaknut 头文件 `94c726ce0338b054eb8cb5ea91de8fe6c19f4392`，与历史 Direct 对应的 Dynarmic 子模块一致。构建脚本校验下载压缩包 SHA-256 `c404db82002f9a851a412b3d55ac9be8a42a2e319fd2fc8a73e63e6ef5d4f97b`。Unicorn 继续作为现有执行对照，候选生成器不依赖其内部代码生成接口。

代码缓存先使用有容量限制的连续分配，容量不足时在返回宿主后清空；每次进入新代码页前校验执行权限及原始内容。读映射仅在调用方代次、身份、回调及页大小相同时复用；本次调用首次进入一个物理代码页时清空写映射，并拒绝后续写入已执行的物理代码页。跨数据页的单条访存返回原 PC，由 Unicorn 处理；16 KiB 模式允许一次访问跨越页内的 4 KiB 边界。这个阶段先检查完整状态和访存边界，缓存回收策略随真实工作集继续评估。

已完成第一轮 CLI/GCD 检查：65,536 条随机整数指令对照全部 GPR/SP/NZCV，930 种访存寄存器组合，32,768 条浮点/SIMD 指令对照四种舍入方式和 FPSR，以及 TLS/x18、写保护重试、跨页访问、代码物理别名、代码替换、跨页间接调用和自循环预算。对照执行器为 Unicorn 2.1.4。初版独立计算在相同 ARM64 字节下完成结果与内存比较，数组读写耗时约为 Unicorn 的 44%；该版本尚未加入异步停止检查，完整参数和后续结果另行记录。

随后通过 `probe_lkl_translation.py --execution direct --mapping pte` 接入现有内核及负载。执行器使用 Linux PTE 回调，系统调用直接返回 Linux；不支持的指令先交由 Unicorn 执行到下一次 Linux 返回，保留这一段内部的独占访存状态。定时请求只写原子标志，生成代码在基本块入口和间接分支处检查；间接分支也需要检查，因为其目标可能处于静态块内部。基础 CLI/GCD 和 Bionic/ART CLI/GCD 已成功，原始结果位于 `work/native-linux-nce/lkl-direct-core` 与 `lkl-direct-android`。

初版 Android 对照中，ART VM CLI/GCD 分别为 2869.809 / 2121.307 ms，尚未测到稳定收益；两轮分别有 75,128 / 72,259 次退回 Unicorn。较多出现的指令包括 `stp q0, q0, [sp, #560]`、`mrs x5, DCZID_EL0`、CRC32C 和 `dc zva`。初版访存表采用 4 KiB 单元，实际 Linux 页为 16 KiB。完整桌面初轮通过 Launcher、Clock 重启、闹钟页面、Files、持久数据和清理检查，执行阶段耗时 275.546 秒，footprint 样本均值 / 峰值 / 最后值为 2,306,702,393 / 3,160,460,384 / 2,826,881,880 字节。这一轮含 2 秒、5 ms 间隔的宿主采样，用于功能与性能诊断。

随后将 Linux 数据映射改用 16 KiB，并将 Unicorn CPU 恢复、代码失效与 TLB 刷新推迟到实际进入 Unicorn 时执行。补充 CRC、`DCZID_EL0`、64 字节 `DC ZVA` 与预取提示；Linux 初始化确认 Unicorn 的 DCZID 为 4，两个执行器采用同一清零范围。写权限检查在清零前完成。四轮 ART 检查全部成功，退回 Unicorn 的次数降至 2,431–2,480；这组结果用于开发诊断，正式交替对照见下节。

### 本机交替对照

环境为 Apple M5 Ultra、macOS 27.0（26A428），Clang `-O2`，Linux 6.12、单客体 CPU、1 GiB RAM、16 KiB 页、2 ms 定时抢占、nterp 开启、扩展 JIT 与快速基线编译关闭、exec/TLB 全量失效、100 ms 内存采样。公共内核、系统盘、DEX 和 Unicorn 静态库采用相同摘要；两种执行器分别生成宿主程序。每种执行器使用 128 MiB 代码缓存，Direct 还保留 Unicorn 回退缓存。均值为样本算术平均值，峰值为采样峰值，进程生存期 RSS 峰值单独记录。

`python3 scripts/benchmark_android_translation.py --comparison execution --repeat 2` 完成 CLI/GCD 各两轮、执行器顺序交替的八个样本，全部成功。原始结果为 `work/native-linux-nce/android-translation-execution-matrix/summary.json`。

第一次成组准备在样本执行前被摘要校验中止：重复构建 Unicorn 后，`build.json` 和 `libunicorn.a` 的摘要变化。各项已登记源码摘要相同，静态库变化的具体构建原因未继续定位。脚本新增 `--reuse-engine-build`，第二个宿主程序逐项校验已有 Unicorn 构建输入与产物后复用，保留同组输入校验；八轮正式结果采用这条流程。

### 独立功能与计算检查

`python3 scripts/probe_direct_execution.py --output work/native-linux-nce/direct-execution-current` 完成 CLI/GCD 各一轮功能检查，以及 native、Unicorn、Direct 各三轮预热后计算。内存、寄存器和结果均校验成功。随机整数与 FP/SIMD 对照之外，覆盖所有通用寄存器访存组合、单寄存器独占访问的四种宽度、16 KiB 内外边界、64 字节清零的地址与权限、异步停止、代码修改、物理别名和 2 MiB 缓存中的 8,192 次代码替换。

同一 ARM64 计算字节下，数组读写的 Direct/Unicorn CLI 中位数为 46.722 / 103.498 ms，GCD 为 45.715 / 103.360 ms；原生参照为 21.496 / 21.490 ms。整数循环的 Direct 与 Unicorn 中位数差异较小；原子循环的 Direct CLI/GCD 为 31.652 / 33.050 ms，Unicorn 为 39.791 / 40.243 ms。工作量分别为整数 64M 次、数组读写 32M 次、原子更新 8M 次。计时包含对应执行入口与寄存器交换，内存采样阶段还包含初始化和结果核对。以上结果仅适用于这些计算循环。

当前源码另完成指令预算抢占的 Linux CLI/GCD、关闭内存采样的定时抢占 CLI/GCD，以及独立执行器关闭采样后的功能与计算检查。八轮 Android 正式结果重新验证成功；执行器选择、统计缺失、容量不匹配、容量超限、回退次数错误和内存均值错误共 24 份变更结果均被校验器拒绝。六组完整记录与 5,113 个内存样本保存于[结构化结果](../../../../experiments/native-linux/results-macos-direct-execution.json)，保存前逐项核对当前源码、依赖和二进制摘要。

### 复杂度审查

独立检查程序与 Linux 用户态回调是新执行器的两个使用方；产品默认路径尚未接入。状态帧同时被 C++ 生成器与汇编入口读取，偏移由 `static_assert` 校验。客体寄存器、地址转换表、代码路由表和源代码副本分别承担客体状态、访存转换、分支跳转与代码修改检查，移除任何一项都会改变现有行为。停止标志只由计时线程写入，执行器所有者负责在销毁前结束该线程；其余缓存和状态只允许顺序调用。

本轮采用容量受限的连续代码缓存，实际发生不足时整批回收。分段淘汰、跨进程代码去重和持久缓存留待真实工作集测量；当前没有新增这些状态。Unicorn 回退保留实际未覆盖指令的执行能力，独立检查还使用它核对指令语义。Mac 原型的可执行内存准备与 iPhone 生命周期分别处理，手机集成完成前维持现有产品执行路径。

复杂度复核确认历史生成器的 FP trap/TBI 参数没有当前调用方，双代码指针和碎片容量分支也没有现有分配器使用。在 `d15ff15` 保存基线后已移除这些接口，保留实际使用的寄存器、权限和有容量限制的代码生成行为。相关边界和 Linux CLI/GCD 检查成功。

### 数据映射与代码路由候选

`d15ff15` 已保存完整基线。当前执行器首次进入一个物理代码页时清空全部写映射，随后对无关数据页的写入也会重新退出并查询 Linux PTE。候选改为只清除与新代码页具有物理别名的写映射；生成代码继续拒绝写入本次调用已执行的物理代码页。保持 4 KiB 与 16 KiB 数据页边界，增加先写入、随后作为代码执行、再次写入同一物理页的回归。

数据映射表和代码路由表当前均为 256 项。增加构建后、执行前确定的容量参数，用相同二进制比较 256 与 4096 项，并记录实际容量、映射未命中和被撤销的写映射数量。容量增大会增加查表工作集和失效扫描成本，需要与仅改变失效范围的配置分别比较。以 Bionic/ART 筛选，再运行完整桌面；CLI/GCD、权限变化、物理别名、代码替换、异步停止、内存采集与关闭采集均保留验收。

新配置为 `NCE_DIRECT_MAPPING_ENTRIES`、`NCE_DIRECT_ROUTE_ENTRIES` 和 `NCE_DIRECT_SELECTIVE_WRITES`，由 probe 参数设置并在运行时结果中核对。表容量支持 256 到 65536 的二次幂，脚本提供 256/1024/4096/16384/65536。原型默认仍为 256 项、全量写映射失效。生成器与汇编入口使用实际表容量，代码路由表的单项布局由偏移检查约束。

基线二进制另完成三次 2 秒、5 ms 间隔的调用栈采样，并正常结束桌面。样本中反复出现 `_platform_memcmp`、`nce_direct_enter/leave` 和 `NceDirect::resolve`。大量等待线程同时被采集，未按全线程样本总数推导 CPU 占比。原始文件位于 `work/native-linux-nce/direct-desktop-profile-d15ff15/`，原构建为 `d15ff15`，该诊断轮次的耗时不用于正式比较。

`benchmark_android_translation.py --comparison direct-mappings --repeat 2` 的五种配置、CLI/GCD 各两轮，共 20 轮成功。设备、系统、内核和 Bionic/ART 负载同上节，每组采用同一个宿主二进制，数据表容量与代码表容量分别控制。独立检查新增先写、转为执行、再次写入同一物理页的 4 KiB/16 KiB 回归，选择失效加双 4096 表的 Linux CLI/GCD 也成功。

## 曾考虑的替代方案

- 继续只调整 Unicorn 缓存大小或清空时机：已保留实验参数，当前测量未显示足以改变可用性的收益；继续作为对照，下一步比较执行器生成的代码。
- 直接引入完整 Frida Stalker：其线程缓存、调用跟踪和 iOS 内存管理与本项目不同，先评估指令重定位及代码生成部分的复用范围。
- 直接恢复旧 Direct 整套构建和 QEMU 适配：包含已经结束的系统执行路径与专用状态，先按实际 Linux 调用方筛选代码，保持产品结构。
- 先要求每个 APK 预编译或重新签名：无法满足通用安装验收，新的准备过程必须在运行期间接收原始 ELF/DEX。

## 验收标准

1. 同一原始 ARM64 ELF 分别使用原生参照、现有 Unicorn 和新执行器，先核对计算结果、寄存器、条件标志、FP/SIMD、原子操作、TLS 与错误 PC，再记录耗时及代码缓存/进程内存。
2. Linux 检查覆盖线程、fork/COW、exec、信号、跨页访问、权限变化、共享内存和代码替换，CLI/GCD 均成功。缺页及定时停止必须恢复到完整的客体指令边界。
3. 先通过 Bionic/ART，再接入同一个 Android 服务与桌面负载。原生 NCE、Unicorn 与候选分别记录配置、输入摘要、启动、应用操作、内存和缓存占用，使用交替轮次比较。
4. 不以局部计算倍数替代完整桌面结果。确认收益后再接入 iPhone 已有的执行区准备方式，集中验证设备特有条件。
5. 仍需通过构建完成后导入的原始签名 JNI APK，检查新库、动态代码、更新和宿主重启；本项与[APK 安装规划](../feature/2026-10-10-APK安装与原生库加载.md)共同验收。

## 风险

地址转换、代码块之间的控制转移和保存寄存器仍会增加成本。指令覆盖率、访存异常恢复、代码物理别名、独占访问和 iOS 可执行内存需要继续验证。若真实 Android 仍主要消耗在地址转换或编译重入，直接生成指令可能只有有限收益；结果必须与当前执行器比较后记录。旧实现的代码量或历史测试数量无法确认这些新条件。
