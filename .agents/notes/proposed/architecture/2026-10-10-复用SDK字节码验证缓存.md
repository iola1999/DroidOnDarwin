# 决策记录: 复用 SDK 字节码验证缓存

状态: proposed

## 问题

08:15 的完整启动中，SystemUI 服务初始化用了 87,730 ms，触发 60,218 ms 的服务 ANR。Launcher3 最终通过绘制和截图检查，时钟也完成首帧，但 ANR 对话框占用输入焦点，桌面检查失败。日志包含大量首次类加载时的方法验证；当前系统只携带 APK/JAR，未携带 SDK 已生成的 VDEX。

## 提案

为已经纳入镜像的 APK 和 JAR 加入同一来源的 VDEX。ART 的 OatFileAssistant 原有 VDEX-only 加载支持在没有 OAT 时读取缓存，校验 DEX 校验和，并由 VdexFile::ComputeClassStatus 检查当前类的类型依赖。依赖不满足时仍运行验证器。此次复用该路径，执行继续使用现有解释器和 NCE JIT。

先纳入 APK 邻接的 oat/arm64 文件，以及现有 Framework JAR 的对应文件，记录数量与字节。AOSP Launcher3 的 VDEX 与 APK 来自同一已校验 SDK 归档，并固定文件 SHA-256。系统镜像的哈希继续纳入打包检查。

## 曾考虑的替代方案

- 关闭字节码验证：会失去验证器原有的格式、类型和访问检查，本次保留这些检查及缓存失效后的重新验证。
- 接入完整 boot image 和 AOT：需要处理镜像地址、预编译代码、ART 对象布局和 NCE 执行准备，仍可后续评估。当前缓存路径已有原版加载与依赖检查。
- 增加启动等待时间：可减少冷启动时的超时提示，无法减少重复验证工作，先测缓存是否带来实际变化。

## 验收标准

构建只为实际携带的代码容器加入 VDEX；检查缓存输入来源、DEX 校验和和运行时使用状态。运行现有 Java 异常、类加载、ART 编译、完整桌面及应用持久数据检查。对照 SystemUI 初始化、Launcher 与应用首帧和 ANR；记录缓存未被使用或无收益的情况。

## 风险

缓存可能因 ART 版本或当前依赖关系而失效，需要实际加载检查。Framework 的 boot classpath 在无 boot image 时采用独立加载路径，邻接 VDEX 的收益范围必须以运行结果为准。新增缓存增加少量系统镜像容量，具体字节由构建记录。

### 08:23 本机对照

加入 31 份邻接 VDEX 共 2,045,084 字节，另有 Launcher3 VDEX 214,564 字节。SystemServer StartServices 为 36,236 ms，前一轮为 40,784 ms；Launcher 首帧为 84,412 ms，前一轮为 94,260 ms。SystemUI StartServices 为 87,772 ms，前一轮为 87,730 ms，仍因 ANR 对话框占用焦点而失败。两轮均使用 Apple M5 Ultra / macOS 27.0、demand、1 GiB RAM 和 JIT 阈值 1024，数据盘沿用前序运行，只有单轮样本。结果见 `experiments/native-linux/results-macos-desktop-vdex.json`。缓存保留作为原版 ART 支持的输入，整机收益仍需后续稳定运行测量。

SystemUI 的详细计时中，SystemActions 用时 51,989 ms，AssistantAttentionMonitor 用时 15,701 ms；计时包含依赖对象构造。对照 [SystemActions](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/packages/SystemUI/src/com/android/systemui/accessibility/SystemActions.java) 和 [AssistantAttentionMonitor](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android16-release/packages/SystemUI/src/com/android/systemui/dreams/AssistantAttentionMonitor.java)，它们初始化通知栏、辅助操作和助手关注状态等依赖。源码尚未确认固定的长时间服务等待。继续检查首次初始化的解释执行成本。

### 08:38 初始化等待与后续方向

将 JIT 热度阈值从 1024 降至 16 的单轮实验中，SystemUI 初始化增加到 99,978 ms，SystemServer StartServices 为 37,429 ms，仍触发服务 ANR。已恢复 1024。记录为 `experiments/native-linux/results-macos-desktop-jit16.json`。

新增可选 `NCE_TRACE_SYSTEMUI=1` 诊断，向 SystemUI 和 system_server 发送 SIGQUIT。ART 将线程栈写入会话 stderr，当前环境没有 tombstoned。采样中 SystemUI 主线程等待 `IActivityManager.bindServiceInstance`，调用来自 LauncherProxyService 的构造；system_server 多个线程等待 ActivityManagerService 的锁，持锁线程仍在执行进程启动与广播调度。栈采集本身增加开销，本轮只用于定位，不作性能比较。

原型将 `ro.hw_timeout_multiplier` 从 3 调整到 6，使 Android 的前台服务期限为 120 秒。此前多轮 SystemUI 用时约 87 秒，60 秒期限会产生遮挡桌面的 ANR 对话框。该调整容纳已观察到的冷启动时间，不增加执行速度；实际窗口绘制、用户解锁、输入焦点和 120 秒桌面等待检查保持原有要求。完整桌面交互仍需继续测量。

进一步检查确认，构建启用 `ART_USE_RESTRICTED_MODE`，上游 `IsNterpSupported()` 因此返回 false。未编译的方法使用 C++ switch 解释器。ARM64 nterp 的寄存器和堆访问假定原版压缩引用地址；当前 ART 使用高地址堆和相对引用，需要逐项处理对象字段、数组、调用参数/返回值、异常和 GC 栈扫描。直接启用存在内存错误风险。将该方向保留为完整桌面建立后的独立性能工作，当前不引入部分适配。

### 全新数据盘的启动范围

09:34 的首次数据盘初始化运行中，SystemServer StartServices 为 47,368 ms，SystemUI 仍在依次创建服务时，KeyguardService 达到 120,467 ms 并触发 ANR。Launcher 已报告首帧，但 keyguard 尚未解除，桌面检查按原条件失败。结果见 [results-macos-desktop-fresh-timeout.json](../../../../experiments/native-linux/results-macos-desktop-fresh-timeout.json)。该轮包含 GSF APK、1 GiB RAM、demand 映射及映射计时；现有开发盘的此前结果无法覆盖首次初始化。

将 `ro.hw_timeout_multiplier` 调整为 10，前台服务期限为 200 秒；桌面可见检查为 180 秒，外层子进程 210 秒，整体启动检查仍为 460 秒。继续要求用户解锁、keyguard 解除、焦点、Activity 绘制和控件像素就绪。该调整只扩大有界的冷启动等待范围，没有减少执行工作，也没有速度提升结论。新建的回归盘在失败后清理，再从种子重新开始；原开发盘保留。
