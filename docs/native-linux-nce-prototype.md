# 原生 Linux 与 NCE 可行性原型

日期：2026-10-09。目标是在 iPhone 内执行完整 Linux 与 Android，减少内核和
用户态的动态翻译开销。实现进度按可运行的验证结果记录。

## 实现顺序

| 阶段 | 产物与验收条件 | 尚未覆盖的条件 |
| --- | --- | --- |
| N0：Darwin 执行与内存 | 独立 ARM64 ELF 代码直接执行；SVC/TLS 改写；通用寄存器（x18 除外）、SIMD 和状态标志恢复；同地址的两个内存空间、共享页、COW、保护异常、代码更新；计算与切换开销测量 | 完整 Linux、Android 与 iPhone 运行条件 |
| N1：真实 Linux 内核 | 编译并启动宿主用户态中的 Linux；NCE 的系统调用交给 Linux；验证文件操作、定时器与阻塞唤醒 | 独立用户态 init、多进程完整语义与 Android |
| N2：Linux 用户进程 | 独立用户态 init、fork/exec/wait、COW、futex、信号、TLS 和动态代码；混合负载与原生对照；形成一次手机测试所需产物 | Android 厂商组件与图形 |
| N3：Android | Binder、Zygote、ART、SurfaceFlinger 和 GPU；随后接入 HyperOS，并测启动、设置、切换与持续交互 | 完整测试前不推算整机倍数 |

## N0 的架构选择

先验证单执行线程、固定客体地址窗口。普通 ARM64 指令和访存保持原样；进入
系统调用时保存寄存器、回到宿主栈，再切换客体内存映射。共享映射保持不变，
连续私有区间按区间 remap。分别测单页、连续大区间与分散页，检查区间合并的
收益能否保留到频繁进程切换场景。

测试代码由独立的 AArch64 ELF 工具链生成，仅改写 SVC 与 TPIDR_EL0 读写。
N0 的回调只提供探针需要的返回值，Linux 尚未接入。客体代码限定为仓库中的
受控汇编，x18 保留给 Darwin；任意 Android ELF 的指令检查、地址布局、安全
隔离、异步抢占和 JIT 页面发现放在后续实现中。

当前 SVC/TLS 跳板临时使用客体 SP 下方 16 字节保存寄存器，要求该范围可写、
SP 按 16 字节对齐。任意客体代码的栈边界与跳板内异常恢复仍需处理。

使用独立的 RX/RW 代码地址，iOS 构建接收 Husk 已获得的 JIT 映射。Mac 负责
开发和对照测试，手机运行时所需部分均编译为本机代码。

## Linux 基础的选择条件

[ARM64 UML](https://github.com/zalexdev/linux-um-arm64/tree/8897487c52233cd00cf2850008ca068892f1ae91)
保留 Linux 用户进程和 MMU 语义，但宿主部分依赖 clone、ptrace、seccomp。
后续评估用 Darwin 内存映射与 NCE 替换该宿主执行部分。

[LKL](https://github.com/lkl/linux/blob/d0f76a77e8c2ca68bd7d96190b8da09040eab072/Documentation/lkl/lkl.txt)
提供可嵌入的 Linux 内核及宿主操作接口，可用于早期验证真实 Linux 子系统。
其用户进程、信号和地址空间仍需扩展；选择它作为最终基础前，必须列出这些
扩展对 Linux 调度与 MMU 的影响。N1 已使用 LKL 验证原生内核与 NCE 的接口。

## 判断与停止条件

N0 的测试通过只支持继续移植 Linux。若固定地址窗口需要重映射大量分散页，
且成本已超过合理的调度时间片，应先验证其他地址空间实现。若 iOS 拒绝必需的
内存操作，应记录具体调用和返回值，调整架构后再继续。

原生计算对照用于判断 NCE 是否仍有逐指令开销。系统调用与地址切换测试用于
发现计算循环隐藏的成本。两者均不能推导 HyperOS 的加速倍数。

`work/native-linux-nce/`。N0/N1 阶段新增约 1,400 行源码与构建脚本。

Linux 内部的可变参数调用保留 Linux ABI，通过固定参数接口调用 Darwin。
内核编译保留 x18。此原型没有接入 CPU 指令模拟器。

已通过的真实 Linux 行为包括：启动与 `uname`、NCE 发出的文件创建/写入/定位/

## 性能记录与解释

以下来自完成检查后的最后一轮运行。N0 计算对照取五轮中位数；N1 与 remap
为该轮单次样本。数据保存于 `experiments/native-linux/results-macos.json`。

| 测量对象 | 结果 | 覆盖范围 |
| --- | ---: | --- |
| 400 万次计算与访存，直接调用 / NCE | 3.633 / 3.677 ms | 同一受控汇编循环；NCE 耗时为原生的 1.012 倍 |
| NCE 每次循环经过探针回调 | 约 22 ns 增量/次 | 完整寄存器保存恢复；回调只返回固定值 |
| 原生 Linux 内核启动 | 34.947 ms | 64 MiB RAM、最小 LKL 配置 |
| 直接调用 Linux `getpid` | 14.95 ns/次 | 10 万次；宿主侧 LKL 系统调用入口 |
| NCE + Linux `getpid` + 少量计算访存 | 46.46 ns/次 | 10 万次；真实 Linux 系统调用 |
| 两地址空间切换并执行探针 | 1.974 μs/次 | 每个私有窗口 64 KiB；只访问部分页面 |
| 连续 2 MiB 重映射，仅访问首页 / 访问每页 | 2.057 / 48.350 μs | 两组已经驻留的后备内存 |
| 分散 128 页重映射，仅访问首页 / 访问每页 | 103.203 / 193.982 μs | 每页 16 KiB，共 2 MiB |

直接执行和系统调用入口已经表现出较低开销。访问完整工作集后，映射切换仍有
明显成本；只测 remap 返回时间会漏掉后续页面访问的开销。后续需要结合实际
Linux VMA 布局、共享页比例、调度频率和工作集验证。

这些数据支持继续实现用户进程环境。当前尚无 HyperOS、iPhone 或旧 QEMU
后端与本原型的同负载对照，整机加速倍数未知。

## N2a：Linux 用户进程原型

2026-10-08：已将 NCE 上下文与 Linux task/mm 绑定。`--processes` 构建启用
`CONFIG_MMU=y`，使用 16 KiB 页、独立进程页表和宿主映射切换。Linux 内核、
客体普通 ARM64 指令及访存均原生执行。每个 Linux 任务对应一个宿主线程，
由 LKL 的单 CPU 调度器决定运行顺序。

本阶段选择继续扩展 LKL。父子关系、PID、页表复制、COW、文件描述符、futex、
ELF 装载和退出状态沿用 Linux 实现。新增部分处理 Darwin 内存映射、异常与
NCE 寄存器上下文；`execve` 经 Linux 的 `binfmt_elf` 装载第二个受控 ARM64 ELF。

连续 32 轮检查覆盖以下行为：

- `clone(SIGCHLD | CLONE_SETTLS)` 创建独立地址空间；按照 AArch64 的参数顺序
  设置子进程 TLS。父进程保留 TLS 值 123，子进程收到 456，随后修改为 789。
- 父进程私有数据保持为 7，子进程修改自己的副本为 11；客体栈同样经过 COW。
- 匿名共享页在子进程写入 88 后，父进程读取到 88。
- Linux futex 实际唤醒一个等待者。检查允许子进程先运行，通过 `sched_yield`
  等待父进程进入 futex，随后验证共享页和 pipe 中的数据。
- 子进程通过继承的 pipe 写入 90，父进程读取同一数值。
- 子进程调用 `execve`，新 ELF 检查 Linux 参数栈中的 `argc`、`argv[0]` 和
  清零的 TLS，随后以状态 42 退出。父进程通过 `wait4` 收到对应状态。
- 改写可执行指令前，Linux 为代码页建立私有副本；32 次 exec 后，文件内容
  与原始 ELF 完全一致。
- 每轮的父子执行上下文都被回收；合计分配和释放各 64 个。负数及越界
  系统调用号返回 `-ENOSYS`。

最后一轮原生内核启动为 34.485 ms；32 组流程共 12.344 ms，平均每组
0.386 ms，期间处理 288 次缺页。N0/N1 回归检查均通过。结果与源码哈希保存在
`experiments/native-linux/results-processes-macos.json`。
这组测量包含小内存进程的创建、通信、exec 和回收，未包含 Android 启动、ART、
图形或大工作集。不能据此计算 HyperOS 加速倍数。

### 地址空间与执行入口

宿主启动时申请连续虚拟地址范围，并将实际地址传给 Linux。客体窗口为
256 MiB，物理内存为 64 MiB，后面保留 64 MiB 的内核虚拟地址范围。运行时
分配可避开当前宿主进程已有映射。固定数值地址在本机返回过 `KERN_NO_SPACE`。

切换 `mm` 时，先取消旧窗口的访问权限，再按新进程的页表映射已有页面。
当前逐页映射，尚未合并连续区间。COW 写异常交给 Linux `handle_mm_fault`。
NCE 跳板读取当前进程的上下文指针，共享代码可服务多个依次运行的进程。

调试时发现，继承内核页表目录会让父子进程共用部分页表，子进程退出后父进程
读到 0。改为独立分配页表后，私有数据和栈的检查通过。这个改动是多地址空间
实现的必要条件。

Darwin 拒绝本轮尝试的 RWX 映射。客体可执行页保持 RX，改写使用独立 RW
别名；可写的 Linux 页面保持不可执行。当前受控 ELF 为跳板预留了 64 KiB
代码区，任意 ELF 的代码布局与动态生成代码仍需扩展。

## 当前边界与下一阶段

N2a 已有 Linux 管理的用户进程及 ELF exec。第一个探针进程仍通过宿主调用
启动；PID 1 保留 LKL 的内部初始化逻辑。下一阶段需要接通独立用户态 init、
Linux 信号帧与 `rt_sigreturn`，并扩大 ELF、线程和内存故障覆盖。

N2a 仅执行仓库中的受控程序。宿主系统调用接口接受宿主地址，尚未隔离任意
客体指针；非法访问仍可能终止整个宿主程序。Darwin 信号回调目前直接调用
Linux 缺页处理，尚未解决所有重入和持锁条件。后续需要建立可恢复的异常入口，
分别处理客体访问失败与宿主故障。

`work/native-linux-nce/ios/Husk-NativeLinux-N2-R1.ipa`。安装包的构建、签名完整性
和 ZIP 检查通过，真机执行待验证。运行方式见[手机测试说明](native-linux-n2-ios-test.md)。

其他待做项包括任意 ELF 的指令检查、x18 使用、4 KiB/16 KiB 混合保护、

## N2 iOS 测试包

Mac 和 iPhone 的 N2 检查现在共用一个 80 MiB RX/RW 内存池。池内依次分配
重映射探针、计算探针、Linux 内核映像、64 MiB Linux 物理内存及进程启动代码。
iOS 使用现有 Husk JIT 分配器，一次申请调试器准备过的页面，然后断开调试器。
代码检查在断开后执行；每个可写 Linux 映射保持 RW，可执行映射从池的 RX 地址
重新映射到客体窗口。Linux 数据段使用可写权限。

把整个 64 MiB 实验 RAM 放入准备过的内存池，可直接检查 Linux ELF 代码页在
COW、exec 和进程切换后是否仍然能执行。扩展到 Android 内存规模时，仍需设计
代码页分配和回收方式；当前分配方式仅用于这个有容量上限的原型。

手机检查顺序：

1. 申请 JIT 页面，写入并执行两条 ARM64 指令，确认基本执行条件。
2. 断开调试器并检查 `P_TRACED` 已清除。在同一地址交替映射两页代码，连续
   八次得到各自的返回值。
3. 对同一段 400 万次计算/访存循环做五轮直接执行与 NCE 对照，并核对结果。
4. 从应用资源装载 Linux 6.12 内核，检查启动和 `uname`。
5. 执行 N2a 的 32 轮进程检查，核对 ELF 文件内容与系统调用边界，然后关闭
   内核，确认 64 个 NCE 上下文全部释放。

共用内存池的 Mac 运行通过以上适用于 Mac 的检查；Mac 使用本地 RX/RW 分配，
未执行 iOS 的调试器准备流程。R1 回归的内核启动 29.362 ms，32 轮进程检查共
11.734 ms，缺页 288 次。计算对照与原始结果保存在
`experiments/native-linux/results-prepared-memory-macos.json`。这些短测试用于
确认实现行为与记录开销，尚未覆盖 Android 的工作集和持续负载。

应用复用 Husk 的内置 JIT 助手、StikDebug 脚本和配对文件存储。界面提供内置
JIT、StikDebug 和日志导出入口。测试开始后禁用自动锁屏；日志直接写到手机的
`Documents/native-linux-n2-ios.log`，重新打开应用可导出上次内容。每次进程启动
只允许执行一轮测试，下一轮需要关闭并重新打开应用，避免复用已经断开的 JIT
会话和 Linux 全局状态。再次开始会覆盖该日志。

初版的手机运行已确认 80 MiB JIT 分配、RW/RX 别名和原生代码执行。断开请求
返回后立即查询调试标志触发断言，Linux 尚未启动。R1 使用最多五秒的状态
等待并保留失败日志；五种退出等待场景的回归通过。下一步需要手机验证 R1
能否完成断开并继续重映射、启动 Linux。

## 重建

需要 Apple Silicon Mac、Xcode SDK、Python 3.12+、Homebrew LLVM、LLD、
GNU Make 和 GNU sed。首次 LKL 构建下载约 239 MiB 压缩源码；展开源码约
1.6 GiB，内核构建目录约 65 MiB。构建脚本固定 LKL 提交及 musl ELF 头文件版本。

```sh
python3 scripts/probe_native_linux.py
python3 scripts/probe_lkl.py
python3 scripts/probe_lkl.py --processes
python3 scripts/package_native_linux_ios.py
```

第一条输出 N0 测试、五轮计算对照与 iOS 静态库。第二条执行 N1 内核子系统
检查。第三条应用 N2a 的 LKL 架构修改，构建并执行用户进程检查，同时编译
对应 iOS 宿主代码；输出位于 `work/native-linux-nce/processes/`。第四条需要
XcodeGen，生成独立 iOS 工程并构建 IPA，输出位于 `work/native-linux-nce/ios/`。
打包前检查参与 Mac 验证的源码及内核哈希；源码变化时使用
`python3 scripts/package_native_linux_ios.py --rebuild-kernel` 重新验证。

修改脚本已在固定提交的原始文件上检查：生成的 21 个文件与实际构建源码一致，
重复应用得到相同内容。失败返回非零状态，原始输出保留在工作目录。

## 实现取舍与审查

保留一个 NCE 入口和一个 Darwin 宿主实现，三个阶段共用寄存器切换代码。测试
ELF 由构建脚本解析，运行程序只装载自己构建的映像，尚未加入通用动态链接器。
iOS 目标增加测试界面并复用原有 JIT 助手；运行核心仍使用同一个实现。

对额外后端、通用 ELF 动态链接器和设备层做了必要性检查：当前受控测试没有
使用这些功能，暂不增加。保留独立原生汇编对照，因为它用于测量执行入口和
回调成本。Linux futex 检查要求实际唤醒一个等待者，覆盖了宿主线程、Linux
任务和阻塞系统调用之间的关系。

与初始顺序的调整是：先借助 LKL 验证真实内核子系统与调用接口，将独立 init
并入 N2 的用户进程工作。完整用户进程目标继续保留，N0/N1 的测试范围已分别
记录。

N2a 的复杂度审查保留了 Linux 的 task/mm 和现有 ELF 加载器，未增加另一套
进程表、用户态调度器或独立文件系统。每个进程的额外状态仅包括 NCE 寄存器、
Darwin 异常栈和代码写别名，并在宿主线程结束后释放。取消私有代码页会修改
文件缓存中的原始指令；文件内容检查覆盖了这一条件。暂不引入映射缓存，先用
完整映射切换验证语义，后续再测大工作集的成本。

与原定顺序的调整：先完成可独立验收的 N2a 多进程与 exec，用户态 init、完整
信号处理和手机执行留在后续阶段。当前没有足够结果判断 HyperOS 的最终可用性。

N2 iOS 的复杂度审查：内存池只负责分配与整体释放，切换权限仍由既有 Linux
页表映射流程处理。配对文件存储从 `JITSetup.swift` 移到独立文件，原 Husk 与
原型目标复用同一份格式校验和存储路径。JIT 分配器增加仅编译准备页面分配流程
的开关，使原型构建脱离 QEMU 的 APRR 头文件；完整 Husk 继续编译原有分支。
当前没有增加通用虚拟机配置、调度缓存或可切换的内核后端。

本轮调整：先交付 iOS 上的内核装载与现有受控进程检查，再继续独立 init 和
完整信号处理。这样可以在扩大 Linux 用户态支持前，取得手机上关键内存操作
的实际结果。N2 阶段整体仍在进行中。
